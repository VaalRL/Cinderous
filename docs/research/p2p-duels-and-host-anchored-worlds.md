# 研究：兩人對戰直接走 WebRTC（免房間），與「host 為首的平行世界」分片架構

> 兩個問題：
> ① 西洋棋這類兩人對戰能不能直接走 WebRTC、不用房間？
> ② 大地圖廣播改成「自動聚合 N 名玩家到某個 host 為首的世界」——host 不開房間，
>    但其他玩家讀得到他在他 relay 上發布的狀態、有互動時也向他的 relay 發事件，
>    於是網路上存在非常多平行世界（類似多遊戲伺服器）。是否可行？
>
> 相關：`docs/research/stranger-relay-discovery-and-matchmaking.md`、
> `docs/research/shared-relay-for-game-clients.md`、ADR-0366（第三方應用車道，提議中）、
> ADR-0243／0342（`/turn`）、ADR-0123（訂閱必須具名）、ADR-0006（免費層容量模型）；
> 下游：《沒當好爸爸》ADR-0007／0008、《元素使》PRD/ref/39、40。
>
> 本文件為**研究記錄、非決策**。

## 結論摘要

| 問題 | 答案 |
| --- | --- |
| ① 兩人對戰免房間走 WebRTC | ✅ **可行，而且《沒當好爸爸》已經實作完成並在跑。** 前提是把「房間」拆成兩個意思，只丟掉其中一個 |
| ② host 為首的平行世界 | ✅ **架構可行，而且是目前為止最能解掉容量問題的形狀**——但有一個必須先解決的核心問題：**誰是權威**。答案是「host 當排序器，不當裁判」 |

兩題共用同一條分層原則：**WebRTC 做即時、relay 做持久與發現。**

---

## 一、兩人對戰：免房間走 WebRTC

### 「房間」其實是兩件事，只有一件丟得掉

| 意思 | 用途 | 已知對手時 |
| --- | --- | --- |
| ① **開放大廳的一筆公告** | 讓**陌生人**找到你 | ❌ 不需要 |
| ② **訊號交換的落點** | 讓兩人交換 SDP／ICE | 🔴 **不能省** |

WebRTC **無法自我啟動**——SDP offer/answer 與 ICE candidate 必須先經由某個雙方都連得到的地方
交換。那個地方就是「房間」的本質，只是不必長成一筆公開的房間事件。

### 已知對手時的正確形狀：指名加密收件匣

《沒當好爸爸》的 ADR-0008 已經把這件事做完了：

> 挑戰、accept／decline、offer／answer、ice 全是 Kind 20078、標籤 `t=nagd`、**`p=對方`**、
> `expiration`（NIP-40，30 秒），內容用 NIP-44 v2 加密給對方；**沒有 `g` 標籤，所以不會混進
> 大廳的 `#g` 訂閱**

🔴 **關鍵：這個形狀 `#p:[自己]` 在 ADR-0123 的 `scoped()` 下是合法的。**
也就是說——**「免房間的兩人對戰」是四款遊戲裡唯一現在就能在 cinder-relay 上跑的功能**，
而開放大廳不行。該 ADR 的背景段落也是這樣寫的：「信令**必須**長成『指名對方＋密文』的形狀才進得去」。

握手完成後：`createDataChannel('game', { ordered: true })` → 走棋走 DataChannel →
**relay 用量歸零**。西洋棋一局 60 步全部 P2P，中繼請求數 0。

### 殘餘依賴（relay 不會真的消失）

| 項目 | 說明 |
| --- | --- |
| **TURN** | 對稱 NAT 下 P2P 建不起來。`cinder-relay` 有 `/turn` 短期憑證（ADR-0243／0342），但 NAGD 的 ADR-0008 寫「等對稱 NAT 成為實際問題再接」＝**目前沒接**。這是已知缺口，不是設計問題 |
| **斷線重連** | DataChannel 掉了要重新握手 ⇒ 又要回 relay。relay 是**常在但低流量**的依賴，不是可以拿掉的東西 |
| **對手離線** | 無伺服器＝無狀態保存。NAGD 定義了 kind 20079（relay 轉發走棋後備）但**未實作**（`TODO.md:277`） |
| **找對手** | 若不是好友邀請，仍需要①——那才是需要公告／大廳的部分 |

### 結論

**兩人對戰應該預設走這條路**：指名加密信令 → DataChannel → 相互 WASM 驗證。
它最便宜、延遲最低（<20ms）、而且已經能用。需要 relay 的只有「找到對手」那一步。

## 二、host 為首的平行世界

### 架構形狀

```
共同發現集（少數、硬編碼、全球一致）
  └─ 世界公告：可尋址 30xxx，d = worldId
       tags: ["relay","wss://alice.example.com"]（世界在哪）
             ["cap","20"] ["pop","13"]（容量／目前人數）
             ["mode","..."] ["region","..."]
             ["expiration", now + 數分鐘]   ← 同時就是 liveness 證明

Host 的 relay（他自己部署、他自己付費）
  └─ 持久層：加入／離開、擊殺結算、掉寶、狀態變更

Host 客戶端的 DataChannel 星狀網
  └─ 即時層：位置、動畫、聊天、特效
```

玩家開遊戲 → 查共同集 → 挑一個還有空位的世界 → 連 host 的 relay ＋ 建 DataChannel → 進場。

**「自動聚合」＝ 客戶端依公告的 `pop`／`cap`／`region` 自動挑一個，不需要 host 主動開房或邀請。**
這正是使用者要的「不用該 host 開房間」——世界是常駐分片，不是一場對局。

### 🔴 核心問題：誰是權威

這是整個設計成敗所在，而且**relay 幫不上忙**：Nostr relay 只轉發與儲存事件，
**不執行任何遊戲邏輯**——它不懂規則，不能仲裁「這一刀有沒有打中」「NPC 掉什麼」。

所以權威只能是 host 的**客戶端**。三個選項：

| 選項 | 說明 | 判定 |
| --- | --- | --- |
| **A：host 全權威** | host 算好結果、簽名發布 | ❌ host 可以任意作弊。低風險內容還行，但「擊殺／掉寶」一旦有價值就一定被濫用 |
| **B：無權威，各自確定性模擬** | 所有人跑同一份確定性 WASM | ⚠ 需要**全序**。而 relay 的 `created_at` 是客戶端自填、不可信；靠 relay 當可信時間源與威脅模型矛盾（PRD §6） |
| **C（建議）：host 當排序器，不當裁判** | host 收事件 → 賦予 `seq` → 重新簽名廣播 `[seq, eventId]`；**各客戶端依 seq 跑自己的確定性模擬算出結果** | ✅ host 能審查／重排（可偵測的 liveness／fairness 攻擊），但**不能偽造結果**——結果是每個人自己算的 |

C 是遊戲業界的成熟形狀（lockstep + 中央排序器），而且**兩款遊戲都已經有需要的原語**：
《沒當好爸爸》有 SRA Mental Poker ＋ SHA-256 承諾（`ARCHITECTURE.md:96`）與「著法在本地 WASM
重新驗證」（`:147`）；《元素使》有雙向雜湊承諾與 `RNG_Seed = SHA256(SeedA ⊕ SeedB)`。

#### 隨機性仍然要另外處理

C 保證「大家算出同一個結果」，但不保證「那個結果是公平的」——如果 NPC 掉寶的亂數種子由 host 選，
他照樣作弊。解法是 commit-reveal：世界建立時由參與者共同產生 `worldSeed`，
每次判定用 `H(worldSeed ‖ seq)`。

⚠ **這是本設計最難的一塊**：玩家會動態進出，晚到的人沒參與 `worldSeed` 的產生。
務實解是**分級**——高價值結果（稀有掉寶、排行榜計分）走 commit-reveal 並限定 epoch 內加入者；
低價值結果（一般 NPC、視覺效果）接受 host 權威。不要一開始就追求全面無信任。

### 容量計算：這才是這個設計真正的價值

以一個 20 人、活躍 4 小時的世界為例。

**❌ 如果位置更新走 relay**（每 2 秒一次）：

```
20 人 × 30 次/分 × 240 分 = 144,000 進站訊息
```

**超過免費層 100,000/日**——單一個世界就爆掉。

**✅ 位置更新走 host 的 DataChannel 星狀網**（不經 relay）：

| 進 relay 的東西 | 每日量 |
| --- | --- |
| 加入／離開（20 人 × 2） | 40 |
| 擊殺結算（1 次/分/人 × 20 × 240） | 4,800 |
| 世界公告續命（每 4 分鐘） | 60 |
| **合計** | **≈ 4,900** |

**⇒ 一座免費層 Worker 可以撐約 20 個這種世界。** 而且那是 host 自己的額度——
**成本跟著開世界的人走**，不集中在官方錨點。

Host 客戶端的負擔：20 條並行 `RTCPeerConnection`，彙整後每人送一份快照
≈ 20 KB/s 上行。桌機沒問題；**行動端當 host 要另外評估**。

### Host 離線會怎樣

- **host 的 relay 不會離線**——那是 Cloudflare Worker，與他的裝置無關 ✅
- **但 host 的客戶端離線** ⇒ 排序器沒了、DataChannel 中樞沒了 ⇒ 世界凍結
- 世界公告的 `expiration` 自然到期消失 ⇒ 其他玩家被退回選世界畫面
- 🔴 **關鍵保證：已結算的東西不會丟**，因為它們在 relay 上（Worker 還活著）

這等同「遊戲伺服器重啟」，是使用者能理解的故障模式。可接受。

### 其他後果

| 項目 | 說明 |
| --- | --- |
| **世界之間不互通** | 你在世界 A 打的 NPC，世界 B 看不到。跨世界排行榜要客戶端自己聚合多個世界的結算事件。符合「多遊戲伺服器」的心智模型，使用者能理解 |
| **只有部署過 relay 的人能當 host** | 這其實是**好的誘因**：一鍵部署解鎖「開世界」。但若部署率低，世界就少 |
| **`pop` 是 host 自報** | 可以謊報人數騙人進來。影響體驗不影響安全；進場後即可察覺 |
| **IP 暴露** | DataChannel 星狀網＝host 看得到所有玩家 IP，玩家也看得到 host 的。WebRTC 本來就會交換 IP ⇒ **邊際成本≈0**，但要在 UI 講清楚 |
| **host 的站要接受陌生人** | 玩家要訂閱世界事件 ⇒ host 的自架站必須跑 ADR-0366 的寬鬆車道。**而且 host 是自費讓陌生人寫入**——需要 PoW／速率限制，或復用 `allowedAuthors`（ADR-0044）限定已入場者 |
| **RTT 選世界是對的** | 前一份研究稿說「不要用 RTT 選 relay」是針對**配對的會合集推導**。這裡不同：世界已經由公告明確識別，玩家是在**已知清單中挑一個**，不存在兩邊各自推導而發散的問題 ⇒ **依 RTT／region 挑世界完全正確** |

## 三、適用性

| 應用 | ① 免房間 P2P 對戰 | ② 平行世界 |
| --- | --- | --- |
| **沒當好爸爸** | ✅ **已實作**（ADR-0008） | ➖ 不需要（回合制桌遊） |
| **元素使** | 🟡 規格有，未實作 | ✅ **這正是 ref/39／40「Zelda 大地圖 ＋ Nostr 遊蕩者」要的東西**，且能取代那個撐不住的「每 30 秒全球廣播」 |
| **辭職信** | ➖ 其 ADR-0009 已否決 WebRTC（「仍需信令伺服器或 relay 當信令，多一層而已」） | ➖ 不需要 |
| **菜鳥教頭** | ➖ 純單機 | ➖ 不需要 |

《元素使》的 `ref/40:39,53-54` 原本寫「每 30 秒廣播一筆 kind 20078」＋「無論全網有多少萬名玩家在
走動」——那個算術撐不住（約 34 人封頂）。**平行世界正是它的正解**：把無界廣播換成 N 人分片，
位置走 DataChannel、結算走 host 的 relay。

## 四、建議的分層（兩題共用）

| 層 | 傳輸 | 內容 | 成本 |
| --- | --- | --- | --- |
| **即時、可丟失** | WebRTC DataChannel | 走棋、位置、動畫、聊天、特效 | **0 relay 請求** |
| **持久、需結算** | host／對手的 relay | 加入離開、擊殺、掉寶、對局結果 | 低，且由 host 自付 |
| **發現** | 共同集（少數硬編碼） | 世界公告、房間公告、找對手 | 極低（可尋址＋expiration，不累積） |

## 五、待決

1. **權威模型選 A 還是 C。** C 正確但要確定性模擬 ＋ 排序器 ＋ commit-reveal；A 簡單但可作弊。
   建議分級（高價值走 C，低價值走 A），但那個分界線要產品決定。
2. **`worldSeed` 在動態進出下怎麼維持**——本設計最難的一塊，需要 epoch 設計。
3. **行動端能不能當 host**（20 條 RTCPeerConnection ＋ 上行頻寬）——需實測。
4. **TURN 要接了**：免房間 P2P 是主要路徑之後，對稱 NAT 不再是「以後再說」的事。
