# 研究：借用公開 Nostr relay（如 relay.damus.io）轉傳訊息的可行性、風險與客戶端檢查缺口

> 目的：評估把訊息透過**外部公開 Nostr relay** 轉傳給他人是否可行、風險為何、
> 客戶端是否需要更進一步的防護；並延伸評估「蒐集多個公開 relay 當緊急備援」的架構。
> 相關：ADR-0039（錨點＋簽章清單）、ADR-0034（Relay Pool）、ADR-0036（hint 陳舊）、
> ADR-0057（NIP-42 AUTH）、ADR-0065（TTL）、ADR-0092（一致性稽核）、ADR-0188/0239（信任根）、
> ADR-0237（連線歸屬）、ADR-0260（NIP-62 vanish）。結論先行。

## 結論摘要

**技術上完全可行**（客戶端本來就支援任意 relay URL；核心訊息 kind 1059 是 NIP-59 標準），
**而且這是去中心化的正當用法**。但代價是：**訊息內容仍加密，元資料保護降級到只剩 Gift Wrap 那一層**。
若當「緊急備援」用，真正的難題不在隱私（那可選擇接受），而在**功能會默默失效**——
且**客戶端目前對 relay 幾乎不做任何行為檢查**，偵測不到這些失效。

## 1. 技術可行性

- 客戶端已支援自填 relay（登入畫面、per-identity relay、relay hint〔ADR-0035〕）。
- NIP-42 AUTH 是**回應式**的：公共站不發挑戰就不認證，連線照常成立。
- 主訊息管線 **kind 1059（NIP-17/59 Gift Wrap）是標準**，主流公共站會收。

## 2. 風險（依嚴重度）

### 🔴 收件匣變成公開可讀（最嚴重）

我方中繼 `requireAuth` **預設開**——須證明自己是收件人才能讀 `#p: 你` 的信箱。
公共站通常不要求認證，於是**任何人**都能下：

```json
{"kinds":[1059], "#p":["<你的 pubkey>"]}
```

內容仍安全（密文＋一次性寄件者），但觀察者免費取得：**每則訊息的精確到達時間**、
訊息量與作息模式、密文大小級距、長期關聯。心跳（20000）與 presence 同理可被匿名長期觀察。
這正是本專案花大力氣藏的東西（Gift Wrap／presence jitter〔ADR-0088〕），在公共站上等於自願交出。

### 🟠 保留政策不可控（兩個方向都糟）

存太久 → 密文永久躺在第三方（未來密碼學進展／司法調閱的暴露面）；清太快 → 離線留言遺失。
我方有 TTL（ADR-0065）＋ NIP-62 立即清除（ADR-0260）；**公共站通常兩者皆無**。

### 🟠 自訂 kind 靜默失敗

`1060`（檔案塊）、`44/45`（emoji blob）、`10038`（企業名冊）是**本專案自訂**。
公共站可能拒收（功能默默壞掉）或照收（資料無限期堆在第三方）。

### 🟠 寫入被拒 / 速率限制（當備援時最致命）

很多公共 relay **讀免費、寫有條件**：付費、白名單、對陌生 pubkey 的反垃圾過濾。
**連線成功、訂閱成功、送訊息卻被靜默丟棄**——最難除錯的故障型態。
心跳（60 秒一次）＋輸入中提示在反垃圾機制眼中就是高頻噪音。

### 🟠 IP 歸屬多一方

ADR-0237 已記載中繼可做連線歸屬；多用一座公共站＝多一方看得到「這個 IP 何時上線」。

## 3. 客戶端 relay 檢查：現況與缺口

### 現況（客戶端**只**做這四件事）

| 檢查 | 位置 | 內容 |
| --- | --- | --- |
| 登入前探測 | `SignIn.tsx: probeRelay()` | 開 WebSocket、3 秒逾時 → **純 liveness**；供自動選座（ADR-0069） |
| 連線狀態與重連 | `relay-backend: onConnection` | 斷線偵測＋退避重連（ADR-0016），回報 UI |
| hint 陳舊偵測 | `RELAY_STALE_MS = 5 分鐘` | 某座連續離線逾時 → 標記 hint 可能過期、改走冗餘廣播（ADR-0036/0039） |
| **簽章驗證** | `verifyRelayList(event, maintainerPubkey)` | 收到 kind 10037 清單時驗維護者簽章才採用——**唯一的信任檢查** |

### 🔴 缺口

`relay/bootstrap/conformance.ts` 的行為探測（**Ephemeral 語意、NIP-40 過期遵守、AUTH**）
**只在 CI 的每小時排程跑，客戶端完全沒有**。因此客戶端連上一座 relay 時：

- 只知道「它活著」；
- **不知道**它會不會把 Ephemeral 事件永久存起來；
- **不知道**它會不會無視過期、把密文留一輩子；
- **不知道**它要不要求 AUTH（＝收件匣是否公開可讀）；
- **寫入被靜默丟棄也偵測不到**。

且有個不對稱：CI 探測的是 `relays.json` 裡的候選站；**使用者自填的 relay（與未來的公共備援池）
從來沒有被任何一層檢查過行為**。

### 補充：客戶端的 relay 來源鏈（釐清常見誤解）

```
① 硬編碼錨點（bootstrap-config.ts）→ 編譯進 app、恆連保底
② 帶內簽章清單（kind 10037，維護者簽章）→ 驗簽後採用，不必重新發版即可調整
③ 使用者自填 / per-identity relay → 覆寫上述
```

**`relays.json` 不在這條鏈上**——全 repo 的客戶端程式碼都不讀它。它是 relay-health workflow
維護的**明文候選清單**，由維護者本機離線簽發成 kind 10037 才進到客戶端（ADR-0239 把信任根
移出 CI，故 CI 被入侵也偽造不出清單）。

## 4. 建議的客戶端防護（若要支援公共 relay）

| 防護 | 做法 | 成本 |
| --- | --- | --- |
| **① 偵測並警告「不要求認證的中繼」** | 連上後若對方**從未發 AUTH 挑戰**，UI 標示「任何人都能看到你何時收到訊息」 | 極低——連線當下即可知，零協定改動。**CP 值最高** |
| **② NIP-11 能力偵測** | 送自訂 kind（檔案／emoji blob）前先讀 relay 的 NIP-11，不支援就別送並明確告知 | 低——`relay-info.ts` 的 `fetchRelayInfo()` 已存在（贊助卡在用） |
| **③ 自填 relay 處的事前提示** | 填非官方 relay 時一句話點明風險，而非事後才發現 | 純 UI |
| **④ 下放輕量 conformance** | 把 `conformance.ts` 的黑箱探測下放客戶端，連非官方 relay 時跑一次，結果影響 UI 提示與路由權重 | 中——探測本身是純黑箱、不依賴伺服器端能力 |

**不建議**：padding／誘餌流量（成本高、效益不明）；**拒絕連公共站**（違反去中心化本義——
使用者有權選擇，我們的責任是讓他**知情**）。

## 5. 延伸：公開 relay 當「緊急備援池」的架構

### 驗證機制已經現成

`relay/bootstrap/conformance.ts`（ADR-0092）已有黑箱探測＋`evaluateAdmission` 分級，
且 `relay-health.yml` 每小時在跑。候選 URL 丟進 `relays.json` 即會自動探測、分級、記 uptime。

⚠️ 但要有心理準備：**多數公共站會卡在 `rejectsExpired`**（不遵守 NIP-40 過期）——
而那正是「你的密文會無限期留在別人伺服器上」的具體表現，也正是它被列為收錄條件的原因。

### 建議：分層，不要混進簽章清單

現行錨點／簽章清單是**維護者簽章背書**的；把來路不明的公共站混進去等於替它們背書，
也稀釋那份簽章的意義。建議兩層：

| 層級 | 內容 | 語意 |
| --- | --- | --- |
| **Tier 1：簽章清單** | 官方錨點＋通過一致性稽核的社群節點 | 維護者背書、完整雙層保護 |
| **Tier 2：緊急備援池** | 公開 Nostr relay | **不背書、降級隱私、僅在 Tier 1 全失聯時啟用**，且 UI 明示 |

Tier 2 的關鍵在於**只在 Tier 1 全掛時才用**＋啟用時明確告知降級——這樣「緊急備援」名副其實，
是「斷線 vs 降級」之間的選擇，而非預設路徑。

### 更省事的替代方案

與其蒐集陌生 URL，**多開一座自己的**可能更划算：`node-relay` 是單檔約 97KB
（見 `retired-phone-home-relay.md`），Cloudflare Workers 免費層即可跑。而**兩座錨點目前都在
Cloudflare**——真正的韌性缺口是**平台單點**，ADR-0189 早已記「第三座宜換平台」。
換平台開一座（Fly／Zeabur／家裡的舊手機）比十個公共 relay 更能提升可用性，且零隱私代價。

## 6. 待裁示

1. 是否支援公共 relay？若是，走 Tier 2 分層（需立 ADR）。
2. 客戶端防護要做到哪一層（①最低成本、④最完整）。
3. 或優先補「第三座自架錨點（換平台）」——用可用性換取零隱私代價。
