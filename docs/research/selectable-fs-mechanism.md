# 研究稿：把 EK 制與雙棘輪做成可設定的選項，可行嗎

- 日期：2026-09-21
- 狀態：**研究稿，尚未成為決策**。採納才進 ADR。
- 起點：使用者問「是否可以讓現行 EK 制與雙棘輪變成可設定的選項（帳號建立時或初次加好友時決定），
  變更機制時自動替換執行」
- **⚠ 這題有前案，而且那份 ADR 就是這個問題生出來的**——見 §1。

## 結論

**技術上做得到，但不建議做成「使用者可設」——而我反對的理由與前案列的四條**只有兩條相同**。**

三句話：

1. **ADR-0302〈非目標〉已經排除過「使用者可設的 FS 模式」**，而它的四條理由到 2026-09-21
   **一條已死、一條只擋一半、兩條仍成立**（§2 逐條重審）。所以不能只是引用前案了事。
2. 🔴 **但有一條前案不可能有的新理由**：ADR-0302 §3（**三天前**才實作）讓「可設」多出一個
   致命後果——**使用者加第二台裝置，會讓所有聯絡人收到安全警告**（§3）。
3. 🟢 **ADR-0302 自己留了逃生口**：「凡是想加第二條路徑者，**把它做成不可設**即可落在本項之外」。
   而這題剛好可以——因為**機制其實不是偏好，是後果**（§5）。

⇒ 建議見 §6：若日後真有棘輪，**由裝置數推導機制**，不要做成設定項。

---

## 1. 前案：ADR-0302 就是這個問題生出來的

ADR-0302 的檔頭原話：

> **起點**：討論「能不能讓棘輪與手動輪替並存、**做成可設的功能**」時查出——
> 那個辨識機制我們已經有了（`FS_CAPABILITY = "ek-v1"`、EK 公告 `{ v: 1, … }`）。

而它的〈非目標〉第二條：

> **不做使用者可設的 FS 模式。**
> ⇒ 凡是想加第二條路徑者，**把它做成「不可設」即可落在本項之外**——
> 這正是 0303 §7.4a 採用的形狀，也是本專案往後處理同類問題的預設答案。

⚠ 所以這題的正確問法不是「可不可行」，是**「四條理由今天還成不成立，以及逃生口走不走得通」**。

## 2. 逐條重審那四條理由（2026-09-21）

| # | 原理由 | 今天 |
| --- | --- | --- |
| ① | 預金鑰／session 是**裝置層的全域狀態**，無法 per-conversation 開關 | 🟠 **只擋一半**——見 §2.1 |
| ② | 降級面隨模式數成長 | 🔴 **仍成立，而且更嚴重**——見 §2.2 |
| ③ | 審計面加倍（ADR-0302 §6 已量化，對「可設」仍成立） | 🔴 **仍成立** |
| ④ | 群組混模無法誠實呈現（群組強度＝最弱成員） | ✅ **已死**——見 §2.3 |
| ⑤ | 使用者答不出這個問題 | 🟠 **可重新框架**——見 §5 |

### 2.1 ① 只擋「初次加好友時決定」，擋不住「帳號建立時決定」

這條理由的實質是：預金鑰與 session 狀態是**裝置層**的東西，開了就是整台都開。
⇒ **per-conversation（初次加好友時決定）真的不可行**，這條完全擋得住。

但使用者問的是兩種形狀，而**帳號層那一種不受此限**：整個帳號用同一套，裝置層狀態要嘛全開要嘛全關。

⇒ **這條理由對使用者提的問題只答了一半。** 前案沒有分開這兩種形狀。

### 2.2 ② 今天比當初嚴重，因為偏序

ADR-0302 §3 的補記已經記下：強度序**不是全序**。
`ek-pq-v1`（後量子、無 PCS）與 `ratchet-v1`（有 PCS、非後量子）**各有對方沒有的東西**。

⇒ 一旦棘輪成為第二個可選機制，`compareFsStrength` 就必須真的處理 `"incomparable"`，
而**偏序本身還沒設計**。「可設」把這件事從「未來可能要面對」變成「上線第一天就要面對」。

### 2.3 ④ 已被 ADR-0319 解掉

當初說「群組混模無法誠實呈現（群組強度＝最弱成員）」。但 ADR-0319 已經決定並實作：

- 成員面板顯示**每位成員**的三態（加密子鑰已知／未知／⚠ 曾知現無）
- 面板頂端一行匯總「本群 N 位成員中，M 位的訊息有前向保密」
- 群訊送出路徑**不做 per-member 警告**（那會在 15 人群裡洗版）

⇒ 混模**已經是現況**（ADR-0320 §2：「逐位成員各自決定⋯那不是失敗，是盡力而為」），
而且已經誠實呈現得出來。**這條理由不再成立。**

## 3. 🔴 一條前案不可能有的新理由：加裝置＝對全體聯絡人發安全警告

這是本研究最重要的發現，而它**三天前才成立**。

ADR-0302 §3（2026-09-19 實作）立下的規則是：**釘選的 `scheme` 只升不降**。
較弱的宣告不覆蓋基準，只記進 `declared`，而送訊時 `pinIsDowngraded()` 為真即發
`onFsRollback` ⇒ 對方看到的是：

> ⚠️ 這位聯絡人**改用了較弱的加密機制**⋯⋯若你沒有預期這件事，建議透過其他管道向他確認。

現在把「可設」的情境套進去：

1. Alice 建帳號時選了「棘輪」（單裝置、有 PCS）
2. 三個月後她買了平板，配對上去
3. 棘輪與多裝置互斥（[另一份研究稿](./double-ratchet-on-current-design.md) §1）⇒ 必須換回 EK
4. 🔴 **她的每一位聯絡人都收到「他改用了較弱的加密機制，建議向他確認」**

⇒ **一個完全正常的使用者行為（多一台裝置），觸發了一次全體聯絡人的安全警告。**

而且更糟：`scheme` 只升不降 ⇒ 對方的釘選**永遠停在 `ratchet-v1`**、`declared` 永遠是 `ek-v1`
⇒ **那個警告不會消失**，除非我們另外定義一種「自願更換機制」的宣告。

### 3.1 補救是做得到的，但它是第三種宣告

ADR-0314 有現成的先例：FS 停用不是讓欄位消失，而是**明示退場**（`fs: "none"`）——
理由正是「讓釘選過我的聯絡人不會永久看到假警報」。

同樣的形狀可以用在這裡：簽章個人檔裡帶一個「我自願改用 X」的宣告。
它**不可偽造**（ADR-0245 §81：`fs` 在簽章個人檔內），攻擊者只能扣住新個人檔，
而那樣我們仍看到舊的、仍然警告 ⇒ 失敗方向落在安全側。

⚠ **但那不能拿來消音。** 對方的保護程度**確實降低了**，只是原因不同。
誠實的做法是第三句話（「他自願改用了較弱的機制」），不是靜默。

⇒ 成本：**第三種宣告 ＋ 第四句文案 ＋ 對應的紅線測試**，疊在 ADR-0302 §4 剛做完的三種上。

## 4. 自動替換：兩個方向的可行性不對稱

使用者問的第二半是「變更機制替換自動執行」。逐向分析：

### 4.1 EK → 棘輪（升級）

| 步驟 | 可行嗎 |
| --- | --- |
| 宣告新能力 | ✅ `fs` 欄位改字串即可，ADR-0302 §3 的「只升不降」正好讓對方自動跟上 |
| 建立 session | 🔴 **需要聯絡人可讀的預金鑰束——今天不存在**（研究稿 §2.1） |
| 舊訊息 | ✅ 本機封存不受影響 |
| 在途訊息 | ✅ EK 私鑰保留到 grace 期滿，解得開 |
| 對方沒升級 | ✅ 退回 EK，per-contact 各自決定（同 ADR-0320 §2 的既有形狀） |

⇒ **升級方向的唯一硬阻擋是預金鑰束**，那是棘輪本身的前置，不是「可設」帶來的。

### 4.2 棘輪 → EK（降級）

| 步驟 | 可行嗎 |
| --- | --- |
| 宣告 | 🔴 需要 §3.1 的第三種宣告，否則永久假警報 |
| 拆 session | ✅ 本機刪掉即可 |
| 舊訊息 | 🔴 **棘輪解過的訊息在本機封存裡；但對方手上的在途密文用的是 session 金鑰** ⇒ 拆太早會解不開 ⇒ 需要一個 grace，與 EK 的 grace 各自一套 |
| 對方的認知 | 🔴 他的釘選停在 `ratchet-v1`，見 §3 |

### 4.3 遷移窗口本身

兩個方向都有一段**兩套機制同時活著**的期間（宣告傳播 ＋ grace）。
那正好是最脆弱的時候，而失敗會落進 ADR-0316 的 `maybeEkLoss` 桶——
使用者看到的是「有訊息解不開」，而**分不出是遷移造成的還是真的出事**。

⇒ 遷移期需要自己的可觀測性，否則它會偽裝成 ADR-0316 想抓的那個問題。

## 5. 🔵 問題重新框架：機制不是偏好，是**後果**

前案第五條理由是「使用者答不出這個問題」。若問法是「你要 EK 還是雙棘輪」，那當然答不出。

但真正的取捨其實是一句人話：

> **你要這個帳號能在多台裝置上用，還是要「被入侵後會自己痊癒」的保護？**

這是使用者**答得出**的——多裝置與否是他每天都在做的決定（買不買平板、要不要在公司電腦登入）。

⚠ **但那正好說明它不該是設定項。** 兩個理由：

1. **答案會變。** 今天單機的人明天買平板。設定項一旦與現實不符，就是「使用者以為自己有 PCS，
   實際上因為多了一台而沒有」——或者反過來，被 §3 的警告轟炸。
2. **它是可推導的。** ADR-0322 S1 已經出貨裝置目錄 ⇒ **「這個帳號有幾台裝置」本機就查得到**。
   把可推導的事實做成設定項，等於製造一個必然會與現實分歧的第二真相。

⇒ **這正是 ADR-0302 逃生口的形狀**：不可設、自動、由既有狀態推導。

## 6. 建議

**不要做成使用者可設的選項。** 但也不要單純引用前案——那四條理由今天只剩兩條完整成立。

真正該寫下來的理由是**新的那一條**：

> 機制與多裝置互斥，而多裝置是**可推導的事實**、且**會隨時間改變**。
> 做成設定項就是讓設定與事實分歧；而每一次分歧的修正，在協定上都是一次**對全體聯絡人可見的降級事件**。

若日後真有棘輪，建議的形狀是：

1. **由裝置數推導**：帳號只有一台裝置 → 用棘輪；超過一台 → 用 EK。無設定項。
2. **加裝置時自動遷移**，並且**必須先有 §3.1 的「自願更換機制」宣告 ＋ 第四句文案**，
   否則那個動作會變成一次全體聯絡人的假警報。
3. **per-contact 的形狀不做**（前案理由 ① 完整成立：裝置層狀態無法逐對話開關）。

⚠ 誠實揭露：**這個形狀有一個我不喜歡的性質**——它讓「安全性」與「便利性」變成一個
使用者不知道自己在做的取捨（他以為只是多配一台平板）。要緩解只能靠配對流程明白告知，
而那又把「不可設」拉回「半個設定項」。**我沒有解掉這個張力，只是指出它在哪裡。**

## 6.5 變體：「建帳號時決定，之後永不可改」可行嗎（2026-09-21 追問）

這個修正**直接打掉 §3 那條最強的反對**，值得認真算。結論是**仍然不可行，但理由換了**。

### 6.5.1 它確實解掉了三件事（這不是客套）

| §3／§4 的問題 | 不可變之後 |
| --- | --- |
| 加裝置 ⇒ 機制變更 ⇒ **全體聯絡人收到安全警告** | ✅ **消失**——根本沒有機制變更 |
| 需要第三種「自願更換機制」宣告 ＋ 第四句文案 | ✅ **不需要** |
| 遷移窗口兩套並存、偽裝成 ADR-0316 的解不開 | ✅ **不存在** |
| `scheme` 只升不降與自願降級衝突 | ✅ **永不衝突** |

⇒ **§4 整節作廢，§3 的致命後果消失。** 這是真實的改進。

### 6.5.2 🔴 但它做不到它想做的事：**不可變的設定，產生不出「單一機制的帳號」**

有效機制是**雙方能力的交集**，不是單方的設定：

```
Alice（帳號設定：棘輪）  ↔  Bob（只有 EK 的客戶端／舊版／選了 EK）
⇒ 這條對話只能走 EK
```

而 per-contact 退回**已經是現況**（`fsSendOpt`：`this.fsState.contactEks[pk] ?? pk`，
ADR-0320 §2「逐位成員各自決定⋯那不是失敗，是盡力而為」）。

由此得到兩個後果，**兩個都致命**：

1. **設定決定的是「我提供什麼」，不是「我得到什麼」。**
   一個選了棘輪、但聯絡人多半是 EK 的使用者，**實際上幾乎不會用到棘輪**——
   而設定頁上寫著「棘輪」。⇒ **這是一個會說謊的設定**，而且它說的謊正是
   ADR-0278／0287 一路在防的那一種（UI 不得說謊）。
2. 🔴 **她仍然要同時跑兩條路徑** ⇒ ADR-0302 的理由 ①
   （「預金鑰／session 是裝置層的全域狀態」）**原封不動地回來了**。
   她的裝置要同時持有：給棘輪聯絡人的 session 狀態、**與**給 EK 聯絡人的 EK 金鑰。

⇒ **不可變省下的是「遷移」，省不到「兩條路徑」。** 而後者才是成本的大頭
（§2.2 的偏序、§2.3 的審計面、預金鑰基礎建設、兩套降級語意）。

### 6.5.3 不可變讓「使用者答不出」從缺點變成**陷阱**

ADR-0302 理由 ⑤ 原本只是「使用者答不出這個問題」。加上不可變之後，
那個答不出的問題變成**永久的**——而且問在資訊最少的那一刻（還沒有聯絡人、還沒有第二台裝置、
還不知道自己會怎麼用）。

本專案對這件事有既有立場，而且方向一致：

- **ADR-0273 §4**：「一律清除，不做『傳送原檔』開關（v1）：隱私預設鐵則；
  **多一個開關就是多一個誤觸的腳槍**。」
- **ADR-0202**：不可逆的破壞性動作放在設定的**「危險區域」**、要二次確認。
  ⇒ 這個專案處理不可逆的方式是**把它藏起來並加閘門**，不是**放進註冊流程**。

### 6.5.4 失敗模式的形狀是最糟的那一種

若「選了棘輪」等於「永遠單裝置」（否則就要 per-device session ＋ 扇出，見 §2）：

1. 使用者在註冊時選了棘輪（可能只是因為它聽起來比較安全）
2. **幾個月後**買了手機，想配對
3. 配對被拒
4. 唯一補救＝**換帳號** ＝ 換 npub ＝ **通知所有聯絡人、丟掉既有身分與歷史**

⇒ 對一個通訊軟體而言，「你的選擇讓你永遠不能用第二台裝置，而補救是換掉你的身分」
是災難級的失敗模式。而且它**延遲數月才顯現**——使用者當下不可能把後果連回那個選擇。

⚠ 對照 §6 建議的推導式形狀：那邊的失敗模式是「配了第二台 ⇒ 失去 PCS」，
**可逆、即時、而且不影響身分**。兩者的嚴重程度差一個量級。

### 6.5.5 ⇒ 結論

**不可行。** 但要說清楚它為什麼不可行，因為它確實修好了一件事：

> 不可變**成功地**消滅了遷移問題，**卻沒有消滅兩條路徑**——
> 因為有效機制取決於對方，不取決於你的設定。
> 於是它付了「不可逆的使用者選擇」這個最貴的代價，
> 買到的只是成本裡較小的那一塊。

若目標是「讓想要 PCS 的人拿得到」，§6 的推導式形狀仍然是較好的答案：
**由裝置數推導、不問使用者、可逆、且失敗模式溫和。**

## 7. 未解問題（沒有一項已經回答）

1. **偏序沒有設計**（ADR-0302 §3 補記）。「可設」會讓它從未來問題變成第一天問題。
2. **預金鑰束不存在**，那是棘輪的前置，與本題獨立但擋在前面。
3. **第三種宣告（自願更換機制）與第四句文案**未設計。
4. **遷移窗口的可觀測性**未設計——會偽裝成 ADR-0316 的解不開。
5. **「多裝置 vs PCS」這個取捨要不要在配對流程告知使用者**，以及怎麼講才不會嚇人又不說謊。
6. 外部審計仍未進行（ADR-0306）——同樣擋在所有新密碼學之前。
