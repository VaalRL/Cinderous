# 研究：客戶端能不能搜尋陌生 relay、在上面找出特定特徵的事件（例如「自動找房配對」）

> 問題：讓客戶端動態發現它原本不知道的 relay，並在上面查詢帶特定 kind／tag 的事件，
> 用來實作「遊戲自動找到房間配對」。
> 相關：`docs/research/public-relay-fallback.md`、`docs/research/shared-relay-for-game-clients.md`、
> ADR-0034（多中繼路由）、ADR-0039（錨點＋簽章清單）、ADR-0092（節點自報與一致性稽核）、
> ADR-0123（訂閱必須具名）、ADR-0239（信任根移出 CI）、ADR-0275（探測下放客戶端）。
>
> 本文件為**研究記錄、非決策**。查證日期 2026-09-22。

## 結論摘要

把問題拆成三層，答案一層比一層壞：

| 層 | 問題 | 答案 |
| --- | --- | --- |
| ① 發現陌生 relay | 客戶端能不能找到它不知道的 relay？ | ✅ **有標準：NIP-66**。而且它已經做了四份遊戲規格想用 NIP-11 做的事，還做得更好 |
| ② 在上面查特定事件 | 能不能查 `{kinds, #t}`？ | ⚠️ 可以，**但大廳事件是 Ephemeral ⇒ 查不到**，只能訂閱後等下一次心跳 |
| ③ 拿來做配對 | 這樣能自動找到對手嗎？ | 🔴 **方向錯了。配對是會合問題，不是搜尋問題**——而規格指定的「選 RTT 最低者」會**主動破壞**配對 |

---

## 一、發現陌生 relay：NIP-66 就是這件事的標準

四份遊戲規格的梯隊③都寫「透過 **NIP-11 探針**動態掃描探索到的最快免費 Relay，
**自動過濾收費節點**」。這裡有個基礎誤解：

**NIP-11 不能「發現」任何東西。** 它是「給我一個 URL，我告訴你這座站的能力」——
描述用的，不是索引。那份規格沒有回答**URL 從哪來**。

真正的答案是 **NIP-66（Relay Discovery and Liveness Monitoring）**：

| 事件 | 用途 |
| --- | --- |
| **kind 30166** | relay 發現事件（可尋址，`d` ＝正規化後的 relay URL）。內容可放該站的 NIP-11 文件 |
| **kind 10166** | 監測者公告：宣告「我會發佈 30166」 |

30166 的 tag 形狀，**正好就是遊戲規格想要的那些欄位**：

| Tag | 意義 |
| --- | --- |
| `["N", "40"]` | 支援的 NIP 編號（可重複） |
| `["rtt-open"]`／`["rtt-read"]`／`["rtt-write"]` | 三種 RTT（毫秒） |
| `["n", "clearnet"]` | 網路型態（clearnet／tor／i2p／loki） |
| `["R", "auth"]`／`["R", "!payment"]` | 站方要求；**`!` 前綴＝不支援** |

**⇒「自動過濾收費節點」＝ 查 `["R", "!payment"]`，一個現成的標準 tag。**
不必自己掃全網、不必自己跑探針——向 NIP-66 的 meta-relay（`relay.nostr.watch`、`relaypag.es`、
`monitorlizard.nostr1.com`）下一個 REQ 就拿得到一整份清單。

這比規格裡的設計**便宜好幾個數量級**：一次查詢 vs. 對幾千座站各開一條 WebSocket 跑探針。

⚠ NIP-66 自己寫明兩件事：
- 「Clients **MUST NOT** require 30166 events to function」——缺監測資料不得阻止連線；
- 「Clients **SHOULD NOT** trust a single source」——監測者可能因設定錯誤或惡意而發假資料，
  建議 web-of-trust 過濾、多來源交叉、以及「若某個過濾條件會砍掉不合理比例的 relay 就丟棄該結果」。

### 與本專案既有機制的關係

Cinderous 其實**已經有一套 curated 版的同一件事**：`relays.json`（候選明文清單）→
`conformance.ts` 的黑箱探測（ADR-0092，探測本體已上移 core，ADR-0275）→ `evaluateAdmission` 分級 →
維護者**離線簽章**成 kind 10037（ADR-0239 把信任根移出 CI）。

**NIP-66 補的是這條鏈最前面那一段——候選從哪來。** 目前 `relays.json` 只有兩筆、靠人工維護。
把 NIP-66 當成**候選來源**餵進既有管線，信任根仍是維護者簽章的 10037，這是低風險、有實益的用法：
發現交給網路，背書仍然由人負責。

## 二、在陌生 relay 上查「特定特徵的事件」：Ephemeral 是硬牆

### 🔴 大廳事件查不到，因為它們依定義不被儲存

四款遊戲的大廳／房間廣播用的都是 Ephemeral kind：

| 應用 | 大廳事件 | 頻率 |
| --- | --- | --- |
| 沒當好爸爸 | **20078**（seek，帶 `#t:nagd` ＋ `#g:<gameId>`） | 心跳每 10 秒、TTL 30 秒 |
| 元素使 | **24000**（約戰廣播）、**20078**（遊蕩者） | 每 30 秒 |
| 辭職信 | **20078**（道具／就緒／聊天） | 事件驅動 |

NIP-01 規定 20000–29999 中繼**不得持久化**；本專案的 `relay-core.ts:562` 也正是這樣實作的。
所以對一座**行為正確**的 relay 送 `REQ {kinds:[20078], "#t":["nagd"]}`，你會拿到**一個 EOSE，零筆事件**。

**⇒「搜尋」開放中的房間在協定上不成立。** 能做的只有：訂閱 → **等一個心跳週期**（10～30 秒）→
收集期間飄過來的 seek。這給了配對一個**下限延遲**，而且每座候選 relay 都要各等一輪。

### 順帶：非一致的實作會讓這件事更難預測

《沒當好爸爸》的 `TODO.md:265-266` 有一筆 2026-09-04 的實測觀察：

> `wss://relay.damus.io` 握手回 503；**nos.lol 會把 20078 存起來、新訂閱時重播**，
> 靠 `since`（TTL 視窗）擋住舊事件

也就是說：同一份查詢在不同陌生站會有不同行為（有的重播舊房間、有的什麼都沒有）。
客戶端必須自己用 `since` 兜底——他們已經在做了，但這是**每接一座陌生站就要重新確認一次**的事。

### 兩個本來可以幫上忙、但實際上沒有的工具

| 工具 | 現況 |
| --- | --- |
| **NIP-45 COUNT**（先便宜地問「這站有幾間房？」再決定要不要訂） | ❌ **實質已死**。NIPs repo 有一個 PR #842 提議移除它；社群討論指出「沒有仍在維護的 relay 實作搭配仍在維護的客戶端實作」。`rnostr` 之類有實驗性支援，但不能假設存在 |
| **NIP-50 SEARCH** | ❌ 全文檢索，與 tag 查詢無關，且支援率低 |

## 三、🔴 最重要的一節：配對是**會合問題**，不是搜尋問題

設 A 把房間廣播到 relay 集合 `S_A`，B 到 relay 集合 `S_B` 去找。

**兩人配得到對，當且僅當 `S_A ∩ S_B ≠ ∅`。**

「搜尋陌生 relay」增加的是 `|S_B|`，**對交集沒有幫助**——除非 A 剛好也選了同一批。
而 A 選自己的寫入集時用的是同一套邏輯，所以關鍵在於：**那套邏輯會讓兩邊收斂還是發散？**

### 規格指定的「選 RTT 最低者」會讓它發散

> | 03 | 🔍 **陌生自組織探針**| 透過 NIP-11 探針動態掃描探索到的最快免費 Relay | 備援 (3) |
> • 自動過濾收費節點，**選取 RTT 最低節點晉升**！

RTT 是**本地量測值**。台灣的玩家量到最快的是台灣的站，德國的玩家量到最快的是德國的站。
**兩人各自「優化」之後，交集為空。** 這個設計若真的生效，它不是沒幫助——它會**主動弄壞配對**。

（對「備援轉發已知對象的訊息」它是合理的——那時你已經知道要找誰。對「找陌生對手」它是反效果。
這兩件事在四份規格裡被寫成同一個梯隊表，是問題的根源。）

### 什麼樣的選法才會收斂

**排序鍵必須是每個客戶端都算得出同一個答案的東西，不能是本地量測值。**

一個可行的形狀（**推論，未實作**）：

```
候選 = NIP-66 30166（從固定的 meta-relay 取）
       ∩ ["R","!payment"] ∩ ["R","!auth"] ∩ 支援所需 NIP
排序 = 依 d（正規化 URL）字典序          ← 全球一致，不是 RTT
會合集 = 前 K 座（K 取小，例如 5）
輪替 = bucket = hash(gameId ‖ floor(now/1h)) % K   ← 分散負載但兩邊仍算得出同一個
```

關鍵是 **sort by URL, not by RTT**。RTT 可以用來在**會合集之內**決定先連哪一座，
但不能用來決定**會合集是誰**。

⚠ 但這仍然比不上硬編碼清單：它要求所有客戶端從 NIP-66 拿到**一致**的候選集，
而 NIP-66 明說監測者會彼此不一致、也可能說謊。任何不一致都會讓交集破洞。

### ⇒ 硬編碼的 Schelling point 仍然是配對的正解

四款遊戲的梯隊①②（專屬主力 ＋ `nos.lol`／`relay.damus.io`）**本來就是正確答案**：
少數、眾所周知、全球一致。配對要的是**收斂**，不是多樣性。

動態發現真正的價值在**韌性**（已知的站全掛了、或被封鎖時還能動），不在配對。
這兩個目標需要不同的選法，不該共用同一張梯隊表。

## 四、成本與風險盤點

| 項目 | 說明 |
| --- | --- |
| **連線成本** | 搜 N 座陌生站＝N 條 WebSocket ＋ N 個訂閱，**每座各要撐滿一個心跳窗**（10～30 秒）。行動端的電力與流量成本是實的 |
| **延遲下限** | 因上一條，「自動找房」最快也要一個心跳週期，不可能是即時 |
| **寫入被靜默丟棄** | `public-relay-fallback.md` §2 已記載：「連線成功、訂閱成功、送訊息卻被靜默丟棄——最難除錯的故障型態」。而 10 秒一次的大廳心跳在反垃圾機制眼中正是高頻噪音 |
| **🔴 假房間（griefing）** | 惡意 relay 營運者可以自產金鑰簽出大量 seek 事件，把你的大廳塞滿**永遠不會接受挑戰的幽靈**。簽章驗得過（它們是合法簽章），你無從分辨。這是開放配對固有的問題，唯一可壓的手段是**成本**——NIP-13 PoW（見 ADR-0366 §7）或信譽 |
| **遮蔽（eclipse）** | 反過來：惡意 relay 可以**只**回它想給你看的房間，把你導向共謀對手。多來源交叉是唯一緩解 |
| **IP 歸屬** | 連上任意陌生站＝把「這個 IP 何時在線」交給任意營運者（`public-relay-fallback.md` §2 的 🟠、ADR-0237） |
| **本專案的反諷** | `{kinds:[24000], "#t":[...]}` 這種形狀正是 ADR-0123 的 `scoped()` 會回 `CLOSED restricted` 的東西 ⇒ **Cinderous 自己的中繼是這套搜尋唯一會拒絕的站**（除非 ADR-0366 落地） |

## 五、建議

**分成兩件事做，不要混在一張梯隊表裡：**

1. **配對** → 維持硬編碼的少數會合集（梯隊①②）。**不要**讓 RTT 參與「會合集是誰」的決定。
   若要動態化，排序鍵必須全球一致（URL 字典序），不是本地 RTT。
2. **韌性／發現** → 改用 **NIP-66 kind 30166**，取代四份規格裡「NIP-11 動態掃描」那個做不到的設計。
   `["R","!payment"]` 直接給你「免費節點」這個條件，不必自己跑探針。

**對 Cinderous 本身的低風險用法（建議優先）：**

把 NIP-66 當成 `relays.json` 的**候選來源**餵進既有管線（`conformance.ts` → `evaluateAdmission` →
維護者簽章的 kind 10037）。發現交給網路，背書仍由人負責——與 ADR-0092／0239 完全相容，
也回應了 `public-relay-fallback.md` §5 留下的那個問題（「與其蒐集陌生 URL，多開一座自己的可能更划算」）：
**兩者不衝突，NIP-66 讓「蒐集」的成本降到接近零，而收錄門檻一點都不用放寬。**
