# 實作計畫：後量子加密子鑰（混合式 EK），參考 Signal 三重棘輪

- 日期：2026-09-21
- 狀態：**計畫稿**。動工時才寫 ADR（依本倉庫慣例：採納決策才進 ADR）。
- 決定背景：使用者於 2026-09-21 決定**保留現行 EK 設計**（不走棘輪），並要求規劃後量子改善。
- 相關研究稿：`signal-triple-ratchet-applicability.md`（設計來源、成本實測、副作用盤點）、
  `double-ratchet-on-current-design.md`、`selectable-fs-mechanism.md`

## 0. 一句話

**不是引進三重棘輪，是把我們已經在每週輪替的那把 EK 換成「古典 ＋ ML-KEM 混合」。**
Signal 花最大力氣的那個工程問題（把 1 KB 塞進逐則訊息的棘輪）**我們沒有**——
因為我們的 FS 是粗粒度的，公鑰放在一顆每週一次的公告事件裡不構成問題。

## 2. 設計

### 2.1 金鑰材料

`EK_e` 從「一把 secp256k1」變成**一對金鑰**：

```
EK_e = { classic: secp256k1 金鑰對, pq: ML-KEM-768 金鑰對 }
```

- **ML-KEM-768（FIPS 203）**，與 Signal 同一個參數集。不用 512（強度不足以撐十年）
  也不用 1024（體積翻倍買不到對應的保障）。
- 輪替與 grace **沿用現行排程**：每週一把、grace 7 天、`pruneFsKeys` 不必改
  （它只看 `at`）。

### 2.2 公告（kind 10040 v2）

```jsonc
{ "v": 2,
  "ek":   "<secp256k1 公鑰 hex>",      // 🔴 必須保留——v1 寄件人要用
  "pq":   "<ML-KEM-768 封裝金鑰 base64>",
  "next": "<下一週的 secp256k1>",       // 同現行
  "nextPq": "<下一週的 PQ>" }
```

🔴 **`ek` 欄位不可省略。** 一個還沒升級的寄件人只看得懂 `ek`；拿掉它等於讓所有舊版
聯絡人**完全送不出 FS 訊息**（退回身分金鑰）。

### 2.3 加密（混合式 KDF）

```
寄件（每則訊息各做一次，無狀態）：
  ss_classic = ECDH(臨時/身分私鑰, 對方 ek)
  (ct, ss_pq) = ML-KEM.Encaps(對方 pq)
  K = HKDF(ss_classic ‖ ss_pq, info = 層別標籤)
  → nip44.encrypt(明文, K)
  → ct 放在**外層 wrap 的 tag**

收件：
  ss_pq = ML-KEM.Decaps(我的 pq 私鑰, ct)
  其餘同上
```

三個要點：

1. **混合，不是取代。** 古典那一半完整保留 ⇒ 即使 ML-KEM 日後被破，
   我們也不會比今天更糟。這是 Signal／Apple／WhatsApp／OpenSSH 的共同做法。
2. **`ct` 只放一份。** seal 與 wrap 兩層共用同一個 `ss_pq`，靠 HKDF 的 `info`
   做域分離；兩層的 `ss_classic` 本來就不同，所以最終金鑰也不同。
   ⇒ 每則訊息 **+1088 bytes（base64 後 1452）**，不是兩份。
3. **無狀態。** 每則訊息各做一次新的封裝，不快取共享祕密。
   理由與 EK 用時間當索引一樣：**不需要跨裝置協調、亂序送達無所謂**。
   （快取可以把攤銷降到近零，但要收端記狀態，而收端有 D 台裝置——又回到協調問題。）

### 2.4 線路格式不變

`nostr-tools` 的 API 是 `nip44.encrypt(plaintext, conversationKey)`——**對話金鑰是參數**。
所以我們改的是「怎麼算出那把金鑰」，**payload 仍是 NIP-44 v2 的格式**。

⇒ 若日後 NIP-44 v3 定案，我們要做的是**改用它的導出方式**，不是拆掉什麼。

### 2.5 能力宣告與降級偵測

- 新字串 `ek-pq-v1`，`FS_SCHEME_RANK` 加一條邊：`{ "ek-v1": 1, "ek-pq-v1": 2 }`
- ⇒ ADR-0302 §3 的「只升不降」自動生效：**有人把你從 `ek-pq-v1` 拉回 `ek-v1`，
  對方會看到 `fs_rollbackWarning`**。這條防線**已經在了**。

## 3. 從 Signal 三重棘輪拿什麼、不拿什麼

| Signal 的做法 | 我們 | 理由 |
| --- | --- | --- |
| **ML-KEM-768（FIPS 203）** | ✅ 照抄 | 同一個參數集，最多實戰檢驗 |
| **混合 KDF，古典那半保留** | ✅ 照抄 | 破一邊不足以解密 |
| **降級只在第一則允許，之後鎖定** | ✅ 精神照抄 | 我們的版本是 ADR-0302 §3 的「只升不降」 |
| **從設計之初上形式化驗證** | 🟠 **做不到同等** | 他們用 ProVerif ＋ hax ＋ F\*，CI 每次改動重跑。我們沒有那個能力，**不得假裝有** ⇒ 改以外部審計替代（§7） |
| **抹除碼分塊（把 1 KB 切成 ~100 bytes 散在多則訊息）** | ❌ **不需要** | 那是為了塞進**逐則訊息的棘輪**。我們的公鑰放在**每週一次**的公告事件裡（1184 bytes vs 中繼上限 256 KiB） |
| **64-byte 種子先傳、其餘並行補齊** | ❌ 不需要 | 同上，是分塊傳輸的配套 |
| **持續棘輪式的 KEM 推進** | ❌ 不做 | 需要 per-device session（見姊妹研究稿）；我們每則各自封裝，無狀態 |

🔵 **Signal 最貴的那部分，正因為我們的 FS 粗而變成非問題。** 粗粒度第一次成為優勢。

每一階段**獨立有價值、可單獨出貨、可單獨回退**。

- ✅ ADR-0302 §1／§3／§4 **已於 2026-09-19 完成**
- ⏳ **外部審計的決定要重新做**（見 §7）——這是唯一的硬閘門

### Phase 1 — 讀端先行（🔴 順序紅線，見 §5）

`readEkAnnounce` 讀得懂 v2 的那一刻，Phase 1 的「等普及」時鐘就可以開始跑了。
兩個階段實際上合而為一。

⏸ **`openWrapWithEks` 的簽章改動延到 Phase 4**。原本排在這裡，但它有一個生產呼叫點

而且在**線路格式（`ct` 放哪個 tag）決定之前**動它是過早。

### Phase 3 — 金鑰生命週期 ✅ **已完成（2026-09-22）**

- ✅ `StoredFsKey` 與 `EkKey` 擴為 `{ nsec, pk, at, pq?: string }`（可選＝向後相容）
- ✅ 四條同步路徑都不丟：EK 分發（ADR-0322 S2）、雲端快照打包與合併、配對捆包
- ✅ `pruneFsKeys` 不必改（只看 `at`）
- ⏸ 生成當時仍關著 → **Phase 4 改成「現在就生」**（2026-09-21）。
  規劃時的顧慮是「白白扛著用不到的位元組」，但實作時量出來那是 **64 bytes**（只存種子），
  而種子要先經 ADR-0322 S2 分發到**每一台**裝置；等到開播才生，開關翻開的第一週會沒得用。
  沒公告 ⇒ 沒有人會拿它加密給我 ⇒ 現在生是零風險。⇒ **生成與公告解耦**，
  真正的閘門只剩 `EK_PQ_ANNOUNCE` 一個。

#### 🔴 Phase 3 抓到的兩件事

**一、`parseKeys` 會靜默丟掉新欄位。**
ADR-0322 S2 的 per-device 分發（`ek-envelope.ts`）解出金鑰時是**逐欄位重建**的
（`out.push({ nsec, pk, at })`）⇒ 加了 `pq` 也拿不到。而它**已經接線在跑**
（`relay-backend.ts:1694/1705`），所以這不是未來的問題。

後果不是「少一個欄位」：從分發事件拿到金鑰的那台裝置只有古典那一半、解不開後量子訊息，
而畫面上看起來像「金鑰還沒同步」（掉進 ADR-0316 的 `maybeEkLoss` 桶）——**最難查的那種**。

**二、🔵 改存「種子」而不是展開後的私鑰（實測驅動的設計變更）。**

原本打算存 2400-byte 的 ML-KEM 私鑰。實測 per-device 分發事件：

| | 事件大小 | 佔中繼 256 KiB 上限 |
| --- | --- | --- |
| 現況（純古典） | 4,515 bytes | 1.7% |
| 存展開後的私鑰 | **110,339 bytes** | **42.1%** |
| **改存 64-byte 種子** | **6,563 bytes** | **2.5%** |

放大 24 倍的原因是分發會**對每台裝置各加密一份**、還要**補空槽到 8 的倍數**
（藏裝置數，ADR-0322）⇒ 金鑰體積被乘上 8。

FIPS 203 的 KeyGen 是由 `d‖z`（64 bytes）**決定性**導出的，所以只存種子、用時再展開即可
（實測展開 0.3 ms，記憶體快取）。

⚠ 代價：**導出方式必須跨版本穩定**，否則既有種子會導出不同的金鑰 ⇒ 所有訊息解不開。
FIPS 203 標準化了它，但 `@noble/post-quantum` 是 pre-1.0 ⇒ 已用**釘死的測試向量**鎖住
（固定種子 → 公鑰 SHA-256），相依升級若改了導出方式，那條測試會紅而不是靜默壞掉。

### Phase 4 — 送收接線 ✅ **已完成（2026-09-21，ADR-0365）**

實作順序與每一步的理由：

**① NIP-44 開出「吃預先算好的金鑰」的入口**（`nip44.ts`）。
`encryptDM` 把 ECDH 算在函式**內部**，呼叫端插不了手，而混合式要的正是「ECDH 之後、
餵進 NIP-44 之前再過一次 HKDF」。⇒ 拆出 `conversationKey` / `encryptWithKey` /
`decryptWithKey` 三個函式，**它們不做任何混合**——混合規則單獨留在
`hybridConversationKey()`，因為那裡有 fail-closed 檢查，而那份檢查只能有一份。

**② 封裝層接線**（`nip59.ts`）。原計畫沒寫的是「怎麼不動 17 個呼叫端」。
做法是把收件目標從 `PubkeyHex` 換成寬鬆型別 `RecipientLike = PubkeyHex | { pk, pq? }`，
解封金鑰同理（`SecretKey | { sk, pqSk? }`）⇒ 既有呼叫端傳字串照舊、一行都不用改，
而且**只有一條路徑**（Fix First：不開 `sealAndWrapPq`）。

**③ 轉址接縫放寬**（`giftwrap` / `calendar` / `group` / `reaction`）。
EK 轉址本來就收斂在**唯一一個** `encryptToFor: (identityPk) => PubkeyHex` 上（ADR-0318），
所以只要把它的**回傳型別**放寬成 `RecipientLike` 就好——不是加第二個平行的 `pqPkFor`。
實際改動：11 處型別、4 行 import。

**④ 引擎接線**（`relay-backend.ts`）。`myCurrentEk()` / `fsDecryptCandidates()` /
`fsSendOpt()` 三個既有函式各自多帶後量子那一半；種子→金鑰對的展開加一層記憶體快取
（`fsDecryptCandidates()` **每收一則訊息就會被呼叫一次**、且會逐把重試，不快取等於每則重算數次）。

**⑤ 文案紅線**（`packages/i18n`）。見下方 Phase 5。

#### 🔴 Phase 4 抓到的三件事

**(a) `ek` 與 `pq` 是一對，拆開來更新會產生「對方手上不存在的組合」。**
混合式訊息要收件人拿出**同一把 EK 的兩半**才解得開。若把新學到的 `ek` 配上舊的 `pq`，
訊息**送得出去**、對方**永遠解不開**，而且兩邊都不會有任何錯誤——直到有人說「我沒收到」。
⇒ 收斂成 `learnContactEk()` 一處原子更新，規則三條：公告帶了 pq 就用新的；沒帶但 ek 沒變
就**保留**（1:1 的 `ek` hint 永遠不帶 pq，會覆蓋的話混合式永遠開不起來）；沒帶而 ek 換了
就**刪掉**。三條各有一支測試。

**(b) 雲端快照的合併是同一個坑的第二個入口。**
`mergeSnapshotContent` 是**逐欄位重建**的（那份程式碼自己的註解就警告過這件事，
ADR-0302／0314 都被咬過），而 `contactPq` 若跟著 `contactEks` 各自 union，
只要兩台裝置學到的 EK 不同步就會合出「A 側的 ek ＋ B 側的 pq」。
⇒ 新增 `pairContactPq()`：某人的 `ek` 從哪一側勝出，`pq` 就只能從那一側拿。

**(c) 「對方沒升級就不該走混合式」這條測試差點被自我副本騙過去。**
每則訊息同時產生「給對方的」與「自我副本」兩顆 wrap，而自我副本永遠加密到**我自己的** EK
（我自己的 pq 一定在手上）⇒ 它永遠帶 `pqct`。測試若只抓「最後一顆 1059」就會永遠是綠的。
⇒ 測試輔助改成按 `#p` 分流。

#### ⏸ 與原計畫的一項偏離：能力宣告**不**在這一階改

原計畫寫「能力宣告改 `ek-pq-v1`，`FS_SCHEME_RANK` 加邊」。**刻意沒做**，理由有兩層：

1. **那會是一句假話。** 能力宣告在簽章個人檔裡，它說的是「我用這個機制」。
   而 `EK_PQ_ANNOUNCE` 關著 ⇒ 我**沒有**公告 `pq` ⇒ 沒有任何人會用混合式加密給我。
   宣告一個實際上沒在跑的機制，正是 ADR-0302 §4 在防的那種事。
2. **它會傷到別人。** 宣告一個舊版不認得的字串，會讓每個還沒升級的聯絡人把我記進
   `unsupported`，而 ADR-0302 §1 造那個桶的全部理由就是別讓升級的人被誤報。
   在我還沒真的升級之前先去觸發它，是白白製造雜訊。

⇒ 能力宣告與 `FS_SCHEME_RANK` 加邊**與 `EK_PQ_ANNOUNCE` 綁在一起**，一起在 Phase 4b 翻開。
偏序本身（`ek-pq-v1` 與 `ratchet-v1` **不可比**）仍是未解問題（§9）。

### Phase 5 — 可觀測與文案 ✅ **已完成（2026-09-21）**

- 🔴 **不得宣稱「量子安全」**——簽章仍是 secp256k1，身分偽造照樣成立。
  比照 ADR-0306「文案不得宣稱 FS」立了一條紅線測試（`packages/i18n/src/i18n.test.ts`）：
  ①掃全語系全字串，不得出現「量子安全／抗量子／防量子／quantum-safe／quantum-proof」；
  ②提到「後量子／post-quantum」的字串**必須同時**寫明實驗性或未經審計。
  🔵 本版**還沒有任何後量子文案**，所以這組測試今天是空跑的——**那正是重點**：
  它不是在驗現況，是在「有人寫下第一句」的那一刻咬住。
- ML-KEM 的**隱式拒絕**（密文被竄改不報錯、回偽隨機祕密）最終表現為 NIP-44 MAC 失敗
  ⇒ 落進 ADR-0316 既有的 `maybeEkLoss` 桶，**確認不需要新 UI**。
  唯一新增的是一個**可診斷的**錯誤：對方用了混合式而這把候選金鑰缺後量子私鑰時直接拋，
  而不是退回純古典（退回最後還是 MAC 失敗，只是錯誤訊息會變得無法診斷）。

## 5. 🔴 順序紅線：讀端必須先普及

這是整個計畫**唯一不能搞錯**的地方。

一個還沒更新的客戶端看到 `v:2` 公告會回 `null` ⇒ 在它眼中對方「沒有 EK」
⇒ 送訊時跳 **「疑似降級（對方可能正在被攻擊）」**。

⇒ **第一個升級到後量子的人，會被所有舊版聯絡人誤報成被攻擊。**

⚠ 修正（`readEkAnnounce` 的 tagged union）已經在 main 上，但**已發布的 v0.0.16 沒有**。

⇒ 形狀與 ADR-0358 的金鑰輪替並存期一模一樣：

```
先發布「讀得懂 v:2」的版本  →  等普及  →  才開始發佈 v:2
```

**判斷「普及」沒有遙測可用**（同 ADR-0358），只能以發版後經過的時間與下載數粗估，
**寧可拖長不要提早**。

## 6. 相容性矩陣

| 寄件人 | 收件人 | 結果 |
| --- | --- | --- |
| v2 | v2 | ✅ 混合（古典 ＋ 後量子） |
| v2 | v1 | 古典（對方公告沒有 `pq`） |
| v1 | v2 | 古典（寄件人只看得懂 `ek` 欄位——所以它必須保留） |
| v1 | v1 | 古典（今天） |
| 任一 | 沒開 FS | 退回身分金鑰（今天的行為，不變） |

🔴 **保護程度取決於雙方之中較舊的那一個** ⇒ 覆蓋率隨兩端的採用率成長，
**實際起算日比出貨日晚數週到數月**。這是「早做」的另一個理由。

## 7. 風險與**不承諾**的事

1. 🔴 **外部密碼學審計仍未進行**（ADR-0306）。在未審計的基礎上疊第二層未審計的東西。
   具體的失敗模式不抽象：**混合式 KDF 若把古典那一半接錯**（域分離寫錯、某條路徑漏掉
   `ss_classic`），結果是**降低了古典安全性**去換一個還沒人需要的後量子性質——
   而且**不會有任何測試會紅**（兩邊都算得出同一把金鑰，訊息一切正常）。
   ⇒ 這是整份計畫最大的風險，而它**不是工程問題**。
2. **簽章仍是 secp256k1** ⇒ 量子攻擊者仍偽造得出事件。只保護機密性，不保護真實性。
3. **`@noble/post-quantum` 是 pre-1.0**（v0.7.x）。API 可能變動。
   🔵 但相依衝突比原估輕——樹裡已同時存在 `@noble/*` v1 與 v2。
4. **訊息 +18～41%**、DO 儲存按比例成長（實際用量未量測）。
   🔵 中繼的免費層瓶頸是**請求數**，而顆數不變 ⇒ **零影響**。
5. **上游可能走不同的路**（NIP-44 v3 無共識）。
   🔵 但啟用 FS 的訊息**本來就不互通**，新增的互通性代價 ≈ 零。

### 不承諾的事

- ❌ 不承諾「量子安全」
- ❌ 不承諾與未來的 NIP-44 v3 互通
- ❌ 不承諾形式化驗證（Signal 有，我們沒有，**不得暗示有**）

## 8. 驗收條件

1. v1↔v1、v1↔v2、v2↔v1、v2↔v2 四種組合**都送得到、都解得開**（測試矩陣）
2. 竄改 `ct` ⇒ **解不開**（fail-closed，不是靜默退回古典）
3. 拿掉 `pq` 欄位 ⇒ 自動退回古典，**且對方看到 `fs_rollbackWarning`**（ADR-0302 §3 生效）
4. 舊版客戶端讀 `v:2` 公告 ⇒ 「請更新」而**不是**「疑似降級」
5. 輪替、grace、多裝置同步、快照還原、配對捆包在 PQ 金鑰下全部正常
6. 文案紅線測試：任何語系都**不得**出現「量子安全」等同義宣稱

## 9. 未解問題

1. **外部審計要不要申請**——這是 §7.1 的唯一解，而它是個決定不是工程（ADR-0290 §2B 記著
   OTF 那條免費、成本只有一份申請書）
2. **DO 實際儲存用量未量測** ⇒ +18～41% 的絕對影響仍未知
3. **「普及」怎麼判斷**——無遙測，同 ADR-0358 的老問題
4. **`nextPq` 的預發**：現行 `next` 的作用是「預發下一週以**消除週界空窗**」（ADR-0238 §3）
   ⇒ PQ 那半**必須比照**，否則每週交界會有一段只有古典保護的窗口。細節未設計
