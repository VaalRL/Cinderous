# 0404. CLI 的 agent 私人頻道：白名單、狀態目錄、等回覆、產金鑰、限時、顯示名稱、前向保密

- 狀態：已接受（使用者 2026-10-30：「--ttl，--name，--fs都要做 依你建議」）
- 日期：2026-10-30
- 相關文件：ADR-0098（無頭 CLI＋AI 接取邊界——本 ADR **修改**其「CLI 絕不寫檔」一條）、0121（訊息請求）、
  0109 S4（收件箱水位只在記憶體）、0112（靜態加密）、0245／0314（前向保密啟用與明示退場）、
  0397（裝置報告）、0107（rumor id 去重）

## 背景與問題

使用者想要的場景（2026-10-30 討論後定案）：**你和你自己的 agent 之間的私人頻道，雙向**——

- 你 → agent：在外面用手機叫家裡的 Claude Code／Antigravity 做事、問進度；
- agent → 你：做完了通知你；要做重要的事（部署、送出、付款）先問你，你核准才繼續。

agent 用**自己獨立的身分**（不是你的 nsec），你在 App 把它加成聯絡人。agent 那端呼叫的就是
`apps/cli`（ADR-0098）。實測（兩把一次性金鑰、錨點 1）CLI 的 `send`／`listen` 收發都通，但有五個
擋路的缺口：

1. **`listen` 照單全收任何人**：沒有寄件人過濾（`main.ts` 的 `onMessage`）。任何知道 agent npub 的人
   都能對一個能執行 shell 的 AI 下指令——致命三角（ADR-0098）裡最直接的那一角。
2. **同一則會重複處理**：CLI 每次都是新的 `MemoryStorage`，重開 `listen` 會把中繼上 7 天內的收件匣
   全部再印一次（實測同一則印兩次）。輪詢式的 agent 會對同一則回覆好幾次。
3. **每跑一次就多一台裝置**：裝置 id 每次隨機，實測同一把金鑰跑 3 次 `send`，中繼上就有 3 份
   kind 30079 裝置報告（ADR-0397；主平面每作者最多 5 份）。用獨立身分時只擠到 agent 自己，
   但還是不乾淨。
4. **沒有「送出並等回覆」**：只有送完就結束的 `send` 與永遠不結束的 `listen`。
   而純文字的「yes」沒有綁定是哪一個請求——舊的核准可能被拿去核准新的動作。
5. **沒辦法在 AI 看不到的情況下產生 agent 金鑰**：CLI 只有 `whoami`。

另外使用者要求一併做：限時訊息（`--ttl`）、顯示名稱（`--name`）、讓 agent 身分可以開前向保密（`--fs`）。

## 考量的選項

- **A. 寫 MCP server**（ADR-0098 訂過邊界）。這個場景用不到：Claude Code／Antigravity 本來就會跑 CLI，
  agent 用的是自己的身分，不需要 `propose_message` 那套代理你本人的機制。
- **B. CLI 加旗標，持久化沿用引擎既有的 `LocalStorage`**（本 ADR）。
- **C. CLI 自己寫一套狀態檔**（只記處理過的 id）。會跟引擎的去重、聯絡人、FS 狀態各存一份——
  平行實作，Fix First 不允許；而且 `--fs` 需要引擎的 FS 狀態真的存下來，C 做不到。

## 決策

採 **B**。全部是 CLI 的旗標，**不改事件契約**；引擎只動了一處開機順序（見〈實作中的發現〉1）。

### 1. `--from <npub>`：寄件人白名單（可重複）

- `listen`／`ask` 只輸出白名單內的人的訊息，其他人的一律丟掉（stderr 只記「丟掉幾則」，不印內容——
  內容本身就可能是注入）。
- 白名單內的人會被加成 agent 的**聯絡人**：引擎開機時才會把他們的歷史記進去重集合
  （`seenMsg` 只回放聯絡人與群組，見 `relay-backend.ts` 的 `start`），顯示名稱也才會送過去（ADR-0061）。
- `listen` 沒給 `--from` 維持舊行為（全部印），但 stderr 警告。
- `ask` 的收件人自動就是唯一被接受的回覆者。

### 2. `--state-dir <目錄>`：持久狀態

- 在 Node 裡裝一個**檔案為底的 `localStorage`**，然後用引擎原本的
  `new LocalStorage(namespace, 0, secretKey)`——儲存格式、靜態加密（ADR-0112，金鑰由 nsec 導出）、
  去重、聯絡人、FS 狀態全部沿用，不另寫。`setKvBackend` 也指向同一份檔案，所以**裝置 id 固定**。
- **綁定身分**：目錄第一次使用時記下 pubkey；之後拿別的金鑰開同一個目錄直接報錯
  （否則 DEK 不同、讀出來全是空的，下一次寫入就把別人的狀態蓋掉）。
- **獨占鎖**：同一個目錄同時只能有一個 cinder 程序（兩個程序各自整份覆寫會互相吃掉更新）。
  鎖先寫成暫存檔再 hard link 成 `lock`，別的程序不會讀到半寫的空檔；空的或看不懂的鎖放超過 10 秒才當成殘留。
  接手殘留鎖時先原子地移到旁邊、確認移走的是剛剛讀到的那一份，不是就放回去並讓出。
- **最多交出一次**：訊息存進狀態目錄就算處理過。程序剛好在存檔和印出之間被砍掉，重開之後不會再印一次。
  要同時跑常駐 `listen` 和 `ask`，就給它們各自的目錄（等於兩台裝置；用獨立身分時無害）。
- **不持久化收件箱水位**：ADR-0109 S4 刻意讓水位只在記憶體，這裡不改。理由：Gift Wrap 外層時戳
  隨機往前推最多 2 天，`since` 最多只能把 7 天的窗縮成約 2 天；agent 的收件匣只有你傳的訊息，
  量很小。重複**處理**已經由去重解決，剩下的只是讀取列數，不值得動儲存層。

### 3. `ask <npub> <問題…>`：送出並等回覆

- 送出後，只接受**那個 npub**、**送出之後**（容許 30 秒時鐘誤差）或**引用了這則問題**（`replyTo`）的
  第一則回覆。
- `--timeout <秒>`，預設 300，最多 7 天（再長 Node 的計時器會溢位成 1ms）。
- `--approve`：在問題後面附一組隨機 4 位數短碼，要回 `yes 1234`／`no 1234`（也接受「核准／同意」「拒絕」）
  才算數；短碼對不上的回覆不算，繼續等。短碼的作用是**綁定**這一個請求，不是保密
  （能回覆的本來就只有白名單內的人）。
- 結束碼：`0`＝收到回覆／核准，`2`＝拒絕，`3`＝逾時，`1`＝沒送到／被拒收。stdout 一行 JSON，`ok` 只在結束碼 `0` 時為 true（`denied` 是 `ok:false`）。
- 全部指令共用：`64`＝用法、金鑰或狀態目錄錯（含目錄正被別的程序使用），`70`＝非預期錯誤。`1` 只留給「沒送到」，agent 才知道哪些可以重試。
- **沒加 `--approve` 是弱關聯**：為了容忍對方時鐘慢，送出前 30 秒內的訊息也算回覆，而且任何回覆都是結束碼 `0`（連「不要」也是）。回答會決定要不要做事時，一定要加 `--approve`。
- **「沒問到你」不是逾時**：等到逾時，問題都還沒被中繼收下（連不上）時回
  `{"decision":"failed","reason":"not-sent"}`、結束碼 `1`；中繼拒收或重試耗盡是 `reason:"rejected"`。
  逾時（`3`）只代表「問題送到了，你沒在時限內回」——agent 據此決定要不要重試。
- 連線狀態與「收到回覆但不是 yes／no＋短碼」寫到 stderr（**不印**回覆內容）。

### 4. `keygen --out <路徑>`：產生 agent 金鑰（**修改 ADR-0098**）

ADR-0098 原本是「CLI 絕不寫檔」。改成：**只有這一個明確的指令會寫私鑰**，而且

- 只寫到使用者指定的路徑，**檔案已存在就拒絕**（不覆蓋任何東西）；
- POSIX 上權限 `0600`；Windows 上沿用目錄的 ACL（要放在只有自己讀得到的地方，help 寫明）；
- 畫面上只印 npub，**絕不印私鑰**——這樣叫 agent 執行 `keygen` 時，私鑰不會進到它的上下文。

其他指令仍然不寫私鑰。

### 5. `--ttl <秒>`：限時訊息（`send`／`ask`）

接上引擎既有的閱後即焚（`sendMessage` 的 `ttlSeconds`）：外層 `expiration` 設成到期時間，
中繼到期就刪，你的 App 也照閱後即焚處理。範圍 1 秒到 7 天（超過 7 天沒有意義：中繼本來就只留 7 天）。
**這是隱私功能，不是省額度**：寫入一樣要寫、到期刪除本身也算寫入。

### 6. `--name <名稱>`：顯示名稱

取代原本寫死的 `"cli"`。只送給聯絡人（ADR-0061 加密個人檔），所以要搭 `--from` 或 `ask`。

### 7. `--fs on|off`：agent 身分的前向保密

- **必須搭 `--state-dir`**，否則直接報錯：EK 存不下來，下一次啟動就解不開你加密到它 EK 的訊息，
  你那邊還會一直跳加密降級警告。
- `on`＝`enableFs()`（冪等）；`off`＝`disableFs()`（ADR-0314 明示退場，不是把宣告拿掉）。
  不給旗標＝維持目錄裡原本的狀態。預設不開。

## 理由

- 七項都是 CLI 層的接線，引擎已經有對應能力（儲存、去重、閱後即焚、FS 啟用與退場）；
  唯一新寫的是 Node 的檔案 `localStorage` 與 `ask` 的比對邏輯。
- 白名單與短碼是這個場景的最低安全線：agent 能執行 shell，收件端是攻擊面。

## 後果

- 正面：Claude Code／Antigravity 可以用 `ask --approve` 在做重要的事之前先問你，用 `listen --from`
  接你的指令；重開不會重複處理；裝置報告不再每跑一次多一份。
- 負面／已知殘餘風險：
  - **狀態目錄的加密跟私鑰檔在同一台機器上**：DEK 由 nsec 導出，而 nsec 檔就在旁邊，
    機器被入侵時兩者一起外流（ADR-0112 自己就寫了：nsec 明文落盤時靜態加密不成立）。
  - **agent 這端的明文會到 LLM 廠商**，Claude Code 也會在本機留對話紀錄。前向保密只保護中繼上的密文，
    文件與 help 不得把 `--fs` 講成整條頻道受保護。
  - `ask` 的「送出之後」靠時鐘：你的手機時鐘若慢超過 30 秒，回覆會被當成舊訊息忽略（引用回覆不受影響）。
  - 手機在背景時收不收得到 agent 的訊息，仍取決於 Android 前台服務在實機上的表現（ADR-0274 待驗收）。
- 後續行動／待辦：
  - 使用指南：在 Claude Code 設定裡禁止讀私鑰檔、你的回覆以外一律當不可信輸入、不要自動核准 shell 指令。
  - 你的 App 必須先把 agent 加成聯絡人，否則它的訊息落在訊息請求、不會跳通知（ADR-0121）。
  - 手機實機測試：agent 送一則，看鎖定畫面多久收到。

## 實作中的發現

1. **引擎開機順序：已存訊息要在訂閱之前進去重集合。** `start()` 原本先 `resubscribe()`、之後才在歷史回放裡
   把已存訊息的 id 加進 `seenMsg`。真實 WebSocket 是非同步的，所以平常不會出事；但只要連線層同步送達
   （記憶體網路），補推來的舊訊息就會在去重集合建好之前到，再走一次 `onMessage`。旁邊的
   `hydrateFileIndex()` 早就為了同一個理由放在訂閱之前（ADR-0294 §1.2），這裡比照新增
   `hydrateSeenMessages()`。歷史回放照舊交付 `onHistory`。
2. **錨點偶爾連不上**：實跑時約十幾次有一次，`ask` 從頭到尾只看到 `中繼狀態：offline`，40 秒內沒有連上；
   你回的訊息其實有存在中繼上（事後 `listen` 補拉得到）。當時是短時間內連開很多條連線的測試，原因沒有查明。
   這就是上面把 `not-sent` 從逾時分出來的原因。原因後來查到了，見下面〈偶發連不上的原因〉。

## 實跑驗證（2026-10-30，錨點 1，一次性金鑰）

- `keygen --out`：stdout 只有 npub、不含 `nsec1`；同一個路徑再跑一次 → 結束碼 1「檔案已存在，不覆蓋」（審查後改為 64）。
- `listen --from 你 --state-dir`：陌生人一則被丟掉（stderr 記一則、不印內容），你的一則印出；
  同一個目錄重開 → 不再印同一則。
- `ask --approve --ttl 3600 --state-dir`：你那端看到附短碼的問題；先回錯的短碼、再回對的 → `approved`、結束碼 0。
- 同一個狀態目錄跑了 4 個程序，中繼上 agent 的裝置報告（30079）**只有 1 份**（修正前是一次一份）。
- Windows 上從程式強制結束程序（不經 Ctrl+C）時鎖檔留著；下一個程序看到 pid 已不在就接手，實跑確認可用。

## 跟 App 實機對接（2026-10-30，錨點 2，一次性金鑰）

上面的實跑兩端都是 CLI。這次「你」那端換成桌面 App（瀏覽器版、獨立的 Chrome 設定資料夾，經除錯連接埠操作）。

- 🔴 **發現並修正：CLI 寄給 App 顯示 `sent`，App 卻收不到。** 原因是 App 預設開分片（ADR-0241），收件匣在錨點的訊息片上，CLI 卻只連基底網址、也只知道自己那座錨點。CLI 對 CLI 測不出來，因為兩邊同樣沒開分片。
  - 修法：建後端抽成 `apps/cli/src/backend.ts`，設定照 App 的個人身分：`shardingBase: relay`、`anchors: ANCHOR_RELAYS`，另帶 `appVersion` 供 ADR-0397 的裝置報告用。
  - 新增 `backend.test.ts`：每個網址一顆 RelayCore，同一座、不同錨點兩種情況都要雙向送達。修正前紅燈。
- **發現並修正：Node 25 以上不帶 `--state-dir` 時，stderr 多一行 `ExperimentalWarning: localStorage is not available`。** Node 內建了全域 localStorage，引擎一碰就警告。修法：沒有狀態目錄時裝一份記憶體的 `MemoryKv`，不落地。
- 修正後的實機結果：
  - CLI→App 送達。App 端顯示的名稱是 `--name`；要帶 `--from`，CLI 才會把名稱送給對方。
  - `ask --approve`：App 回「核准 8438」→ `approved`、結束碼 0；回「不要 6307」→ `denied`、結束碼 2。
  - App 傳指令 → `listen --from` 印出一行 JSON。同一個狀態目錄裡先前已處理過的回覆不重複印。
  - 跨錨點：CLI 用預設的錨點 1、App 在錨點 2，送達。
  - `--ttl 30`：App 對話視窗顯示 ⏱，到期後換成「訊息已到期」。
  - `--fs on`（App 沒開前向保密）：照常送達。
- 同一輪一併修正（使用者 2026-10-30 指示）：
  - **App：限時訊息到期後，聯絡人清單的預覽還是原文**，用原文搜尋也還找得到這個人。
    - `messagePreview` 對已到期的末則改回「訊息已到期」，經典與三欄佈局都適用。
    - 共用的 `nameOrMessagesMatch` 會跳過已到期的訊息，桌面與手機的搜尋都適用。
    - 實機確認：到期後清單會自己重繪，原文搜不到。
  - **CLI：沒帶 `--name` 時，App 裡的名稱被改回「cli」。** 有 `--state-dir` 時記住上次的名稱，沒帶就沿用（`resolveName`）。實機確認名稱維持不變。
- 手機版完全沒處理 `expiresAt`（到期的限時訊息在手機上仍顯示原文）→ 已由 ADR-0406（PR #63）修正。
- 接著發現：手機版從沒開分片，桌面與開了分片的 CLI 寄給手機的訊息全部遺失 → 已由 ADR-0407（PR #64）修正。

## 程式碼審查後的修正（2026-10-30）

- **`ask` 綁錯問題 id**：原本拿這個聯絡人的第一個狀態事件當成這次的問題。有 `--state-dir` 時，舊訊息的回條或重送狀態可能先到，結果成功送出卻報 `not-sent`，或舊訊息的 `failed` 讓這次直接失敗。改成只認 `sendMessage` 當下同步發出的那則自己的訊息。`send` 有同樣的問題（任何一則 `sent` 都當成功），一併改用 `sendAndConfirm`。
- **`denied` 印 `ok:true`**：改成 `ok:false`；用法與狀態錯誤改用 `64`／`70`，不再跟「沒送到」共用 `1`。
- **`--timeout` 沒上限**：超過約 24.8 天會溢位成 1ms。改成最多 7 天。
- **狀態目錄的鎖有競態**：見上面〈獨占鎖〉。
- **CLI 一律開分片**，不看 App 的 `nb.sharding` 關閉開關（ADR-0407）：CLI 沒有設定畫面，而錨點都已經開分片。要退回非分片得改程式。

## 偶發連不上的原因（2026-10-30）

- **原因**：主平面的重連限速（SDK ADR 0111）。
  - Worker 端：同一個 IP 對同一個分片每分鐘 4 次新連線（`STRICT_UPGRADE_LIMIT`）。
  - DO 端：每 10 分鐘 20 次，超過封鎖 10 分鐘（`RECONNECT_GUARD`）。
  - 實跑時同一台機器連開很多個 `ask`／`listen`，加上同一個網路的桌面版，很容易超過。
  - 中繼以 1013 拒絕。引擎把這座標成暫時不能用，約 5 分鐘後才重連（SDK ADR 0108），所以 40 秒內都是 offline。
- **證據**：錨點 1 的 Worker 呼叫紀錄（10-29～10-30）沒有任何錯誤，排除中繼本身出錯。錨點沒開 Worker 日誌，所以沒有直接拒絕紀錄；結論來自程式路徑與現象吻合（中繼正常、訊息有存下、只有短時間大量連線時出現）。
- **限速不改**：它擋的是不退避的用戶端與爬蟲，正常使用的 App 碰不到。
- **CLI 的修正**：
  - 引擎早就把原因與重試時間交給 `onConnection`，CLI 卻只印 `state`。現在狀態行照實說：暫時拒絕連線（並提示同一台機器連太多次）、額度用完、或主機有回應卻不是中繼，附上本機時間。
  - `ask`：收件中繼要到逾時之後才重連＝這次不可能等到回覆，直接回 `{decision:"failed", reason:"relay-unavailable", retryAt, sent}`，結束碼仍是 `1`。`sent` 表示問題在那之前已經被中繼收下。只看自己的收件中繼，因為回覆只會從那裡進來；逾時前就會重連的就繼續等。
  - `send`：說得出原因時才在 stderr 印一行，平常照舊安靜。不提早結束，因為寄件走對方的分片，自己的收件中繼不能用不代表寄不出去。
- **官網 CLI 頁**：結束碼 `1` 加上 `relay-unavailable`；「中繼站與額度」補上「同一台機器一分鐘內不要啟動超過三、四次，要等訊息就讓一個 `listen` 開著」。
