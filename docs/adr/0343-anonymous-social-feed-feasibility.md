# ADR-0343：內建匿名社群功能可行性研究——「匿名」做不到，但漏斗值得做

- 狀態：**提議中**（研究型；§7 的形狀選擇待裁示）
- 日期：2026-08-07
- 關聯：**ADR-0237（連線歸屬打穿事件層隱藏——本研究的決定性依據）**、ADR-0057／0123（NIP-42 AUTH 與具名訂閱）、ADR-0027（群組扇出）、ADR-0121（訊息請求）、`CLAUDE.md` 全域硬規則、`docs/SECURITY.md` 威脅模型、PRD §6

## 1. 被提出的功能

> 使用者能**匿名發文**，發文時自己設定標籤；也可以選擇上去觀看他人發布的匿名文章，
> 要先自己選想看的標籤然後**真正隨機**推薦。雖然發文都是匿名，但可以針對發文者發出
> **好友邀請**，加入的好友就等同原本 Cinderous 中的聯絡人。

本 ADR 評估它與現行架構的相容性。**結論：核心的「匿名」承諾在目前傳輸上做不到，
但功能中最有價值的部分（公開→私密的漏斗）不但可行，而且補的是這個產品的真實缺口。**

## 2. 🔴 阻擋一：匿名承諾做不到，而且本專案已經下過定論

`relay/src/worker.ts` 寫死 `requireAuth: true` ⇒ **每條連線都以真實 npub 做 NIP-42 認證**，
而發布走同一條連線。

ADR-0237 已完整分析過這個根因，其最重要的結論是：

> **crypto／連線層的混淆，在沒有傳輸層匿名（Tor/onion）之前，對託管中繼幾乎不付出實質效益。**

它連「用臨時身分另開一條連線發布」都已駁回——**所有連線來自同一個 IP**，而對託管中繼
（Cloudflare）而言跨連線的應用層關聯是**零成本**、IP 關聯是低成本。

⇒ 在自家 relay 上發「匿名文」，營運者用它**本來就握有的 `authState`** 即可還原作者。

🔴 **這不是「匿名度不夠高」，是承諾本身為假。** 而 `docs/SECURITY.md` 已將此列為紅色殘餘風險
——**把一個已知洩漏包裝成產品賣點，是這個專案至今沒做過的事**（FS、裝置金鑰分級、
APK debug 簽章都選了誠實揭露）。

## 3. 🔴 阻擋二：relay 架構上禁止「瀏覽全站」

`relay-core.ts` 的 `scoped()`（ADR-0057）規定：認證後只能訂閱**自己的收件匣**（`#p` == 自己）
或**有界的 `authors` 清單**（≤1024）。沒有 `authors` 的訂閱直接被拒：

```ts
if (!authors) return false; // ← 消防水管
```

而「給我所有標籤 X 的文章」正是這種訂閱。

⇒ 要在自家 relay 做這個功能，**必須拆掉反爬蟲的核心防護**。那不是加功能，是拆地基。

## 4. 🔴 阻擋三：與全域硬規則正面衝突

`CLAUDE.md`：

> 加密與零伺服器狀態：**明文不上雲**；中繼站只轉發密文與 Ephemeral 狀態，不持久化。

公開貼文按定義是**明文、公開、需持久化**。目前 relay 只存離線密文留言（NIP-40 有界保留）。

## 5. 🔴 阻擋四：營運者的責任性質會改變

現行營運者的第一道防線是「**我看不到任何東西**」——只有密文經過。這在面對傳喚、DMCA、
違法內容時是實質防禦。

**公開內容摧毀這條防線。** relay 一旦儲存並提供明文，營運者即成為內容主機：
需要審查機制、下架流程、法遵能力。對一個沒有營運團隊的專案，這是壓垮性的。

⚠ 這一條與技術無關，但**它才是實務上最難繞過的**。

## 6. ✅ 但功能中最有價值的部分可行——而且它不是社群媒體

重新框定：**這不是社群媒體，是交友漏斗。**

Cinderous 是私密通訊，但有個真實缺口：**你只能跟已經認識的人聊天**，沒有「認識新的人」的入口。

提案中最有價值的其實是這一條：

> 匿名發文 → 別人看到 → 發好友邀請 → **接受後成為聯絡人**

⇒ **公開到私密的漏斗。** 它完全落在既有機制內：邀請就是對那把 persona 金鑰發 NIP-59 Gift Wrap，
接受時揭露真 npub，之後即為正常聯絡人（可沿用 ADR-0121 訊息請求的「尚未接受」狀態）。
**不需要新協定。**

另外兩點也與專案價值觀一致，值得保留：

- **真隨機而非演算法**——沒有互動最佳化，就沒有激怒式內容。
- **自選標籤是唯一過濾器**——控制權在使用者，不是系統推給你。

⚠ 但「真正隨機」要誠實：客戶端只能在**取得的樣本內**隨機，不是全網均勻隨機。
文案不得暗示後者。

## 7. 三種形狀（待裁示）

### 形狀 A：完全不碰自家 relay（建議）

公開內容本來就是 Nostr 的 kind 1 ＋ `t` 標籤，**外面已有一整個公開網路**。

- 客戶端連**公共 relay** 讀寫公開內容；**自家 relay 完全不碰**
- 以一把與主身分**無關的 persona 金鑰**發文
- 隨機：向多座公共 relay 取 `#t` 樣本，**客戶端自己洗牌**
- 好友邀請走 Gift Wrap 到 persona 金鑰

**買到**：§3／§4／§5 三個阻擋全部消失（硬規則不破、地基不動、營運責任不變），且可快速實作。

⚠ **買不到匿名**：同一個 IP 同時連自家 relay（真名）與公共 relay（persona）。
需兩邊串通才會被關聯，風險遠低於形狀 B——但**「不串通」是假設，不是保證**。

### 形狀 B：自架第二座公開 relay

承擔全部內容責任、需拆 `scoped()`、需新的儲存與保留模型。**不建議**（§5 是主因）。

### 形狀 C：誠實降級為「化名」

不宣稱匿名，明講「這是一個化名身分，可隨時丟棄」。功能不變，承諾誠實。
**與 A 相容且應同時採用。**

## 8. 建議

**做，但改名。** 它不是「社群媒體功能」，是「**以興趣標籤認識新聯絡人**」——
這個框架讓範圍縮小一個量級，且補的是產品真正的缺口。

採 **A ＋ C**：外掛公共 Nostr 網路、用化名而非匿名、文案誠實說出「同一個 IP 存在被關聯的可能」。

🔴 **不得宣稱匿名。**

## 9. 買不到什麼

1. **不解決 ADR-0237 的根因。** 真正的匿名需要傳輸層匿名（Tor/onion），那是獨立的大工程，
   本 ADR 不涵蓋，也不應假裝化名等同它。
2. **形狀 A 把內容託付給公共 relay**：可用性、審查、保留期都不在我們控制內。
   貼文可能消失，這要在 UI 上說清楚。
3. **沒有處理垃圾訊息與騷擾。** 開放的好友邀請入口是騷擾向量；至少需沿用 ADR-0121
   訊息請求的隔離（不通知、不進主清單）與封鎖名單，但**那只擋單一來源，擋不住量**。
4. **沒有內容審查。** 形狀 A 下我們不主機內容，但**客戶端仍會顯示它**——
   使用者可能在我們的 UI 裡看到違法或極端內容。這需要產品層的決定（過濾清單？回報？），
   本 ADR 未解。
5. **「真隨機」只在樣本內成立**（§6）。
6. **未評估行動端的成本**：公開動態流是持續拉取，與 ADR-0116「不做推播、接受背景休眠」
   的省電取向相衝，需另行評估。
