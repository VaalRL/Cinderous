# 0272. 背景推播：FCM／APNs「無內容喚醒」＋明示同意、可關閉

- 狀態：已接受（**設計決策**；行動端原生化後才能實作，見「後續行動」）
- 日期：2026-07-29
- 相關文件：ADR-0116（行動端通知平台縫——當年明確劃線「不做推播」並設下本 ADR 的條件）、
  ADR-0088（在線元資料最小化：jitter／P2P 卸載）、ADR-0065（離線留言 TTL）、
  ADR-0002（元資料保護基線）、ADR-0044/0048（企業自架與政策）、`docs/research/`（Android 打包研究）

## 背景與問題

行動端目前只有**本機通知**——App 關掉就收不到訊息（ADR-0116）。要做到「關掉也收得到」，
Android 有兩條路（前台服務／推播），**iOS 只有推播**（無前台服務等價物、系統不允許替代推播通道）。

ADR-0116 當年劃線「不做推播」，並為未來的 ADR 設下兩個條件：
（a）推播內容一律不含明文；（b）**「中繼站要能在不知道收件人是誰的前提下觸發推播
（技術上很難，可能根本做不到）」**。

**必須誠實修正條件 (b) 的前提**：中繼站**本來就知道收件人是誰**——Gift Wrap 的離線投遞
正是靠外層 `#p` tag 定址（這是離線留言能運作的前提，ADR-0002 已記為殘餘）。因此
「不知道收件人」從來就不是現況，推播**並未新增中繼端的知識**。真正新增的是下列三項。

## 推播真正新增的洩漏（逐項）

| 新增項 | 內容 | 嚴重度 |
| --- | --- | --- |
| **第三方時序** | Google／Apple 得知「這台裝置在時間 T 被喚醒」 | 🔴 主要代價 |
| **中繼持久狀態** | 中繼須保存 `pubkey → push token`——與「只轉發密文＋Ephemeral 狀態」的立場相違 | 🟠 |
| **裝置連結性** | push token 是長期識別碼，把 pubkey 綁到一台裝置／一個 Google 帳號 | 🟠 |

不新增的：訊息內容、寄件者身分（Gift Wrap 一次性作者不受影響）、中繼端知識。

## 考量的選項

- **A：永不做推播**——iOS 永遠無法背景收訊；Android 只能靠前台服務。最保守但對 iOS 是死路。
- **B：UnifiedPush（使用者自選／自架 distributor）**——隱私最佳，但**僅 Android**，
  且需使用者理解並安裝 distributor。
- **C：FCM／APNs 無內容喚醒＋明示同意（採納）**——覆蓋雙平台，代價以設計手段壓到最小。
- 預設值：opt-in（預設關）vs opt-out（預設開）。

## 決策

採 **C**，並以四道設計把代價壓到最小：

1. **無內容喚醒**：推播 payload **不含任何訊息內容、寄件者或計數**——只是一個喚醒訊號。
   App 被喚醒後自行連中繼取密文、本機解密後才產生**本機通知**（通知文字永遠來自本機）。
2. **時序模糊化（借 ADR-0088 的 jitter 思路）**：中繼對同一 token 的喚醒**合併＋抖動**——
   每 60 秒最多一次、並加 0–30 秒隨機延遲。於是第三方看到的是「這台裝置在這個時間窗有活動」
   而非「訊息在 14:32:07 抵達」；連續對話的 50 則訊息只產生 1 次喚醒（同時省電、省配額）。
3. **Token 是 Ephemeral，不是永久狀態**：註冊帶 TTL（預設 30 天，比照 ADR-0065 的壽命上限
   哲學），App 啟動時續期；逾期自動清除。中繼**不因推播而變成有永久狀態的伺服器**。
   客戶端另定期輪替 token，限制長期連結性。
4. **平台差異化的預設值**（**預設關，明示同意才開**）：
   - **Android 預設＝前台服務**（常駐通知、自己保住 WebSocket、**零第三方**）。推播是
     「省電替代方案」，使用者可主動改用。
   - **iOS ＝推播或無背景通知**二選一，於首次啟用時以**明確同意畫面**呈現，不得靜默開啟。
   - 同意畫面必須逐條寫明上表的三項新增洩漏（不是一句「可能影響隱私」）。
   - 設定中隨時可關；**依身分獨立**（工作身分開、個人身分關是合理需求）。
5. **企業自架**：企業政策（ADR-0048）可全域停用推播；自架中繼者若不設推播憑證即自動無此功能。

## 理由

「不能有背景通知」與「不能洩漏元資料」被混為一談了——真正該永遠拒絕的是**把內容或收件人
交給推播供應商**，那從來不在選項裡。無內容喚醒＋合併抖動後，第三方拿到的是粗粒度的裝置活動
時間窗，這與 ADR-0088 對 presence 心跳所做的取捨同構（該 ADR 也接受了「中繼看得到粗略在線
時序」）。iOS 若不接受這個代價，就等於**永遠沒有可用的 iOS 客戶端**——那不是隱私的勝利，
是把使用者推回 WhatsApp。預設關＋明示同意讓這個取捨由使用者自己做，符合專案的隱私預設鐵則。

## 後果

- **正面**：iOS 背景收訊成為可能；Android 多一個省電選項；通知文字永遠本機生成（內容零外流）；
  合併抖動同時改善電池與配額。
- **負面 / 已知殘餘風險**：
  - **開啟者的 pubkey ↔ 裝置在中繼端有 TTL 內的連結**，且 Google／Apple 取得粗粒度活動時序；
    這是**真實且不可完全消除**的代價，只能靠 opt-in＋自架中繼＋輪替緩解。
  - 中繼新增一類需保存的狀態（即使有 TTL），實作時須確保它與訊息密文分離、可獨立清除
    （並納入 NIP-62 vanish 的清除範圍，ADR-0260）。
  - Android 前台服務有常駐通知與各 OEM 省電策略的現實問題（見 Android 打包研究）。
  - iOS 上「拒絕推播」＝沒有背景通知，體驗明顯較差——同意畫面必須誠實說明，不得誘導。

## 後續行動 / 待辦

1. **前置**：行動端目前是 react-native-web，**沒有原生 app**——本決策要能實作，需先完成
   原生化（真 RN／Expo 或 Capacitor 殼，見 `docs/research/` 的 Android 打包研究）。
2. 中繼端：token 註冊事件（帶 TTL）、喚醒觸發器（合併＋抖動）、納入 NIP-62 清除範圍。
3. 客戶端：同意畫面（逐條列洩漏）、依身分設定、token 輪替、Android 前台服務實作。
4. UnifiedPush 作為 Android 的第三選項，日後可另評估（不影響本決策）。
