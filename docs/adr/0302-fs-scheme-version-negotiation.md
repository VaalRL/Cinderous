# 0302. FS 機制的版本協商語意：未知版本不等於降級，釘選要記強度而非布林

- 狀態：**提議中**（範圍刻意限縮；本文不改變任何產品行為，實作待決策）
- 日期：2026-07-30
- 相關文件：**0245**（EK 輪替：`FS_CAPABILITY`、TOFU 釘選、降級偵測——**本文動的是它的版本語意**）、
  0236（為何選輪替子鑰而非棘輪；多設備共用 nsec 是根因）、
  **0290 §2**（現行阻擋＝外部審計，建議**縮小**範圍——本文據此限縮）、
  0291（方便性重新審查：opt-in 讓成本歸零，也讓覆蓋率歸零）、
  **0301**（否決 UPKE/PPRF；並釐清群組 FS 來自 1:1 成對扇出）、
  0300 §5（Keychat 的版本歧異：兩代規格並存而無法辨識，正是沒有版本協商的下場）
- 資料來源：本倉庫程式碼查證（`packages/core/src/subkey.ts`、`packages/engine/src/backend/relay-backend.ts`、
  `packages/engine/src/storage/types.ts`）

> **起點**：討論「能不能讓棘輪與手動輪替並存、做成可設的功能」時查出——
> **那個辨識機制我們已經有了**（`FS_CAPABILITY = "ek-v1"`、EK 公告 `{ v: 1, … }`）。
> 但它現在扛的是**降級保護**，而它對「未知版本」的處理是**巧合正確、不是設計**。
> 本文只修那一小塊，**不引入第二種 FS 機制**（那是另一個題目，見〈非目標〉）。

## 背景與問題

### 1. 現況（查證）

| 位置 | 現況 |
| --- | --- |
| `subkey.ts:25` | `FS_CAPABILITY = "ek-v1"`，寫進**簽章**個人檔的 `fs` 欄位 |
| `subkey.ts:67` | EK 公告內容 `JSON.stringify({ v: 1, ek, next? })` |
| `subkey.ts:83` | `readEkAnnounce`：**`c.v !== 1` 直接回 `null`** |
| `relay-backend.ts:1725` | 收到個人檔且 `profile.fs === FS_CAPABILITY` → `pinFs(sender)` |
| `types.ts:490` | `pinned?: Record<string, boolean>` —— **布林** |
| `relay-backend.ts:1174` | `fsWouldDowngrade(to)` ＝ 已釘選 **且** 無其 EK |
| `relay-backend.ts:2568` | 送訊前若成立 → `onFsDowngrade(to)` → UI 警告（不得靜默退回靜態） |

這套在**單一機制**下是完整的。問題出在它對「不是這個機制」的東西怎麼反應。

### 2. ⚠ 未知版本目前被當成「降級」，而那是巧合

假設日後出現 `v: 2`（無論是棘輪、UPKE、或只是 EK 格式改版）：

1. 舊客戶端 `readEkAnnounce` 對 `v: 2` 回 `null` → **不學該聯絡人的 EK**
2. 於是 `contactEks[peer]` 缺席
3. 若該聯絡人先前已被釘選 → `fsWouldDowngrade` **成立** → 跳降級警告

**結果碰巧是安全的**（不會靜默退回靜態），但**語意是錯的**：

- 對方**沒有降級**，對方是**升級了**
- 使用者看到的訊息會是「疑似降級」，而正確的訊息是「**對方用了你這版不支援的機制，請更新**」
- 而我們的紅線是 **UI 不得說謊**（ADR-0278 隱身狀態點、ADR-0287 搜尋範圍都是這個立場）

⇒ 這不是安全漏洞，是**誠實性缺陷**：正確的行為建立在「兩個獨立條件恰好同時成立」上，
而不是建立在明確的判斷上。任何一邊改動（例如日後讓未知版本不清空 `contactEks`）就會失效。

### 3. ⚠ `pinned` 是布林，撐不住兩個以上的強度

`pinned: Record<string, boolean>` 只能表達「這個人期望 FS / 不期望」。

若日後有第二種機制，「從強機制退回弱機制」**也是降級**，但布林表達不了。
⇒ 真要加模式時，**降級保護沒有地方掛**——這正是應該先修好的地基。

### 4. 對照：沒有版本協商的下場

ADR-0300 §5 查證 Keychat 時撞到的：`keychat-io/docs`（NIP-04 世代）與 `keychat-protocol`
的 spec v2（NIP-17 世代）**並存，而外部無法判斷上架版本跑哪一版**。
那份 ADR 只好把「版本歧異」列為自己最大的限制。

⇒ 版本協商不是為了未來的功能，是為了**未來的可判斷性**。

## 非目標（刻意排除）

- **不引入第二種 FS 機制**（棘輪／UPKE 皆不在本文範圍；見 ADR-0301 與 ADR-0236 的取捨）。
- **不做使用者可設的 FS 模式**。討論已釐清那不可行：
  ~~per-device 身分是棘輪的入場費、無法 per-conversation 開關；~~
  🔴 **更正（2026-07-31，見 ADR-0303 §1／§2）**：入場費是**每裝置各自的預金鑰／session**，
  不是 per-device 身分。⚠ **但本項〈非目標〉不變**——理由改為下面這條，
  而它與更正無關：**預金鑰／session 是裝置層的全域狀態，仍然無法 per-conversation 開關。**
  （原論證用錯了前提，結論碰巧仍成立；已換上正確前提。）
  其餘理由照舊：降級面隨模式數成長；審計面加倍（與 ADR-0290 §2 相反）；
  群組混模無法誠實呈現（群組強度＝最弱成員）；而且**使用者答不出這個問題**。
- **不改變 ADR-0245 的範圍、預設值或上線條件**。

## 決策

### 1. 把「未知版本」與「沒有 FS」分開

`readEkAnnounce` 目前對所有不合法輸入一律回 `null`。改為區分兩種失敗：

- **格式錯誤／簽章錯誤／公鑰不合法** → 照舊丟棄（那是垃圾或攻擊）。
- **`v` 是我們不認得的數值，但其餘結構合法** → 回一個**明確的「版本較新」結果**，
  而不是與垃圾同一個 `null`。

呼叫端據此**記住「這個聯絡人宣告了我不支援的版本」**，而不是讓它退化成「沒有 EK」。

### 2. 個人檔的 `fs` 欄位同理

`profile.fs === FS_CAPABILITY` 是**精確字串比對**。`fs: "ratchet-v1"` 之類的值目前
既不觸發釘選、也不留下任何痕跡——等於**當作對方沒有 FS**。

改為：`fs` 為非空字串即視為「對方宣告了某種 FS」，**記下它宣告的是什麼**。

### 3. `pinned` 從布林改為記錄「宣告的機制」

```
pinned?: Record<string, boolean>              // 現況
pinned?: Record<string, { scheme: string; at: number }>   // 提議
```

- 向後相容：讀到 `true` 視為 `{ scheme: "ek-v1", at: 0 }`。
- 降級判斷從「有沒有 EK」擴為「**對方現在宣告的強度，是否低於曾經釘選的**」。
- 有了這個欄位，日後真要加模式時，降級保護才有地方掛（§3 的地基）。

### 4. UI 要分成三種訊息，不得混用

| 情況 | 訊息 |
| --- | --- |
| 已釘選 ＋ 無其 EK ＋ 同一機制 | **疑似降級**（現況，不變） |
| 已釘選 ＋ 對方宣告**更新的**機制 | **「對方使用你這版不支援的加密機制，請更新」**（新增） |
| 未釘選 | 無訊息（不打擾） |

**紅線**：不得把第二種顯示成第一種。那是把「你該更新」講成「對方可能被攻擊」。

## 後果

**正面**

- 修掉一個「碰巧正確」的行為，使它變成明確的判斷。
- 為日後任何 FS 機制變更（換版、加模式、乃至採用 MLS）預留**可判斷的**升級路徑，
  而不是像 ADR-0300 §5 的 Keychat 那樣兩代並存卻無從辨識。
- 範圍小（`subkey.ts` 的解析、`fsState` 的一個欄位、一條 UI 訊息），
  **與 ADR-0290 §2「縮小審計範圍」不衝突**——它不新增任何密碼學原語。

**負面／代價**

- `StoredFsState.pinned` 的形狀改變 → 需要向後相容讀取（讀到 `true` 當 `ek-v1`）。
  這個欄位**會進雲端快照**（`buildSnapshotContent` 以 `{ ...localFs }` 整份帶出）。

  **已查證，風險比預期低**：快照的形狀驗證（`cloud-snapshot.ts:179`）**只檢查 `fs.keys` 是陣列**，
  合併時 `pinned` 是原樣 union（`{ ...remote.pinned, ...local.pinned }`）、**不做任何值驗證**；
  而讀取端 `fsWouldDowngrade` 只取真值性（`this.fsState.pinned?.[to] ?? false`）。
  ⇒ 舊版客戶端收到 `{ scheme, at }` 物件時**不會拒收快照**，且物件為真值 ⇒ 仍視為「已釘選」，
  **行為與今天一致**。

  殘留的只有一項小事：首次合併時 `JSON.stringify(merged) !== JSON.stringify(local)` 必然成立
  （布林 vs 物件），會多寫一次快照。無害。
- 多一條 UI 訊息與一組文案。
- **不解決任何現存的使用者問題**——它買的是未來的可判斷性。若永遠不改 FS 機制，
  這份工作就是純成本。

**已知限制**

- 本文**未實作、未測試**。§4 的三態 UI 尚無文案。
- 「更新的機制」如何判斷「更強」需要一個順序表（`ek-v1 < ratchet-v1 < …`），
  而那個順序表本身是**未來的判斷**，現在只能留一個字串與一個比較函式的位置。
- 未評估：若對方宣告的機制我們不認得，**送訊該不該擋**。傾向不擋（照舊以現有機制送出）
  並提示更新，但那是可用性與安全的取捨，**本文不決定**。
