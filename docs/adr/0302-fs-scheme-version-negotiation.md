## 補記二：§4 其實是**四**種情況——而 §3 讓既有的那句話變成假的（2026-09-19）

§4 原本列三種情況。**做完 §3 之後變成四種**，而且是我們自己做出來的：

| 情況 | 訊息 |
| --- | --- |
| 已釘選 ＋ 無其 EK | 疑似降級（既有，`fs_downgradeWarning`） |
| 🔴 **已釘選 ＋ 對方退回較弱機制** | **新增**（`fs_rollbackWarning`）——§3 帶進來的 |
| 已釘選 ＋ 對方宣告更新的機制 | 請更新（既有，`fs_unsupportedWarning`） |
| 未釘選 | 無訊息 |

🔴 **§3 上線當下，第二格用的是第一格的文案，而那句話對它字面為假。** 原文是：

> 這位聯絡人啟用了前向保密，但**你這端還沒收到他的目前金鑰**——這則訊息暫時**以一般方式加密**
> （無前向保密）。可能是對方金鑰尚未同步（**稍後會自動更新**），若持續出現請留意。

對「對方退回較弱機制」而言：我們**有**他的金鑰、訊息**有**加密（只是較弱的機制）、
而且它**不會**自己好。三個子句全錯，而且錯的方向是**安撫**——把一個確定的訊號
講成暫時的雜訊。這正是 §4 紅線（「不得把第二種顯示成第一種」）的同一種錯誤，
只是換了一組。

⇒ 新增 `fs_rollbackWarning`（雙語）＋ `onFsRollback` 回呼，兩端各自接上；
i18n 的文案紅線測試加兩條：**三句話兩兩互異**、以及**退回較弱機制不得說成「稍後會自動更新」**。

⚠ 兩種降級同時成立時（既沒有 EK、又退回過）**說 rollback**——它比較確定，也比較嚴重。

## 補記三：§1 的公告那半（2026-09-19）

§1 的決策同時涵蓋「個人檔的 `fs` 欄位」與「`readEkAnnounce` 的未知版本」，
但 ADR-0306 D3.3c 只落地了前者，**公告那半漏了兩個月**。

漏著的後果與 §2 描述的完全相同，只是換條路徑：`readEkAnnounce` 對 `v !== 1` 回 `null`，
與「垃圾」沒有區別 ⇒ 一個**升級了的**對方在我們眼中等於「沒有 EK」⇒ 送訊時跳
「疑似降級（可能正在被攻擊）」。

🔴 **而後量子的公告正是 `v: 2`**——不修的話，第一個升級的人就會被誤報成被攻擊。

⇒ `readEkAnnounce` 改回 tagged union：`{ kind: "ok", … } | { kind: "newer", ik, v } | null`。
引擎收到 `"newer"` 時走 `markFsUnsupported`（＝「請更新」那條路），不再當成沒學到 EK。

⚠ **未來版本刻意不驗其餘欄位**——我們不知道未來的格式長什麼樣，拿今天的規則去驗它
只會把合法的新版判成垃圾，那正是本次要修的病。簽章仍然一律驗（「新版」不是繞過驗證的後門）。

## 補記：§3 為什麼在 2026-09-19 被排進來，以及強度序不是全序（2026-09-19）

**排進來的原因不是這份 ADR 本身，是後量子。** `docs/research/signal-triple-ratchet-applicability.md`
§5.6 查證出一件事：現行的布林釘選**分辨不出「後量子 → 古典」的降級**——
一個仍然有 EK、只是退回古典機制的對方，在舊判定（`pinned && !contactEks`）下完全看不出來，
而攻擊者只要供應一份較舊的簽章個人檔就做得到。

⇒ 沒有 §3，後量子出貨等於把一個**可被靜默降級**的機制當成保護。順序不能反。

### 🔴 強度序**不保證是全序**——這是本 ADR 原文沒有寫到的

〈後果〉原本寫「需要一個順序表（`ek-v1 < ratchet-v1 < …`）」，隱含線性排列。**那個假設是錯的。**
選項空間其實有兩個軸：

| | 古典 | 後量子 |
| --- | --- | --- |
| 共用金鑰 | `ek-v1` | `ek-pq-v1` |
| per-device session | `ratchet-v1` | `triple-ratchet-v1` |

`ek-pq-v1`（後量子、無 PCS）與 `ratchet-v1`（有 PCS、非後量子）**各有對方沒有的東西**，
用一個整數排不出來。用 `<` 比較會被迫在兩個不可比的機制之間硬選，而無論選哪邊都會產生
假警報或漏報。

⇒ 實作因此把回傳值定成 `"weaker" | "same" | "stronger" | "incomparable"`，
**不認得的一律回 `"incomparable"`**（安全側：把「我沒聽過這個機制」當成降級，
就是把「你該更新」講成「對方可能被攻擊」＝§4 的紅線）。

⚠ **目前 `FS_SCHEME_RANK` 只有一項，所以實質上仍是全序。** 真要加第二個軸時，
那張表要換成偏序——`"incomparable"` 已經替那一天留好位置，但**偏序本身還沒設計**。
這一點必須寫下來，否則就是本 ADR 自己在防的那件事：把一個撐不住第二種情況的地基當成修好了。
  - 🔵 **§6 為新增**（2026-07-31）：審計面的實際量測，與版本協商無關但同屬本文範圍。

## 背景與問題

### 1. 現況（查證）

| 位置 | 現況 |
| --- | --- |
| `subkey.ts:25` | `FS_CAPABILITY = "ek-v1"`，寫進**簽章**個人檔的 `fs` 欄位 |
| `subkey.ts:67` | EK 公告內容 `JSON.stringify({ v: 1, ek, next? })` |
| `subkey.ts:83` | `readEkAnnounce`：**`c.v !== 1` 直接回 `null`** |
| `relay-backend.ts:1725` | 收到個人檔且 `profile.fs === FS_CAPABILITY` → `pinFs(sender)` |
| `types.ts:490` | `pinned?: Record<string, boolean>` —— **布林** |
| `relay-backend.ts:1174` | `fsWouldDowngrade(to)` ＝ 已釘選 **且** 無其 EK |
| `relay-backend.ts:2568` | 送訊前若成立 → `onFsDowngrade(to)` → UI 警告（不得靜默退回靜態） |

這套在**單一機制**下是完整的。問題出在它對「不是這個機制」的東西怎麼反應。

### 2. ⚠ 未知版本目前被當成「降級」，而那是巧合

假設日後出現 `v: 2`（無論是棘輪、UPKE、或只是 EK 格式改版）：

1. 舊客戶端 `readEkAnnounce` 對 `v: 2` 回 `null` → **不學該聯絡人的 EK**
2. 於是 `contactEks[peer]` 缺席
3. 若該聯絡人先前已被釘選 → `fsWouldDowngrade` **成立** → 跳降級警告

**結果碰巧是安全的**（不會靜默退回靜態），但**語意是錯的**：

- 對方**沒有降級**，對方是**升級了**
- 使用者看到的訊息會是「疑似降級」，而正確的訊息是「**對方用了你這版不支援的機制，請更新**」
- 而我們的紅線是 **UI 不得說謊**（ADR-0278 隱身狀態點、ADR-0287 搜尋範圍都是這個立場）

⇒ 這不是安全漏洞，是**誠實性缺陷**：正確的行為建立在「兩個獨立條件恰好同時成立」上，
而不是建立在明確的判斷上。任何一邊改動（例如日後讓未知版本不清空 `contactEks`）就會失效。

### 3. ⚠ `pinned` 是布林，撐不住兩個以上的強度

`pinned: Record<string, boolean>` 只能表達「這個人期望 FS / 不期望」。

若日後有第二種機制，「從強機制退回弱機制」**也是降級**，但布林表達不了。
⇒ 真要加模式時，**降級保護沒有地方掛**——這正是應該先修好的地基。

### 4. 對照：沒有版本協商的下場

ADR-0300 §5 查證 Keychat 時撞到的：`keychat-io/docs`（NIP-04 世代）與 `keychat-protocol`
的 spec v2（NIP-17 世代）**並存，而外部無法判斷上架版本跑哪一版**。
那份 ADR 只好把「版本歧異」列為自己最大的限制。

⇒ 版本協商不是為了未來的功能，是為了**未來的可判斷性**。

## 非目標（刻意排除）

- **不引入第二種 FS 機制**（棘輪／UPKE 皆不在本文範圍；見 ADR-0301 與 ADR-0236 的取捨）。
- **不做使用者可設的 FS 模式**。
  🔵 **2026-07-31 措辭精修**：本項排除的**不是「第二種 FS 機制」，而是「讓使用者選」**。
  原措辭把兩件事綁在一起，導致 ADR-0303 §7.4a 這種**自動、必然升級**的引導階段
  被誤讀成違反本項。正確的界線是：

  | | 排除？ | 理由 |
  | --- | --- | --- |
  | 使用者可設的模式（開關、下拉選單） | ✅ **排除** | 下方四條理由全部成立 |
  | **自動且必然升級**的轉換（不可設、無設定項） | ❌ **不排除** | 四條理由中三條不適用（見 0303 §7.5a），審計增量已量化為「轉換狀態機」而非第二條路（§6.4） |

  ⇒ **凡是想加第二條路徑者，把它做成「不可設」即可落在本項之外**——
  這正是 0303 §7.4a 採用的形狀，也是本專案往後處理同類問題的預設答案。

  以下四條理由**針對「可設」而言**：
  ~~per-device 身分是棘輪的入場費、無法 per-conversation 開關；~~
  🔴 **更正（2026-07-31，見 ADR-0303 §1／§2）**：入場費是**每裝置各自的預金鑰／session**，
  不是 per-device 身分。⚠ **但本項〈非目標〉不變**——理由改為下面這條，
  而它與更正無關：**預金鑰／session 是裝置層的全域狀態，仍然無法 per-conversation 開關。**
  （原論證用錯了前提，結論碰巧仍成立；已換上正確前提。）
  其餘理由照舊：降級面隨模式數成長；~~審計面加倍（與 ADR-0290 §2 相反）~~
  🔵 **「審計面加倍」已於 2026-07-31 重新量化，見 §6——該說法對「使用者可設的模式」
  仍成立，但對 ADR-0303 §7.4a 的 bootstrap 引導階段**不**成立**；
  群組混模無法誠實呈現（群組強度＝最弱成員）；而且**使用者答不出這個問題**。
- **不改變 ADR-0245 的範圍、預設值或上線條件**。

## 決策

### 1. 把「未知版本」與「沒有 FS」分開

`readEkAnnounce` 目前對所有不合法輸入一律回 `null`。改為區分兩種失敗：

- **格式錯誤／簽章錯誤／公鑰不合法** → 照舊丟棄（那是垃圾或攻擊）。
- **`v` 是我們不認得的數值，但其餘結構合法** → 回一個**明確的「版本較新」結果**，
  而不是與垃圾同一個 `null`。

呼叫端據此**記住「這個聯絡人宣告了我不支援的版本」**，而不是讓它退化成「沒有 EK」。

### 2. 個人檔的 `fs` 欄位同理

`profile.fs === FS_CAPABILITY` 是**精確字串比對**。`fs: "ratchet-v1"` 之類的值目前
既不觸發釘選、也不留下任何痕跡——等於**當作對方沒有 FS**。

改為：`fs` 為非空字串即視為「對方宣告了某種 FS」，**記下它宣告的是什麼**。

### 3. `pinned` 從布林改為記錄「宣告的機制」

```
pinned?: Record<string, boolean>              // 現況
pinned?: Record<string, { scheme: string; at: number }>   // 提議
```

- 向後相容：讀到 `true` 視為 `{ scheme: "ek-v1", at: 0 }`。
- 降級判斷從「有沒有 EK」擴為「**對方現在宣告的強度，是否低於曾經釘選的**」。
- 有了這個欄位，日後真要加模式時，降級保護才有地方掛（§3 的地基）。

### 4. UI 要分成三種訊息，不得混用

| 情況 | 訊息 |
| --- | --- |
| 已釘選 ＋ 無其 EK ＋ 同一機制 | **疑似降級**（現況，不變） |
| 已釘選 ＋ 對方宣告**更新的**機制 | **「對方使用你這版不支援的加密機制，請更新」**（新增） |
| 未釘選 | 無訊息（不打擾） |

**紅線**：不得把第二種顯示成第一種。那是把「你該更新」講成「對方可能被攻擊」。

## 6. 🔵 重新審視「審計面」：它到底是什麼、有多大（2026-07-31 量測）

〈非目標〉與 ADR-0290 §2 都把「審計」當成阻擋，但**從未量化**。本節補上。

### 6.1 我們一行密碼學原語都沒有自己寫

`packages/core/src/nip44.ts` **全長 28 行**，其註解寫明：

> NIP-44 v2 加密的**薄包裝**。密碼學原語委由**審計過的** `nostr-tools/nip44`（底層 @noble）。

且 **ADR-0004／0007 明載「不自行實作加密原語」**，全 `core` 的密碼學相依是
`@noble/hashes`、`@noble/ciphers`、`nostr-tools`——**都是已審計的既有實作**。

⇒ **審計的標的不是「這些密碼學正確嗎」，是「這些已審計原語的綁定與狀態機正確嗎」。**
⇒ 這是**協定／組合審計**，不是原語審計。**兩者不是同一個價位。**

### 6.2 範圍量測

| 檔案 | 行數 | 與 FS 相關 |
| --- | --- | --- |
| `nip44.ts` | **28** | ✅ 薄包裝 |
| `giftwrap.ts` | **221** | ✅ rumor／seal／wrap 三層封裝 |
| `subkey.ts` | **119** | ✅ EK 輪替狀態機、公告、hint |
| `keys.ts` | **52** | ✅ 金鑰型別與導出 |
| **FS 小計** | **420 行** | ← ADR-0290 §2-A 說的「core 那幾百行」，**數字對得上** |
| `at-rest.ts` | 64 | ❌ 靜態加密，可分開審 |
| `pairing.ts` | 218 | ❌ 搬家，可分開審 |
| `snapshot.ts` | 57 | ❌ 雲端快照，可分開審 |
| （`core` 全部非測試） | 7,105 | 其餘與密碼學無關 |

⇒ **ADR-0290 §2-A「縮小審計範圍」不只是建議，是可執行的**：
FS 審計標的是 **420 行**，而非 7,105 行、更非整個 App。

### 6.3 審計實際要看什麼

1. **NIP-44 綁定**：conversation key 的導出與使用是否正確、是否誤用同一把
2. **Gift Wrap 三層封裝**：rumor／seal／wrap 的欄位是否洩漏、外層 tag 是否洩漏內層資訊
3. **EK 輪替狀態機**：grace 窗、降級偵測、TOFU 釘選、`readEkAnnounce` 的拒收條件
4. **隨機性來源**：一次性金鑰與 nonce 的產生
5. **（棘輪上線後追加）**：棘輪狀態機、跳過訊息金鑰窗、per-device session 索引

### 6.4 ⇒ 對〈非目標〉的影響：分開兩件事

| | 審計增量 |
| --- | --- |
| **使用者可設的 FS 模式**（本文〈非目標〉排除的） | **真的加倍**——兩條完整路徑都要審，且要審「使用者設定如何影響選路」 |
| **ADR-0303 §7.4a 的 bootstrap 引導階段** | ⚠ **不是加倍**——增量是**轉換狀態機**（判定此對話在引導或棘輪階段），不是第二條完整密碼學路徑 |

**且關鍵的一點**：ADR-0303 §5.2 已確立**首則訊息在任何 per-device 方案下都是特殊的**
（無一次性預金鑰、FS 由簽章預金鑰輪替週期界住）——
⇒ **該轉換在選項 1 也存在**，只是先前沒被記為「兩套模式」。
⇒ **選項 4 相對選項 1 的審計增量，是「把已存在的轉換寫明確」，不是新增一條路。**

⇒ **本文〈非目標〉維持不變**（不做使用者可設的 FS 模式），
但**其「審計面加倍」一詞不得被引用來反對 ADR-0303 §7.4a**。

### 6.5 ⚠ 誠實揭露：本節量的是行數，不是報價

- 行數 ≠ 價格。**審計報價取決於協定複雜度與往返次數**，420 行的協定審計
  仍可能高於 4,000 行的例行程式碼審查。
- **未取得任何實際報價**，ADR-0290 §2 的「要付錢而 0257 說沒有營收面」仍然成立。
- **ADR-0290 §2-B（OpenSats 等開源資助）的資格與時程仍未查證**——
  該項在 0290 就標著「待查證」，至今未動。**那可能才是真正的關鍵路徑。**

## 後果

**正面**

- 修掉一個「碰巧正確」的行為，使它變成明確的判斷。
- 為日後任何 FS 機制變更（換版、加模式、乃至採用 MLS）預留**可判斷的**升級路徑，
  而不是像 ADR-0300 §5 的 Keychat 那樣兩代並存卻無從辨識。
- 範圍小（`subkey.ts` 的解析、`fsState` 的一個欄位、一條 UI 訊息），
  **與 ADR-0290 §2「縮小審計範圍」不衝突**——它不新增任何密碼學原語。

**負面／代價**

- `StoredFsState.pinned` 的形狀改變 → 需要向後相容讀取（讀到 `true` 當 `ek-v1`）。
  這個欄位**會進雲端快照**（`buildSnapshotContent` 以 `{ ...localFs }` 整份帶出）。

  **已查證，風險比預期低**：快照的形狀驗證（`cloud-snapshot.ts:179`）**只檢查 `fs.keys` 是陣列**，
  合併時 `pinned` 是原樣 union（`{ ...remote.pinned, ...local.pinned }`）、**不做任何值驗證**；
  而讀取端 `fsWouldDowngrade` 只取真值性（`this.fsState.pinned?.[to] ?? false`）。
  ⇒ 舊版客戶端收到 `{ scheme, at }` 物件時**不會拒收快照**，且物件為真值 ⇒ 仍視為「已釘選」，
  **行為與今天一致**。

  殘留的只有一項小事：首次合併時 `JSON.stringify(merged) !== JSON.stringify(local)` 必然成立
  （布林 vs 物件），會多寫一次快照。無害。
- 多一條 UI 訊息與一組文案。
- **不解決任何現存的使用者問題**——它買的是未來的可判斷性。若永遠不改 FS 機制，
  這份工作就是純成本。

**已知限制**

- 本文**未實作、未測試**。§4 的三態 UI 尚無文案。
- 「更新的機制」如何判斷「更強」需要一個順序表（`ek-v1 < ratchet-v1 < …`），
  而那個順序表本身是**未來的判斷**，現在只能留一個字串與一個比較函式的位置。
- 未評估：若對方宣告的機制我們不認得，**送訊該不該擋**。傾向不擋（照舊以現有機制送出）
  並提示更新，但那是可用性與安全的取捨，**本文不決定**。
