# 0258. 桌面託管清單加密落盤（補上 ADR-0163 承諾、對齊行動端）＋舊明文就地遷移

- 狀態：**已接受（已實作）**
- 日期：2026-07-27
- 相關文件：ADR-0163（入職金鑰託管＋離職接管——**其決策 #1 承諾加密落盤，桌面實作未兌現**）、
  0179（行動端託管加密落盤——本 ADR 把同一作法補回桌面）、0112（靜態加密／nsec 絕不明文落盤）、
  0044/0047/0052（企業成員管制與輪替）、0257 §6.1（查核發現此落差）；
  `apps/desktop/src/ui/org-escrow.ts`、`apps/desktop/src/App.tsx`

## 背景與問題

ADR-0257（relay 營運盈利研究）在盤點「企業客戶資安稽核會問什麼」時，查核了金鑰託管的實作，
發現**桌面與行動端不一致，且桌面與自己的 ADR 文字不一致**：

- **ADR-0163 決策 #1 寫**：「管理者端持久化……App 存 `nb.orgEscrow.<admin>`（隨管理者身分的
  **加密儲存**落地，ADR-0112）」。
- **實作卻是**：`apps/desktop/src/ui/org-escrow.ts` 直接
  `localStorage.setItem(key, JSON.stringify(list))` ＝ **明文**，且**繞過**引擎的加密儲存基質
  （`packages/engine/src/storage/local.ts` 的 `sealValue` 路徑）。
- **ADR-0179 誠實記錄了這個差異**（「桌面把託管 nsec 明文存 localStorage……行動端一律加密落盤」），
  但只修了行動端，桌面未跟進。

這份清單的內容是**一整家公司所有公司帳號的私鑰**（`EscrowEntry.nsec`）。暴露面：

- **web 版（自架 web app／瀏覽器執行）**：任一 XSS ＝ 一次撈走全公司公司帳號 nsec。
  這正是 ADR-0179 為行動端加密的理由，而桌面 web 面對的是**同一個威脅**——原註解所謂
  「其 Tauri 版另有 OS 層保護」在 web 版根本不存在。
- **Tauri 版**：webview 的 localStorage 仍以明文落磁碟，保護僅來自 OS 檔案權限／帳號邊界，
  **不是** ADR-0112 的靜態加密。而 ADR-0112 §3 早已論證過：OS 帳號邊界是桌面與瀏覽器**唯一**
  的差別，不足以作為「不加密」的理由。

## 考量的選項

- **選項 0：維持明文，靠 Tauri 的 OS 邊界。** 零改動，但 web 版無此邊界、Tauri 版也只有檔案權限；
  且與 ADR-0163 白紙黑字的承諾不符——文件說加密、實作沒加密，是最壞的一種狀態。
- **選項 1（採用）：比照 ADR-0179，以企業主 sk 導出的金鑰 `sealValue` 加密落盤，並就地遷移舊明文。**
- **選項 2：把託管清單改走引擎的 `AppStorage`／`LocalStorage` 基質。** 語意上最「正統」，但這份
  資料是**管理者身分專屬的 UI 層索引**、不屬於聊天資料快照，硬塞進基質會擴大快照/搬家/配對捆包的
  範圍（把全公司私鑰帶進 `PairBundle` 是新的風險面，非改善）。否決。

## 決策

**採選項 1：桌面託管清單一律加密落盤，與行動端同一套作法；讀到舊明文就地遷移。**

1. **加密落盤**：`saveEscrow(adminPubkey, ownerSk, list)` 以 `deriveStorageKey(ownerSk)` ＋
   `sealValue` 封裝，磁碟上只有 `c1:` 密文；`loadEscrow(adminPubkey, ownerSk)` 以 `openValue`
   解出，**金鑰不對回空、不拋**。純函式（`upsertEscrow`／`removeEscrow`／`offboardedEntries`）不變。
2. **舊明文就地遷移**：`openValue` 對無 `c1:` 前綴的值原樣回傳，故舊明文仍讀得出來——但**光能讀
   不夠，磁碟上的明文必須真的消失**。故 `loadEscrow` 一旦讀到未加密的舊值即**當場重寫為密文**
   （`migrateIfPlaintext`），不等下次清單變動；企業主只要開過一次即完成遷移。已是密文則不重寫。
3. **無私鑰＝不落盤，而非退回明文**：`App.tsx` 三個接點都先取 `backend.selfNsec`；取不到就
   **放棄該次寫入**（`onOrgEscrow`／`onDeleteEscrow` 直接 return），清單顯示為空。
   **寧可不存，也不明文落地。**
4. **載入時機改依 `backend`**：原效果只看 `profilesState.active`（那時沒有解密金鑰）。改為依
   `backend`＋`selfNsec` 載入。
5. **寫入改為「以磁碟為準的讀-改-寫」**：`onOrgEscrow`／`onDeleteEscrow` 不再拿 React state 當
   基底，而是 `loadEscrow` → 改 → `saveEscrow`。這順手修掉一個既有的競態——託管在清單載入前
   就到達時（backend 剛起、`escrow` 尚為空），以 state 為基底會把既有條目**整批蓋掉**。

## 理由

- **Fix First／零新機制**：直接複用 ADR-0112 的 `deriveStorageKey`／`sealValue`／`openValue` 與
  ADR-0179 已驗證的行動端作法，不新增加密原語、不新增儲存基質。
- **兩端一致**：桌面與行動端此後同一套規則，`org-escrow.ts` 兩份檔案的差異收斂為零，
  不會再出現「一端修了另一端沒修」。
- **遷移零損失**：`openValue` 的 pass-through 語意讓舊資料自然可讀，遷移只是把它重新封裝——
  既有託管條目不會因升級而消失（若消失，企業主就永久失去離職接管能力）。

## 後果

- 正面：桌面（含 web 版）託管的員工私鑰不再明文落盤；ADR-0163 決策 #1 的承諾終於與實作相符；
  順手修掉載入前到達託管會清空清單的競態；企業銷售時 §5 的揭露清單少一項自打嘴巴的例外。
- 負面 / 已知殘餘風險：
  - **只擋靜態**：頁面內的惡意 JS 在**企業主已解鎖、金鑰在記憶體中**時仍可能取得明文——
    這與 ADR-0112 對桌面/瀏覽器的結論一致，不假裝能防。
  - **金鑰＝企業主 nsec**：企業主換裝置若未帶走身分，密文即無法解開＝失去離職接管能力
    （與行動端同語意；本就該靠既有的配對搬家／備份路徑處理）。
  - **遷移需「開過一次」**：從未以新版載入該身分的裝置，磁碟上仍是舊明文——這是就地遷移的
    固有邊界，無法遠端執行。
  - 未處理 ADR-0047 的「單一管理者金鑰為信任根」限制（多管理者／輪替仍為後續）。
- 測試：`org-escrow.test.ts` 7 項（純函式 2、round-trip／毀損／形狀 1、**落盤為密文且不含 nsec**、
  **換鑰匙解不開**、**舊明文遷移後可讀且磁碟改寫為密文**、**已是密文不重寫**）；
  desktop 全套 539 綠、typecheck 綠。
- 後續行動：無（本 ADR 自足）。ADR-0257 §6.1 的待決策項至此關閉。
