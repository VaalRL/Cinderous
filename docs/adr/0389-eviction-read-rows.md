# 0389. 檔案車道塞滿後的讀取列數：淘汰時只讀要刪的那幾列

- 狀態：已接受（未部署）
- 日期：2026-10-20
- 相關文件：SDK ADR 0102（同一件事在 SDK 中繼）；ADR-0386（整批淘汰）、ADR-0381（檔案車道保底與溢位帶）、ADR-0371（檔案車道、分桶索引）、ADR-0387（額度用完時說明原因）、ADR-0388（拿掉 `idx_offline_kind`）

## 背景與問題

2026-10-19 錨點 1 整座中繼一整天連不上。Cloudflare GraphQL 用量分析，依 DO 名稱、每 5 分鐘看：
- 用完的是**讀取**額度。免費方案每日 500 萬列，當天讀了 693.7 萬列；寫入只有 3.2 萬列。
- 全部來自 `app:cindersync`，集中在台灣時間 13:15–14:05。那段時間正在做 CinderSync 實機測試，三台裝置反覆重新載入外掛、同步。
- 那一小時寫入 2.36 萬列、讀取 568 萬列，平均每寫一列讀約 240 列。
- （10-15 那天寫了 10.1 萬列，寫入額度也超過了。）

用 `wrangler dev` 跑本庫 `relay/src` 的 `SqlMessageStore`，設定與錨點檔案車道相同（天花板 512 MiB、每收件人 1,440 塊、保底 64 MiB、溢位帶 20%、預警、丟棄計數），三位收件人輪流寫 128 KB 的檔案塊，加總 SQL 游標回報的 `rowsRead`：

| | 每寫一顆平均讀 | 最多一次讀 |
|---|---|---|
| 天花板以下 | 0 | 0 |
| 塞滿以後 | **172** | **10,438** |

依 SQL 語句分別統計，塞滿後的讀取來自下面這些，全部都是「本來只該讀幾列，實際掃過一整個索引」：

1. **淘汰前查「這幾列屬於哪一批」**（ADR-0386 的 `batchesOf`）：寫成 `INDEXED BY idx_offline_batch ... rowid IN (...)`，本意是「只讀索引、不碰 json 溢位頁」。但部分索引不是以 rowid 排序，SQLite 只能把整個批次索引掃一遍，而每顆檔案塊都在裡面，每次約 4,400 列。
2. **淘汰後把每收件人的列數快取整個清掉**（`bucketCounts.clear()`）：下一次寫入就得對那位收件人重數 `COUNT(*)`，每次約 1,400 列。塞滿以後幾乎每次寫入都淘汰，快取一直被清。
3. **列出溢位帶的借用列**：規劃器為了省掉 `ORDER BY expiration` 的排序，不走借用列的部分索引，改走整個到期索引，也就是每一列，每次約 4,300 列。
4. **每小時清理時查到期借用列的批次**：與第 1 點同一個寫法，每小時約 4,200 列。

## 考量的選項

- 選項 A：逐條修正，讓每條查詢只讀需要的列。
- 選項 B：把檔案車道的天花板調低或關掉保底與溢位帶，減少淘汰。
- 選項 C：升級 Cloudflare 付費方案。

## 決策

採用選項 A：

1. **新增 `describeRows(rowids)`**：以 rowid 逐列查出要刪的那幾列的收件人、批次與桶別。取代 `batchesOf`。
   - `batch`、`kind` 在大表上排在 json 後面，要走溢位頁，但只有要刪的那幾列。
   - 回收借用列時，先決定要刪哪幾列（刪到放得下為止），只查那幾列，不查全部借用列。
2. **刪掉的列照實從各桶扣掉**（`forgetRows`），不再整個清掉 `bucketCounts`：
   - 回收、份額外淘汰、舊版天花板淘汰：從 `describeRows` 知道每列的收件人與桶別，逐列扣。
   - 整批淘汰（`dropBatchMates`）：有批次的列一定是那位收件人的檔案塊，扣掉同批的列數。
   - 每收件人上限（`enforceCap`）：整批刪完改從快取取回列數，不再 `COUNT(*)`。
   - `prune`、`vanish` 等算不出確切數字的路徑照舊整個作廢，只在每小時清理或清除帳號時發生。
3. **列出借用列時指定 `INDEXED BY idx_offline_borrowed`**：讀出借用列再排序，借用列通常只有幾十到幾百列。
4. **每小時清理的批次查詢**：先從借用列的部分索引找出到期的那幾列，再以 rowid 查批次。

## 理由

- 行為完全不變，只改查法；既有的整批淘汰、容量、相容性測試全過。
- 改完同一套量測，塞滿後每寫一顆：

  | | 平均讀 | 最多一次讀 |
  |---|---|---|
  | 修正前 | 172 | 10,438 |
  | 只改 1、2 | 72 | 5,006 |
  | 1–4 全改 | **42** | **1,541** |

  每小時清理從 4,233 列降到 54 列。以 10-19 那一小時的 2.36 萬次寫入換算，約從 400 萬列降到 100 萬列。
- 選項 B 會減少收件匣能放的量，是用體驗換額度。選項 C 是費用決策，使用者另外處理（2026-10-19「我之後會處理節點額度問題」）。

## 後果

- 正面：檔案車道塞滿後的讀取列數降到約四分之一，最壞一次降到約七分之一；每小時清理幾乎不再讀。
- 負面 / 已知殘餘風險：
  - 剩下的平均 42 列，主要是保底份額的用量快取（`ownerNormal`）在整批淘汰後被作廢、下次重建（每次約 4,200 列，約每百次寫入一次）。要再降，得在刪除時逐列扣掉正常列的用量，需要多讀每列的 `borrowed` 欄，留待之後。
  - 外掛每次啟動從頭補拉收件匣（SDK ADR 0084），收件匣塞滿 1,430 塊時一次約 3.4 萬列。這條這次沒動。
  - `describeRows` 要讀大表上的 `batch`／`kind`，會走溢位頁。這是 I/O 成本，不是讀取列數，且只有要刪的那幾列。
- 驗證：`relay/src/evict-reads.test.ts`。node:sqlite 量不到列數，改用查詢計畫與「下了哪些 SQL」守住：
  - 任何淘汰情境都沒有 SQL 掃過整個 `idx_offline_batch`；
  - 借用列查詢不走整個到期索引；
  - 每小時清理不掃批次索引；
  - 塞滿後連續寫入不再下 `COUNT(*)`；
  - 被淘汰的列有扣掉，每收件人上限剛好在上限才動手。
- 後續行動 / 待辦：
  - 部署到錨點要使用者同意。
  - SDK 中繼同步修改（SDK ADR 0102）。
