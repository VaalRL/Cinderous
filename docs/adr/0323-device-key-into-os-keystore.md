# ADR-0323：裝置金鑰移進 OS 金鑰庫

- 狀態：已採用
- 日期：2026-08-04
- 關聯：ADR-0322（裝置撤銷）、ADR-0297（平台金鑰分級）、ADR-0053（B5 身分私鑰進金鑰庫）、ADR-0122（拿不到金鑰要大聲失敗）

## 1. 背景

ADR-0322 的撤銷（移除某台裝置 ⇒ 它拿不到新的 EK）成立的前提只有一個：**被移除那台的裝置私鑰，攻擊者拿不到**。

而 2026-08-04 校正 ADR-0322〈買不到什麼〉第 4 點時發現，那個前提在**所有平台上**都不成立：

```
getDeviceKey() → getKv() → localStorage／MMKV → 明文
```

沒有加密。ADR-0297 的 L0 定義是「不明文落盤」，所以裝置金鑰**低於 L0**——比我們自己定的最低一級還低。後果：

> 磁碟被複製（備份、舊機沒清、惡意程式讀檔）⇒ 裝置金鑰外洩 ⇒ **對那個人而言，「移除裝置」是個沒有作用的按鈕**。

身分私鑰早在 ADR-0053（B5）就解決了這件事——進 OS 金鑰庫。裝置金鑰只是當時沒跟上。

## 2. 決策

**比照 B5，把裝置金鑰放進 OS 金鑰庫**：`keyring` crate（Windows Credential Manager／macOS Keychain／Linux Secret Service），走既有的 `key_set`／`key_get` IPC，帳號名用保留槽 `"device"`（身分 pubkey 恆為 64 hex，不會相撞）。

引擎不直接依賴桌面模組，而是比照 `setKvBackend()` 的既有慣例開一個可注入基質：

```ts
setDeviceKeyVault({ load, save });   // 桌面在模組載入時注入；不注入＝維持今天的 KV 行為
await openDeviceKey();               // 啟動時一次；之後同步的 getDeviceKey() 讀快取
```

### 2.1 為什麼 `buildBackend` 變成 async

金鑰庫是非同步的，而 `RelayChatBackend` **在建構時**就要拿裝置金鑰（它得知道自己是誰才能查裝置目錄）。兩者只能靠一個 await 接起來。

考慮過在 `main.tsx` render 前 await，一處搞定——**桌面否決**：Linux 的 gnome-keyring 可能彈出解鎖對話框，那會讓使用者先看到一片空白視窗。改成在 `buildBackend` 內 await，阻塞的是登入流程，而那裡本來就有載入態。

**行動端則相反，就是在 render 前 await**：`createBackend` 是同步的、改 async 會擴散，而 Android 這把金鑰刻意沒設 `setUserAuthenticationRequired`（見 §3.5）⇒ 不會有提示、不會卡住 ⇒ 擋在進入點是安全的。兩端做法不同不是不一致，是**同一個判準（會不會讓使用者對著空白畫面等）在兩個平台上得到不同答案**。

## 3. 三個會讓這件事白做的失敗方向

### 3.1 遷移順序寫反 ⇒ 裝置身分蒸發

舊裝置的金鑰已經在 KV 裡。遷移必須**先存進金鑰庫、成功後才刪 KV**。

反過來寫（先刪再存）而存檔失敗 ⇒ 這台的裝置金鑰沒了 ⇒ 掉出裝置目錄 ⇒ 使用者得重新授權，而他完全不知道為什麼。KV 刪除失敗則無害：下次開機仍先讀金鑰庫。

### 3.2 金鑰庫打不開時靜默生一把新的長期金鑰

Linux 沒跑 Secret Service、keyring 被鎖住——這些是會發生的。此時若走「生一把新的存起來」，等於**每次開機換一個裝置身分**，而使用者只看到裝置清單裡莫名其妙多出一堆項目。

這正是 ADR-0122 在**身分**金鑰上禁止過的事：

> 拿不到金鑰時大聲失敗，而不是靜默產生一把新的把使用者換掉。

故新增第四個等級 `ephemeral`：用臨時金鑰、**不落地**，這台不會進裝置清單，重開又是新的一把。是安全側的失敗方向，而且**看得見**——設定頁直接說「這台不會出現在你的裝置清單裡，修好金鑰庫後重開即可恢復」。

### 3.3 遷移後宣稱「已受金鑰庫保護」

從明文搬進金鑰庫的金鑰，**曾經明文躺在磁碟上**。刪掉那份副本不能收回已經被複製走的東西。

只顯示 `keystore` 會讓這種使用者以為自己和原生於金鑰庫的人處境相同——他們不是。故額外記一個 `deviceKeyEverPlaintext()`，遷移者的設定頁多一句告白，並給出出路（移除這台再重新配對，換一把從未明文躺過的金鑰）。

考慮過**強制**在遷移時換一把新的（乾淨、不用告白）——**否決**：那會讓每台舊裝置都掉出目錄、都要重新授權。代價由所有人付，而受益的只有「磁碟真的被複製過」的少數人。改成**告知＋提供選項**，讓當事人自己判斷。

## 3.5 Android（同批完成）

自寫的 Capacitor 外掛 `DeviceKeyStorePlugin`：在 `AndroidKeyStore` 產一把**不可匯出**的 AES-256-GCM 金鑰，用它把 nsec 加密後放進 SharedPreferences。落地的只有密文。

**刻意不引入 `androidx.security`（EncryptedSharedPreferences）等第三方套件**——Keystore 本身就夠，少一個相依就少一條供應鏈。

**刻意不設 `setUserAuthenticationRequired`**：這把金鑰要在開機／背景重連時就取得，掛上生物辨識會讓「收訊息」變成要先解鎖，而它保護的東西（裝置身分）不值得那個代價。

🔴 **`keystore` 與 `encrypted` 必須分開**。沒有 TEE／StrongBox 的機型上，AndroidKeyStore 是**軟體實作**，完整磁碟映像仍可能解得開。把兩者一律講成 `keystore` 就是 ADR-0297 §6 紅線說的「用最強平台的說法涵蓋最弱平台的現實」。故 `DeviceKeyVault` 多一個可選的 `tier()`，由保管庫**自報實際等級**：外掛問 `isInsideSecureHardware()`（API < 31）／`getSecurityLevel()`（API 31+），**問不出來就往低的講**。

同樣的紅線在原生側：**解不開時 `reject`，不得 `resolve` 一個 null**——回 null 會讓引擎以為「還沒有金鑰」而生一把新的覆蓋上去，正是 §3.2 那條。JS 橋因此也**刻意不 catch**。

因為原生程式碼 JS 測不到而寫錯的後果是靜默的，這些紅線改以掃原始碼看守（同 ADR-0279 對 `allowBackup` 的做法）。

## 3.6 行動端的移除入口（同批補上）

ADR-0322 S3 的移除只做在桌面，等於**「手機丟了要開電腦才撤銷得掉」——而手機正是最常掉的那一台**。這次一併補上，與桌面同樣的閘門（不能移除自己、已撤銷的不再給鈕）。

二次確認用 **fail-closed** 的 `confirmRequired`（取不到 confirm 就不做），而非 `confirmAction`：那段文案講的是**這個按鈕買不到什麼**（歷史救不回、保留期內仍讀得到、身分私鑰外洩時完全擋不住），跳過它等於默許誤解。同 ADR-0306 D1 對「未經審計」揭露的處置。

## 3.7 瀏覽器（同批完成）

`browserKeyVault` 只收 Argon2id 密碼包裹的 blob，所以一開始的結論是「沒有密碼就沒地方放」。那個結論**只在「一定要用密碼」的前提下成立**。

**先評估過用 nsec 導出的 DEK 包裹**（ADR-0112 的 `deriveStorageKey`）。那條路**更強**——攻擊者得先有密碼或 nsec 才解得開。**否決的理由是遷移**：它會把裝置金鑰變成**身分層**的東西，而舊的明文 `nb.deviceKey` 是**跨身分共用**的。第一個身分把它包進自己的槽並抹掉明文之後，同一台上的其他身分就找不到自己的裝置金鑰了 ⇒ 掉出目錄、要重新授權，而使用者只會看到「我另一個帳號的裝置不見了」。**用一個看不見的破壞換一級保護，不划算。**

**採用的是 IndexedDB 裡一把不可匯出的 WebCrypto 金鑰**（`generateKey(..., extractable: false, ...)`）。它是**來源層級**（per-origin）的，天然裝置層，沒有上面那個問題，也不需要密碼或已解鎖的身分。

🔴 **必須說清楚這買到的是什麼**：

- ✅ **想偷金鑰的腳本偷不走它**。以前 localStorage 一行就撈走，現在原始金鑰材料連腳本自己都讀不到。
- ❌ **完整複製瀏覽器設定檔的人仍可能取得**——包裹金鑰由瀏覽器保管，沒有任何使用者祕密參與。

所以它是 `encrypted`，**不是** `keystore`。

⚠ **同批校正**：`encrypted` 原本的文案是「**以密碼包裹**後存放……除非對方也拿到你的密碼，否則解不開」。那是寫這個等級時**還沒有任何實作**所預設的形態，而現在佔用它的兩個實作（Android 軟體 Keystore、瀏覽器 IDB 金鑰）**都沒有密碼參與**——那句話會承諾一個不存在的東西。已改成照實說，並有測試釘住不得寫回「以密碼包裹」。

**包裹金鑰與密文刻意放在同一個 store**：瀏覽器清儲存時兩者一起消失 ⇒ 只會落到「什麼都沒有」（乾淨地生一把新的），不會落到「有密文卻沒鑰匙」那種永遠解不開的狀態。

## 4. 各平台實際落在哪一級

| 平台 | 等級 | 為什麼 |
| --- | --- | --- |
| Tauri 桌面 | `keystore` | OS 金鑰庫（`keyring`） |
| Android 原生殼（有 TEE／StrongBox） | `keystore` | 包裹金鑰在安全晶片內不可匯出 |
| Android 原生殼（軟體 Keystore） | `encrypted` | 密文落地，但包裹金鑰是軟體實作 ⇒ 完整磁碟映像仍可能解得開 |
| 瀏覽器 / 行動端網頁預覽 | `encrypted` | IndexedDB 內不可匯出的 WebCrypto 金鑰包裹（見 §3.7） |
| 非安全脈絡 / 無 IndexedDB | `plaintext` | 沒有可用的包裹金鑰；**不裝比裝了說謊好** |
| iOS | — | 專案尚無 iOS 殼；有了之後走同一個 `setDeviceKeyVault()` 注入點 |

⚠ `keystore` 指的是**靜態保護**（磁碟被複製解不開），**不是** ADR-0297 L2 的完整形態
「金鑰永不離開晶片」——被包住的 nsec 在使用時仍會取回 JS 記憶體。見 §5-1。

🔴 **不把瀏覽器講成金鑰庫**。硬講只會讓 `deviceKeyTier()` 說謊，而那個函式存在的唯一理由就是不說謊（ADR-0297 §6 紅線）——**難看的實情勝過好看的假話**。

## 5. 買不到什麼

1. **裝置被入侵時不安全**。金鑰庫擋的是「磁碟被複製」，不是「以你的身分執行的惡意程式」。
   ⚠ 2026-08-04 校正文案：原本寫「惡意程式仍可**請金鑰庫代簽**」——那**高估了**我們的做法。
   我們是把金鑰**取出來用**（解回 nsec 進 JS 記憶體），不是請晶片代簽 ⇒ 惡意程式**直接讀得到**，
   比「請代簽」更差。文案已改成照實說，並有測試釘住不得改回過度承諾。
   真正的「金鑰永不離開晶片」是 ADR-0297 L2 的完整形態，我們沒有做到（同 ADR-0307 §3-b 的觀察：
   金鑰已在 JS 記憶體待過，換 WASM 也清不掉那些副本）。
2. **瀏覽器擋得住偷竊腳本，擋不住設定檔被整包複製**（§3.7）。撤銷在瀏覽器上仍可被
   「拿到整份設定檔且知道怎麼做」的人繞過。
3. **遷移者的歷史風險**。見 §3.3。
4. **Linux 依賴 Secret Service**。沒有它就是 `ephemeral` ——可用，但那台不進裝置清單。

## 6. 後續

- **未實機驗證**：Android 外掛只跑過原始碼紅線測試與 JS 橋測試，**沒有在真機上跑過**
  （TEE 有無、StrongBox 退回、遷移路徑）。列入待驗收。
- iOS 殼出現時接 Keychain（同一個注入點，引擎不用改）。
- 瀏覽器的 `idbWrapStore()` 是薄接線，**未自動測試**（Node 無 IndexedDB，未引入 fake-indexeddb
  這個相依）。加解密與失敗方向以記憶體 `WrapStore` 測到；IDB 本身列入待驗收。
- 瀏覽器要再往上一級，只剩「把使用者祕密也放進包裹」那條路（passlock），但要先解掉 §3.7
  說的跨身分遷移問題。
