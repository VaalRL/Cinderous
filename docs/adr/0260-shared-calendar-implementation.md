## 背景

ADR-0259 是研究記錄，把行事曆從「與 IM 定位無關」改判為值得做，並在多輪追問下定了五件事：
中繼不依行程日期保存（§1.5 否決）、日期偵測走提示不導覽（§1.6）、群組行程建立一次而非每人各建
（§1.7）、v1 主揪權威（§1.7）、RSVP 依人數分級（§1.4）。本 ADR 記錄**實作時的具體選擇**，
以及設計文件沒寫、但寫程式時必須決定的細節。

## 決策

### 1. 協定層：借 NIP-52 的形狀，走既有 1059 管線

- **kind `CALENDAR_EVENT=46`／`CALENDAR_RSVP=47`**，接續既有 app 內部 rumor kind 40–45。
  **刻意不用 NIP-52 的 31922/31923**——那是可尋址且全公開的（ADR-0259 §1.1 的三個硬阻礙）。
- **欄位照抄 NIP-52 的 tag 名**（`title`／`start`／`end`／`location`），`content` 放備註。
  照抄一個想清楚過的資料形狀沒有壞處，而「借形狀不借傳輸」這句話因此是字面上成立的。
- **零新協定面、零新加密原語**：傳輸完全是既有的 `sealAndWrap` → kind 1059 → `#p`。

### 2. 行程 id ＝ `rumor.id`（不自造 id）

群組扇出時每位成員各收到一份 wrap，但 rumor 對每位收件人**完全相同 → 雜湊相同**。
ADR-0095 為群訊回條釘死的正是這個性質，**RSVP 需要的「所有人都同意的 id」因此免費取得**。

自造一個 uuid 也能用，但那會讓 id 與內容脫鉤、且需要另一套跨成員一致性的保證——既有機制已經
提供了，不需要。

### 3. RSVP 存在事件內，不另立集合

`StoredCalendarEvent.rsvps: Record<pubkey, {status, at}>`。理由：**RSVP 是每人對自己狀態的
宣告、由本人簽章**，所以不存在多人對同一格的衝突，用不到獨立集合或 CRDT。

兩個實作細節是靠測試才釘住的：

- **`setCalendarRsvp` 只往前推進**：亂序抵達（多裝置/重送）的舊回覆不覆蓋新的。
- **`upsertCalendarEvent` 保留既有 `rsvps`**：主揪改時間的那則 rumor **不帶回覆**，
  直接覆寫會把大家的回覆清光。這是寫的時候差點漏掉、且不會有型別錯誤的那種 bug。

### 4. 權威：`applyCalendarChange` 是執行點，不是提示

收端與自己送出時**共用同一條 `applyCalendar`**——兩邊分歧是 bug 的溫床。規則：

- `create`：較新者勝（重複收到不倒退）。
- `update`／`cancel`：**`incoming.organizer !== existing.organizer` 一律忽略**，
  即使它的 `created_at` 更新。
- 沒有原行程時，`update`／`cancel` **不憑空生出一個**。

**為何不用 ADR-0242 的 CRDT 機具**：它的 per-field LWW＋墓碑是為**同一身分的多裝置**設計的。
推到多使用者會帶出它從不必解的問題——**LWW ＝時鐘最快的人贏，而 `created_at` 是自報的**。
對多裝置良性（都是你自己），對多使用者是真的攻擊面。測試以「非主揪偽造 update 且時間更新」
覆蓋這一點。

送出端也先擋一次（不送注定被忽略的事件），但那是省流量，**不是安全性**——安全性在收端。

### 5. RSVP 廣播閘：`CALENDAR_RSVP_BROADCAST_MAX = 10`

ADR-0259 §1.4 算出 RSVP 全體可見是 **O(N²)**（形狀等同 ADR-0095 量測的群組回條）。差別在
**「不送」不是選項**——邀請本來就要人回覆。故調的是**送給誰**：

- ≤10 人：送全體（每輪 O(N²)，但 N 小、絕對量可接受）；
- \>10 人：只送主揪（每輪降回 **O(N)**）。

取 10 與 ADR-0095 的 `GROUP_RECEIPT_COUNT_MAX` 同值，沿用其 knee 分析的保守值。

### 6. 儲存：四個方法 ＋ 進快照

`AppStorage` 加 `loadCalendar`／`upsertCalendarEvent`／`removeCalendarEvent`／
`setCalendarRsvp`，三個實作（memory／local／tauri）皆補；進 `StorageSnapshot`
（舊快照無此欄位 → 退回 `[]`）與 `LocalStorage` 開機 hydration。

**本機是真實來源**（ADR-0259 §1.2）：中繼那份 7 天就過期，不影響行程本身。

### 7. 日期偵測（階段四）：偵測→提示，形態由 ADR-0259 §1.6 定死

`core/date-detect.ts` 為純函式（比照 `calc.ts`／`sticker-triggers.ts`）：`detectDates` 掃全文，
`detectDateAtEnd` **只看游標前的尾端**（同 ADR-0037 的尾端比對語意——使用者還在打字，只有
剛打完的那個才值得跳建議）。

**取捨一律偏向少報**，因為誤判會讓使用者看到沒意義的標記：

- **過去的一律不報**——「我昨天看到」不是在約時間。寫的時候差點漏掉 `上週三`／`last friday`：
  前綴表沒列它們的話，比對會從第二個字（`週三`／`friday`）開始，**把過去的事報成未來的約定**。
  測試把這一條釘住。
- 「今天」但時刻已過也不報（現在 12:00 時的「今天早上 9 點」）。
- 裸數字不算（`315`、`1234`）；`2026/3/15`／`v1/2/3` 這類多段數字不誤判。
- 重疊時長的優先——`下週三` 不會被其中的 `週三` 蓋掉。

UI 兩處，皆為**提示**：訊息氣泡下方的可點標記（已收回/過期的訊息不掃）、composer 尾端的
建議列（**不劫持 Enter**，Enter 照樣送出訊息）。點擊才切到行程分頁並預填時間——
**這是使用者觸發的導覽，不是 ADR-0259 §1.6 否決的自動切換**。未提供 `onPickDate`
（後端無行事曆能力）＝**完全不偵測**。

分頁切換與表單開啟用 **render 期間調整 state**（React 官方的 derived-state-from-props 模式）
而非 `useEffect`：少一次 paint，且 SSR 走得到——effect 在 `renderToStaticMarkup` 下不執行，
用 effect 就等於這段行為沒有測試覆蓋。

### 8. UI：權威的三層一致

右欄新增「行程」分頁（住在便條旁邊，ADR-0182/0183 的鄰居，不新造導覽層）。

- **主揪**看到「編輯／取消」；**非主揪連按鈕都不出現**，不是按了才被拒。
  core／engine／UI 三層一致——三層都擋才不會讓人以為改得動。
- **RSVP 名單只列「要來」與「也許」，不列缺席者**：那是噪音，且會把「明說不來」與「還沒回覆」
  混在一起看。也許者標問號。
- **已過去的行程留著但退到背景**（`opacity: .5`）：本機是真實來源，不刪；但也不搶注意力。
- 取消行程二次確認，文案明講不可復原且**所有參與者都會移除**。
- 示範後端無 `calendarPublish` → 整個分頁不出現。

## 後果

- 正面：ADR-0259 已定的五項全部落地；行事曆可用（建立／扇出／RSVP／改時間／取消／多裝置同步）。
  中繼端**零改動**——這個功能沒有讓中繼多知道任何事（ADR-0259 §1.3 的性質保住）。
- 負面 / 已知缺口：
  - **§1.5 的未送達／新成員補送未做**：離線超過 7 天、或事後才加入群組者收不到既有行程，
    且**沒有訊號顯示他少了東西**（靜默分歧）。這是目前最大的缺口。
  - **行動端未接**：引擎層共用，`apps/mobile` 只差 UI。
  - **提醒未做**：若要做，紅線是**本機計時器、零中繼成本**（ADR-0259 §1.4）。
  - **無保留上限**：行程只增不減（過去的也留著）。訊息有每對話 1000 則上限，行程目前沒有
    ——量級遠小，但終究該有個界。
- 測試：core 43（協定 20：外層與一般訊息無異且不含任何行程欄位、id 跨成員一致、廣播閘四個
  邊界、**兩個權威攻擊案例**；日期偵測 23：相對日/週幾/明確日期/時刻、**五組偽陽性防線**、
  重疊優先、尾端偵測）＋engine 8（經真實 `RelayCore` 端到端）＋desktop 22（權威在 UI、
  RSVP 名單、過去樣式、分頁顯示條件與對話歸屬、日期標記與預填）。
  全工作區綠：core 506／engine 369／desktop 573／relay 197／mobile 197；`pnpm -r typecheck` 綠。
- 過程中修掉一個**自己寫的假通過測試**：`createGroup` 回傳 `void` 而非 group id，使群組測試
  變成 `expect(undefined).toBe(undefined)`。改為從 `onGroups` 取 id，並補上會抓到它的斷言。
