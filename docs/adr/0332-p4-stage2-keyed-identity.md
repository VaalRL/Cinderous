# ADR-0332：Phase P4 階段 2——以 `key` 取得結構性重設

- 狀態：已採用（2a／2b／2c 全部完成）
- 日期：2026-08-04
- 關聯：ADR-0331（階段 1：按功能簇抽 hook）、ADR-0294 §2／ROADMAP Phase P4、ADR-0328／0329／0330（階段 0 的三支守衛）

## 1. 我上一輪說錯了：階段 2 可以拆

ADR-0331 §5 與當時的回報說「階段 2 不可再拆——`key` 一掛，41 個 state 的重設語意同時改變，中間沒有可停的位置」。

**那個判斷只對其中一小部分成立。** 真正不可分割的只有「掛上 `key`」那一步本身；它前面的準備工作可以拆，而且拆開之後**風險落點完全不同**：

| 步驟 | 內容 | 語意變化 | 風險 |
| --- | --- | --- | --- |
| **2a** | 7 個簇聚合成一個 `session` 物件 | **無** | 低 |
| **2b** | 把 session ＋ 後端接線 ＋ 登入後的 UI 抽成 `IdentityApp` 子元件（**先不掛 `key`**） | **有**（見 §4：控制流會反轉） | 高——1400 行搬移 ＋ 控制流反轉 |
| **2c** | 掛上 `key={pubkey}`、刪掉手寫重設與世代守衛 | **有**（這才是結構性保證生效的一刻） | 集中在少數幾行 |

把 2b 與 2c 分開的價值很具體：**2b 若壞，是搬家搬錯；2c 若壞，是重設語意錯。** 混在一起就分不出來。

⚠ 這是計畫修正，記在這裡而不是默默改掉——因為「不可再拆」這句話本身會影響下一個人要不要一次做完。

## 2. 2a：把 7 簇聚合成一個 session

`useIdentitySession()` 只做一件事：呼叫那 7 個 hook 並回傳一個物件。**刻意不改任何語意。**

理由不是少打幾個字：

1. 2b 要把 UI 抽成子元件。傳 7 個 hook 物件過去，介面會隨著日後加簇而變；傳 1 個 `session` 則不會。
2. 「什麼算一個身分的 session」原本散在 `MobileApp` 的 7 行宣告裡，沒有一個地方說得清楚。現在 `IdentitySession` 這個型別本身就是答案。
3. 2c 掛 `key` 時，**要重掛的東西恰好就是這一個 hook 呼叫**，不是七個。

`MobileApp` 端維持 `const { self, roster, threads, … } = session;`——**讀取點與守衛規則都不受影響**（三支守衛都以 holder 名稱為準）。

### 🔴 刻意不提供 `resetAll()`

看起來很順手，但那會讓「切身分要做什麼」又變回一份清單。而各簇的 `reset` 需要**各自不同的種子**（歸零／捆包精華／從後端重讀，ADR-0331 §7），包成一個只會逼出一個什麼都收的參數物件。

**2c 的正解是讓那些 `reset` 一起消失，不是把它們併成一行。** 有測試釘住這件事（掃程式碼、排除註解）。

### 聚合物與登記表不得漂開

三支守衛都以 `IDENTITY_CLUSTERS` 為準，而 UI 拿到的是 `IdentitySession`。兩邊若對不上，就會出現：

- **登記了但不在聚合物裡** ⇒ 2c 掛 `key` 時那個簇不會被重掛（守衛還以為它被管著）。
- **在聚合物裡但沒登記** ⇒ 用了但沒被守衛看著。

兩個方向都有測試。

## 3. 待做

- **2b**：`IdentityApp` 子元件。`MobileApp` 留下 14 個裝置／外殼 state ＋ 登入前的 6 個畫面；其餘（session、後端生命週期、登入後的 UI）移進子元件。**先不掛 `key`**，測試必須完全不變地綠。
- **2c**：`key={pubkey}` ＋ 刪掉 `signInWith` 內的逐簇 `reset`、刪掉世代守衛（ADR-0329）與它的掃描器。屆時：
  - `perIdentityState` 的「簇必須有 `reset()` 且被呼叫」規則要改成「子元件必須掛 `key`」；
  - ~~`asyncEpoch` 整支可以退場~~ 🔴 **這句話是錯的，見 §6.3**；
  - `refScope` 的簇規則保留（ref 仍要收尾，那是計時器洩漏，與身分無關）。

## 4. 🔴 校正：2b **不是**純搬家

§1 的表把 2b 寫成「語意無變化，只是換了檔案」。實際規劃時發現**那不成立**：

1. `key` 要能重設 session，session 就必須在子元件裡。
2. 後端的事件接線（`backend.start({ onContacts: roster.setContacts, … })`）**引用 session** ⇒ `start()` 也得跟著進子元件。
3. 於是登入的控制流必然反轉：

| | 現在 | 2b 之後 |
| --- | --- | --- |
| 登入 | 外殼畫面呼叫 `signInWith(identity)`，它**命令式地**建後端、重設、`start()` | 外殼只設定「作用中身分」，子元件**掛載時**在 effect 裡接線 |

**這個反轉正是 2c 能成立的原因**（掛載順序天然是「先有乾淨 state，才有後端灌入」，而那正是 ADR-0331 §1 否決 `useIdentityState` 時說的、React 掛載生命週期免費給的東西）。但它是語意變更，不是搬家。

⇒ 誠實的分工是：**2b 承擔控制流反轉，2c 只承擔「刪掉那些已經沒用的 reset」**。2b 的驗收標準因此不能是「測試不動就綠」，而是「**行為不變**，測試不動就綠」——兩者的差別在於前者是宣稱，後者要有覆蓋率支撐。

### 4.1 動刀前先補網（已完成）

2b 會切開的接縫是**登入／登出／切換**，而 ADR-0328 的互動測試原本只覆蓋「新增身分」與「切回來」。已補兩條：

- **登出後改登入另一個身分**：看不到上個身分的訊息與聯絡人。
- **軟登出回解鎖畫面**：聊天內容不再顯示。

⚠ 補的過程中我自己寫錯過一條斷言：原本斷言「登出後解鎖**同一個**身分，不該看到先前的訊息」——**那是錯的**。同一個身分的歷史本來就會從本機儲存回放，看得到才對。錯的是斷言，不是程式。已改成測「登出後換**另一個**身分」，那才是真正的不變式。

互動測試 5 → 8。

### 4.2 企業流程也補了（使用者選擇：先補網再動刀）

`signInWith` 有 7 個呼叫點，而**只有帶 `opts` 的那幾條會決定連哪座 relay、帶不帶入職權杖、是不是企業主**——那正是控制流反轉後最容易掉東西的地方。

| 路徑 | `opts` | 覆蓋 |
| --- | --- | --- |
| 一般登入／解鎖／切身分 | 無 | ✅ ADR-0328 |
| **建立公司** | `overrideOrg` | ✅ 本次 |
| **邀請碼入職** | `joinInvite` | ✅ 本次 |
| 離職接管 | `overrideRelay` ＋ `forceInvisible` | ❌ 需要先有託管事件（企業主端收到 `onOrgEscrow`），jsdom 內造不出來 |
| 配對搬家匯入 | `bundle` | ❌ 需要真的 WebRTC 配對握手 |

新增三條：建立公司落在名冊畫面（`createCompany` 在 `signInWith` **之後**覆寫畫面，那個順序反轉後最容易掉）、貼邀請碼切到入職模式並登入成功、**企業主的名冊入口不得跟著切到個人身分**。

⚠ 第三條刻意寫成**先驗有、再驗沒有**——只驗「個人身分看不到名冊入口」的話，那個入口就算從此消失、測試也一樣綠。

互動測試 8 → 11。**剩下兩條無法自動覆蓋的路徑（離職接管、配對匯入）列入 2b 的實機驗收項**，不假裝它們被測到了。

## 5. 2b 完成

### 5.1 檔案切法：外殼 vs 一個身分的 App

| 檔案 | 內容 |
| --- | --- |
| `MobileApp.tsx`（外殼） | **只放比一個 session 活得久的東西**：`profiles`（身分登錄——切身分時它必須存活，否則切完找不到要切去哪）、`theme`／`locale`／`accent`（這台裝置的偏好）、`active`（**指向 session 的指標**，本身不能住在 session 裡） |
| `AppSession.tsx` | 一個身分的全部：session state、後端生命週期、所有畫面 |

有守衛釘住外殼只有這 5 個 `useState`——**多出任何一個都要先回答「它憑什麼比 session 活得久」**。

### 5.2 控制流反轉

7 個 `signInWith(...)` 呼叫點全部改成 `onEnter(identity, opts)`；真正的接線移到一個以 `active` 為依賴的 effect。

`createCompany` 原本是「`signInWith` 末尾設 `main`、下一行覆寫成 `roster`」——**那個覆寫時機在反轉後不存在了**（接線改成非同步觸發）。改為把落點放進 `opts.landOn`，由接線完成時決定。這是 2b 唯一一處需要重新設計而非搬移的地方。

外殼的 `active` 帶一個 `gen`：**同一個身分重新登入也算新的一次 session**。2c 會把 `key` 綁在它身上，屆時「登出再登入自己」與「切到別人」一樣都會重掛。

### 5.3 🔴 搬家最容易發生、也最沒人會發現的事故

三支掃原始碼的守衛原本指著 `MobileApp.tsx`。本體搬走之後，它們會**掃到一個幾乎空的外殼並全部變綠**——測試從 444 條紅的變成 444 條綠的，而覆蓋率其實歸零。

已把目標檔集中到 `test/app-session-path.ts`，測試檔一併改名為 `AppSession.*.test.ts`。三支守衛本身都有反空轉檢查（state 總數、`.then(` 數量、ref 數量下限），所以掃到空檔會紅——**那些下限這次真的派上用場了**。

### 5.4 驗收

- 全 repo typecheck 綠、2120 測全綠、四個 app 建置成功。
- **11 條互動測試全綠**：登入／登出／切身分／切回來／建立公司／邀請碼入職／企業入口不跨身分。
- ⚠ **仍待實機驗收**（§4.2）：**離職接管**與**配對搬家匯入**——這兩條登入路徑帶 `opts` 但無法在 jsdom 驅動。2b 動到的正是它們共用的那條路，**沒有自動覆蓋這件事必須跟著版本一起走**。

### 5.5 已知的暫時瑕疵（2c 會消失）

2b 沒有 `key`，所以 `active` 變動時本元件不重掛，接線走的是 effect 依賴。effect 在 render 之後才跑 ⇒ 切身分時**有一個 render 的空窗**，畫面可能短暫停在舊 session 的狀態。

2c 掛上 `key` 之後，`active` 一變就是重掛，`screen` 與所有 session state 從**初值**開始（`useState` 的 initializer 已經讀 `active.opts.landOn`），空窗自然消失。**不另外修**——為一個下一步就會不存在的狀態加補丁，只會多一段要記得刪的程式碼。

## 6. 2c 完成——Phase P4 的結構性保證成立

### 6.1 一行 `key`

```tsx
<AppSession key={active ? `${active.session.identity.pubkey}:${active.gen}` : "none"} … />
```

換身分（`pubkey` 變）或重新登入同一個身分（`gen` 變）都讓 `AppSession` 重掛 ⇒ 7 個功能簇一律回到初值。

**這不是「記得呼叫重設」，是 React 的掛載語意。** ADR-0294 §2 抓到的三個漏網（`archived`／`purged`／`calDraft`）從此**不可能**再發生——不是「有守衛擋著」，是沒有那條路。

### 6.2 刪掉的東西

| 刪除 | 為什麼 |
| --- | --- |
| `signInWith` 內 4 個 `reset()`（call／threads／roster／cal） | 純歸零，重掛已涵蓋 |
| `logout` 內 `threads.reset()`／`self.clear()`／`clearTimeout` | 同上；只留真正的副作用（停後端、撤常駐通知） |
| 那 4 個簇的 `reset()`／`SelfSession.clear()` 方法本身 | **沒人呼叫了**。留著會讓下一個人以為那條路還在用 |
| 對應的單元測試（含整個 `use-roster-session.test.tsx`） | 測一個已刪除的方法＝測死程式碼 |

保留的是三個**帶種子**的：`self.reset(seed)`／`org.reset(seed)`／`settings.reset(seed)`。它們不是歸零，是**從後端與登錄檔讀出這個身分的值**（ADR-0331 §7 的三種語意），重掛給不了那些值。

### 6.3 🔴 校正：`asyncEpoch` 守衛**不退場**

§3 原本寫「2c 之後 `asyncEpoch` 整支可以退場——舊身分的落地寫進的是已卸載元件的 state，React 直接忽略」。

逐一檢查四個守衛點之後：**那個推論只對一半。**

- `openConvo → setArchived`：純 state 寫入 ⇒ 重掛涵蓋。✅
- `sendFileFromPicker`／`sendPhotoFromCamera`／`depositToSlot`：`.then` 裡呼叫的是**閉包抓住的舊後端**（`b.sendFile(...)`）。**元件卸載不會取消那個呼叫**——那是副作用，不是 setState。

⇒ 「React 會忽略已卸載元件的 setState」買到的是**狀態**那一半，**不是副作用那一半**。守衛與掃描器都保留（ADR-0329 §5 已記）。

憑「反正 React 會忽略」拆掉它，會**靜默地**讓後三個點失去保護。

### 6.4 守衛的演進：換對象，不刪

`perIdentityState` 裡那條「ADR-0294 §2 三個漏網」的回歸，斷言對象已經換過**三次**：

1. ADR-0294：`signInWith` 內有 `setArchived(`／`setPurged(`／`setCalDraft(`
2. ADR-0331：搬進功能簇 → `threads.reset(`／`cal.reset(`
3. ADR-0332 2c：`reset()` 已刪 → **它們住在會被重掛的地方**（簇 → 聚合物 → 被 `key` 掛住的 `AppSession`）

**每一次都是換對象，不是刪掉。一條回歸一旦被刪，那個 bug 就等於沒發生過。**

新增的規則：**外殼必須以作用中 session 當 `key`**（含身分與世代），以及「已無人呼叫的 `reset()` 不得留著」。

### 6.5 驗收

全 repo typecheck 綠、**2109 測全綠**、四個 app 建置成功；**11 條互動測試**（登入／登出／切身分／切回來／建立公司／邀請碼入職／企業入口不跨身分）全綠。

⚠ **仍待實機驗收**：離職接管、配對搬家匯入（§4.2）。
