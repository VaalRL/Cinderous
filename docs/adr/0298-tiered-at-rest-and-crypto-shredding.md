# 0298. 分層靜態保護與分段金鑰刪除（不是前向保密）

- 狀態：**提議中**（本文不改變任何產品行為；實作待決策）
- 日期：2026-07-30
- 相關文件：**0296**（否決「輪替 at-rest 金鑰」，並把本機暴露面導向裝置綁定金鑰——
  其 §3-A-3「使用者密碼」路徑被以「每次開 App 輸密碼」的可用性代價帶過，**本文主張那個前提不必成立**）、
  **0297**（裝置綁定可行性：Linux 與瀏覽器補不上 B 級——**本文填的正是那兩格**）、
  **0073**（忘記密碼救援：`rescue:{ns}` blob——**§2 指出它使本地密碼的靜態保障失效**）、
  0054（Tauri 加密儲存基質 `encstore.rs`）、0067／0112（本地密碼與 Argon2id 包裹）、
  0053（OS 金鑰庫＝A 級祕密儲存，非裝置綁定）、0111／0126（封存與保留上限）、
  0245（EK 與 at-rest 金鑰分離；「凡進持久備份的東西就不受保護」的同構張力）、
  0256（訊息搜尋，階段 3 封存搜尋）
- 資料來源：本倉庫程式碼查證（`at-rest.ts`、`storage/local.ts`、`storage/opfs-archive.ts`、
  `src-tauri/src/{encstore,keyvault,passlock}.rs`、`src-tauri/src/main.rs`）

> **這不是前向保密。** 本文提的是**靜態資料的區隔化**與**可靠刪除**，
> 針對的對手與 FS 完全不同（見 §5）。命名混用會讓文案超出實作。

## 背景與問題

### 1. 起點：0296 指出的方向，0297 說有兩格補不上

ADR-0296 正確地否決了「輪替 at-rest 金鑰」——本機 FS 與「歷史保得住」互斥，輪替繞不過。
它把本機暴露面導向 §7-1 的**裝置綁定金鑰**；ADR-0297 補做可行性後結論是
**B 級只在 Android／iOS／Apple Silicon Mac／有 TPM 的 Windows 可達，Linux 與瀏覽器補不上**。

而 0296 §3-A-3 列過第三條路——**使用者密碼**——但以「收益來自密碼、不是來自輪替」帶過，
並在〈已知限制〉自述「未考慮使用者密碼路徑的可用性代價（每次開 App 輸密碼）」。

**「每次開 App」正是它被放棄的唯一理由，而那個前提不必成立**（見〈決策〉§1）。

### 2. ⚠ 查證：桌面啟用本地密碼，**並沒有**取得「磁碟映像＋nsec 也解不開」

先更正一個容易的誤讀：桌面**不走** `deriveStorageKey`。
`deriveStorageKey(sk)` 只有 `storage/local.ts:101` 在用（瀏覽器與行動端）。
桌面走 `TauriStorage` → `encstore.rs`，資料金鑰是一把**隨機 32-byte AES 金鑰**，存 OS 金鑰庫。

啟用本地密碼時（`src-tauri/src/main.rs:464–471`）寫入三個條目：

| 金鑰庫條目 | 內容 |
|---|---|
| `{pubkey}` | Argon2id(password) 包裹的 nsec |
| `db:{namespace}` | Argon2id(password) 包裹的資料金鑰 |
| **`rescue:{namespace}`** | **`rescue_wrap(nsec, 資料金鑰)`** |

第三個是 ADR-0073 的忘記密碼救援，而 `rescue_key(nsec)` 就是 nsec 的域分隔雜湊。

⇒ **拿到磁碟映像 ＋ 金鑰庫 ＋ nsec，可繞過密碼直接解開整個資料庫。**
密碼在這條路徑上完全不參與。

**這一條已有實證，不是讀碼推論**：`passlock.rs` 的
`adr0298_rescue_blob_bypasses_the_password` 走完整條鏈——
照 `main.rs:464–471` 產生三個金鑰庫條目與一份 `encstore` 磁碟 blob，
先確認錯密碼解不開兩個包裹（密碼保護本身有效），
再**只用 nsec ＋ 救援 blob** 取回同一把資料金鑰、解出明文；
對照組以錯的 nsec 失敗，確認前一步不是測試寫鬆。

這是刻意的設計取捨，不是缺陷。但它的後果過去沒有被寫下來：
**「我啟用了本地密碼」不等於「磁碟被複製也解不開」**——這與 ADR-0297 §2 更正
「OS 金鑰庫不等於裝置綁定」是同一類的誤讀，只是更深一層。

### 3. ⚠ 查證：保留上限提供的刪除保障，比使用者以為的弱

`opfs-archive.ts:104` 的刪除是 `this.dir.removeEntry(key)`——**檔案系統刪除**。
在 flash 儲存與日誌式檔案系統上，刪除檔案**不保證底層區塊被抹掉**。

而所有封存共用**同一把**由 nsec 決定性導出的金鑰
（`deriveStorageKey` ＝ `hkdf(sha256, sk, undefined, INFO, 32)`，**無 salt、無分段**）。

⇒ 任何殘留區塊，**只要拿到 nsec 就仍然解得開**。
ADR-0126 的保留上限、0013 的限時訊息、0234 的無痕收回，
**三者的刪除保障都因此打折**——而 ADR-0296 §7-2 正是建議「把它們當成 local FS 的正解」。

### 4. 根秘密住在哪，決定暴露面——而它平台不對等

| 平台 | 資料金鑰的根 | 只拿磁碟映像（無 nsec、無密碼） | 磁碟映像 ＋ nsec |
|---|---|---|---|
| Tauri 桌面（無密碼） | OS 金鑰庫明文 | 取得金鑰庫即可解 | 可解 |
| Tauri 桌面（**有**密碼） | Argon2id(password) | 解不開 | **仍可解**（§2 救援 blob） |
| 瀏覽器 | nsec（Argon2id 包裹落地） | 解不開 | 可解 |
| 行動端 | nsec（Argon2id 包裹落地，sk 只在記憶體） | 解不開 | 可解 |

⇒ **沒有任何平台今天擋得住「磁碟映像 ＋ nsec」**，這正是 ADR-0296 §3 的威脅模型。

## 考量的選項

- **A：輪替 at-rest 金鑰**——ADR-0296 已否決（本機 FS ⟷ 歷史保得住互斥）。不重議。
- **B：裝置綁定金鑰（0297 的 L2）**——有效，但**四平台原生矩陣**，Linux 與瀏覽器永遠補不上，
  且行動端整段卡在真 RN 移植（0290 §1）。
- **C（本文）：分層靜態保護 ＋ 分段金鑰**——純軟體、跨平台一致、可與 B 疊加。

B 與 C 不互斥：C 換掉的是「根秘密所在地」，B 換掉的是「根秘密的保管硬體」。

## 決策

### 1. 本機資料分成熱層與冷層，用不同的根保護

| 層 | 內容 | 金鑰的根 | 何時需要密碼 |
|---|---|---|---|
| **熱層** | 近 N 天訊息 ＋ 聯絡人／群組／設定等日常必需 | 沿用今日各平台現況 | 不變 |
| **冷層** | OPFS 封存（歷史的大宗） | **Argon2id(密碼)**，**不由 nsec 導出、不由資料金鑰導出** | 只有存取封存時 |

**「每次開 App 輸密碼」的前提就是在這裡被拆掉的**：日常操作只碰熱層。

而在**已經有登入密碼的平台**（瀏覽器、行動端、以及啟用本地密碼的桌面），
冷層金鑰可於解鎖時一併導出並留在記憶體 ⇒ **零額外提示**。
只有「桌面且未啟用本地密碼」的使用者，才會在存取封存時第一次看到密碼框。

### 2. 冷層按時間分段，每段一把**隨機**金鑰，各自包裹

> **⚠ 本節已更正（2026-07-30）。** 初版寫的是「分段金鑰各自由冷層根金鑰導出
> （`HKDF(root, salt=段識別碼)`）」——**那樣 crypto-shredding 不成立**：決定性導出
> 意味著只要有密碼就能**重新導出**那把段金鑰，「丟棄」什麼都沒達成。
> 差別就在**金鑰是導出的還是包裹的**：導出＝密碼在手即可重建；包裹＝刪掉包裹就永久失去。
> 這是這個機制成立的唯一條件，不是措辭問題——照初版實作出來的東西不會有刪除效果。

```text
K_root   = Argon2id(password, salt_cold)      # salt 落地，裝置本地
K_seg(p) = 隨機 32 bytes                       # 每個段落 p 建立時生成
索引     = { p → wrap(K_root, K_seg(p)) }      # 落地，裝置本地
封存塊   = sealValue(K_seg(p), json)           # 檔名帶段識別碼，讀取時才知道用哪把
```

- **讀取**：輸密碼 → `K_root` → 解包該段的 `K_seg(p)` → 解塊。
- **丟棄段落 p**：**刪掉索引裡 p 那筆包裹**。`K_seg(p)` 從此不可復原，殘留區塊變成
  不可解的亂數——**即使攻擊者有密碼也解不開**。

這才是在無法保證實體抹除的介質上唯一可靠的刪除方式（crypto-shredding）。

⇒ 讓 ADR-0126／0013／0234 的刪除**真的等於刪除**（§3 的缺口）。

### 3. ⚠ 冷層**預設不提供 nsec 救援**，且此選擇必須明示

> **⚠ 本節的範圍隨 §2 的更正縮小了（2026-07-30）。** 初版寫「分段刪除同理——救援 blob
> 還在，丟掉分段金鑰就沒有意義」。那在**導出式**的初版構造下成立（有 `K_root` 就能重新
> 導出 `K_seg`）；改成**包裹式**之後**不再成立**：丟棄＝刪掉 `wrap(K_root, K_seg(p))`
> 這筆索引，即使拿到 `K_root`（無論來自密碼或救援 blob），`K_seg(p)` 一樣不可復原。
>
> ⇒ 救援路徑的影響因此**只剩機密性一項**，不影響刪除：
>
> | 目標 | 有救援路徑 | 無救援路徑 |
> | 對「磁碟映像＋nsec」的機密性 | ❌ 等於零 | ✅ 有效 |
> | 分段刪除（crypto-shredding） | ✅ **仍然有效** | ✅ 有效 |
>
> 這讓取捨變乾淨：**只想修好「保留上限不等於刪除」那個缺口（§3）的人，可以保留救援路徑
> 而不失去刪除保障。** 只有想擋「磁碟映像＋nsec」的人才必須放棄救援。

（殘留：**更早的磁碟映像**裡索引還有那筆包裹，配上密碼仍解得開已丟棄的段落。
任何刪除機制都無法回收已被複製出去的資料，這一點無法靠設計解決，只能寫清楚。）

因此：

- **熱層保留救援**（日常資料丟失代價高，且它本來就常在多裝置間流動）。
- **冷層預設不救援**。啟用時必須跳一次誠實揭露：
  **忘記密碼 ＝ 冷層歷史永久失去，nsec 也救不回。**
  （比照 ADR-0245 §5 對換鑰彈窗的規定。）
- 允許使用者**明確選擇**替冷層開啟救援——那等於放棄本文的保障，
  但那是知情的選擇，不是預設替他決定。

### 4. 命名紅線：不得稱為前向保密

對外文案與 UI 一律用「**封存加密／獨立密碼保護**」與「**永久刪除**」，
**不得**使用 FS／前向保密字樣，亦不得暗示「裝置被入侵也安全」。
本機這側不存在 forward 性質——見 §5。

### 5. 保護範圍（必須照這個講）

| 對手 | 本設計 |
|---|---|
| 取得磁碟映像（偷硬碟、備份外洩、舊機沒清） | ✅ 冷層解不開 |
| 取得磁碟映像 **＋ nsec** | ✅ 冷層仍需密碼（這是 §4 表中今天**沒有任何平台**擋得住的那一格） |
| 中繼囤積傳輸密文，日後取得長期金鑰 | ❌ **完全沒碰**——那是 FS 的題目（ADR-0245／0290） |
| 以你的身分正在執行的惡意程式 | ❌ 擋不住（解鎖時可側錄密碼；同 ADR-0297 §5 的限界） |

**沒有 forward 性質**：今天被攻破不會保護昨天。它是區隔化，不是前向保密。
唯一不可逆的部分是 §2 的分段丟棄——對**已丟棄**的段落，事後拿到 nsec 也解不開。

## 理由

- **填得到 0297 補不上的兩格**：純軟體，Linux 與瀏覽器同樣適用。
- **成本落點與收益落點一致**：唯一多付提示的是「桌面且未啟用本地密碼」的使用者，
  而那正是 §4 表中保障最弱的一格。
- **與 B 級疊加而非競爭**：日後桌面上了 TPM／SE，熱層可升級到裝置綁定，冷層設計不變。
- **順帶修好一個沒人記過的缺口**（§3 的刪除保障）。

## 後果

**正面**

- 首次讓「磁碟映像 ＋ nsec」這一格有防線（§4 表顯示今天全平台皆無）。
- 保留上限／限時訊息／無痕收回的刪除保障變成真的，**而且這一項不需要放棄救援路徑**
  （§3 的更正）——想修刪除缺口與想擋磁碟映像是兩個可以分開採納的目標。
- 歷史**不會失去**——不落進 ADR-0296 §3 的二選一，因為沒有刪任何還想留的金鑰，
  只是換了根秘密的所在地。

**負面／代價**

1. **新增一種資料遺失方式**：桌面版今天忘記密碼不會失去任何東西（有 §2 的救援）；
   本設計之後，忘記密碼 ＝ 冷層歷史永久失去。這是**刻意的**，但必須明示。
   （瀏覽器與行動端本來就是這個性質，桌面是第一次面對。）
2. **一次性遷移**：既有封存需整批重新加密一次。可背景執行、可中斷續跑，
   但歷史大時是重量級操作，**中途失敗有寫成新舊混雜的風險**——需要明確的遷移狀態機。
3. **⚠ 搜尋的誠實問題（紅線）**：ADR-0256 的封存搜尋若在未解鎖時只搜熱層，
   **不得顯示「找不到」**——必須明說「已搜尋近 N 天；更早需解鎖封存」。
   靜默縮小搜尋範圍等於 UI 說謊。
4. **匯出**（`export.ts:66` 的 `loadAllArchived`）需要冷層解鎖。
5. **金鑰數量上升**：分段越細，管理成本越高。

**未定參數（實作前須決定）**

- **N（熱層天數）**：太短→常要解鎖；太長→保障範圍縮小。傾向與 ADR-0126 的保留上限**脫鉤**、
  獨立設定，預設 30–90 天之間。**無使用數據支撐，這是猜測。**
- **分段粒度**：決定 crypto-shredding 的丟棄精度（按月＝一次丟一個月）。

**已知限制**

- **本文為設計提案，未實作、未測量**。遷移耗時、Argon2id 在各平台的解鎖延遲皆未評估。
- ~~§2 的救援 blob 分析基於程式碼閱讀，未實際驗證~~ → **已補做實證**
  （`passlock.rs::adr0298_rescue_blob_bypasses_the_password`；Rust 測試 24 項全綠）。
  §2 的前提成立。
- ~~§3 的刪除缺口基於程式碼閱讀~~ → **已補做特徵化測試**
  （`storage/archive-residue.test.ts`）：把「刪除只移索引、位元組留在介質上」模型化，
  證實**殘留仍能用同一把 `deriveStorageKey(sk)` 解開**、金鑰決定性且無 salt（任何年代的殘留
  都用得上同一把）、且所有塊共用一把（想「只丟棄去年」在今天的構造下做不到）。
  分段金鑰實作後該測試會紅，屆時把斷言翻正為「殘留解不開」。
- **刻意不驗「位元組是否真的從實體介質消失」**。flash 的耗損平均與預留空間讓軟體沒有可靠
  手段保證抹除——那是已確立的硬體事實，引用即可。用 VM 去「驗證」會得到漂亮但不成立的
  結論（虛擬磁碟沒有耗損平均、也沒有預留空間），那比不驗更糟。
  ⇒ 主張切成兩半：**「殘留可解」是我們的設計缺陷（已測）**，「殘留存在」是介質特性（不測）。
- 未評估企業情境：受管裝置可能有金鑰託管要求，與「冷層不可救援」衝突（同 ADR-0297 的殘留問題）。

4. **既有缺口的獨立處置（與本 ADR 是否採納無關）**：§2 的救援 blob 是 ADR-0073 的刻意設計，

   本設計補的是另一條軸，不能拿來聲稱補齊了 FS。
