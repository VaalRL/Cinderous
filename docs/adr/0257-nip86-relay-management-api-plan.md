# 0257. NIP-86 Relay 管理 API 的規劃（提議中，未實作）

- 狀態：**提議中（規劃；接受後為實作依據）**
- 日期：2026-07-27
- 相關文件：ADR-0255 §2.3（本 ADR 是其展開）、0253 §4.2（託管營運＝主要收入項，需要管理面）、
  **0044**（企業封閉 allowlist）、**0047**（管理者簽章名冊＝成員權威）、0048（政策 `allowedKinds`）、
  0052／0163（輪替與離職）、0057（NIP-42）、0256（NIP-11 `supported_nips`）；
  `relay/src/relay-core.ts`（`allowedAuthors`／`allowedKinds` 目前的注入點）

## 背景與問題

目前 relay 的成員與政策管制**只有部署期入口**：

| 能力 | 現況注入點 | 問題 |
|---|---|---|
| 成員 allowlist | `RelayCoreOptions.allowedAuthors`（由名冊匯出、部署時佈建） | 改一個人要重新佈建／重啟 |
| 事件類型政策 | `allowedKinds`（同上） | 同上 |
| TTL／檔案開關 | `MAX_TTL_DAYS`／`MAX_FILE_MB` 環境變數 | 同上 |

ADR-0253 把「託管營運」列為唯一有毛利的收入項，而託管必然需要**執行期**的管理面：客戶打電話
說「小明今天離職」，你不該需要一次部署。NIP-86 已經把這件事定義好了（HTTP＋NIP-98 授權＋
一組方法名），不必自創。

**但直接照抄會撞上本專案的信任模型**，這是本 ADR 要先解的。

## 核心張力：誰是成員的權威？

- **本專案**：權威是**管理者簽章的名冊**（ADR-0047，kind 10038）。信任根＝管理者金鑰，
  **客戶端可自行驗簽**；relay 只是執行者，且**被視為對手**。`rosterAllowlist(doc)` 是單一真實來源。
- **NIP-86**：`allowpubkey`／`banpubkey` 讓 **relay 營運者**直接改 allowlist。信任根＝營運者。

兩者若並存，就會有**兩個真實來源**：名冊說 A 是成員、relay 說不是。而下一次名冊佈建又會把
營運者的手動修改蓋掉——這種「靜默互相覆蓋」正是最難查的那類 bug。

## 決策（提議）

**採用 NIP-86 作為「名冊 → relay」的執行管道與唯讀觀測面，不讓它成為獨立權威。**

### 1. 成員類方法：唯讀 ＋ 由名冊推導

- `listallowedpubkeys`／`listbannedpubkeys`：**實作**（唯讀，運維要看得到現況）。
- `allowpubkey`／`unallowpubkey`／`banpubkey`／`unbanpubkey`：**不實作**，回 NIP-86 的錯誤，
  並在錯誤訊息指向名冊流程。
  - 理由：成員資格的唯一入口必須是**簽章名冊**，否則 ADR-0047 的「客戶端可驗證成員資格」
    這個性質就破了——relay 能悄悄加人，而客戶端驗不出來。
- 新增**本專案專屬**方法 `cinder_applyroster`：吃一份**管理者簽章的名冊事件**，relay 驗簽
  （`verifyOrgRoster`）＋`shouldAdoptRoster`（較新才取代）後，以 `rosterAllowlist` 更新
  `allowedAuthors`。**這才是執行期改成員的正途**：權威仍是簽章，只是送達方式從「重新佈建」
  變成「一次 API 呼叫」。

### 2. 政策類方法：可寫（那本來就是站方的權責）

- `allowkind`／`disallowkind`／`listallowedkinds`：**實作**——事件類型政策（ADR-0048）本來
  就是站方決策，不涉及「誰是成員」的可驗證性。
- `changerelayname`／`changerelaydescription`：**實作**，直接改 NIP-11 文件（ADR-0256）的對應
  欄位。需要一個小的持久化（目前 NIP-11 內容全部來自啟動時的環境變數）。

### 3. 明確不實作

| 方法 | 理由 |
|---|---|
| `createrole`／`editrole`／`deleterole`／`assignrole`／`unassignrole` | 本專案沒有角色概念；成員資格是二元的（在名冊／不在名冊） |
| `listeventsneedingmoderation`／`allowevent`／`banevent`／`listbannedevents` | **中繼看不到內容**（全是 Gift Wrap 密文）。「審核事件」在本專案不可能，提供這些方法等於暗示 relay 讀得懂內容 |
| `blockip`／`unblockip`／`listblockedips` | 引入以 IP 為單位的封鎖清單＝relay 開始持有**連線層可識別資料**，與 ADR-0237（元資料可連結性）方向相反。DDoS 防護交給 Cloudflare／反向代理那一層，不進協定面 |
| `changerelayicon` | 無此需求 |

### 4. 授權：NIP-98，但金鑰不是管理者金鑰

NIP-86 要求 `Authorization` 帶 NIP-98 事件。**授權金鑰必須與管理者名冊金鑰分離**：

- 名冊金鑰＝**組織的成員權威**，離線保管、只用來簽名冊（ADR-0047 的信任根）；
- 管理 API 金鑰＝**這台機器的運維憑證**，放在託管方（ADR-0253 的服務商）。

不分離的話，把運維外包就等於把組織的成員權威交出去。這條是本 ADR 最重要的一句。

### 5. 宣告

`supported_nips` 加 86（ADR-0256 的文件），並以 `supportedmethods` 誠實回報**實際實作的子集**
——NIP-86 本來就設計了這個方法，用它比「宣告支援卻半數方法回錯誤」誠實。

## 考量的選項

- **選項 0：不做，維持部署期佈建。** 零工，但託管服務每次改成員都要一次部署——ADR-0253 的
  單位經濟裡，人力才是天花板，這正好打在天花板上。
- **選項 1（採用）：NIP-86 子集＋`cinder_applyroster`，成員唯讀。** 拿到執行期管理面，
  同時保住 ADR-0047 的可驗證成員資格。
- **選項 2：完整實作 NIP-86，讓 relay 成為成員權威。** 生態相容性最好，但破壞 ADR-0047 的
  信任模型（relay 可悄悄加人、客戶端驗不出來），且與名冊佈建互相覆蓋。否決。
- **選項 3：自創管理 API。** 不必解相容性問題，但要自己定義授權、方法名、錯誤語意——
  NIP-86 已經定義好了，重造只是多一份要維護的東西。

## 後果（若接受）

- 正面：託管服務有了執行期管理面（ADR-0253 §4.2 的必要條件）；成員權威仍在簽章名冊，
  企業客戶「誰能改成員名單」這題的答案不變。
- 負面 / 已知殘餘風險：
  - **部分實作**：宣告支援 NIP-86 但半數方法不提供，通用管理工具可能出現半殘的 UI。
    以 `supportedmethods` 誠實回報緩解。
  - **多了一個對外 HTTP 面**：新的攻擊面（NIP-98 驗證、方法分派）。須比照 ADR-0235 的
    資源上限與例外圍籬處理，且**預設關閉**（未設管理金鑰＝端點不存在）。
  - `cinder_applyroster` 是**非標準**方法，只有本專案的工具會用。
  - 分片（ADR-0241）下管理操作要作用到**所有分片 DO**——`allowedAuthors` 目前是每個 DO
    各自從設定建構的，執行期更新需要一條跨分片的傳播路徑。**這是實作前必須先解的問題**，
    也是本 ADR 維持「提議中」的主因。
- 後續行動（實作前需完成）：
  1. 解決分片下的設定傳播（可能需要一個共享的設定 DO 或 KV，並與 ADR-0241 的血條隔離取捨）。
  2. 定義 `cinder_applyroster` 的請求／回應格式與錯誤碼，補 core 端的驗證共用函式。
  3. 決定管理金鑰的佈建方式（`wrangler secret`／環境變數）與輪替流程。
  4. 決定 NIP-11 可變欄位的持久化位置（目前全部來自啟動時環境）。
