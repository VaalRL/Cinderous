# 0297. 裝置綁定金鑰的跨平台可行性（研究記錄）

- 狀態：**研究記錄（未決策，本文不改變任何產品行為）**
- 日期：2026-07-28
- 相關文件：**0275**（否決「輪替 at-rest 金鑰」，並把本機暴露面導向裝置綁定金鑰——
  其 §7-1 明載「**未做可行性評估**」，**本文補做**）、**0053**（OS 金鑰庫——
  **§2 更正一個對它的可能誤讀**）、0112（靜態加密與瀏覽器 Argon2id 包裹）、
  0245（EK 與 at-rest 金鑰分離）、0269 §1（真 RN 移植＝行動端一切原生能力的前置）
- 資料來源：各平台官方文件與技術資料（擷取於 2026-07-28）＋本倉庫程式碼查證

> **結論：技術上可行，但平台不對等是真的、而且比 ADR-0296 §7-1 猜的更嚴重**——
> **Linux 與瀏覽器這兩格沒有可攜的方案**，所以這永遠只能是**分級保障**，不能統一宣稱。
> 另外查出一件更要緊的事：**我們今天用的 OS 金鑰庫並不提供這個保護**（§2）。

## 1. 先把兩個等級分開——整份評估都靠這個區分

| 等級 | 機制 | 對手拿到磁碟映像時 |
|---|---|---|
| **A. 祕密儲存** | Windows Credential Manager（DPAPI）、macOS Keychain、Linux Secret Service | 金鑰**位元組會被取回**（受 OS ACL／登入祕密保護，不是硬體）⇒ 拿得到就解得開 |
| **B. 不可匯出金鑰** | TPM 2.0、Secure Enclave、Android StrongBox/TEE | 私鑰**永不離開晶片**，只能請它 sign／decrypt／derive ⇒ **複製磁碟拿不到金鑰** |

ADR-0296 §7-1 要的是 **B**。**A 給不了那個保障。**

## 2. ⚠ 更正對現況的理解：我們今天在 A，不在 B

`apps/desktop/src-tauri/src/keyvault.rs` 用 `keyring` crate ⇒
Windows Credential Manager／macOS Keychain／Linux Secret Service。**三者都是 A 級。**

Windows 那格特別值得講清楚：**Credential Manager 以 DPAPI 加密，而 DPAPI 是以使用者/機器祕密
做對稱加密**——與 TPM 支援的 `NCrypt` + Microsoft Platform Crypto Provider 是**不同的東西**。

⇒ **「我們已經把 nsec 放進 OS 金鑰庫」不等於「複製磁碟也沒用」。**
ADR-0053 提供的是「**不明文落盤**」，那是真的、也有價值；
但它**不是**「裝置綁定」。這個區別過去沒有寫下來，容易被讀成後者。

瀏覽器那格則是另一條路：`native/keyvault.ts` **只接受 Argon2id 包裹的 blob、拒絕明文落盤**
（ADR-0112 紅線）⇒ 根秘密是**使用者密碼**，不是裝置。

## 3. 各平台能力盤點

| 平台 | 最強可用機制 | 等級 | 能包住我們的 DEK 嗎 | 關鍵限制 |
|---|---|---|---|---|
| **Android** | Keystore／**StrongBox**，**原生支援 AES** | **B** | ✅ **直接**（AES 金鑰本身不可匯出） | StrongBox 需 API 28+ 且 `FEATURE_STRONGBOX_KEYSTORE`；不支援會丟 `StrongBoxUnavailableException` ⇒ **必須有 TEE 退路**。`setUnlockedDeviceRequired(true)` 可要求解鎖才可用 |
| **iOS** | **Secure Enclave** P-256 ＋ ECIES | **B** | ✅ **間接**：以 SE 金鑰 `SecKeyCreateDecryptedData`＋`eciesEncryptionCofactorX963SHA256AESGCM` 解封 DEK | ⚠ **SE 只支援 P-256，沒有對稱金鑰**——不能把 AES DEK 直接放進去，只能用 ECIES 包。`…ThisDeviceOnly` 可禁止備份/遷移 |
| **macOS** | Secure Enclave（T2／Apple Silicon）；否則 Keychain | **B／A** | ✅ 有 SE 時同 iOS | **Intel 舊機無 SE** ⇒ 同一個 OS 兩種保障 |
| **Windows** | CNG ＋ **Microsoft Platform Crypto Provider**（TPM 2.0）：`NCryptCreatePersistedKey`，私鑰永不離晶片、只能 sign/decrypt/derive | **B** | ✅ **間接**（TPM 金鑰解封 DEK） | 需 TPM 2.0；**換 provider 不是換設定**，等於重寫金鑰庫那一層 |
| **Linux** | Secret Service（gnome-keyring／KWallet）＝檔案＋登入密碼解鎖 | **A** | ❌ | **沒有可攜的 B 級路徑**（TPM 可行但非標準、桌面環境差異大） |
| **瀏覽器** | WebCrypto `extractable: false` 的 `CryptoKey` 存 IndexedDB | **半級** | ✅ 對 **JS** 不可讀 | ⚠ **見 §4——對本文的威脅模型幾乎無效** |

## 4. ⚠ 瀏覽器那格：它擋的是**另一個**威脅

`crypto.subtle.generateKey(…, extractable: false, …)` 產生的 `CryptoKey` 可存進 IndexedDB，
金鑰位元組**不暴露給 JS**。這是真的保護——**擋得住 XSS 把金鑰偷走**（攻擊者能在頁面存活期間
*使用*它，但帶不走）。

**但它不是硬體綁定**：金鑰材料由瀏覽器存在它自己的 profile 目錄裡。
⇒ **對手取得磁碟映像仍可從瀏覽器 profile 取出**，而那正是 ADR-0296 §3 的威脅模型。

**結論：瀏覽器版拿不到 B 級保障。** 它能拿到的是「防 XSS 竊鑰」（有價值，但是不同的題目），
以及現有的 Argon2id 密碼路徑（根秘密＝使用者記在腦子裡的東西，某種意義上比裝置更強，
代價是每次要輸入）。

## 5. ⚠ 就算全做到 B 級，保護範圍也要講清楚

**裝置綁定金鑰擋的是「離線攻擊」，不是「線上攻擊」**：

- ✅ **擋得住**：偷走硬碟／取得磁碟映像／備份外洩／舊機沒清乾淨；
- ❌ **擋不住**：以你的身分**正在執行**的惡意程式——它可以直接呼叫 API 請 TPM/SE 解密。
  （`setUnlockedDeviceRequired`／生物辨識可以提高門檻，但不能消除。）

⇒ 文案只能說「**磁碟被複製也解不開**」，**不能說「裝置被入侵也安全」**。

## 6. 可行的設計形狀：分級 ＋ 誠實揭露

因為 §3 的不對等無法消除，唯一誠實的做法是**分級**：

| 層級 | 平台 | 保障 |
|---|---|---|
| L2 裝置綁定 | Android（StrongBox/TEE）、iOS、Apple Silicon Mac、有 TPM 的 Windows | 磁碟被複製也解不開 |
| L1 密碼包裹 | 瀏覽器（現況）、無 TPM 的 Windows／Intel Mac 的退路 | 解不開除非拿到密碼 |
| L0 祕密儲存 | Linux、其餘退路 | 不明文落盤（＝今天的水準） |

**紅線**：降級必須**可見**（比照 ADR-0245 的降級偵測），不得靜默退到 L0；
且**設定頁要如實顯示目前這台裝置在哪一級**——否則等於用最強平台的說法涵蓋最弱平台的現實。

## 7. 成本與相依

- **這不是一個功能，是一張平台矩陣**：Windows（CNG/PCP）、Apple（Security framework SE）、
  Android（Keystore）各要一套原生實作＋各自的退路判斷，Linux 與瀏覽器維持現狀。
- **行動端整段卡在真 RN 移植**（ADR-0290 §1）——與推播同一個前置。
  `react-native-web` 拿不到 Keystore／SE。
- **桌面 Windows 那格是重寫金鑰庫層**，不是加個參數（`keyring` crate → 直接用 CNG）。
- **可以只做一格**：Android 的性價比最高（原生支援對稱金鑰＝**直接**包 DEK，不必繞 ECIES），
  但它同時是最需要真 RN 的那一格。

## 決策（研究記錄，未決策）

- 本文**不改變任何產品行為**，只補完 ADR-0296 §7-1 缺的評估。
- **可行性結論：B 級技術上可達，但只在四個平台上；Linux 與瀏覽器補不上。**
  因此它**永遠是分級保障**——這一點必須在採納前就接受，否則文案會超出實作。
- 建議：若要動，**先做 §6 的分級與可見化（純 UI/狀態，成本低）**，
  讓「這台裝置目前的保護等級」成為使用者看得到的事實；
  各平台的 B 級實作再依真 RN 移植與桌面重構的節奏分別排。

## 後果

- 正面：補完 ADR-0296 的缺口；**更正一個對 ADR-0053 的可能誤讀**（OS 金鑰庫＝不明文落盤，
  不是裝置綁定）；把「平台不對等」從擔憂變成具體的四級矩陣。
- 已知限制：
  - **全部為文件研究，未在任何平台實作或實測**。尤其 TPM／SE 的**效能**（每次開機解封 DEK
    的延遲）與**失敗模式**（TPM 被清除、換主機板、SE 因還原而失效 ⇒ **金鑰永久遺失**）
    完全沒有評估——**後者是產品風險**：裝置綁定的反面就是「裝置壞了資料就沒了」，
    必須有備份路徑（而備份路徑又會回到 ADR-0245 §2 的張力：進備份的東西就不受裝置保護）。
  - Android StrongBox 的實際普及率、iOS SE 在舊機型的可用性，**未查數據**。
  - 未評估企業情境：受管裝置（MDM）可能有自己的金鑰託管要求，與裝置綁定衝突。
- 後續行動（**皆待決策**）：
  1. 若採納，先立 ADR 定義**分級與降級可見化**（§6），那是跨平台共用的部分。
  2. 評估「裝置綁定 vs 可還原」的張力——這是本文最大的未解問題，且它與 ADR-0245 §2
     的「備份碼身分-only」是同一個結構。
  3. **與 ADR-0298 一起看**（後續補記）：0298 的分段金鑰把「要銷毀的東西」從**整個歷史**
     縮到**幾百 bytes 的金鑰材料**，而本文提供的 B 級是**唯一能把那幾百 bytes 真正銷毀**
     的地方（軟體刪除在 flash 上留殘留，再包一層只是遞迴）。
     ⇒ 兩者互補：**0298 讓刪除可選擇，0297 讓刪除可保證**；只做 0297 則沒有分段、
     無從選擇性刪除。見 ADR-0298 §6。
