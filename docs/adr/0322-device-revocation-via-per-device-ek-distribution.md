# 0322. 裝置撤銷：per-device **分發**（而非 per-device session）＋簽章裝置目錄

- 狀態：已接受（**設計與分階段**；S1 以後逐階段實作，各階段獨立有價值）
- 日期：2026-08-03
- 相關文件：**ADR-0303（裝置目錄的選項空間、§6.2b 配對已具備授權性質、§7 清單住在哪——**該節標題的「未決策」已於 2026-08-03 更正為「已決（選項 4）」**）**、
  ADR-0321（E-lite 觀測清單＝本文的前身與其盲點）、ADR-0245／0313（EK 與自動輪替）、
  ADR-0072／0118（配對）、ADR-0071（加密雲端快照）、ADR-0297（平台金鑰分級）、
  ADR-0052（身分輪替＝目前唯一的撤銷原語）

## 背景與問題

ADR-0321 把「我有哪些裝置」變成看得見的，但清單只能看、不能動：
**看到一台可疑裝置，使用者能做的只有換 nsec。**

而「撤銷」在共用 nsec 的模型下，字面上不成立——那台裝置手上的東西與你這台一模一樣。

## 🔵 讓 L3 變得負擔得起的關鍵發現

ADR-0303 把「per-device **session**」當成入場費，並據此估出「棘輪要動到配對、快照、備份、名冊」
的成本。那個估計對**棘輪**是對的。

**但撤銷不需要 per-device session。** 撤銷需要的只是：

> **讓「讀新訊息的金鑰」不再是每台裝置自動拿得到的東西。**

我們已經有那把金鑰——ADR-0245 的 EK。它與 nsec 分離、每 7 天輪替（ADR-0313）、
寄件人已經 retarget 到它。**唯一的漏洞在分發**：

```
EK 私鑰 → 進加密雲端快照 → 快照加密到 **nsec 導出金鑰** → 任何有 nsec 的裝置都拿得到
```

⇒ **把 EK 的分發從「加密到 nsec」改成「加密給目錄內每台裝置的公鑰」，撤銷就成立了**
——身分層仍然只有一把 EK（不是 per-device session），只是**送法**變成點對點。

這比 ADR-0303 設想的入場費小一個層級。

## 🔴 先講清楚 L3 買不到什麼

1. **nsec 仍然是目錄的簽章根。** 持有 nsec 的攻擊者**簽得出一份競爭目錄**（ADR-0303 §6 已指出
   「任何一台被攻陷的裝置都簽得出 v+1」）。
   ⇒ 對**完整 nsec 外洩**，L3 給的是**偵測**（同版本兩份不同目錄＝證據），**不是防止**。
   真正的解仍是 ADR-0052 換身分。
2. **歷史救不回。** 撤銷只讓它讀不到**之後**的訊息；已經抄走的密文與已解密的歷史不受影響。
3. **入侵當下的窗關不掉**（ADR-0303 §6.7-1b）：攻擊者若在你的裝置上有執行權，
   他可以直接操作配對 UI，而 **SAS 是他自己跟自己比對的**。
4. **裝置金鑰目前是明文存放**（2026-08-04 校正）⇒ **在所有平台上**，磁碟被複製即可繞過撤銷。
   `getDeviceKey()` 走 `getKv()`＝localStorage／MMKV，**沒有加密**——那**低於 ADR-0297 的 L0**
   （L0 的定義是「不明文落盤」）。
   ✅ **已依 ADR-0297 §6 紅線如實顯示**（2026-08-04）：`deviceKeyTier()` 回報**實作現況**
   而非平台能力（猜平台會給出比實情好看的答案，那正是紅線要擋的），兩端設定頁顯示，
   明文時直接寫出後果：「**這種情況下「移除裝置」擋不住他**」。
   ✅ **已修（ADR-0323，2026-08-04）**：Tauri＝OS 金鑰庫；Android 原生殼＝AndroidKeyStore
   （有 TEE 才算 `keystore`，軟體實作只算 `encrypted`——兩者不得混講）。
   ⏳ **瀏覽器仍是明文**，撤銷在那裡仍可被繞過——設定頁如實顯示。
   ⚠ 屆時文案仍**不得**宣稱「裝置被入侵也安全」（ADR-0297 §5）——已寫在 `keystore` 那段文案裡。

⇒ **L3 真正買到的是最常見的那個情境**：裝置遺失／被偷／舊機沒清乾淨／離職員工的公司機。
那些情況下攻擊者拿到的是**一台裝置**，不是 nsec 本身——而在 L2 平台上，
那台裝置的金鑰不可匯出 ⇒ 把它移出目錄，它就真的讀不到新訊息。

## §7 的分歧為何不約束撤銷（並更正本文初稿）

⚠ **本文初稿寫「ADR-0303 §7（清單住在哪）未決策」——那是照抄該節的過期標題。**
§7.4 表格早已把選項 4 標為「採用，2026-07-31」，§7.4b 也寫著「§7 現在就能決」。
（該標題已於 2026-08-03 一併更正。）

但更重要的是：**§7 的分歧本來就不約束本文的用途。**

§7 的四個選項，軸線全都是「**陌生人／聯絡人能不能讀到清單**」——因為在該文的脈絡（棘輪）裡，
per-device 預金鑰**必須讓對方讀到**，否則 X3DH 建不起來。

**而撤銷用的清單，讀者只有我自己：**

| 用途 | 誰需要讀裝置清單 |
| --- | --- |
| 棘輪 per-device 預金鑰（ADR-0303） | **對方** |
| 撤銷／EK per-device 分發（本文） | **只有我自己** |

聯絡人照舊加密到我的 **EK**（身分層一把，不變），完全不需要知道我有幾台裝置；
裝置公鑰只被我自己用來決定「這輪 EK 要加密給哪幾把」。

⇒ 於是有第三個象限：**加密給自己的可取代事件**。ADR-0303 沒有列它，因為在棘輪的脈絡下沒有意義。
它同時避開該節列出的三項代價：

- **隱私**：中繼與公眾**數不出基數**（只看得到「這個 npub 有一顆 kind 10041」，一個位元）
- **無 O(N) 扇出**、**不打破 ADR-0121 訊息請求**（選項 2 的兩個代價）
- **無兩套模式**（選項 3 與 ADR-0302〈非目標〉的衝突不存在）

⚠ **但目錄不能只放在雲端快照裡**：快照合併是 add-biased，而被移除的裝置有 nsec
⇒ 它可以寫一份把自己加回去的快照。專用的可取代事件 ＋ 單調版本 ＋ ADR-0099 §2 的決勝規則
（`created_at` 較新者勝、同時 id 字典序小者勝）才站得住。
（它**仍然簽得出 v+1**——那是本文〈買不到什麼〉第 1 點，S4 分歧偵測要處理的東西。）

## 決策：分四階段，各階段獨立有價值

### S1 — 可指名的裝置（裝置金鑰 ＋ 簽章目錄）

- 每台裝置生一把**裝置金鑰對**，私鑰**永不離開該裝置**（L2 平台綁 TPM/SE，依 ADR-0297 分級）。
- 新事件 **kind 10041 裝置目錄**（可取代，接續 10037/10038/10039/10040）：
  由 **nsec 簽**，內容為 `{ v, devices: [{ pk, label, addedAt }] }`，**加密給自己**。
- ADR-0321 的觀測清單升級為**可驗證清單**：目錄內的裝置有金鑰佐證，
  觀測到但不在目錄內的 ⇒ 顯著標示（那正是今天完全看不出來的東西）。
- **此階段撤銷尚未生效**，但盲點縮小、且是後面每一階段的前提。

### S2 — EK 改 per-device 分發（**撤銷在此才成立**）

- EK 私鑰**停止進入**加密雲端快照與配對捆包的 nsec 加密層。
- 改為：輪替時對目錄內每台裝置的 `pk` 各加密一份（NIP-44，自封定址）。
- 配對新裝置時，EK 隨捆包給（配對本來就是點對點且 SAS 驗證過的）。
- ⚠ **相容性＝自我協商的雙軌**（實作決定，2026-08-03）：
  **「所有觀測到的裝置都在目錄內」才停用舊路徑**（`revocationActive()`）。
  觀測得到卻不在目錄內的裝置＝還沒升級 ⇒ 它只能從快照拿 EK，此時貿然停掉舊路徑
  會讓**自己的另一台裝置靜默收不到新 EK**（＝訊息解不開，ADR-0316 才剛讓它可觀測）。
  這條協商是可靠的，因為**舊路徑本來就只服務「有開雲端備份」的裝置，而那正是觀測得到的那些**。
- ⚠ **槽位補齊**：逐台加密會讓密文數 ＝ 裝置數，**中繼直接數得出你有幾台**——
  那正是 S1 花力氣藏起來的東西。故補到 `EK_ENVELOPE_SLOTS`（8）的倍數，
  空槽是「加密給隨機公鑰的等長垃圾」，與真槽外觀不可區分。

### S2a — 撤銷判定的修正（實作後回頭修，2026-08-03）

初版 `revocationActive(): boolean` 有三個嚴重問題，**兩個是我自己在別的 ADR 反覆主張過的錯**：

1. 🔴 **會單調卡死**：觀測清單只增不減 ⇒ 三年前丟掉的手機永遠是「不在目錄內」
   ⇒ 判定**永遠 false**。一個「用得越久越不可能成立」的判定等於沒有。
2. 🔴 **失敗方向不安全**：中繼扣住某台的快照 ⇒ 觀測不到 ⇒ 誤報「已生效」。
   與 ADR-0321 那句「看到只有一台不等於沒有人在讀」是同一個錯誤，只是寫進了判定邏輯。
3. 🔴 **布林壓掉三態**：「目錄還沒建立」（等一下）與「有一台沒升級」（去更新那台）
   對使用者的意義完全不同——正是 ADR-0316／0319 分桶／分三態的同一個理由。

修正：

- **A 以證據取代推論**：舊路徑就是「EK 隨快照走」，而快照我們**解得開、也知道是哪台發的**
  ⇒ 「某台的最近一份快照仍帶著 EK 私鑰」是**直接證據**，且不受中繼扣住影響
  （扣住只會讓證據晚到，不會假陽性）。狀態會自己復原（那台改成不帶就轉回 active）。
- **B 三態＋指名**：`unknown`／`dual-track`（列出是哪些裝置）／`active`。
- **D 保守**：`active` 需要「目錄已建立 ＋ 本機已登記 ＋ 無舊路徑證據」，不是「沒看到反例」。
- **E 可證性**：`deviceIdInDirectory` 改三態——**找不到但目錄有項目沒帶 `id` ⇒ `null`（無法證明）**，
  不得講成「不在目錄內」（`id` 是選填欄位）。

⚠ **一個關鍵區分**：「我這台要不要停止在快照裡帶 EK」**不能**用上面的證據判定
——那會死鎖（A 因為看到 B 還帶著而繼續帶，B 亦然，誰都不先停）。
該決定必須**單方面**：只看「有沒有觀測得到、卻不在目錄內、且未被我移除的裝置」（`shouldOmitFsKeys()`）。
**回報用證據（保守），行動用單方面（免死鎖）——兩者刻意不同。**

### S3 — 移除流程

- 移除＝簽 v+1 目錄（不含它）**＋立刻輪替 EK**（否則它還握著當前 EK）。
- 舊 EK 照 grace 老化（ADR-0245）——**被移除的裝置在 grace 內仍解得開舊訊息**。
  這是刻意的：不留 grace 會讓所有在途訊息一起掉（ADR-0313 已有的取捨）。
- 移除需**二次確認並說明後果**：不影響歷史、grace 內仍可讀、**若外洩的是 nsec 而不只是那台裝置，
  移除擋不住**（要換身分金鑰）。
- ⚠ **移除必須同時標記 `revoked`**：不標的話它會被當成「還沒升級的裝置」
  ⇒ `shouldOmitFsKeys()` 轉回 false ⇒ 本機又把 EK 放回快照 ⇒ **剛撤銷的裝置立刻拿回金鑰**。
- **不得移除自己**：那只會把這台鎖在門外。

### S4 — 分歧的處置（ADR-0303 選項 E 的最小版）

⚠ **本節於實作時修正（2026-08-03）。原設計「同版本、內容不同＝攻擊證據」是錯的。**

🔴 **同版本的分歧無法判斷方向。** 我有 {A,B}、收到 {A,C}：可能是對方**加了 C**
（而它還沒看到我的 B），也可能是對方**拿掉了 B**。**兩者在資料上完全一樣**——
沒有因果歷史（vector clock／父雜湊）就分不出來，而那是另一個量級的機制。

而把它一律當成攻擊，會把**兩台裝置升級後先後開機、各自登記自己**這個**正常情況**
誤報成「你的身分私鑰可能外洩」。假警報會讓真警報一起被無視（同 ADR-0319 的理由）。

⇒ 修正後：

- **同版本分歧 ⇒ 以聯集收斂**（重簽 v+1 為兩邊的聯集）。理由：
  - 聯集**不會把任何合法裝置鎖在門外**；反過來（拒絕兩份）會讓「另一台同時登記自己」
    變成那台**靜默收不到 EK**，而使用者看不出原因。
  - 攻擊者的裝置確實會被併進來——**但它本來就會被看見**：出現在裝置清單、觸發新裝置警示
    （ADR-0321），使用者可以直接移除（S3）。
    ⇒ **安全訊號放在「看得見 ＋ 可移除」，而不是放在一個判不出來的分類上。**
- **版本倒退 ⇒ conflict**（不含糊：較低版本只可能來自重放或倒退）。**不採用**，並
  **持久記錄**（保留最近 8 筆，有界防灌爆）。
- **常駐呈現**而非一次性對話框：這是「身分私鑰可能外洩」等級的事件，
  看過一次就消失太輕——使用者事後想確認「我到底看到了什麼」必須查得到。
- 不做完整透明日誌（CONIKS 式）——那是另一個量級。

### S5 — 裝置授權取代自我登記（2026-08-04；**修 S3 的實質失效**）

🔴 **S1 的自我登記讓 S3 的移除完全無效。** 實測（`removeDevice()` 的同一個呼叫堆疊內）：

```
移除前  : [A, B]
移除後  : [A, B]   ← 沒變
```

流程：A 簽 v+1（不含 B）→ B 收到、版本較新 → 採用 → B 執行 `ensureSelfInDirectory()`
發現自己不在 → **自己簽 v+2 加回來** → A 收到 v+2、版本較新 → 採用 ⇒ **B 回來了**。

**撤銷與自我登記在同一個系統裡是互相抵銷的。** 本文原本的分階段裡沒有「授權」這一階段，
那是設計時的漏——ADR-0303 §4.4 早就引論文指出承重點是
「**授權憑證必須是當期的短期狀態，不能是長期祕密**」，而自我登記只需要 nsec ＝ 長期祕密。

修正：

1. **`ensureSelfInDirectory()` 只做創世**（目錄尚不存在時）。加入既有目錄一律走
   `authorizeDevice(pk)`——**由一台已在目錄內的現役裝置主動授權**。
2. **同版本分歧不再以聯集收斂**（S4 的原決定）。聯集會讓自我登記從另一扇門回來：
   兩台各自創世、合併後兩台都在，授權形同虛設。改用 **ADR-0099 §2 的既有決勝規則**
   （`created_at` 較新者勝、相同則事件 id 字典序小者勝），兩邊必然收斂到同一份。
3. **敗方/未授權的裝置不會失聯**：照舊走舊路徑（快照帶 EK），`revocationState()`
   如實回報 `dual-track`；使用者在勝方按一次「授權」即可。
   ⇒ S4「不鎖住合法裝置」的目的仍然達成，只是改由**授權**達成，而不是自動合併。

⚠ **這擋不住已經在你機器上有執行權的攻擊者**（他可以直接操作授權 UI，ADR-0303 §6.7-1b）。
它擋的是「只拿到 nsec／磁碟映像、沒有你這台的活體參與」的那一類——而那正是本文
〈L3 真正買到什麼〉鎖定的情境。

## 考量的選項

- **per-device session（Sesame 式）**：ADR-0303 的原始設想。**撤銷不需要它**（見上），
  且它的成本正是該文列為「比密碼學本身更深」的那一塊。留給棘輪，不在本文。
- **只做本地移除（L1）**：使用者會以為「撤銷了」，而那台裝置照樣讀得到。
  UI 說謊，否決（ADR-0278／0287）。
- **靠 ADR-0052 換身分**：有效但代價極高（換 npub、通知所有人）。維持為**最終手段**，
  不是日常的裝置管理。

## 後果

- 正面：裝置遺失／被偷／舊機／離職機這些**最常見的情境**第一次有解；
  ADR-0321 的清單從「只能看」變成「能動」；成本比 ADR-0303 的原始估計小一個層級。
- 負面 / 已知殘餘風險：見上〈L3 買不到什麼〉四點，**全部必須在 UI 誠實揭露**。
  另有：
  - **S2 是相容性斷點**：EK 分發改變 ⇒ 需過渡期雙軌，而雙軌期間撤銷是無效的
    （舊路徑還在）。這段期間不得宣稱「已可撤銷」。
  - 這一切疊在**尚未經外部審計**的 FS 程式碼上（ADR-0306 定位不變）。
- 後續行動 / 待辦：
  - ~~**S1 先做**~~ ✅ **S1 已實作（2026-08-03）**：`packages/core/src/device-directory.ts`
    （kind 10041、加密給自己、單調版本、分歧判定）＋`storage/device-key.ts`（裝置金鑰，
