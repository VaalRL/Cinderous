# 0358. 輪替維護者信任根金鑰（它曾在 CI 裡住過二十天）

- 狀態：已接受
- 日期：2026-09-18
- 相關文件：ADR-0039（混合式引導路由／簽章清單信任根）、ADR-0092（節點自報與分級收錄）、
  ADR-0188（填入維護者公鑰）、ADR-0239（供應鏈信任與離線簽章）、
  `docs/MAINTAINER-ACTIVATION.md`、`packages/engine/src/bootstrap-config.ts`

## 背景與問題

`MAINTAINER_NSEC` 是整個容錯拓樸的**唯一信任根**：握有它就能簽出一份 relay 清單，而所有
客戶端**自動採用**那份清單。外洩＝攻擊者可以把使用者導到自己的 relay（eclipse／元資料收割）。

2026-09-18 的稽核查出一段時間線：

| 日期 | 事件 |
| --- | --- |
| 2026-07-03 | `MAINTAINER_NSEC` 以 GitHub Actions secret 注入 `relay-health.yml` |
| 2026-07-18 | 公鑰 `6efd2603…` 釘進客戶端（ADR-0188） |
| 2026-07-23 | ADR-0239 把金鑰移出 CI |

**公鑰是在金鑰住在 CI 的期間釘進去的。** ADR-0239 的後續行動 2 早就寫了：
「若曾以任何形式進過 CI，視為**已曝險**、應輪替一次並更新客戶端釘死公鑰。」
那條後續行動從 2026-07-23 至今沒有被執行。

那二十天裡，CI 的**任何一個傳遞相依**被投毒都足以讀走它。沒有證據顯示它被拿走——
但「沒有證據」不是「沒有發生」，而這把金鑰的爆炸半徑是全體使用者的連線路由。

## 考量的選項

- **A：不輪替，接受風險。** 理由會是「沒有外洩跡象，而輪替要重建所有客戶端」。
  否決：信任根的處置不該建立在「我們沒看到壞事」上。ADR-0239 自己已經判定它曝險了，
  留著它等於讓那份判定變成空話。
- **B：立刻停用舊金鑰、只用新的。** 否決：公鑰是**編譯期常數**，已出貨的 v0.0.15 只認舊公鑰。
  立刻停用會讓那些客戶端收不到任何清單更新——包括「這座 relay 退役了」——變成孤島。
- **C（採用）：輪替，並在新版本普及前讓新舊金鑰並存。**

## 決策

新的信任根公鑰：

```
7b5cd386c71c1c68ecf979ffe9dde6a008090ee3fbe377934a1bbb3ff6dd5114
```

舊的 `6efd2603…` 進入**並存期**，不立即銷毀。

### 並存期的操作義務

🔴 **每次 `relays.json` 變動，同一份清單要用新舊各簽一次、各發佈一次。**

舊客戶端只驗得了舊簽章，新客戶端只認新公鑰。少簽哪一把，那一邊就收不到更新。
這一步**沒有自動化**——`bootstrap:sign` 一次只吃一把 `MAINTAINER_NSEC`，所以是跑兩次：

```bash
MAINTAINER_NSEC="$(cat 新的.nsec)" pnpm --filter @cinderous/relay bootstrap:sign
MAINTAINER_NSEC="$(cat 舊的.nsec)" pnpm --filter @cinderous/relay bootstrap:sign
```

### 什麼時候可以停用舊金鑰

帶新公鑰的版本在使用者間**普及之後**。這個專案沒有遙測，所以「普及」判斷不了精確數字——
以 Releases 的下載數與發版後經過的時間作粗略依據，寧可拖長也不要提早。

停用＝停止用舊金鑰簽章，並銷毀它的所有副本。屆時應補一份 ADR 記錄。

### 順帶修掉工具本身

`relay/bootstrap/genkey.ts` 產完金鑰後，**印出來的下一步是教人把 nsec 設成 GitHub secret**
——正是 ADR-0239 拔掉的反模式；而且它接著說「從本機刪除」，照做的人會再也簽不了清單。
本 ADR 一併改掉那段輸出，並補上輪替時「舊金鑰先別刪」的警告。

⚠ 另外記錄一個實測發現：genkey 會嘗試 `chmod 600`，但**在 Windows 上不生效**（產出的檔案
是 644）。多人共用的 Windows 機器上，其他使用者讀得到那個檔案。已寫進檔頭註解。

## 理由

- **ADR-0239 已經替我們做過判斷了**，這份 ADR 只是執行它。判定曝險卻不輪替，等於把安全
  決策降級成一句話。
- **並存期不是保守，是必要**。B 選項的代價落在**已經安裝的使用者**身上，而他們什麼都沒做錯。
  把他們變成收不到退役通知的孤島，比多簽一次章嚴重得多。
- **舊金鑰仍在本機**（實測確認：`Downloads/maintainer.nsec` → `6efd2603…`），所以並存期
  確實做得到。若舊金鑰已遺失，這份 ADR 的第 4 步會不成立，那就得接受一批孤島客戶端——
  這也是為什麼「輪替前先確認舊金鑰還在」值得寫下來。

## 後果

- **正面**：曝險的信任根被換掉；ADR-0239 的後續行動 2 結案。
- **正面**：genkey 不再教反模式，下一個產金鑰的人不會重蹈覆轍。
- **負面 / 已知殘餘風險**：
  - **並存期要簽兩次，而且沒有自動化**。漏簽一把不會有任何錯誤訊息，只會讓一邊的客戶端
    安靜地停在舊清單上。這是本 ADR 最可能出錯的地方。
  - **舊金鑰在並存期仍然有效**。如果它真的在那二十天裡被拿走，攻擊者在並存期內依然簽得出
    舊客戶端會接受的清單。輪替降低的是未來的風險，不是已經發生的。
  - **需要一次全平台發版**才能讓新公鑰生效（桌面、網頁、行動、CLI）。
  - 停用舊金鑰的時機沒有客觀依據（無遙測），只能憑判斷。
- **後續行動 / 待辦**：
  1. 重建並發佈所有客戶端（桌面 MSI/NSIS、網頁、Android APK、CLI）。
  2. 發版後每次 `relays.json` 變動，記得**簽兩次**。
  3. 新版普及後停用舊金鑰、銷毀副本，並補一份結案 ADR。
  4. 舊金鑰檔目前在 `Downloads/maintainer.nsec`、新的在 `relay/maintainer.nsec`——
     兩者都**不在**版本庫（`.gitignore` 第 61 行涵蓋 `maintainer.nsec`），但都在 Windows 上是
     644。請自行搬到受保護的位置並離線備份。
