# 0316. 讓「解不開」看得見：FS 解封失敗的可觀測性

- 狀態：已接受
- 日期：2026-08-03
- 相關文件：ADR-0315（本工作是該研究列的**第 1 步、阻擋性前提**）、ADR-0313（自動輪替提高發生率）、
  ADR-0245（opt-in FS）、ADR-0306（實驗性定位）、
  `packages/core/src/subkey.ts`、`packages/engine/src/backend/relay-backend.ts`

## 背景與問題

收件路徑上有兩處：

```js
try { opened = this.openFs(event); } catch { return; }
```

一則加密到「我已回收的舊 EK」的訊息就這樣**無聲無息地不存在**。沒有錯誤、沒有佔位、
沒有計數。這個 `catch` 本身是對的（畸形事件本來就該丟），但它讓
**「密文解不開」與「這顆事件是垃圾」變成同一件事**。

ADR-0313 開啟自動輪替後發生率會上升；ADR-0315 若擴大到更多事件型別，會再乘以型別數。
在看不見失敗的情況下擴大加密面，等於擴大一個**你不會知道它發生了**的資料遺失面。
故 ADR-0315 把本工作列為第 2 步之前的阻擋性前提。

## 先講清楚一件做不到的事

需求原話是「區分『缺 EK』與『壞事件』」。**密碼學上做不到。**

NIP-44 解密失敗就是 MAC 驗證失敗，「我沒有正確的金鑰」與「這段密文是垃圾」在該層是
同一個錯誤。任何宣稱能區分的實作都是在猜。

**但有一個方向是確定的**：如果我**從未持有過 EK**，那麼一顆定址給我（`#p` = 我）卻解不開的
wrap **確定與 FS 無關**——我從來沒有一把可能被回收的金鑰。反過來（我有或曾有 EK）則
**無法區分**。

⇒ 本 ADR 採用這個**不對稱**的分類，並在型別名稱與 UI 文案上誠實標示不確定性。
把「可能」寫成「是」就是說謊（ADR-0302 §4 已為降級警告立過同一條原則）。

## 考量的選項

- **選項 A：只加一個總計數器。** 無法分辨「本來就有的垃圾事件基線」與「FS 造成的遺失」，
  數字會被基線淹沒 ⇒ 看得見但看不懂。否決。
- **選項 B：在對話中插入「有一則訊息解不開」的佔位泡泡。** **技術上不可能**——
  NIP-59 的外層作者是一次性臨時金鑰，寄件人身分在**加密的內層**。解不開就
  **不知道是誰送的**，也就無從決定放進哪個對話。這個限制本身值得記錄下來。
- **選項 C（採用）：兩個桶的計數 ＋ 最後一次時間，存在該身分的加密儲存，並在設定頁的
  FS 區塊顯示（僅在「可能與 EK 有關」那個桶 > 0 時）。**

## 決策

1. **純函式放 core**（`subkey.ts`，與 EK 生命週期同一處）：
   - `FsFailureLog { notFs: number; maybeEkLoss: number; lastEkLossAt?: number }`
   - `recordFsFailure(log, at, hadEk)` 純 reducer。
   - 桶名刻意是 `maybeEkLoss` 而不是 `ekLoss`——**名稱本身要帶著不確定性**，
     否則下一個讀這段程式的人會把它當成事實。
2. **落點在 `StoredFsState.failures`**：per-identity、與 EK 同一把 DEK 加密落地，
   零新增儲存管線。
3. **不進雲端快照、不進配對捆包**：這是**這台裝置**的觀測（另一台裝置可能有那把 EK）。
   兩處既有的「淨化」邏輯（`enabled: false` 強制）各加一行剝除。
4. **引擎**：兩個 `catch` 各呼叫 `noteUndecryptable()`；新增 `onFsUndecryptable` handler
   （UI 可即時反應）與 `fsFailures()` getter。
   `hadEk` 判定＝`keys.length > 0 || retired`——涵蓋「停用後金鑰尚未老化完」的情形。
5. **UI**：桌面與行動端的 FS 區塊，在 `maybeEkLoss > 0` 時顯示一行說明＋最後發生時間。
   **`notFs` 不對使用者顯示**——那是本來就存在的垃圾事件基線，不可行動，顯示只會製造焦慮。
6. **不做的事**：不保留解不開的密文以待日後補解。那是**復原**不是觀測，屬 ADR-0315 之後的
   獨立工作（需要儲存原始事件與重試機制）。本 ADR 只負責讓它看得見。

## 理由

- **不對稱分類是唯一誠實的分類**。給出一個看似精確的分類器，會讓後續決策建立在猜測上。
- **放 `StoredFsState` 而非新開儲存槽**：FS 專屬、per-identity、已加密——三個性質都對上了，
  而新增一個 `AppStorage` 方法要動 3 個實作 ＋ 快照匯出入。用既有欄位是 Fix First。
- **不顯示 `notFs`**：使用者對「有 3 顆畸形事件被丟掉」無法採取任何行動。
  可觀測性的對象在這裡是**開發者與診斷中的使用者**，不是每個人的日常畫面。

## 後果

- 正面：ADR-0315 的阻擋性前提解除；自動輪替（ADR-0313）造成的遺失不再隱形；
  「無法區分」這個事實被寫進型別名稱而不是註解裡。
- 負面 / 已知殘餘風險：
  - **仍然不知道是誰送的、內容是什麼**（NIP-59 的必然結果）。使用者看到的是
    「這台裝置有 N 則訊息解不開」，不是「Bob 的某則訊息掉了」。
  - `maybeEkLoss` 混著真實 EK 遺失與畸形事件；只有在**啟用 FS 之後才開始累積**的情況下
    才有較強的因果指向。
  - 每次失敗都寫一次儲存。失敗應屬罕見；若日後觀測到高頻，需加節流。
- 後續行動 / 待辦：
