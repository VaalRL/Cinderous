# 0355. 檔案合集、斷點續傳與整檔校驗

- 狀態：已接受
- 日期：2026-09-17
- 相關文件：`docs/research/file-transfer-optimization-large-and-small-files.md`、ADR-0093（App 不保管檔案本體）、ADR-0102（縮圖）、ADR-0128（路徑授權白名單）、ADR-0273（送圖清除 EXIF）、ADR-0345（亂序寫入契約）、ADR-0346（惰性送出來源）、ADR-0347（收檔串流落盤）、ADR-0349（Tauri 原生暫存區）

## 背景與問題

ADR-0346／0347 把**單一大檔**治好了：送出端不再把整檔讀進記憶體，收檔端來一塊寫一塊。剩下三個洞：

1. **大量小檔。** 傳一千個小檔的成本不在位元組，在**每檔一次的固定成本**：一則 `file-begin`、一次開檔、一次另存互動、一則聊天訊息。實際位元組可能只有幾 MB，使用者卻要等好幾分鐘，然後收到一千則訊息。「傳一整個資料夾」更是完全做不到。
2. **斷線就從頭來。** 收檔端已經把位元組寫在磁碟上了（ADR-0347／0349），但重連之後送出端仍從第 0 個位元組送起。一個 2 GB 的檔在 90% 斷線，代價是整整 2 GB。
3. **沒有任何完整性檢查。** 亂序寫入（ADR-0345）加上續傳，意味著一個檔案是由多段拼起來的。拼錯了沒有人會發現——收檔端不知道整檔應該長什麼樣。

## 考量的選項

- **合集格式：tar vs zip。**
- **折疊時機：一律折疊 vs 有門檻 vs 使用者自選。**
- **續傳協商：新增協定欄位 vs 新增訊息型別。**
- **校驗範圍：逐塊雜湊 vs 整檔雜湊。**

## 決策

### 一、合集用 **tar（ustar，不壓縮）**，自己寫

tar 是「標頭＋內容」線性排列，**位移算得出來**，所以整個合集能實作成 `OutgoingFileStream`（ADR-0346）：要哪一段就去讀哪一段，合集本身從不進記憶體，斷點續傳也天然成立。zip 的中央目錄在檔尾，得先掃過一遍才知道版面。

不壓縮是刻意的：聊天傳的多半是已壓縮的媒體檔，壓縮率趨近於零，代價卻是整份都要進 CPU。

自己寫而不引入套件：ustar 的寫入端約 100 行，而 `file-begin` 必須**先宣告確切大小**——這要求「不產生任何位元組也能算出總長度」的能力，現成套件不保證這點。實作上先算出一份 `Segment[]` 版面（標頭／補零是算得出來的位元組，內容則指向某個項目的某一段），`slice(offset, length)` 只是在版面上找位置。

### 二、折疊有**門檻**：超過 8 個檔，或含任何資料夾

少量檔案要維持聊天體驗——收到三張相片就該是三張可預覽的相片，不是一個壓縮包。多到一定程度時，逐檔的固定成本才是主要痛點。

**折疊會改變隱私行為，所以要先問。** ADR-0273 的 EXIF／GPS 清除是 canvas 重編碼，需要整張圖在記憶體裡，與串流打包互斥；合集裡的檔案是**原封不動**傳送的。也就是說同一個動作（拖一批相片）在折疊之後**不再清除位置資訊**。這是使用者看不見的改變，因此偵測到可清理的圖片時先跳一次確認。

### 三、續傳協商用**新的訊息型別 `file-resume`**，且它同時是能力回執

收端在 `file-begin` 之後回 `{ t: "file-resume", id, have, v }`，送出端從 `have` 接續。三個細節：

- **`have` 向下對齊到分塊邊界**：半塊接不回去。
- **只回給宣告了 `v >= 2` 的送出端**：舊客戶端收到未知訊息會顯示成錯誤。這一則因此**同時是能力回執**——送出端據此知道對方聽得懂 `file-end`。
- **`have = 0` 也要回**：那一則是「我在，而且我是新版」，不是續傳。

### 四、校驗是**整檔 SHA-256**，由 sink 自己算

送出端在送完最後一塊後送 `{ t: "file-end", id, sha }`。收端比對後才 `close()`，不符就 `abort()` 並回報。

雜湊由 **sink** 計算而不是 core：續傳時早先那些位元組是**上一個 session** 寫下的，core 手上根本沒有它們——只有持有那個檔案的宿主算得出整檔。sink 沒有實作 `digest()` 就跳過校驗，行為與過去相同。

沒收到 `file-end` 會在 300 ms 寬限後照常收尾：對方是舊版時不能讓檔案卡住不交付。

### 五、解包：**解析在 TS，落地在宿主**

tar 的解析是純位元組運算，桌面與瀏覽器沒有差別。留在 core 表示**解析**只有一份，不會「桌面補了瀏覽器忘了」。

⚠ zip-slip 守衛則刻意**有三層**且必須各自成立：core 的 `safeArchivePath`（合集內容不可信）、
Rust 的 `filestream::safe_join`（**webview 不可信**——XSS 能直接呼叫寫入指令）、
以及 `fs_read_range_in` 的 `canonicalize` containment（符號連結不可信）。
後兩層不是重複，是不同的威脅來源；而 Rust 那層必須是 TS 那層的**超集**，否則
「Rust 擋 XSS」的論證只成立一半。

落地分兩條：

- **桌面**：`listTar` 只讀標頭拿到每個項目的內容位移，再由 Rust 的 `extract_copy` **直接從合集檔案複製到目的檔案**。內容一個位元組都不經過 IPC——走 IPC 會把每個位元組轉成 JSON 數字再轉回來，1 GB 的合集會變成 4～5 GB 的字串。
- **瀏覽器**：File System Access API 的 `showDirectoryPicker`。

🔴 **「瀏覽器沒有檔案系統寫入能力」是過時的說法。** Chromium 系（Chrome、Edge、Opera、Brave）有 `showDirectoryPicker`，Firefox 與 Safari 沒有。所以能力**問過再決定顯示什麼**：有就給解包按鈕，沒有就說「請用系統的解壓縮工具打開」。照那句過時的話做，就是讓一大半使用者少一個本來做得到的功能。

### 六、合集帶 **mtime 與權限**，收件端**不必解開就看得到內容**

不帶 mtime，解開後每個檔案都變成 1970 年；不帶權限，可執行腳本解開後就不再可執行。權限只取低 9 位——setuid／setgid／sticky 不跟著合集跑。

內容列表用 `listTar`：每個項目讀完 512 位元組的標頭就跳過整段內容，列一千個檔只要讀一千個小區塊，與合集多大無關，**全在本機、不連網**。收件人因此在決定要不要解開之前就看得到裡面有什麼。

## 理由

**為什麼折疊不需要改協定。** `ChatMessage.file` 是一則訊息一個檔，要送「一批檔案」得改四層（協定訊息、backend 介面、訊息模型、UI）。合集把 O(N) 變成 O(1) 卻**零協定改動**——它就只是一個檔案。

**為什麼續傳要一個新訊息而不是擴充 `file-begin`。** 續傳的資訊流向是**收端 → 送出端**，而 `file-begin` 是反向的。硬塞只能靠猜。

**為什麼不逐塊雜湊。** 逐塊雜湊能指出「哪一塊壞了」，但重傳單塊的機制並不存在（壞了就是整檔重來）。多出來的資訊沒有人用，代價卻是每塊都多一個欄位。

## 後果

- **正面**：傳一整個資料夾成立了；一千個小檔變成一次傳輸、一則訊息、一次另存。
- **正面**：續傳讓大檔在不穩的網路上可用；重連後從斷點接續，且整檔雜湊保證接對了。
  ⚠ **整檔雜湊從每條連線的第二個檔案起生效**：`file-end` 只送給宣告 `v>=2` 的對方，
  而那個宣告來自 `file-resume`——它是**當下這個檔案**的 `file-begin` 的回應。不在第一個檔案
  上先付一趟往返是刻意的取捨，但保證的起點確實是第二個檔，不是第一個。
- **正面**：合集的隨機存取讓續傳對合集同樣成立（它就是一個可定位的檔案）。
- **負面**：**合集內的圖片不清除 EXIF／GPS**。以送出前的確認處理，但那是提示而非保證——按下確定的人未必讀了它。
- **負面**：磁碟餘量檢查**只有 Windows 問得到**（走既有的 `windows` crate，不新增相依）。其他平台靠作業系統在寫入時報錯，代價是可能先寫了一段才失敗。
- **負面**：瀏覽器解包**還原不了 mtime 與權限**——File System Access API 沒有這兩個東西。要保留時間戳的人得用桌面版或系統工具。
- **負面**：合集只在**已另存**之後才列得出、解得開（ADR-0093：App 不保管檔案本體）。使用者按了取消就沒有東西可以操作。
- **後續行動**：行動端的送出仍是單檔選取（`<input type=file>` 未開 `multiple`／`webkitdirectory`），折疊目前只在桌面的拖放路徑成立。
