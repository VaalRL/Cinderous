# ADR-0331：Phase P4 階段 1——按功能簇抽 hook（第 1 簇：通話）

- 狀態：已採用
- 日期：2026-08-04
- 關聯：ADR-0294 §2／ROADMAP Phase P4、ADR-0328（互動測試）、ADR-0329（世代守衛）、ADR-0330（`useRef` 守衛）、ADR-0101（通話 UI）

## 1. 為什麼是「抽 hook」而不是直接做子元件

治本解是把 per-identity state 關進以身分為 `key` 的子元件（重掛＝結構性重設）。但那是**一次性、不可分割**的大動作：`key` 一掛，41 個 state 的重設語意同時改變，中間沒有可停的位置。

階段 1 先做**可以分拆**的部分——按功能簇抽成 hook。它純機械、**不改任何執行順序**、逐簇可回退，而且做完之後子元件那一步會是「移動」而不是「重寫」。

### 評估過但否決的中間方案：`useIdentityState`

看起來最省事的一步是把 41 個 `useState` 換成「key 變了就自動重設」的版本，刪掉手寫清單、不搬任何東西。**它會壞。**

今天的順序是「重設 → `backend.start()` → handlers 同步灌入新身分的資料」，而 `start()` 內的 `resubscribe()` 在記憶體網路上是**同步送達**的（引擎自己的註解寫著這件事）。`useIdentityState` 的重設發生在 **render 時**＝整個事件處理完之後 ⇒ 順序反轉成「⋯⋯新資料灌入 → render 才發現 key 變了 → 把剛灌進來的清掉」。

要修這個反轉就得把「切 key」和「起後端」拆成兩次 commit——而那**正是子元件 `key=` 從 React 掛載生命週期免費拿到的東西**。⇒ 這個中間站不比終點便宜，只是把同一個難題換個地方解。**跳過。**

## 2. 第 1 簇：通話

選它打頭陣的理由是**最獨立**：5 個 state（`callPeer`／`callState`／`callMedia`／`localStream`／`remoteStream`）、只由後端事件驅動、只餵一個覆蓋層畫面，與聯絡人／訊息／群組那一大團零耦合。

`use-call-session.ts` 同時擁有三件事：欄位、後端事件處理、`reset()`。原本那 5 個歸零呼叫散在 `signInWith` 的手寫清單裡；現在「這一簇有哪些欄位」和「這一簇怎麼歸零」在同一個檔案裡，新增欄位時漏掉的機會小得多。

⚠ 這**還不是結構性保證**（那要等子元件＋`key`）。它把手寫清單從 5 行縮成 1 行，並把責任移到看得見的地方。

## 3. 🔴 抽出去不能變成繞過守衛的方法

`MobileApp.perIdentityState.test.ts` 掃的是 `MobileApp.tsx` 裡的 `useState`。**把 state 搬進 hook，它就從那份掃描裡消失了**——若不同步納管，「重構」就等於「把東西藏到守衛看不到的地方」。

這是這批工作最容易出錯、也最沒人會發現的地方。故新增登記表 `test/identity-clusters.ts`，每抽一簇登記一筆，三支守衛據此接手：

| 守衛 | 對已抽出的簇要求什麼 |
| --- | --- |
| `perIdentityState` | 簇必須提供 `reset()`，且 `signInWith` 內必須呼叫；**簇內的 setter 不得再出現在 `MobileApp`**（否則是搬了一半） |
| `asyncEpoch` | 簇內**一律不許有非同步落地**——簇檔案裡沒有 `epochRef` 可用。哪天真的需要，正確做法是讓 hook 接受世代守衛當參數，並把規則改成「必須用它」，**而不是刪掉這條測試** |
| `refScope` | 不受影響（只掃 `MobileApp.tsx` 的 `useRef`；簇目前沒有 ref） |

兩支守衛的「幽靈條目」檢查在這次抽取時**確實紅了**，逼我同步更新分類表——那正是它們存在的目的。

## 4. 附帶收穫：這一簇現在測得到

抽出來之後才有辦法單獨測它。5 個新測試，其中一條釘住一個真實的失敗方向：

> **結束時必須連兩條串流一起放掉**——只清狀態的話畫面沒了，但 `MediaStream` 還在，麥克風／鏡頭指示燈不會滅。

以前這段邏輯埋在 1800 行元件的一個 handler 裡，沒有任何測試碰得到。

## 6. 第 2 簇（企業）補充的三件事

### 6.1 `reset` 帶種子，不是歸零

通話簇的 `reset()` 是純歸零；企業簇不是——切過去要**以新身分的 org 精華重新播種**（企業旗標、企業主 pubkey、核准權杖、**這個身分的**託管清單、已廣播的頭銜）。

把它當純歸零用，企業主切回來就看不到自己的託管清單了。ADR-0327 的教訓正是這一類：「重設了但值是錯的」是獨立的失敗類別，**歸零成空**與**重讀成新身分的值**不能混為一談。守衛的規則因此放寬成 `holder.reset(`（允許帶參數）。

### 6.2 邊界：state 在 hook，閉包留在呼叫端

這簇比通話糾纏：託管要用**企業主自己的 sk** 加密落盤。

🔴 **刻意不把 sk 搬進 hook**——多一個地方持有金鑰材料，就多一個地方要證明它沒外洩；為了整齊而搬，划不來。故託管與佇列以 **updater** 形式暴露（`updateEscrow`／`updateSlots`），呼叫端在 updater 裡做自己的加密落盤。

### 6.3 🔴 抽 hook 讓 `asyncEpoch` 守衛出現新漏洞

`depositToSlot` 原本是 `pickFile().then(… setSlotQueue(…))`，被 ADR-0329 的掃描器盯著。搬進 hook 後變成 `org.updateSlots(…)`——**掃描器的 setter 名單裡沒有它，就看不到了**。

不補這條，「抽 hook」本身會變成繞過世代守衛的方法。故掃描器新增第二種寫入形式：**任何 `.then(` 內經由已登記簇的呼叫（`<holder>.…`）同樣需要守衛**，並附合成案例驗證它抓得到。

⚠ 這是第 2 簇才浮現的，第 1 簇沒有非同步落地所以沒踩到。**後續每一簇都要再想一次「這次搬走的東西，哪支守衛會因此看不見」。**

## 7. 第 3 簇（身分層開關）：`reset` 的第三種形態

三簇下來，`reset` 出現了三種語意，而**分不清它們正是 ADR-0327 抓到的失敗類別**：

| 簇 | `reset` 是什麼 |
| --- | --- |
| 通話 | **歸零成空**（通話結束就是沒有通話） |
| 企業 | **以捆包精華播種**（企業主切回來要看到自己的託管清單） |
| 身分層開關 | **從新身分的後端重讀**（`fsEnabled()`／`fsFailures()`／`groupInviteFromAnyone()`／`devices()`／`cloudSyncOf()`） |

第 3 簇的 `reset(seed)` 因此把種子設為**必填**——這一簇沒有「歸零成空」這個選項。開過 FS 的身分切回來若顯示「未啟用」，那不是遺漏，是**說謊**。

## 8. 守衛的防呆門檻也會被重構侵蝕

`perIdentityState` 有一條「掃得到 state（避免 regex 壞掉時假性通過）」的下限檢查。每抽一簇，`MobileApp` 的 state 就少一批，這條門檻就要調低一次——

🔴 而「**因為重構所以調低防呆門檻**」與「**regex 壞了**」在數字上看起來一模一樣。

改成計算 **MobileApp ＋ 所有已登記簇**的總和，總數維持在 55 左右，之後每一簇都不必再動它。

## 9. 第 4 簇（行程）：把防禦包進 API，而不是留給呼叫端記得寫

`calDraft` 原本帶著 `convo` 欄位，而呼叫端要自己寫 `calDraft?.convo === activeId ? … : …`。那段比對防的是**同一種錯，只是粒度不同**：對話畫面以 `key={activeId}` 重掛，但這一層的 state 不會——不比對就會冒出上一個對話的預填表單。

⇒ 抽出來時順手把它包成 `draftFor(convo)`：**拿錯對話的草稿在 API 上就做不到**，不再依賴呼叫端記得寫那個三元式。

這也是抽 hook 的一個非顯而易見的收益：原本散在呼叫端的「記得比對」，可以在搬家的同時變成型別擋得住的東西。

⚠ 順帶：`calDraft` 是 ADR-0294 §2 抓到的三個漏網之一（漏網③）。守衛裡那條「三個漏網確實補上了」的斷言已改為檢查 `cal.reset(`——**斷言的對象變了，但那條回歸沒有被刪掉**。

## 10. 第 5 簇（「我自己」）：金鑰材料的界線，與收攏後才看得見的一件事

### 10.1 `nsec` 搬進 hook 是「重新安置」，不是「增加持有者」

它本來就在 `MobileApp` 的 state 裡——行動端從不持久化 nsec（ADR-0112），但 session 內必須在手，因為儲存層的 DEK 由它導出。

⚠ 故這個 hook **刻意不提供任何「順手」的密碼學便利**（不導金鑰、不簽章、不加解密），它只是個容器。

**多一個地方「做」金鑰運算，就多一個地方要證明沒外洩；多一個地方「放」同一份已存在的參照，沒有增加攻擊面。** 這條界線與第 2 簇（企業託管的 sk 留在呼叫端）一致。

### 10.2 🔵 軟登出沒有把 `nsec` 抹掉

四個身分欄位散在元件裡時看不出來；收攏成一簇之後很明顯：軟登出（ADR-0201）清了分頁／作用中對話／隱身，**但沒有清 `nsec`／`pubkey`／`name`**。

已確認登出後會渲染的畫面（解鎖／切換／新增身分／登入／配對匯出）**沒有任何一個讀 `self.*`**，所以這不是資料外洩路徑；但那仍是「session 結束了，金鑰還在記憶體」。補上 `clear()`。

這是抽 hook 的第二個非顯而易見的收益（第一個見 §9）：**把同一類東西放在一起，缺了哪一塊會自己浮出來。**

## 11. 修正原計畫：第 6 簇不該存在

原本的 7 簇規劃把 `connState` 列為獨立一簇。做到這裡才看清楚**那是把計畫切太細**：

- 1 個 state、3 個使用點、歸零就一行。
- 做成 hook 只有形式沒有內容——一個 `use-connection-state.ts` 裡面一個 `useState` 和一個 `reset`，讀的人得多開一個檔案才知道那是什麼。

改為**併入第 5 簇**。理由不是「反正它很小」，是語意真的對得上：

> 「我現在**看起來**在線」（`status`／`invisible`）與「我現在**實際上**連著嗎」（`connection`）是同一個問題的兩面。

而且歸零時機完全相同——切身分＝重連，兩者都回到初值。

⚠ 這是計畫的修正，不是跳過。`connState` 一樣進了簇、一樣被守衛納管、一樣多了測試（「切身分不沿用上個身分的 online」）。**分簇是為了讓東西好找，不是為了湊數字。**

⇒ 階段 1 剩最後一簇：核心通訊（12 個）。

## 12. 最後一簇：核心通訊拆成「名冊」與「對話」

原計畫把 12 個核心通訊 state 當一簇。實際看下來它們沿著一條清楚的縫分成兩邊：

- **名冊**（誰）：`contacts`／`groups`／`blocked`／`requests`。全部由後端整批推送，元件端**只讀不寫**。介面小到一眼看得完。
- **對話**（說了什麼）：`convos`／`unread`／`archived`／`reactions`／`unsent`／`purged`／`activeId`／`typingFrom`。有大量元件端的區域性修改（樂觀送出、加回應、標收回、記封存塊數）。

兩邊的寫入模式完全不同，合成一簇只會得到一個「什麼都有」的 hook。

### 12.1 讀取端用解構，不改名

`activeId` 有 **49 個讀取點**、`contacts` 有 17 個。全部改成 `threads.activeId` 只會製造無意義的 diff，還多 49 次打錯字的機會。

改成 `const { activeId, … } = threads;`——**擁有權在 hook，讀取點原封不動**，diff 與**寫入**數成正比而不是與讀取數成正比。守衛檢查的是「簇內 setter 不得殘留在 `MobileApp`」，解構讀取不受影響。

### 12.2 不硬包成「語意方法」

對話簇保留 `setConvos((c) => …)` 這種 updater 形式，沒有包成 `addMessage`／`markUnsent`。

🔴 那會把十處各自不同的合併邏輯搬進 hook，變成一個什麼都懂的物件——而它們真正該去的地方是**引擎**，不是另一個 UI hook。階段 1 的目標是**搬家，不是順手重新設計**（同 §1 否決 `useIdentityState` 的理由）。

兩個例外值得包：`activeId` 的開關與 `typingFrom` 的自動逾時——**它們有明確的生命週期，而生命週期正是散在元件裡最容易忘記收尾的東西**。計時器也一起搬了，連同它的卸載清理。

### 12.3 🔴 第三支守衛也被侵蝕了

`typingTimer` 隨對話簇搬走 ⇒ `refScope` 掃 `MobileApp.tsx` 就找不到它，兩條斷言直接紅。

這是第 2 簇建立的那個問題第三次出現（第一次是 `perIdentityState`，第二次是 `asyncEpoch`）。**三支守衛現在都會掃簇檔案**：

- `perIdentityState`：簇必須有 `reset()` 且被呼叫、簇內 setter 不得殘留。
- `asyncEpoch`：`.then(` 內經由簇的呼叫同樣要世代守衛；簇內不許有非同步落地。
- `refScope`：簇裡的每個 `useRef` 都要有明確收尾（清計時器或歸 null）。

⚠ 另外 `asyncEpoch` 的**自我檢查**也曾一度失效：它用 `setArchived` 當合成違規案例，而那個 setter 已經不存在了 ⇒ 檢查恆綠。已改用簇當例子。**「驗自己抓得到違規」的測試本身也會過期。**

## 13. 階段 1 完成

`MobileApp.tsx` 剩下的 **14 個 `useState` 恰好就是裝置／外殼層那 14 個**——`profiles`／`screen`／`pendingSwitch`／`tab`／`theme`／`locale`／`accent`／`fgOn`／`notify`／`notifyHide`／`chatBg`／`retentionCap`／`readReceipts`／`pairPhase`。

**每一個 per-identity state 都在簇裡了**，而守衛的「每個 state 都必須被分類」在 `PER_IDENTITY` 為空的情況下，等價於「MobileApp 不得再直接持有 per-identity state」。

⇒ 階段 2（子元件＋`key={pubkey}`）的前置條件完成：屆時要移動的是 6 個 hook 呼叫與一段渲染，不是 1823 行裡的 41 個散點。

（`MobileApp.tsx` 只剩 5 個外殼 state），三支守衛掃的檔案也隨之改變。本文不改寫——ADR 記的是
