# ADR-0340：關鏡頭就要真的關——廢除送黑畫面那條路

- 狀態：已採用（**部分取代 ADR-0337 §3**）
- 日期：2026-08-05
- 關聯：ADR-0337 §3（關鏡頭＝送黑畫面，本 ADR 取代之）、ADR-0338（升降級）、ADR-0243（明確標示、非靜默失敗）、ADR-0319／0314（假警報的代價）

## 1. 問題：三種狀態，只分得出兩種

ADR-0338 讓 UI 說得出「對方未開啟視訊」，但那條件是 `remoteMedia === "audio"`——**只涵蓋降級**。

| 對端在做什麼 | 我看到 | 有解釋嗎 |
| --- | --- | --- |
| 語音通話／已降級 | 頭像＋「對方未開啟視訊」 | ✅ ADR-0338 |
| 視訊通話但按了「停止視訊」 | **一塊黑色** | ❌ **沒有** |
| 視訊正常 | 畫面 | ✅ |

第二列正是 ADR-0337 §3 的關鏡頭：`track.enabled = false` 的語意是**送黑畫面**，型態仍是 `video` ⇒ 對端照樣渲染 `<video>`，只是裡面是黑的。

🔴 **而黑畫面與「網路斷了」、「他的鏡頭壞了」在畫面上長得一模一樣。** ADR-0243 早就定下立場：明確標示，非靜默失敗。這裡違反了。

## 2. 更根本的問題：兩個入口本來就很像

| | 相機實際狀態 | 恢復速度 | 對端看到 |
| --- | --- | --- | --- |
| 停止視訊（ADR-0337 §3） | **仍開著**，指示燈可能仍亮 | 立即 | 黑畫面（無解釋） |
| 改為純語音（ADR-0338） | 真的關閉 | 需重新 `getUserMedia` | 頭像＋說明 |

ADR-0337 §4-2 已經因為這個差異，把文案從「關閉相機」改成「停止視訊」。

**那是誠實的補救，不是好的設計。** 使用者想的是「關掉我的鏡頭」，沒有人想的是「保持相機運轉但送黑畫面」。

## 3. 決策：合併成一個，走降級

廢除 `enabled = false` 那條路。「關閉我的視訊」直接實作為 ADR-0338 的降級——`replaceTrack(null)` ＋ `track.stop()`。

理由，依重要性排序：

1. 🔴 **相機指示燈變誠實。** 按了關，燈就滅。一個把「明文與私鑰不離開裝置」當賣點的 App，不該有「你以為關了但其實開著」的控制項。
2. **對端的呈現已經做好了**（ADR-0338 的「對方未開啟視訊」）⇒ §1 的缺口自動補上，不必新增信令。
3. **只剩一顆按鈕。** 兩顆功能相近、差別要靠使用者猜的按鈕，本身就是設計債。
4. ⇒ ADR-0337 §4-2 那條「文案不得暗示相機已關閉」的限制**就此解除**——現在它真的關了，就可以這樣說。

代價（明知而接受）：

- 恢復要重新 `getUserMedia`（數百毫秒～1 秒）。快速連按會反覆開關相機，部分網路攝影機有可見或可聽的啟動延遲。
- 對端會看到型態變成「語音」。**但那其實是準確的**——你確實停止傳送視訊了。

## 4. 🔴 順帶更正 ADR-0338 §4 的一處過度宣稱

ADR-0338 §4 寫著「偵測不到視訊 transceiver 時，升級入口就不顯示」，並把它當成**舊版對端**的防護。

**那不成立。** `ensurePc()` 是**無條件**執行 `addTransceiver("video")` 的——在**我們自己這一端**。所以通話中 `videoSender()` 永遠找得到東西，`canChangeMedia()` 實際上恆為真。它真正涵蓋的只有「**我們自己**的執行環境沒有 `addTransceiver`」這一種情形，與對端版本無關。

舊版對端的真實行為是：我們送得出視訊（他的 answer 是 `recvonly`，我們是 `sendonly`），**但他的 UI 不會顯示**，而我們無從得知。

⇒ 這是**靜默失敗**，且無法從 SDP 判定（那是能力問題不是協商問題）。要真正偵測需要一次能力宣告握手。

**本 ADR 不做那個握手**——為一個過渡期相容問題新增協定，代價高於收益，且雙端都會更新。**但把這件事寫下來**，因為 ADR-0338 §4 目前讀起來像是已經處理了，而它沒有。

### 由此得到的一個真實修正

合併之後，那顆按鈕同時承擔兩件事，而**兩件事的可用條件不同**：

| 方向 | 條件 |
| --- | --- |
| 開啟我的視訊 | 需要可用的視訊 sender（`canChangeMedia`） |
| **關閉我的視訊** | **一律可用** |

🔴 **關掉自己的鏡頭永遠不該被閘門擋住。** 若沿用 ADR-0338 那個一體適用的 `canChangeMedia` 閘門，會做出「視訊通話中關不掉自己鏡頭」的 UI——那比原本的問題嚴重得多。

## 5. 網路造成的停滯：不做偵測

還有第三種黑畫面：對端網路爛到視訊停了但通話還在。

**不做偵測。** `getStats()` 的 `framesReceived` 停滯可以推論，但誤判率高（弱網下短暫停滯很常見），而誤判的代價是顯示一句錯誤的「對方暫停了視訊」。

🔴 **假警報會讓真警報一起被無視**——這個專案已經在 ADR-0319／0314 上為同一件事付過兩次學費。

⇒ 只解釋我們**確知**的事（對端明確降級）。網路造成的停滯維持現狀不解釋。

## 6. 買不到什麼

1. **不涵蓋對端 App 崩潰或裝置睡眠**——那時沒有信令送出來，我看到的仍是凍結畫面。
2. **舊版對端仍是無解釋的黑畫面**（§4）。偵測不到就不假裝知道。
3. **失去「立即恢復」**。這是選項 A 的主要優勢，明知而放棄——見 §3 的代價。
4. **不做「對方在看你嗎」之類的呈現**（視窗是否在前景）。那是可疑的遙測，不是通話控制。
5. **不處理快速連按的節流**。若實測發現相機啟動延遲造成困擾，再另立 ADR 加去抖動。
