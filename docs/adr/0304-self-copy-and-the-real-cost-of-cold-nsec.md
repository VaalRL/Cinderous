# 0304. 自封副本不是難的那一半——難的是「nsec 冷保存」會同時打掉本機靜態加密與雲端快照

- 狀態：**研究記錄**（本文不改變任何產品行為；含一項對 **ADR-0298 定位與實作順序**的提議）
- 日期：2026-07-31
- 相關文件：
  - **0303 §6／§8**（per-device session 與裝置目錄——**本文回答其〈已知限制〉列為未評估的那一項**）
  - **0107**（自封副本：同一 rumor 包給對方與自己兩份）
  - **0245**（EK 輪替——**本文 §1 顯示它已經把路鋪好了**）
  - **0298**（分層靜態保護與分段金鑰刪除——**本文提議改變其定位**）
  - 0071（加密雲端快照）、0111/0112（OPFS 封存與 nsec 不得明文落盤）
  - 0015/0072（nsec 佈建與配對搬家）、0027（群組成對扇出）
- 資料來源：本倉庫程式碼查證（`packages/core/src/giftwrap.ts`、`snapshot.ts`、`at-rest.ts`、
  `packages/engine/src/storage/local.ts`、`packages/engine/src/backend/relay-backend.ts`）

> **起點**：ADR-0303〈已知限制〉記著一項未評估的風險——
> 「未評估 per-device session 對 **0107 自封副本**、**0071 雲端快照**、**0245 EK 共享**
> 的具體衝擊——**三者都假設「所有裝置解得開同一份密文」**」。
> 該項被判定為「唯一會讓使用者覺得產品壞掉」的候選，故優先查證。
>
> **結論與預期相反**：自封副本是**簡單的那一半**。查下去撞到的是另一件事——
> **ADR-0303 §6 的前提閘門（nsec 冷保存）成本被嚴重低估**。

## 1. 自封副本本身：不是架構問題，因為 ADR-0245 已經把路鋪好了

`packages/core/src/giftwrap.ts:75`：

```ts
return { id, events: to.map(wrapFor), selfCopy: wrapFor(senderPk) };
```

自封副本是**一顆** wrap，定址給自己的身分公鑰。表面上 per-device session 會打掉它
（每台裝置各自的 session ⇒ 一份密文不可能全部解得開）。

**但 `wrapFor` 內已有現成的間接層**（`giftwrap.ts:64-73`，為 ADR-0245 而做）：

```ts
const encryptTo = opts.encryptToFor ?? ((pk) => pk);
const wrapFor = (pk: PubkeyHex): NostrEvent =>
  // 外層 `#p` 仍為身分 pk（供路由/收件匣）；加密對象為其 EK（FS）或身分（退回）。
  sealAndWrap(input, senderSk, encryptTo(pk), { kind: ..., tags: [["p", pk], ...] });
```

⇒ **路由層（`#p` ＝ 身分）與加密目標早已解耦**。per-device 只需把
`encryptToFor: (identityPk) => pk` 改為回傳**多個**目標（該身分的各裝置），
**不是架構改動**。

⇒ 至於辨識那一半——`relay-backend.ts:1629` 的 `const selfCopy = sender === this.self.pubkey;`
在 `openWrap()` 改回傳裝置公鑰後會失效，但**ADR-0303 §8.3 的單一正規化收口已經蓋掉它**
（解回身分層、下游不改）。

**⇒ 自封副本這一格不會讓產品壞掉。ADR-0303 的擔心在此項上可以降級。**

## 2. 但扇出成本 ADR-0303 漏記了自己這一邊

0303 §「後果」記了群組 **O(N×D)**，但沒算自封副本的 `D_self - 1`。

| 情境 | 今天 | D=4（雙方皆是） |
| --- | --- | --- |
| 1:1 | 2 顆（對方＋自己） | 4 ＋ 3 ＝ **7 顆**（3.5×） |
| 群組 N=10 | 10 顆（9 ＋ 自己 1） | 9×4 ＋ 3 ＝ **39 顆**（3.9×） |

⇒ 不影響可行性，但 **ADR-0303 §「代價」該補上 `+ (D_self − 1)` 這一項**，
且它與 ADR-0263 的回條 O(N²) 疊加時要一併看（0303 已提示壓縮 `GROUP_RECEIPT_LIST_MAX`）。

## 3. 🔴 真正的發現：三處**直接從 nsec 導金鑰**

查證過程中撞到的，才是本文的主要內容。**有三個地方假設「這台裝置手上有 nsec」**：

| 位置 | 用途 | 怎麼導 |
| --- | --- | --- |
| `packages/core/src/snapshot.ts:33` | **雲端快照**（0071） | `encryptDM(plaintext, sk, getPublicKey(sk))` ＝ 自己對自己 NIP-44 |
| `packages/core/src/at-rest.ts:36-38` | **本機靜態加密**（0112） | `hkdf(sha256, secretKey, undefined, "cinder-storage-v1", 32)` |
| `packages/core/src/giftwrap.ts:75` | 自封副本（0107） | `wrapFor(senderPk)` |

且 `packages/engine/src/storage/local.ts:101` 顯示本機那把是**整個儲存層的 DEK**：

```ts
this.dek = secretKey ? deriveStorageKey(secretKey) : undefined;
```

而 `local.ts:106` 的 `storageKey()` 註解寫明「**供 OPFS 封存共用同一把**（ADR-0112）」
⇒ **熱區儲存與冷封存用的是同一把、同一個來源。**

### 3.1 ⇒ ADR-0303 §6.2 對「nsec 冷保存」的成本估計錯了

0303 §6.2 的 C 列把它寫成「需把身分金鑰移出熱路徑（**動 0015/0072**）」。

**不只 0015/0072。** 裝置上沒有 nsec 時：

- 雲端快照**導不出金鑰**（`snapshot.ts:33` 需要 `sk`）
- **本機資料庫與 OPFS 封存整個沒有 DEK**（`at-rest.ts:36` 需要 `sk`）

⇒ 第二項是致命的：**裝置上沒有 nsec 的話，本機資料用什麼加密？**
這不是「附帶要改的模組」，這是**沒有答案就走不下去**的問題。

⇒ **⚠ 這一項與 per-device session 無關。** 它是**冷保存閘門本身**的成本，
而該閘門在 0303 中是 §6 全部方案的共同前提。

## 4. ⇒ ADR-0298 的定位要改：它不是加強項，是這條路的地基

ADR-0298（分層靜態保護）設計的正是「**以密碼導出 `K_root`**」來承擔靜態加密，
而不是從 nsec 導。

⇒ **它恰好就是 §3 那個「沒有答案就走不下去」的答案。**

⇒ 定位改變：

| | 原定位 | 本文提議 |
| --- | --- | --- |
| ADR-0298 | 獨立的靜態保護加強（提議中、可選） | **nsec 冷保存的前置**；沒有它，0303 §6 整條路不成立 |

⚠ 但 ADR-0298 自己仍是**提議中**，且其〈已知限制〉列著三項未決：
**遷移狀態機、搜尋範圍揭露、N 與分段粒度**。⇒ 這些現在都變成 §6 的阻擋項。

## 5. 一個使用者看得見的退步：新裝置對「加入前」的訊息永遠是空的

**今天**：新裝置取得 nsec（配對或救援）→ 訂閱自己的 `#p` →
中繼上**還在 7 天窗內的自封副本它全解得開**（因為共用 nsec）。

**per-device 之後**：訊息只加密給**送出當下已在清單裡的裝置**。
新加入的裝置對更早的訊息**永遠沒有金鑰**——不是「暫時看不到」，是**不存在解法**。

⇒ **配對搬家（0072）從「方便功能」變成「必要步驟」。**
⇒ 且 0072 要求**兩台同時在線**（P2P），該限制隨之從可繞過變成**硬性**。
⇒ 這與 ADR-0303〈已知限制〉記的 Signal 對照（他們用伺服器上的加密封存檔、可非同步）
   是同一格——我們的隱私較強，代價在此處具體化。

## 6. 依賴鏈：而 FS **不在**這條鏈上

把上述整理成順序：

```
ADR-0298（密碼導出 K_root）
    ↓ 沒有它，裝置上就不能沒有 nsec
nsec 冷保存
    ↓ 0303 §6 全部方案的共同前提閘門
裝置授權（加＝live 配對／刪＝救援碼）
    ↓
裝置撤銷
```

**而棘輪 FS 不在這條鏈上。** ADR-0303 §2 已證明：

| 目標 | 需要 | 需放棄共用 nsec？ |
| --- | --- | --- |
| 棘輪可行（per-message FS） | per-device 預金鑰＋session＋可列舉對方裝置 | **不用** |
| 裝置撤銷 | 身分金鑰不在每台裝置上＋一個權威 | 要 |

⇒ **FS 可以先走，撤銷那條後面再說。** 這是本文最有價值的一項結論：
兩者原本被 ADR-0236 §43 的錯誤敘述綁在一起（見 0303〈提議〉1），拆開後路徑短很多。

## 決策（研究記錄，未決策）

1. **ADR-0303 §「已知限制」中「自封副本」那一項可降級**——它有現成鉤子（§1）。
2. **ADR-0303 §6.2 的 C 列成本描述應更正**——「動 0015/0072」不足以描述冷保存的成本（§3.1）。
3. **提議把 ADR-0298 重新定位為 0303 §6 的前置**，並據此調整實作順序（§4）。
4. **FS 與撤銷解耦，FS 先行**（§6）。
5. 本文**不決定** ADR-0298 的三項未決，也不決定裝置數上限 D。

## 後果

**正面**

- 把 0303 一項標為「未評估」的風險查到底，並**推翻了它的嚴重性排序**：
  自封副本不是問題，冷保存閘門才是。
- 找到 ADR-0298 與 ADR-0303 之間**先前沒被連起來的依賴**——兩份 ADR 各自寫作時
  都沒有指向對方，而其中一份其實是另一份的地基。
- 確認 **FS 不需要等這整條鏈**，縮短了 FS 的關鍵路徑。

**負面／代價**

- ADR-0303 §6 的整條路**比原本估計的遠**：多了一份仍為提議中、且自身有三項未決的前置。
- §5 的退步是真實且不可逆的（新裝置拿不回加入前的訊息），只能靠 0072 補，
  而 0072 要求兩台同時在線。

**已知限制**

- **未實作、未測試**；§2 的扇出數字是算出來的，**未量測**實際事件體積與中繼負載。
- **未評估 ADR-0245 EK 共享**受到的衝擊——0303 把它與自封副本、雲端快照並列，
  本文只查了後兩者。EK 目前如何在裝置間同步、per-device 後是否還需要同步，**未查**。
- **未評估 ADR-0107 自封副本的「回條先於自封副本抵達」暫存邏輯**
  （`relay-backend.ts:549` 註解描述的亂序處理）在 D 倍扇出後是否仍成立。
- 未評估 §5 的退步對「使用者實際感受」的嚴重程度——沒有使用者研究，
  這是**我的判斷**，不是實證。
- 未查 `deriveStorageKey` 的 `INFO` 版本化（`cinder-storage-v1`）是否足以支撐
  從 nsec 導改為從 `K_root` 導的**平行共存與遷移**——這正是 ADR-0298 未決的
  「遷移狀態機」那一項，兩者應一併處理。
