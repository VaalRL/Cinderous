# ADR-0287：行動端對話畫面不得橫向溢出

- 狀態：已接受
- 日期：2026-07-29
- 相關：ADR-0085（行動端畫面）、ADR-0277（行動端正式進入點）、ADR-0284（安全區與鍵盤修正）

## 脈絡

實機回報：對話開啟後畫面**比螢幕寬**，要往右滑才看得到送出鈕。

ADR-0284 已經修過安全區與鍵盤，但那兩項不影響寬度。真正的原因在輸入列，把數字攤開就很清楚：

| 元件 | 寬度 |
| --- | --- |
| 5 顆圖示（📎📷🗄😊⏱），各約 34px | ~170 |
| 6 個 `gap: 8` | 48 |
| 容器 `padding: 8` 左右 | 16 |
| 送出鈕 | ~60 |
| 輸入框 | **~173** |
| **合計** | **~467** |

而手機寬度是 360–412px。

關鍵在最後一項：`TextInput` 在 react-native-web 下就是一個 HTML `<input>`，
**有約 173px 的內建寬度（`size` 屬性），而且 `min-width: auto` 讓它拒絕收縮**。
`flex: 1` 只給了它「可以長大」，沒有給「可以縮小到內容以下」。
於是這一列硬是撐到 467px，整個畫面跟著橫向溢出。

同一類問題也在標頭：`headText: { flex: 1 }` 沒有 `minWidth: 0`，且對話名稱沒有截斷——
名字一長，標頭同樣會被撐寬。

## 決策

三項一起，缺一不可：

1. **輸入列可折行**（`flexWrap: "wrap"`）：塞不下時折到下一行，而不是把畫面撐爆。
2. **輸入框給明確最小寬度**（`minWidth: 160`）：解除 `min-width: auto` 的拒縮，
   同時保證折行後仍有足以打字的寬度。
3. **送出鈕不收縮**（`flexShrink: 0`）：被擠掉的話這個畫面就沒有主要動作了。

標頭一併修：`headText` 加 `minWidth: 0`，對話名稱 `numberOfLines={1}`。

**不把圖示藏進「＋」選單**：那是更大的 UX 變動，且現有測試對「提供 `onSendPhoto`
→ 📷 出現」等行為有明確斷言；折行已足以解決溢出，五顆圖示仍全部可見。

## 測試怎麼寫的

react-native-web 把版面樣式編成 class（`r-flexWrap-…`），hash 是它的內部實作，
寫死會在升版時假性失敗。所以用**探針法**：測試裡先渲染一個帶目標樣式的 `View`，
取出它的 class，再比對真實元件——不綁死 hash。

而且斷言**指名道姓**到 `testID`：`flexWrap: "wrap"` 在這個畫面另有 6 處使用
（貼圖格、附件分頁、日期 chip…），掃整份 HTML 會誤判成通過。
寫完後把修正暫時拿掉跑過一次，確認三條斷言真的會紅，才算數。

## 後果

**正面**

- 畫面不再橫向溢出，送出鈕永遠看得到。
- 有回歸鎖：日後有人拿掉 `flexWrap` 或 `minWidth` 會被測試擋下。

**負面／代價**

- 窄螢幕上輸入列會變成兩行，佔掉一點訊息區高度。這是「全部功能可見」與
  「單行緊湊」之間的取捨——選了前者。
- `minWidth: 160` 是個魔術數字。它的意義是「折行後仍打得了字的最小寬度」，
  已寫在註解裡。

**待辦**

- 實機驗收：360px 級的窄機上輸入列是否折成兩行、送出鈕是否可見；長名字的對話標頭不被撐寬。
