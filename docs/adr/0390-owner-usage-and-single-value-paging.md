# 0390. 保底用量照實扣、單一值的查詢順著索引分頁

- 狀態：已接受（未部署）
- 日期：2026-10-20
- 相關文件：ADR-0389（同一次量測的前半）；SDK ADR 0103（同一件事在 SDK 中繼）；SDK ADR 0042（保底份額）、SDK ADR 0084（外掛啟動從頭補拉收件匣）；ADR-0371 §決策 6（位元組預算的兩步查詢）、ADR-0372（`json_each` 綁定）

## 背景與問題

ADR-0389 修完後，同一套 `wrangler dev` 量測還剩兩處讀取，使用者 2026-10-20 決定都處理：

1. **保底用量快取被作廢後要重建**：
   - 每收件人上限刪了某人的列，會逐人重算 `refreshOwner`，每次約 1,400 列。
   - 整批淘汰、舊版天花板淘汰之後，會把整個快取（`ownerNormal`）丟掉，下次判斷保底時 `GROUP BY` 掃過整個分桶索引重建，每次約 4,200 列。
   - 塞滿後每寫一顆平均還要讀 42 列，主要就是這裡。
2. **外掛每次啟動從頭補拉收件匣**（SDK ADR 0084）：
   - 收件匣塞滿（約 1,430 塊）時，一次約讀 3.4 萬列。
   - 原因是 `#p`、`kinds` 都以 `IN (SELECT value FROM json_each(?))` 下推，SQLite 不能順著分桶索引的順序讀。
   - 所以每一頁都得把這位收件人剩下的列全部拿出來排序，有位元組預算時還排兩次（先查大小、再取內容）。

## 考量的選項

保底用量：
- A1：刪幾列扣幾列（使用者選定）。
- A2：只重算那一個人。
- A3：不動。

啟動補拉：
- B1：中繼改查法（使用者選定）。
- B2：中繼改查法，外加外掛限制從頭讀的頻率。
- B3：只改外掛的頻率。

## 決策

1. **保底用量照實扣**：`describeRows` 多帶出每列的大小、是否借用列、作者，新增 `forgetUsage`：
   - 刪掉借用列：借用總量扣掉它的大小。
   - 刪掉正常列：那個人（收件人；沒有收件人時是作者）的正常列用量扣掉它的大小。
   - 用在每收件人上限、舊版天花板淘汰、整批淘汰（同批的列多讀 `borrowed`、`pubkey`，只有那幾列）。
   - 不再 `refreshOwner`，這個方法因此刪掉。也不再把快取整個丟掉。
   - 只有 `prune`、`vanish` 這類算不出確切數字的路徑照舊作廢，每小時一次或清除帳號時。
2. **單一值直接比等號**：`pushIn` 遇到只有一個值時寫成 `column = ?`。
   - 外掛的補拉正是一位收件人、一種 kind，SQLite 就能順著分桶索引讀，夠一頁就停，只有同一秒的那幾列需要排序。
   - 多個值照舊用 `json_each`，綁定參數仍是固定數量（ADR-0372）。

## 理由

同一套量測（錨點檔案車道設定，三位收件人輪流寫 128 KB 檔案塊）：

| | 塞滿後每寫一顆平均讀 | 最多一次讀 | 一次啟動補拉（約 1,430 塊） |
|---|---|---|---|
| ADR-0389 之前 | 172 | 10,438 | 33,828 |
| ADR-0389 | 42 | 1,541 | 33,828 |
| 本 ADR | **25–30** | **約 830** | **約 18,200** |

- 行為不變：保底的判斷用的是同一個數字，只是不再重算。有測試比對快取與實算完全一致。
- B1 讓所有客戶端都受惠，不改協定。B2 的外掛頻率限制要拿「收不齊的塊晚一天才確認」來換，使用者沒有選。

## 後果

- 正面：塞滿後每寫一顆的讀取再降約三分之一，最壞一次降約一半；一次啟動補拉降約一半。
- 負面 / 已知殘餘風險：
  - 補拉每一頁的「先查大小」仍會讀到筆數上限 1,024 列（大小欄 `COALESCE(bytes, LENGTH(json))` 不在索引上，每列還要回大表），而一頁實際只取約 130 塊。要再降，得把大小改成只讀索引上的 `bytes`，並分段查大小。舊版程式寫入、`bytes` 還沒回填的那段期間，預算會算不準。這次不做。
  - 整批淘汰時多讀同批那幾列的 `borrowed`／`pubkey`，要走大表的溢位頁。這是 I/O 成本，不是讀取列數。
- 驗證：`relay/src/evict-reads.test.ts`：
  - 錨點比例下塞滿後連續寫入，沒有 `GROUP BY`、沒有逐人重算，且快取與實算一致；
  - 補拉形狀的查詢計畫沒有整個重排；
  - 多個值的查詢結果不變。
  - `sql-message-store.test.ts` 三則「下推到 SQL」的斷言改成接受 `IN` 或 `=`。
- 後續行動 / 待辦：
  - 與 ADR-0389 一起部署到錨點。使用者 2026-10-20：「等下面處理完後再部署」。
  - SDK 中繼同步修改（SDK ADR 0103）。
