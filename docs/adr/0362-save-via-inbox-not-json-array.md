# 0362. 另存改走暫存區——匯出紀錄那條路沒有任何大小上限

- 狀態：已接受
- 日期：2026-09-18
- 相關文件：ADR-0093（收檔另存，App 不保管檔案本體）、ADR-0094（明文紀錄導出）、
  ADR-0128（webview 信任邊界與讀檔白名單）、ADR-0347／0349（收檔串流落盤與原生另存）、
  ADR-0346（大檔惰性讀取）

## 背景與問題

桌面端的兩個「另存」入口都走同一個 Rust command：

```ts
invoke("save_file", { name, bytes: Array.from(bytes) })
```

`Array.from` 先把 `Uint8Array` 攤成一個**每格一個 JS number** 的陣列（8 bytes/格），
Tauri 再把整份序列化成 JSON 文字（一個位元組在途中是「`255,`」這樣四個字元）。
峰值大約是原始大小的**十倍上下**，而且在寫出第一個位元組之前就已經全部發生了。

兩個入口的風險不同：

| 入口 | 大小上限 |
| --- | --- |
| `saveIncomingFile`（收到的檔案） | 8 MiB——超過就走 sink 落盤（ADR-0347），不會到這裡 |
| `saveTextFile`（匯出紀錄，ADR-0094） | **沒有上限** |

`exportRecords` 產出的文字要多大有多大。用了幾年的人匯出 JSON 輕易就是上百 MB，
而 `Array.from` 到那個尺寸是必掛的——**而且掛的時機是使用者按下「匯出」之後**，
也就是他最不想失敗的那一刻。

諷刺的是，ADR-0349 已經為收檔做好了整條「零位元組過 IPC」的機制，
另存這一側卻沒有用上。

## 考量的選項

- **A：只給匯出加大小上限。** 否決：那是把「我們做不到」包裝成「你不該這樣做」。
  匯出自己的紀錄是 ADR-0094 明白承諾的能力，不該因為傳輸方式而被截斷。
- **B：新增一個吃 raw bytes 的 IPC command**（`tauri::ipc::Request` 的 `InvokeBody::Raw`）。
  否決：可行，但會是一條**與暫存區平行**的新路徑，而 `valid_handle` 那類路徑穿越守衛
  就得再寫一份。ADR-0361 才剛因為平行路徑刪掉一整個模組。
- **C（採用）：重用 ADR-0349 的暫存區機制。**

## 決策

`saveIncomingFile` 與 `saveTextFile` 的 Tauri 分支都改走 `saveViaInbox()`：

```
inbox_begin → inbox_write × N（每塊 1 MiB）→ save_from_inbox（原生移動，零位元組過 IPC）
```

峰值因此被**一塊**的大小釘死，與檔案總大小無關。

`save_file` command 隨之刪除——它已經沒有呼叫者，而留著沒有呼叫者的東西正是 ADR-0361
剛處理過的問題。ADR-0128 的讀檔授權不受影響：`save_from_inbox` 一樣呼叫 `authorize_path`，
兩處提到 `save_file` 的註解改指它。

### 取消時丟棄暫存檔

收檔那側刻意**保留**取消後的暫存檔（「他可能想再存一次」）。這裡相反：暫存檔是我們
為了這一次另存才剛造出來的，取消就是放棄。寫入途中失敗也一樣丟棄——否則每一次
磁碟寫滿都留下一份，要等 `inbox_sweep` 24 小時後才收。

## 理由

- **機制已經在那裡了。** ADR-0349 解的是同一個問題的另一半（收進來），而它解得更徹底
  （原生移動）。另存這一側不用它，純粹是當初沒想到要回頭看。
- **1 MiB 一塊是有意的折衷**：收檔那側用 16 KiB（要配合網路分塊與進度回報），
  本機另存沒有那些顧慮，大塊能少掉幾百次 IPC 往返，而十餘 MB 的峰值無關痛癢。
- **刪掉 `save_file` 而不是留著備用**：沒有呼叫者的 command 仍然是 webview 打得到的
  攻擊面（ADR-0128 的前提正是 webview 不可信），留著只有壞處。

## 後果

- **正面**：匯出紀錄不再有實質大小上限；收檔另存的峰值也從 8 MiB × 10 降到 1 MiB × 10。
- **正面**：桌面端所有「位元組落到磁碟」的路徑現在統一經過暫存區，守衛只有一份
  （`valid_handle`），要稽核的地方也只有一個。
- **負面 / 已知殘餘風險**：
  - **對話框出現的時機變了**：舊路徑是先跳對話框再寫檔，新路徑是先寫進暫存區再跳。
    大檔匯出時使用者會先等一下才看到對話框。這與收檔那側的體驗一致，但確實是行為改變。
  - **磁碟會被寫兩次**（暫存區一次，移動一次）。同一個磁碟上 `rename` 是免費的；
    跨磁碟另存時會退化成真的複製。收檔那側早就是這樣，不是新引入的。
  - **匯出的明文會短暫落在暫存區**。ADR-0094 的匯出本來就是明文落地（那是它的用途），
    但暫存區多了一個副本；若使用者在對話框上取消，它會被立刻丟棄，異常中止則由
    `inbox_sweep` 在 24 小時內回收。這一點值得知道。
  - `inbox_write` 的參數仍是 `Vec<u8>`，所以**每一塊**依然走 JSON 數字陣列。
    真正的 raw IPC 是進一步的最佳化，本 ADR 不做——有界之後它就不再是正確性問題。

## 後續行動 / 待辦

1. 實機驗收：匯出一份大紀錄（>100 MB），確認對話框跳得出來、檔案內容正確。
2. 實機驗收：另存時取消，確認暫存區沒有殘留 `.part`。
