# 0411. 企業 G5：SSO 綁定與連線元資料稽核——範圍、紅線與分期（只定設計，實作等企業試點）

- 狀態：已接受（**只定設計**；實作要等企業試點與真實 IdP，**尚未動工**）
- 日期：2026-11-11
- 相關文件：PRD §13（企業模式）；ADR-0044（封閉 allowlist 中繼）、0046（成員判定與對外邊界——
  「公司身分 → npub」唯一綁定點是佈建）、0047（管理者簽章名冊＝成員權威）、0048／0312（名冊政策
  與設定頁條列）、0052（否決金鑰託管）、0057（NIP-42 AUTH；企業原本刻意不用）、0112／0323（本機
  靜態加密與 OS 金鑰庫）、0156（邀請碼入職）、0163（揭露的入職託管）、0237（連線歸屬打穿事件層
  隱藏）、0257 §8（G5 範圍草案，本文把它正式化）、0260（NIP-11）、0261（NIP-86 管理 API）、
  0370（中繼程式碼的單一真實來源在 SDK）；`docs/relay-metadata-observability.md`

## 背景與問題

ROADMAP 與 PRD §13.7 把 G5（SSO／元資料稽核）列為企業模式**唯一未動工**的缺口，ADR-0257 §8
只留了一份草案，並註明「實作前須立 ADR」。使用者決定（2026-11-11）：**先寫 ADR、不實作**，
讓日後企業試點或報價時有現成且已經想清楚紅線的範圍。

企業常見的兩個要求：

1. **SSO**：員工用公司既有帳號（AD／LDAP／OIDC）綁定工作身分，IdP 停用帳號時要能反映。
2. **稽核**：「誰在什麼時候連過公司節點」要查得到。

兩者都直接碰本專案的兩根柱子：**私鑰不離開裝置／無後門**（ADR-0002、0052），以及
**中繼不累積可重建社交圖譜的元資料**（ADR-0237）。草案的做法是可行的，前提是界線寫死；
寫不死的話，G5 會變成一扇後門。

## 考量的選項

### SSO

- **A. IdP 導出或包裹私鑰**（例如用 IdP 的權杖或密碼派生金鑰、或 IdP 保管加密後的 nsec）：
  員工換電腦登入就能還原，最方便。**否決**——這就是 ADR-0052 否決的金鑰託管，而且託管人變成
  第三方 IdP、還不必經過 ADR-0163 的入職揭露。IdP 被攻破＝全公司歷史可解。
- **B. IdP 只當「佈建輸入」與「本機解鎖的政策閘門」**（採用）：IdP 證明「這個人是員工」，
  但金鑰仍由員工裝置自產、自存；IdP 手上沒有任何金鑰材料。
- **C. IdP 取代簽章名冊成為成員權威**（relay 直接問 IdP 誰能連）：**否決**——成員資格會變成
  客戶端無法驗證的東西（ADR-0047 的核心性質），而且 relay 要對外連 IdP，把一個新依賴放進
  訊息主流程。

### 稽核

- **D. 記錄完整連線與事件元資料**（含收件人 `p` tag、訂閱 filter）：資訊最多。**否決**——
  收件人＋時間足以重建誰跟誰講話（`relay-metadata-observability.md` 的 M1／M7），等於在公司
  節點上主動建立社交圖譜資料庫。
- **E. 只記「連線層」元資料，預設關、對員工揭露**（採用）。
- **F. 不做稽核**：最乾淨，但企業採購常把它列為硬需求，結果是企業自己在反向代理加一層、
  記得更多又沒人揭露。提供一個「記得少、有揭露」的官方做法比較好。

## 決策

### 1. 共通紅線（任何分期都不得違反）

1. **IdP 不得成為解密路徑**：IdP 不產生、不導出、不包裹、不保管任何私鑰或資料金鑰。
   需要「雇主持有金鑰」的唯一合法路徑仍是 ADR-0163（邀請碼勾選＋入職明示同意）。
2. **成員權威仍是管理者簽章名冊**（ADR-0047）。IdP 只是名冊的**輸入**，relay 不直接查 IdP。
3. **稽核不記「誰對誰」**：不記事件的 `p` tag、不記訂閱 filter 內容、不記事件內容（本來就是密文）。
4. **稽核只存在自架企業 relay、預設關**；官方錨點（Cloudflare Workers）的設定**不得開啟**。
5. **開了就要讓員工看得到**：透過名冊政策公告、在設定頁「公司政策」條列（ADR-0312），
   並在 NIP-11 宣告（ADR-0260）。沒有揭露就不是稽核，是監控。

### 2. G5a：連線元資料稽核（三期中最小，建議先做）

- **啟用條件**：自架 node／Docker relay 的環境變數開啟，且名冊政策 `auditConnections: true`。
  兩邊都要開：前者是技術開關，後者是對員工的公告；只開前者時 relay 拒絕啟動稽核並記警告。
- **必須同時開 NIP-42 AUTH**（ADR-0057 的 `requireAuth`）。企業節點原本刻意不用 AUTH
  （allowlist 只比對事件簽章），但不認證就無法把連線歸屬到 pubkey，只會剩 IP。
- **記錄欄位**（每條連線一筆）：連線開始／結束時間、通過 AUTH 的 pubkey、來源 IP（可設定
  截斷為 /24、/48 或完全不記）、User-Agent 類別、這條連線發布的事件數與位元組數（按 kind 彙總）、
  斷線原因代碼。
- **不記錄**：見紅線 3；也不記每則事件的時間戳（只有連線層彙總，避免逐則時序比對）。
- **保存**：寫在 relay 主機本地（JSON Lines 或 SQLite），不送第三方；保存天數可設定、
  預設 90 天，到期刪除。讀取介面先只提供本機 CLI 匯出，不做網頁介面。
- **誠實揭露**：能回答「誰、何時、從哪裡連過公司節點、量多大」；**不能**回答
  「誰對誰說了什麼」。但 relay 營運者（即公司）本來就能改程式多記——這是 AGPL 自架的本質，
  我們只能保證官方程式碼不記，並讓員工知道開關有沒有開。
- **程式落點**：中繼程式碼的單一真實來源在 SDK（ADR-0370），稽核實作在 SDK 的 relay 自架執行
  環境，Cinderous 端只負責名冊政策欄位與設定頁條列。

### 3. G5b：SSO 綁定在入職（佈建輸入）

- 延伸 ADR-0156 的邀請碼：邀請碼可要求 `sso`（帶 OIDC issuer 與 client id，不帶秘密）。
- 員工貼碼後，在本機用 OIDC Authorization Code＋PKCE（桌面走 loopback redirect）登入 IdP，
  取得 ID token，**連同入職請求以既有 Gift Wrap E2E 交給管理者**（同 0156／0163 的管線）。
- 管理者端驗 ID token 的簽章、issuer、audience、有效期，通過才核准入名冊。
- **IdP 身分與 npub 的對應只存在管理者本機**（隨管理者身分的加密儲存，ADR-0112），
  **不寫進名冊**——名冊會分發給全員，沒必要讓每位同事都拿到公司帳號識別碼。
- 離職：IdP 停用帳號**不會自動**移出名冊；仍由管理者移除名冊成員（ADR-0047／0052），
  那才是真正會生效的封鎖（allowlist）。自動同步（SCIM 之類）留給之後，屆時走 ADR-0261 的
  `cinder_applyroster` 送入簽章名冊，不讓 IdP 直接改 relay。

### 4. G5c：本機解鎖閘（政策閘門，不是密碼學保證）

- 名冊政策可設 `ssoUnlock: { issuer, clientId, graceHours }`。工作身分要解鎖本機金鑰時，
  先完成一次 SSO；成功後在 `graceHours` 內（預設 72 小時）免再登入，離線也可用。
- 解鎖本身仍走既有機制（OS 金鑰庫 ADR-0323／本地密碼 ADR-0112），SSO 只是放不放行。
- **誠實揭露**：這是**政策閘門**。有本機系統權限、或自行編譯 AGPL 客戶端的人可以繞過。
  真正能執行的切斷只有名冊／allowlist；這一點要寫進企業文件，不得宣稱 SSO 等於「離職後無法解密」。
- IdP 故障時：寬限期內照常使用；寬限期外工作身分鎖住，但**不刪任何資料**，IdP 恢復後解鎖即回復。
  訊息即時性不得因 IdP 故障在寬限期內受影響。

### 5. 分期與前置

| 期 | 內容 | 前置 |
|---|---|---|
| G5a | 連線元資料稽核 | 一座自架企業 relay；SDK 加稽核模組；名冊政策欄位 |
| G5b | 入職 SSO 綁定 | 一個真實或開源 IdP（例如 Keycloak）作為試點與測試環境 |
| G5c | 本機解鎖閘 | G5b 完成；桌面先做，行動端隨企業功能補齊 |

每期動工前照 TDD；若實作時發現本文的欄位或流程需要調整，在本 ADR 補充或另立 ADR 取代。

### 6. 明確不做

- IdP 派生或保管金鑰（紅線 1）。
- 稽核記錄收件人、訂閱 filter、逐則事件時間（紅線 3）。
- 官方錨點開稽核（紅線 4）。
- 讓 IdP 或 SCIM 直接改 relay 的 allowlist（紅線 2）。
- 以 IP 為單位的封鎖清單（同 ADR-0261 的理由）。

## 理由

- 選項 B＋E 讓企業拿到真正需要的兩件事——「入職確認是員工」與「連線紀錄」——而不需要碰
  私鑰或社交圖譜。需要更多的企業，已經有 ADR-0163 這條揭露過的路，或是系統外的 MDM。
- G5a 先做：它只動 relay 與政策欄位，不碰客戶端金鑰流程，風險最低、最常被採購要求。
- 把「SSO 只是政策閘門」寫進決策而不是只寫在文件，是為了防止日後行銷或銷售文案把它講成
  密碼學保證（同 ADR-0306 不對等宣稱的精神）。

## 後果

- 正面：G5 有了可以直接報價、拆期實作的範圍；三條紅線讓日後的討論可以直接引用，
  不必每次重新論證。
- 負面／已知殘餘風險：
  - 稽核要求企業節點開 NIP-42 AUTH，等於多一層連線時的簽章往返；企業節點流量小，可接受。
  - 公司作為 relay 營運者可以改程式多記元資料；本專案只能保證官方程式碼與揭露機制。
  - G5c 可被有本機權限的人繞過（已在決策中揭露）。
- 後續行動／待辦：
  - 企業試點出現時，依第 5 節選定期別並各自開 PR（SDK＋Cinderous）。
  - 實作 G5a 時同步更新 `ARCHITECTURE.md` 企業模式段落、`docs/SELF-HOSTING.md`、PRD §13.7。
