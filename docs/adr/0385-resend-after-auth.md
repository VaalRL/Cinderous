# 0385. 認證前送出被拒的事件，認證完成後由連線自動重送

- 狀態：已接受
- 日期：2026-10-14
- 相關文件：ADR-0057（NIP-42 認證）、ADR-0041（外送匣只保護 kind 1059）、ADR-0072（配對信令原本自帶的重送）、ADR-0241（presence 獨立層）、ADR-0383（跨錨點）、ADR-0384（直連協商）；ARCHITECTURE.md〈Nostr 事件契約〉

## 背景與問題

錨點在連線一開就送出 NIP-42 挑戰，認證完成前收到的 `EVENT` 一律回 `OK false "auth-required: …"`（2026-10-14 以一次性金鑰實測：同一座、同一顆心跳，認證前被拒、認證後收下）。而 `webSocketConnector` 在連線一開就把排隊的事件送出去——**一定早於認證**。

- 私訊（kind 1059）有外送匣，`auth-required` 被歸為暫時性錯誤、退避後重送，所以只是晚一點到。
- **即時事件沒有外送匣**：心跳（kind 20000）、直連信令（21000）、輸入中、敲一下。剛連上時送的那一顆就此消失。

實際後果（2026-10-14 跨錨點實測）：

- 重新整理後的第一顆心跳沒到 presence 層，對方要等下一顆（沒人在線時 5 分鐘一次）才看得到我上線——兩邊都顯示對方「離線」。
- 跨錨點寄信令要新開一條到對方錨點的連線，那條連線的第一顆 answer 被拒，直連卡住（ADR-0384 的「answer 掉了」就是這樣來的）。

配對信令（`pairing-transport.ts`）早就遇過同一個問題，在那一層自帶了「被拒就等認證後重送」；聊天的連線沒有。

## 考量的選項

- 選項 A：在 `RelayClient`（core，所有連線共用）處理：認證前送出的事件先記著，被回 `auth-required` 就等認證成功再送一次。
- 選項 B：連線一開先不送，等認證完成才送。但開放中繼不會發挑戰，要等多久無從判斷；也會讓不需要認證的中繼變慢。
- 選項 C：每種即時事件各自補重送（像配對那樣）。重複實作，漏一種就又是同一個問題。

## 決策

採選項 A，並把配對信令那份移除（單一真實來源）：

1. 有 `authSigner` 的連線（會回應挑戰）在**尚未認證**時送出的事件記在 `preAuth`（上限 200 顆，最舊的先丟）。
2. 這些事件被回 `OK false` 且理由以 `auth-required` 開頭 → 放進 `awaitingAuth`，**不轉給 `onOk`**（是時間點的問題，不是事件的問題，不該讓外送匣把它當失敗）。
3. 認證成功 → 先呼叫 `onAuthenticated`（上層重掛訂閱），再把 `awaitingAuth` 依序重送。之後該事件的 `OK` 照常轉給 `onOk`。
4. 認證**之後**才送、仍被回 `auth-required` 的（例如中繼要求重新認證）照常轉給 `onOk`，不自己重送；其他拒收理由一律照常轉。
5. 收到新的挑戰、或連線斷了（`connectionLost()`，`webSocketConnector` 在 `close` 時呼叫；同一個 client 會沿用到重連後）→ 回到「尚未認證」。
6. 沒有 `authSigner` 的連線（開放中繼）完全不受影響。

## 理由

- 修在所有連線共用的那一層，心跳、信令、輸入中、敲一下、私訊一次全好，之後新增的即時事件也不必記得補。
- 不延遲任何送出：開放中繼照舊直接送；要認證的中繼只有被拒的那幾顆晚一點點（認證通常在 1 秒內完成）。
- 私訊同樣受益：原本靠外送匣退避重送，現在認證完成就立刻補送。

## 後果

- 正面：剛連上時的心跳與直連信令不再消失；跨錨點的在線狀態與直連在實測中都能在第一輪建立。
- 負面 / 已知殘餘風險：
  - 認證前送出、但認證一直沒成功的事件會留在 `awaitingAuth` 直到連線關閉（量很小；連線重建時是新的 client 或 `connectionLost` 後再被拒時重新累積——不會無限長，但也不會主動清）。
  - 錨點有時對同一條連線發兩次相同挑戰（實測可見），兩次的認證事件 id 相同，不影響判斷。
- 後續行動 / 待辦：無。測試：`packages/core/src/relay-client.test.ts`〈認證前送出的事件〉5 項；配對信令原本那一項（以假 handler 驅動）移除，`requireAuth` 中繼上的配對互通測試保留。
