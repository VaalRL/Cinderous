# 0381. 檔案車道開保底份額與溢位帶：每位收件人保底 64 MiB、天花板之上借用 20%

- 狀態：已接受 (Accepted)——2026-10-14 使用者核准（「ok」）；部署另需同意
- 日期：2026-10-14
- 相關文件：ADR-0371（檔案車道、每收件人 1,440 塊）、0377（天花板預算）、**0379**（容量訊號；當時保底與溢位帶不開的理由）、0380（收件確認）；
  SDK（cinderous-sdk-dev）ADR 0038（P1 客戶端耐久度、P2 保底）、0039（B1 溢位帶）、0041（`borrowed` 非耐久）、**0042**（保底與溢位帶的語意）；
  CinderSync ADR 0016（丟棄通知）、0072；`relay/wrangler.toml`、`relay/src/wrangler-vars.test.ts`

## 背景與問題

2026-10-14 手機（Pixel 8a）同步時收到 `warning: dropped:`：錨點 1 的 `app:cindersync` 在收件確認（ADR-0380）部署前已用到 95%，
淘汰制滿了就刪**整顆 DO**最快到期的列——桌機持續寫入檔案塊，手機還沒收的被擠掉。檔案車道所有使用者共用一顆 DO（ADR-0366），
沒有保底時任何人的大量同步都能刪掉別人還沒收的資料，寄件端還以為送到了（`OK true`）。

ADR-0379 不開保底與溢位帶的兩個前置條件，對檔案車道都已滿足：
- **溢位帶**：怕 App v0.0.18 把只存 2 小時的借用當成送達。檔案車道的客戶端只有 CinderSync 與 Cinder Coffice，都跑 SDK ≥ v0.33，
  `borrowed` 算即時送達、不算耐久收下（SDK ADR 0041），會補到備援。App 不連檔案車道。
- **保底**：「超出保底的人被拒」要客戶端接得住（SDK ADR 0038 P1）——SDK v0.33 起有耐久度、全滿回報與長退避；CinderSync 有「中繼都滿了」的提示與待送佇列。

## 考量的選項

- 選項 A：維持現狀，只靠收件確認讓空間不再塞滿。——確認讓**正常**情況不滿，但滿的時候誰被刪仍是整顆 DO 的 FIFO。
- 選項 B（採用）：只在 `file` 類開保底＋溢位帶。
- 選項 C：重新分配天花板，把冷門 DO 的額度挪給檔案車道。——加大空間，但不改「別人擠掉我」的語意；需要時另案。

## 決策

`relay/wrangler.toml` 兩份 vars（頂層與 `env.unified`）：

```toml
DO_GUARANTEE_KIB = "file=65536"   # 每位收件人（可尋址：每位作者）保底 64 MiB（中繼接受的上限）
DO_BORROW_PERCENT = "file=20"     # 天花板之上借用 20%，保存 2 小時
```

- 64 MiB ≈ 一位收件人最壞配額（1,440 塊 ≈ 126 MB）的一半；512 MiB 的離線天花板可以讓 8 位收件人都在保底內。
- 滿了的時候（SDK ADR 0042 §2、§3，`capacity.ts` 的 `decideCapacity`）：
  - 收件人仍在保底內 → 先刪借用列，再刪**別人超出保底的部分**（最快到期優先），任何人不會被刪到低於保底；騰不出來就拒收、一列都不刪。
  - 收件人超出保底 → 只能借用（`OK true "warning: borrowed: 7200: …"`，2 小時、最先被刪；每人最多借帶子的 1/16）；借不到回 `OK false "blocked: ceiling: …"`。
- 嚴格平面、一般車道、共用分片不變（理由見 ADR-0379）；`wrangler-vars.test.ts` 釘住「只有 `app:cindersync`、`app:cinder-coffice` 有保底與溢位帶」。
- 沒有程式與 schema 變更（ADR-0379 已移植 `borrowed` 欄與部分索引）。

## 後果

- ＋ 一位收件人的大量同步不再刪掉別人還沒收的資料；超量的那一方當下就知道（`borrowed`／`blocked`），由寄件端的佇列與備援接手，不再是收件人事後才收到 `dropped`。
- － 寄件端看到的失敗變多：原本「先成功、之後被擠掉」變成「直接拒收」——這正是目的（SDK ADR 0038 決策 1）。
- － **可尋址的保底（64 MiB）大於可尋址天花板（32 MiB）**：每位作者都在保底內，可尋址側滿了不再淘汰別人、改成拒收。CinderSync 的可尋址資料很小，預期碰不到；碰到時由預警（80％）先看到。
- － **預算**：溢位帶在兩側都生效（淘汰制有保底時），最壞量 = 3,724,541,952 ＋ 2 × (⌊512 MiB × 0.2⌋ ＋ ⌊32 MiB × 0.2⌋) = **3,952,712,088 bytes**，
  ≤ 4,000,000,000；餘裕 45.1 MiB——**APP_LANES 一條都不能再加**（每條 64 MiB），要加車道先調降別處或把溢位帶降到 10%。
- 部署：沒有遷移；比照 ADR-0380 記兩座回滾點、部署後查 `/app/cindersync` 的 NIP-11 多了 `cinder_guarantee_bytes`（67108864）與 `cinder_borrow_ttl_sec`／`cinder_borrow_percent`（20）／`cinder_borrow_planes`，其他欄位不變，並以 CinderSync 實機同步一輪確認沒有新的拒收。
- 驗證：`relay/src/wrangler-vars.test.ts`〈保底與溢位帶只開在檔案車道〉。
