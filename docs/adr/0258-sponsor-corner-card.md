# 0258. 「贊助此節點」角落卡（ADR-0089 決策 2 落地）

- 狀態：**已接受（已實作）**
- 日期：2026-07-27
- 相關文件：**ADR-0089**（營運者贊助入口——本 ADR 完成其「後續行動 2」，決策 2/3/4 皆在此落地）、
  0256（relay 端 NIP-11 文件＝本卡的資料來源）、0253（社群 relay 的永續性問題）、
  0034/0035/0039（relay pool／hint 學習／錨點——**為何只對 home 顯示**的理由來源）、
  0044/0045（企業身分）、0038（URL 風險）、PRD §12（非金融 App、非廣告）；
  `packages/engine/src/backend/relay-info.ts`、`apps/desktop/src/ui/SponsorCard.tsx`

## 背景與問題

ADR-0089 決定讓使用者能自願贊助**目前所連中繼站**的營運者，並列了三項後續行動。
ADR-0256 做完第 1 項（relay 端回 NIP-11 文件）；**第 2 項（客戶端讀取＋桌面角落卡）尚未做**
——於是營運者填了 `cinder_donations` 也沒有人看得到。本 ADR 補完。

動機不是新的：ADR-0253 算過，公共 relay 的營運**結構上不可能盈利**，只能靠營運者自費與自願
贊助支撐。那份分析的結論之一就是「若要支撐社群營運者，優先實作 ADR-0089 的導流」。

## 決策

### 1. engine：`relay-info.ts`——抓取與**把不可信輸入擋在 UI 之外**

- `fetchRelayInfo(url)`：對 `https://<host>/` 帶 `Accept: application/nostr+json` GET，
  比照 `turn-fetch.ts`（ADR-0243）的形狀：可注入 fetch、**任何失敗一律回 `undefined`**。
  贊助卡是純加分功能，抓不到不能影響通訊，也不該在 UI 留下錯誤痕跡。
- **scheme 白名單是這個模組的重點**。文件由**中繼站營運者**提供，而威脅模型把 relay 當對手
  ——這些字串最後會變成可點的 `href`：
  - 三個網頁平台**只收 `https:`**。**刻意不收 `http:`**：贊助連結會把使用者導向輸入付款資訊
    的頁面，明文連線在這個情境沒有任何可接受的理由。
  - `lightning` 正規化為 `lightning:` deep link，且限制在保守字元集
    （擋掉夾帶空白／協定分隔符的怪值）。
  - `javascript:`／`data:`／`file:`／`vbscript:` 等一律丟棄（測試逐一釘死）。
  - 長度有界（URL 512、站名 64）。
- **順序固定**，不隨文件的鍵順序跳動（避免營運者用鍵順序搶眼球）。
- 沒有任何合法項目 → `parseRelayInfo` 回 `undefined`＝呼叫端不顯示卡片。

### 2. 桌面：低調、可關閉、關了就記住

- `SponsorCard.tsx`：右下角固定小卡，**z-index 40**——刻意低於對話框／通話／貼圖編輯器
  （55–70）。它是畫面上最不重要的東西，不該蓋住任何互動。
- 連結一律 `target="_blank" rel="noopener noreferrer"`（沿用專案既有外連方式）；
  `lightning:` 交由 OS 的外部錢包處理。**App 不解析金額、不代付、無站內付款。**
- `sponsor-dismiss.ts`：**依 relay 記，不依身分記**——這是「我對這一座的態度」，換身分不該
  讓它又冒出來；換到別座才該重新問一次。URL 正規化（去尾斜線、小寫）避免同一座被當兩座。
  純本地 UI 偏好 → 裝置層 localStorage，**刻意不進加密儲存基質**，也就不會混進配對捆包／
  快照（ADR-0071/0072）。
- 讀不到 localStorage 時**當作沒關過**：寧可多顯示一次，也不要因儲存故障永久隱藏。

### 3. 只對 **home** 座顯示

ADR-0089 決策 2 明訂「不對錨點／簽章清單自動塞入、使用者未選擇的 relay 跳贊助卡」（防蹭曝光／
釣魚）。對照現況的 pool 組成：

| 座的來源 | 使用者選過嗎 | 顯示贊助卡 |
|---|---|---|
| home（登入／設定填的，或 home 遞補後的健康座） | 是（ADR-0089 明列） | ✅ |
| 錨點常數（ADR-0039） | 否 | ❌ |
| 聯絡人 hint 自動學習（ADR-0035） | 否 | ❌ |

桌面目前也**沒有**「手動加入 relay」的 UI，所以「使用者主動選擇的座」＝home，就這一座。
未來若加了手動加入的入口，該座應一併納入（ADR-0089 原文即如此）。

### 4. 企業身分整個跳過

依 profile 型別 gate（`enterprise` 或 `orgOwner`）——沒有「贊助雇主的 relay」這種語意
（ADR-0089 決策 4）。

### 5. 行動端：不做

ADR-0089 決策 3 的刻意選擇（App 商店對站內捐款流程敏感）。本次**未動 `apps/mobile`**。

### 6. 措辭：三件事必須同時說

卡片文案（中英雙語）同時承載：

1. **「由其營運者自費提供……由該節點自報，非官方背書」**——這是自報，不是我們的推薦；
2. **「完全自願」**——不是慈善勸募；
3. **「本 App 不經手金流，也永不自動付款」**——點擊只會開外部連結。

免責那行刻意排得比連結更小、更淡：它是免責，不是行動呼籲。測試把這三句釘死
——**這些字是這個功能的安全機制**，不是文案潤飾。

## 理由

- **把驗證放在 engine、把誠實放在 UI**：scheme 白名單是技術防線，措辭是社會防線，
  兩者都必要——只有白名單擋不住「偽裝成知名 relay 騙捐」，只有措辭擋不住 `javascript:`。
- **沿用既有形狀**：抓取比照 `turn-fetch.ts`、外連比照 `markdown.tsx`／`BrandWordmark`，
  不新造機制。
- **只對 home 顯示**是 ADR-0089 已經想清楚的取捨，本 ADR 只是把它對應到現況的 pool 組成。

## 後果

- 正面：ADR-0089 的三項後續行動至此全部完成；社群營運者第一次有可見的回饋管道
  （ADR-0253 §2 指出的「收入面為零」不再成立）；使用者對「誰在幫我轉發」有可見度。
- 負面 / 已知殘餘風險：
  - **地址仍是營運者自報**（ADR-0089 已列）：UI 已框為「此節點聲稱」且不自動付款，
    但無法阻止一個惡意 relay 填上別人的收款連結。**未在 App 內驗證營運者身分**
    ——NIP-11 的 `pubkey` 是選填，且不強制對應到捐款帳號。
  - **付款隱私在 App 之外**：導流後由使用者的外部帳號／錢包決定，App 不介入亦不保證。
  - **home 遞補後的座也會顯示**：那時 home 是從簽章清單自動挑的（ADR-0039），嚴格說使用者
    沒「選」過它。仍照 ADR-0089 原文（home 顯示）——它是使用者主要連線的那一座，且清單本身
    有維護者簽章與收錄門檻（ADR-0092）。
  - 每次 home 變更會多一次 HTTPS GET（失敗即靜默）。
- 測試：engine 17（scheme 白名單逐項、lightning 正規化、順序固定、端點推導、
  fetch 的五種失敗路徑）＋desktop 8（連結外開屬性、**三句措辭都在**、站名/URL 退回、
  關閉鈕、空清單不渲染、dismiss 記憶與 URL 正規化、localStorage 不可用不炸）。
  全工作區綠：engine 361、desktop 551、core 463、relay 197、mobile 197、website 51、
  cli 30、theme 14、i18n 8、brand 4；`pnpm -r typecheck` 綠。
- 後續行動：
  1. 自架文件補「如何填 `DONATE_*`」（ADR-0089 後續行動 1 的文件部分仍缺）。
  2. 若日後新增「手動加入 relay」的 UI，該座應一併顯示贊助卡。
