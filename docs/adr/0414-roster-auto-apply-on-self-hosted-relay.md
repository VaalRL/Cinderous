# 0414. 自架站收到管理者簽的名冊就自動換成員（不做「推送名冊」按鈕）

- 狀態：**已接受（Accepted，2026-11-12）**——使用者 2026-11-12 選「中繼自動套用」，不做管理端按鈕
- 日期：2026-11-12
- 相關文件：**0261**（NIP-86 管理 API；本文補它的後續）、**0047**（管理者簽章名冊＝成員權威）、0044（企業封閉 allowlist）、0052（金鑰輪替）、0278／0287（UI 不得說謊）；SDK ADR 0132／0133／**0134**

## 背景與問題

ADR-0261 的實作紀錄留了一項後續：企業管理端加一個「推送名冊到自架站」的按鈕，讓管理者改完名冊就能讓自架中繼跟著換成員，不必請站方重開或手動呼叫 NIP-86。

動工前發現這個按鈕會打破 ADR-0261 §4（本 ADR 最重要的一句）：

- NIP-86 的請求要用**運維金鑰**簽。
- 運維金鑰**不能**是名冊金鑰：名冊金鑰是組織的成員權威，運維金鑰是機器的憑證，可能交給託管方。
- 管理端的 App 持有的就是名冊金鑰（管理者身分）。要它按按鈕推送，就得把運維金鑰也交給它，兩把金鑰又回到同一個人、同一台裝置上。

同時，管理者按「發布名冊」時，名冊事件（kind 10038）**本來就發到組織的中繼**——成員端就是從那裡收名冊的。

## 考量的選項

- **A. 中繼收到名冊金鑰簽的名冊就自動套用（採用）**：改 SDK 的 Node 主機（SDK ADR 0134，v0.89.0）。管理者照常發布，不必有按鈕、不必經手運維金鑰。
- **B. 管理端按鈕，每次貼運維金鑰的 nsec 簽 NIP-98（不存檔）**：只改 Cinderous，但管理者的裝置要經手兩把金鑰，§4 的分離形同虛設。
- **C. 先不做**：站方自己用 NIP-86 工具送 `cinder_applyroster`。對自架的小組織等於沒有執行期改成員。

## 決策

1. **採用 A**。自架 Node 中繼設了 `ROSTER_ADMIN_PUBKEY`，收到那把金鑰簽的名冊事件就換成員（細節見 SDK ADR 0134）：
   - 檢查與 `cinder_applyroster` 完全相同：驗簽、比上次新、`updatedAt` 是秒、成員 pubkey 格式、至少一個在世成員、先存檔後生效。
   - 不需要開 NIP-86 管理 API（只設 `ROSTER_ADMIN_PUBKEY` 時不開 HTTP 端點）。
   - 名冊金鑰一定寫得進這座站，否則管理者沒把自己列進名冊時，下一份名冊會被白名單擋在門外。
   - Cloudflare 版（含官方錨點）不做，同 ADR-0261。
2. **不做「推送名冊」按鈕**。
3. **管理端發布名冊後的說明改成實話**（ADR-0278／0287）：
   - 原文案「名冊已發布並佈建到中繼站」不實：只有設了 `ROSTER_ADMIN_PUBKEY` 的自架 Node 站會跟著換成員。
   - 改為「名冊已發布」，再說明哪種站會自動套用（`ROSTER_ADMIN_PUBKEY` 要設成管理者的 npub），其他站要把下列 pubkey 手動設進 `ALLOWED_PUBKEYS`。
4. `@cinderous/client` 升到 v0.89.0；自架文件說明名冊自動套用、`ALLOWED_KINDS` 要包含 10038。

## 理由

- 成員資格的權威是名冊的**簽章**（ADR-0047），不是誰把它送來。中繼本來就驗簽、擋舊名冊，運維金鑰對成員資格不多提供保障。
- A 讓 §4 的金鑰分離保得住，管理者的操作也最少（發布名冊這個動作本來就要做）。
- 拿到名冊金鑰的人本來就能簽一份所有客戶端都採用的名冊，讓中繼也採用並沒有擴大它的能力。

## 後果

- 正面：
  - 自架企業站改成員不必重開、不必開管理 API、不必經手運維金鑰。
  - 管理端的說明不再宣稱「已佈建」。
- 負面／已知殘餘風險：
  - 名冊金鑰外洩＝對方能改自架站的成員。這在本文之前就成立（外洩的名冊金鑰能簽出所有客戶端都採用的名冊）。處理方式不變：輪替名冊金鑰（ADR-0052）並更新 `ROSTER_ADMIN_PUBKEY`。
  - 管理者的名冊必須真的發到那座自架站（組織的中繼要是它）；發到別的中繼不會生效。
  - 名冊移除某人後，他已連著的連線不會被切斷（SDK ADR 0133，未變）。
- 後續行動：無。
