# 0406. 行動端限時訊息到期處理，到期判斷收斂到 engine

- 狀態：已接受
- 日期：2026-10-30
- 相關文件：ADR-0013（限時訊息）、ADR-0169（行動端對齊批次二）、ADR-0111（封存）、ADR-0256（封存搜尋）、ADR-0404（CLI 實機對接時發現）

## 背景與問題

ADR-0013 定的行為是：限時訊息到期後，客戶端改顯示「訊息已到期」。桌面版有做，App.tsx 每秒掃一次。

ADR-0169 說行動端的限時訊息「對齊桌面」，實際上只做了**送出**。收到之後從來不到期：手機的對話、聊天清單預覽、回覆引用、歷史紀錄，全都一直顯示原文。2026-10-30 用 CLI 對接 App 時發現，並在手機版瀏覽器建置上實機確認。

清查時另外發現，兩端的「歷史紀錄」（封存，ADR-0111）都直接印原文，也都搜得到到期訊息的內容：
- 桌面的 `HistoryWindow`／`matchesStored`；
- 行動端的 `HistoryScreen`。

到期判斷原本散在各處，各寫一份 `expiresAt <= now`，所以容易漏掉某一處。

## 考量的選項

- A. 行動端照桌面的做法，每秒掃描。
- **B. 到期判斷收斂到 engine 的純函式。行動端只在「下一則到期的時刻」排一個計時器。**
- C. engine 到期時直接從本機儲存刪掉明文（ADR-0013 列的後續）。這會改變資料保留行為，畫面、封存、匯出、雲端快照都會受影響，需要另外決策。

## 決策

採用 **B**。C 列為後續待辦，不在這次處理。

- **engine `backend/expiry.ts`**（桌面與行動端共用）：
  - `isExpired(m, now)`：`expiresAt <= now`，與桌面每秒掃描的判斷一致。
  - `nextExpiryAt(msgs, now)`：尚未到期的訊息裡，最早的到期時刻。
  - `visibleText(m, expiredLabel, now)`：清單預覽與封存列要顯示的文字。到期時連檔名也不露。
- **行動端**：
  - `useExpiryClock(msgs)` 只排一個 `setTimeout`，時間點是最近一則的到期時刻再加 50ms。沒有限時訊息就不排計時器，比每秒掃描省電。
    - 超過 24.8 天（setTimeout 上限）的到期時刻分段排。2026-10-30 審查發現原本只依賴 `next`，第一段醒來後 `next` 沒變就不再排，到期也不會換字；改成同時依賴 `now`。
  - `ConversationScreen`：到期比照「已收回」，原文、表情回應、@提及徽章、日期提示、長按操作、送出狀態全部不顯示，改顯示「訊息已到期」。回覆引用也不露原文。未到期的限時訊息加上 ⏱，跟桌面一致。
  - 聊天清單預覽（`chatList` 的 `expiry` 參數）在最後一則到期時，改顯示「訊息已到期」。
  - `HistoryScreen` 的封存列也改用 `visibleText`。
- **桌面**：`HistoryWindow` 的封存列改用 `visibleText`；`matchesStored` 跳過到期訊息，所以封存搜尋搜不到它。

## 理由

- 只有一份到期判斷，行動端不會再出現「這一處忘了做」的情況。
- 行動端不做每秒掃描：手機在背景時，計時器越少越好。到期時刻本來就算得出來，排一次就夠了。
- C 能從根本上解決本機明文留存，但它會動到資料保留、匯出、雲端快照與「訊息已到期」佔位的呈現方式，影響範圍比這次的畫面修正大得多，應該另外決策。

## 後果

- 正面：手機上的限時訊息到期後真的看不到了，與桌面一致。兩端的歷史紀錄與封存搜尋也不再翻出到期訊息。
- 負面 / 已知殘餘風險：
  - 🔴 **本機仍保存明文**（ADR-0013 原本的限制，這次沒改）。到期訊息還在本機儲存與封存裡，只是畫面不顯示。匯出（`exportRecords`）與加密雲端快照也還會帶到它們。要真正清掉，需要選項 C。
  - 聊天清單搜尋（`nameOrMessagesMatch`）在 PR #62 已改成跳過到期訊息；兩個 PR 都合併後才完整。
- 後續行動 / 待辦：
  - 評估選項 C：到期後由 engine 從本機儲存、封存、匯出中移除明文。
- 實機驗證（2026-10-30，手機版瀏覽器建置，錨點 1）：
  - 手機自己送出的 1 分鐘限時訊息：對話畫面放著不動，到期時自己換成「訊息已到期」。
  - 聊天清單顯示「你：訊息已到期」。
  - 接收端的桌面也同步遮掉。
