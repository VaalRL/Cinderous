# 0368. 連不上時要說為什麼：拒絕連線改為「接受、說明、立刻關閉」，並指向官網開發者文件

- 狀態：已接受
- 日期：2026-09-24
- 相關文件：ADR-0366（§決策 4「未知路徑一律拒絕」、§容量「車道升級 IP 限速」）、
  ADR-0090（官網與通訊平面硬隔離）、ADR-0235 SEO-6（官網網址寫死在多處）、
  `docs/relay-changes-adr-0366-0367.md`、`relay/src/worker.ts`、`apps/website/src/routes.ts`

## 背景與問題

ADR-0366 讓錨點對第三方應用開放 `/app/<id>` 車道，並規定**認不得的路徑一律拒絕**。
實作是在 WebSocket 握手時回 HTTP 404（`unknown relay path`）；車道升級超過 IP 限額則回 429。

這兩個回應對第三方開發者**幾乎看不見**：

- 瀏覽器的 `WebSocket` API 不暴露握手的 HTTP 狀態碼與內容。開發者只拿到一個沒有訊息的
  `error` 事件，接著是 close code 1006——和「中繼站掛了」「網路斷了」長得一模一樣。
- 常見的 Nostr 函式庫（nostr-tools 等）也只會回報「連線失敗」。
- 要看到 `unknown relay path`，得知道要去開 DevTools 的 Network 分頁，或另外用 curl 打。

⇒ 打錯網址（忘了 `/app/`、車道 id 有空白或底線開頭、`/APP/` 大寫）的開發者，
最可能的結論是「這座中繼不能用」，而不是「我的網址錯了」。錨點既然已經決定對第三方開放，
**拒絕時說不清楚原因就是開放的一半沒做完**。

同時，官網目前沒有任何給第三方開發者的文件；要說「去看文件」，得先有文件可看。

## 考量的選項

- **A：維持 404／429，只在官網寫「連不上請用 curl 檢查」。** 零程式改動，但前提是開發者
  已經找到官網——而找不到官網正是問題本身。
- **B：404／429 的回應內容加上文件網址。** curl 與 DevTools 看得到，但瀏覽器 `WebSocket`
  與 Nostr 函式庫**依然看不到**，對最常見的情境沒有改善。
- **C：在 Worker 內接受 WebSocket，送一則 `NOTICE`（含原因與文件網址），立刻以 1008 關閉，
  關閉原因也帶文件網址。不碰任何 DO。** 瀏覽器看得到 `CloseEvent.reason`，Nostr 函式庫
  會記錄 `NOTICE`，curl 則能看到升級成功後的第一則訊息。
- **D：把錯誤路徑導進某顆「說明用」的 DO。** 與 C 效果相同，但多一顆 DO 的成本，
  且違反 ADR-0366 §決策 4「認不得的連線不落在任何 DO」。

## 決策

採用 **C**。

1. **錯誤路徑**（`routeForPath` 回 `undefined`）的 WebSocket 升級：Worker 自己建一組
   `WebSocketPair`、`accept()`、送一則 `NOTICE`、以 **1008（policy violation）** 關閉，
   回 101。**不呼叫 `idFromName`、不碰任何 DO、不套任何政策。**
2. **車道升級超過 IP 限額**：同一個形狀，`NOTICE` 以 `rate-limited:` 開頭，一樣不碰 DO。
3. `NOTICE` 內容依錯誤種類給**具體**的修正方向：
   - 以 `/app/` 開頭但車道 id 不合法 → 說明合法字元與長度。
   - 其他路徑 → 說明第三方應用應連 `wss://<host>/app/<your-app-id>`。
   - 限速 → 說明是以 IP 計數，稍後再試。
   三者都附上文件網址。
4. 關閉原因（`CloseEvent.reason`）固定為一行短句加文件網址，受 WebSocket 規格的
   **123 bytes** 上限約束；超過就退回不含網址的短句（網址仍在 `NOTICE` 裡）。
5. 文件網址預設為官網開發者頁 **`https://vaalrl.github.io/Cinderous/developers/`**
   （英文為官網預設語言，ADR-0246），可用環境變數 `DEVELOPER_DOCS_URL` 覆寫。
6. 官網新增 `developers` 頁（中英雙語），作為第三方開發文件的**單一落點**；之後所有
   給第三方的說明都放在那裡。
7. **非升級的 HTTP 請求不變**：錯誤路徑的一般 GET 照舊回 200 純文字（健康檢查與 ADR-0089
   的契約）；NIP-11 照舊依路徑回文件。

## 理由

- **「拒絕」的定義沒有變**：錯誤的連線仍然不落在任何 DO、不套任何政策、拿不到任何資料，
  ADR-0366 §決策 4 要的 fail-closed 性質完整保留。變的只有**拒絕時說了什麼**。
- **成本相同**：原本的 404 本來就是一次 Worker 請求；改成 101＋一則訊息＋關閉，
  仍是同一次 Worker 請求，且連線在同一次呼叫內就關掉，不累積 duration。
  限速的情境也一樣——被擋下的那一次本來就已經付掉了，重點是**不碰 DO**，這點不變。
- **只有 C 讓最常見的情境看得到原因**：瀏覽器與 Nostr 函式庫是第三方開發者實際在用的東西。
- **不回顯使用者輸入**：`NOTICE` 不包含對方送來的路徑。那不是必要資訊（對方自己知道打了什麼），
  回顯只會把中繼站變成反射任意字串的地方。
- **網址可覆寫**：自架站跑的是同一份 worker；文件描述的是協定本身，預設指向官方文件是合理的，
  但自架者若有自己的說明頁，應該能換掉。

## 後果

- 正面：
  - 第三方開發者在瀏覽器 console 就看得到「網址錯了、該怎麼改、去哪裡看」。
  - 官網有了第三方開發文件的固定位置。
- 負面 / 已知殘餘風險：
  - **錯誤路徑的握手從 404 變成 101**。任何以「狀態碼是不是 101」判斷「路徑對不對」的
    外部監測會誤判；正確的判斷方式是看連上後第一則是不是 `NOTICE`、或是否立即被 1008 關閉。
    本 repo 內沒有依賴 404 的程式（已查 `relay/`、`apps/`、`packages/`）。
  - **官網網址又多寫死了一處**（ADR-0235 SEO-6 已列出的那份清單）。緩解：`routes.ts` 的
    「換網域要一起改」清單加上本項，並以測試比對中繼端常數與官網路由算出的網址。
  - `node-relay` 沒有路徑路由（ADR-0366 §決策 8，單一 profile），不受本 ADR 影響。
- 後續行動 / 待辦：
  - 官網開發者頁隨本 ADR 一起上線；中繼部署**必須在官網頁面上線之後**，否則網址指向 404。
  - 開發者頁的內容與 `docs/research/game-layer-spec.md`、ADR-0366／0367 的數字要同步；
    數字變更時一併更新該頁。
