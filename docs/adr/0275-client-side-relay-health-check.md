# 0275. 中繼健檢下放客戶端：三層分級、首次探測一次、只提示不阻擋

- 狀態：已接受
- 日期：2026-07-29
- 相關文件：ADR-0092（節點一致性稽核）、ADR-0057（NIP-42 AUTH）、ADR-0039（錨點＋簽章清單）、
  ADR-0065（TTL）、ADR-0123（探測需先 AUTH）、`docs/research/public-relay-fallback.md`

## 背景與問題

公共 relay 研究揭露一個缺口：**客戶端對自己連的 relay 幾乎一無所知**。現況只做四件事——
liveness 探測（`SignIn.probeRelay`）、重連、hint 陳舊偵測、清單簽章驗證。而
`relay/bootstrap/conformance.ts` 的**行為**稽核（Ephemeral 語意、NIP-40 過期、AUTH）
**只在 CI 的每小時排程跑**。

且有個不對稱：**CI 探測的是 `relays.json` 裡的候選站；使用者自填的 relay 從來沒有被任何一層
檢查過行為**。於是使用者連上一座公共 relay 時，不知道它是否要求 AUTH（＝收件匣是否公開可讀）、
會不會無視過期把密文永久留存、會不會把 Ephemeral 事件存起來。

## 考量的選項

- **每次連線都檢查**——**否決**：主動探測**會寫入事件**（送一顆再查是否還在），
  每次開 App 就對 relay 寫兩顆測試事件，流量、對方反垃圾機制、我方免費額度都不划算。
- **只在使用者手動點擊時檢查**——零意外流量，但多數人不會去點，警告等於不存在。
- **首次自動一次＋快取（採納）**——第一次見到某座 relay 正是使用者該知道風險的時刻。

## 決策

### 1. 三層，依成本決定頻率

| 層 | 檢查 | 成本 | 頻率 |
| --- | --- | --- | --- |
| **A. 被動觀察** | 對方有無發 **AUTH 挑戰** | **零**（正常連線就看得到） | 永遠 |
| **B. NIP-11** | 宣稱的能力與限制 | 一次 HTTP GET | 快取（`relay-info.ts` 已存在，本 ADR 未接） |
| **C. 主動探測** | Ephemeral 語意、NIP-40 過期、liveness | **會寫入事件** | **首次＋30 天到期** |

**A 層最划算**：「不要求認證＝任何人都能看到你何時收到訊息」是研究列出的**最大風險**，
而它完全免費——`authSigner` 收到挑戰即記 `true`；連上後 3 秒仍未收到挑戰即記 `false`。

### 2. 官方錨點不做客戶端探測

`relay-health.yml` 每小時已在稽核（ADR-0092），客戶端重複是純浪費。`shouldProbe()` 明確排除。

### 3. 探測本體上移至 `@cinderous/core`

原本只在 `relay/bootstrap/`。上移理由：**`relay` 與 `engine` 都依賴 core、彼此不成環**
（engine 對 relay 是 devDependency，反向會成環），且 core 本就有 WebSocket I/O
（`relay-client.ts`）。`relay/bootstrap/conformance.ts` 改為轉引，CI 行為不變。

**探測一律用臨時金鑰**（`generateSecretKey()` 每次現產）——這是能下放的前提：
relay 只看到一把用完即棄的鑰匙在做行為測試，**不洩漏使用者身分**。

### 4. 結果只提示、不阻擋

設定頁顯示徽章（✓正常／⚠隱私疑慮／✕無回應）**並列出具體原因**（「哪裡不對」比「有問題」有用）。
不因此拒連、不自動降路由權重。理由：**使用者有權選擇連哪座中繼**（去中心化本義），
我們的責任是讓他**知情**。分級未知（如錨點）時**不顯示徽章**——沒有資訊就不製造噪音。

## 理由

把最大風險（收件匣公開可讀）的偵測放在零成本的 A 層，是整個設計的重心；昂貴的 C 層則以
「首次＋TTL」把寫入成本壓到一座 relay 一生只有幾次。快取存裝置層（`nb.relayCheck.<url>`）
——這是「這座 relay 的性質」，與誰在用無關。

## 後果

- **正面**：自填 relay 首次連線即獲得行為評估；公共 relay 的最大風險有具體警示；
  CI 與客戶端共用同一套探測（不會漂移）。
- **負面 / 已知殘餘風險**：
  - 首次連新 relay 會寫入兩顆測試事件（臨時金鑰的 ephemeral／過期事件，成本極小但非零）。
  - A 層以「3 秒未見挑戰」判定不要求 AUTH——極慢的網路可能誤判為 `false`（偏保守：
    誤報「有疑慮」比漏報安全）；後續若收到挑戰會被更新為 `true`。
  - B 層（NIP-11）**尚未接上**——`fetchRelayInfo()` 已存在，可作為後續增強。
  - 徽章目前只在桌面設定頁；行動端未接。

## 後續行動 / 待辦

- 接上 B 層：送自訂 kind（檔案／emoji blob）前以 NIP-11 判斷支援度，不支援就不送並告知。
- 行動端顯示同一徽章。
- 若日後支援公共 relay 備援池（研究記錄的 Tier 2），以此檢查結果決定路由權重與 UI 降級提示。
