# 0377. 分片連線也處理 `OK`，外送匣依中繼詞元分類（滿了就稍後重試、改送引導座）

- 狀態：已接受 (Accepted)——2026-09-30 使用者核准 SDK ADR 0038（P0-C 的 App 缺口）；**需走 App 發版流程（重建 APK），排入哪一版由使用者決定**
- 日期：2026-09-30
- 相關文件：ADR-0041（外送匣：OK 感知重試）、0058（送達分級：已送中繼）、0095（傳送失敗紅色圖示）、0039（引導座有界冗餘）、
  0241（中繼分片）、0375（離線留言存不下回 `OK false "blocked: ceiling:"`）、0376（拒收訊息加英文詞元）；SDK ADR 0038、SDK ADR 0040；
  `packages/core/src/outbox.ts`、`packages/engine/src/backend/relay-backend.ts`

## 背景與問題

SDK ADR 0038 P0-R1 的盤點指出一個 App 端的缺口：

- `RelayChatBackend` 的 home 連線（自己的訊息片）接了 `onOk`：外送匣確認／重試／判失敗、`markSent`（已送中繼）、雲端備份留痕。
- **外部連線（`poolClient`）沒有接 `onOk`**，只有 `onEvent` 與 AUTH。而分片模式（ADR-0241）下**寄給別人的訊息走的正是對方訊息片那條外部連線**；
  主路由離線時的冗餘引導座（ADR-0039）、單一 relay 模式下的聯絡人 hint 也是外部連線。
- 結果：寄給別片的訊息，中繼回的 `OK`（收下或拒收）全部被丟掉。外送匣等 `inflightTtl`（30 秒）後把它當成「已送達」靜默移除：
  - 被拒收（例如對方訊息片的離線天花板滿了，ADR-0375 起回 `blocked: ceiling:`）→ 不會變紅、不會重試，**訊息默默遺失**；
  - 被收下 → 也不會標成「已送中繼」，停在「傳送中」直到收到送達回條。

另外，外送匣的 `classifyOk` 把所有 `blocked:` 都當成永久失敗；`blocked: ceiling:`（中繼滿了）其實稍後或換一座就能收下。

## 考量的選項

- 只把 `onOk` 接到外部連線（最小修正）：修掉靜默遺失，但「中繼滿了」會直接變紅，使用者只能手動重送。
- 接 `onOk`，並讓外送匣依詞元分類（採用）：`ceiling`／`quota` 稍後重試並改送健康的引導座；`rate-limited` 只退避；其他照舊。
- 由 App 讀 SDK 的 `classifyRelayMessage`：App 目前不依賴 SDK 客戶端，為了兩個詞元引入整包不划算；用一條前綴＋詞元的正規式即可，詞元表以 SDK ADR 0040 為準。

## 決策

1. **所有連線共用同一個 `onRelayOk`**：home 與外部連線（對方訊息片、引導座、presence、聯絡人 hint）都呼叫它——外送匣 `onOk`、`markSent`、備份留痕。
2. **外送匣依詞元分類**（`core/outbox.ts`）：
   - `blocked: ceiling:`／`blocked: quota:` → **重試**（退避），而且重送時帶 `{ elsewhere: true }`：除了主路由，也送到健康的引導座（`okRetryElsewhere`）；
   - `rate-limited` → 重試，**不換座**（限速是對寄件人的，平移到別座只會連別座一起撞上限）；
   - 其他 `blocked`（`not-allowed`、`kind-disabled`、`too-large`、`stale`…）、`invalid`、`pow`、`restricted`、`mute` → 永久失敗（與 v0.0.18 相同）；
   - `duplicate`（`OK true` 或舊中繼的 `OK false`）→ 確認。沒有詞元的舊中繼與第三方中繼，判定與 v0.0.18 完全相同。
3. **冗餘座的拒收不算數**：同一顆事件同時送到主路由與引導座時，記下主路由（`okRoute`，上限 1024 筆）；只有主路由的拒收會讓外送匣重試或判失敗，
   冗餘座的收下照樣算「已送中繼」。理由：冗餘座可能是企業白名單站或也滿了，主路由卻會收下（或離線中、重連後才送達），拿冗餘座的永久拒收把訊息標紅是誤判。
4. **分片模式不把自己的訊息片當冗餘座**：home 是**我自己的**片，收件人不在那裡掛收件匣——送過去對方收不到，卻會回 `OK true` 讓訊息被標成「已送中繼」。
   （這個問題在本 ADR 之前就存在於「主路由離線時的冗餘廣播」，只是外部連線不處理 OK 所以看不出來。）

## 理由

- 修掉的是實際的靜默遺失：分片模式是官方錨點的預設，每一則寄給別片的訊息都走外部連線。
- 「中繼滿了」是暫時的、而且換座有用（SDK ADR 0038 M1 分類）；引導座本來就是收件人會掛收件匣的地方（ADR-0039），改送過去對方收得到。
- 只有主路由的拒收算數，讓冗餘只會「多一次收下的機會」，不會多一種誤判失敗的方式。

## 後果

- 正面：寄給別片的訊息被拒收時會變紅（永久）或自動重試／改送引導座（中繼滿了）；被收下時立刻標成「已送中繼」。
- 負面 / 已知殘餘風險：
  - 主路由一直滿、而且沒有健康的引導座時，重試耗盡（約 12 秒、4 次）後標成失敗——這是真相，使用者可以手動重送。
  - 主路由離線、只有冗餘座可用而冗餘座全部拒收時，仍是舊行為（30 秒後靜默移除）；要等 SDK ADR 0038 P1 的 `minAccepted`／備援才完整。
  - presence 連線的心跳 `OK` 也會進 `onRelayOk`：外送匣、扇出紀錄找不到那一筆就略過，沒有副作用。
- 後續行動 / 待辦：
  - **需走 App 發版流程**（版號、release notes、重建 APK、桌面安裝檔），排入哪一版由使用者決定。舊版 App 不受影響（行為與 v0.0.18 相同）。
  - 與中繼的部署獨立：第 1 點（外部連線處理 OK）對任何中繼都立即生效；「中繼滿了」的分類要等錨點部署 ADR-0375（`blocked: ceiling:`，目前尚未部署——部署前滿了的中繼仍回 `OK true`）；ADR-0376 的其他詞元只影響顯示。
