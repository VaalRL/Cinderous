# 0386. 中繼淘汰檔案塊時整批一起刪（SDK ADR 0085 移植）

- 狀態：已接受（未部署）
- 日期：2026-10-14
- 相關文件：SDK ADR 0084（每次啟動先從頭補拉）、SDK ADR 0085（整批淘汰）、SDK ADR 0081（收不齊也確認）；ADR-0162（每收件人分桶上限）、ADR-0371（檔案車道）、ADR-0379（容量訊號）、ADR-0381（檔案車道保底與溢位帶）；ARCHITECTURE.md〈容量訊號〉

## 背景與問題

錨點 1 的檔案車道一直在 95% 附近：A 的收件匣有約 130 MiB（1,035 則）永遠收不齊的檔案塊。2026-10-14 研究「relay 是否應定期清理永遠收不齊的檔案塊」的結論：

- 中繼**判定不了**哪些塊收不齊（檔案 id、第幾塊、一共幾塊都在密文裡），定期清理不做。
- 收不齊的孤兒**主要是中繼自己切出來的**：每收件人上限（FIFO）、天花板、保底份額外、借用列 2 小時到期都是**逐列**刪，一則幾十塊的訊息只被刪掉一部分。
- 它們會在 7 天後過期，但這 7 天裡佔空間、每次完整補拉都被重新下載，還逼中繼去淘汰別人完整的塊。

## 考量的選項

- 選項 A：中繼定期清理「N 小時沒有新塊又不齊」的批——判定不了，要判定就得加明文元資料，還會誤刪長期離線收件人完整的資料。
- 選項 B：縮短檔案車道保存期——長期離線的裝置收不到。
- 選項 C：客戶端每次啟動先從頭補拉一次，讓「收不齊也確認」生效（SDK ADR 0084）＋中繼淘汰時整批一起刪（SDK ADR 0085）。

## 決策

採選項 C（使用者 2026-10-14：「客戶端修法和整批淘汰都做，先 SDK 再移植」）。本 ADR 是中繼那一半的移植，程式與 SDK v0.60.0 逐字相同：

1. **批次**＝同一收件人、kind 1060、同一個 `expiration` 標籤值（同一次送出的所有檔案塊共用同一個值）。
2. 四條淘汰路徑只要刪到某一批的一部分，就把那批其餘的列一起刪、一起計入丟棄計數：每收件人上限、天花板舊路徑、天花板回收與保底份額外、借用列到期。
3. 借用到期：借用的那幾塊 2 小時到期時，同一批正常存放的一起刪（使用者選較簡單的這一級，不做「寫入時整批決定借不借」）。
4. SQLite：新增可為 NULL 的 `batch` 欄（`expiration` 標籤的原始值——借用列的 `expiration` 欄會被改成 2 小時）與部分索引 `idx_offline_batch(recipient, batch, bytes, created_at) WHERE batch IS NOT NULL`。相容遷移：舊版寫入的列是 NULL、不參與，回滾照常讀寫；DDL 與 SDK 逐字相同（PR #9 切換不必再遷移）。
5. 檔案塊保存期維持 7 天。

客戶端那一半（SDK ADR 0084）在 CinderSync／Cinder Coffice 升到 SDK v0.60.0 時生效；Cinderous App 的經中繼傳檔只在企業自架站，不用 vault 傳輸層，不受影響。

## 理由

- 不加任何元資料、不需要客戶端更新：所有產生檔案塊的程式本來就共用 `expiration`。
- 處理孤兒的**來源**（中繼自己淘汰）；客戶端的確認處理已經存在的與寄件端送到一半的那些。兩者互補。

## 後果

- 正面：中繼不再切出新的孤兒，刪一批就騰出整批空間、少刪別人。
- 負面 / 已知殘餘風險：
  - 同一秒送給同一人的另一則（`expiration` 剛好相同）可能被一起刪；收件端由摘要／索取重送。
  - 整批刪可能讓那位收件人掉到保底以下；被一起刪的本來就收不齊。
  - 既有的元資料面（不是本 ADR 新增的）：中繼能從「同一個 `expiration`」推出每批大小（SDK ADR 0064 已補記）；要消除它，整批淘汰就做不到。
- 後續行動 / 待辦：**部署兩座錨點要先取得同意**（新欄位與索引在第一次喚醒時建立；錨點 1 的檔案車道約 512 MiB，建索引只掃檔案塊列）。部署後觀察錨點 1 的檔案車道用量與 `dropped` 計數。
- 測試：`relay/src/batch-evict.test.ts`（記憶體版、SQLite 版各 5 項，與 SDK 逐字相同）；`relay/src/schema-compat.test.ts` 的從零建 schema＝移植前＋SDK ADR 0042＋SDK ADR 0085 的遷移（逐字）。
