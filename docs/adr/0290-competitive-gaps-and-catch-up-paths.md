## 1. ⚠ 行動端沒有推播 —— 本文認為這是最傷的一項，而且原本的否決理由需要下修

### 現況（已查證）

`apps/mobile/src/native/notify.ts` 直接沿用 `webNotifier`（Web Notification）。檔頭自述：

> 本機通知**只在 App 還活著時有效**。真正的「App 關掉也收得到」需要推播（FCM/APNs），
> 那會把「有訊息」這件事洩漏給推播供應商——與 Cinderous 的威脅模型衝突。

ADR-0116 進一步寫「中繼站要能在不知道收件人是誰的前提下觸發推播（**技術上很難，可能根本做不到**）」。

### 為什麼這是最傷的一項

**一個關掉就收不到訊息的通訊軟體，在行動端不具競爭力**——這比群組 PCS 更早勸退一般使用者，
也更早在企業試用時被發現。White Noise 已出貨 iOS 推播，其 Notification Service Extension
**在裝置上解密**，Apple 只看得到「有一則投遞」，看不到內容、寄件者或身分。

### ⚠ 否決理由要下修的地方

「洩漏給推播供應商」這個顧慮**在種類上正確、在程度上被高估了**，而且它遺漏了一個關鍵對照：

- **中繼站早就知道了。** ADR-0237 已自行認定：每條連線都做 NIP-42 AUTH ⇒
  **接收端中繼有能力把「誰來拿信」與身分連結**。所以在**自架企業**情境下，
  推播觸發器與中繼站是**同一個信任域**——加推播**不引入任何原本不知情的第三方**，
  增量洩漏≈0。
- Apple／Google 學到的是「某個 device token 在時刻 T 收到一則推播」——
  **不是誰寄的、不是內容、不是對話對象**（NSE 本地解密）。這與「洩漏有訊息」的措辭差距很大。
- 「中繼要在不知道收件人是誰的前提下觸發推播」——**這個條件本來就不必成立**：
  中繼透過 `#p` 本來就知道信是給誰的（那正是收件匣的定位方式），ADR-0116 把一個
  既有事實當成了新增的洩漏。

⇒ 建議把 ADR-0116 的「不做推播」從**原則性否決**改為**分情境**：
自架/企業＝可做且幾乎沒有隱私成本；公共節點＝需要使用者明示同意（因為那才真的多一個觀察者）。

### 追趕路徑

| 選項 | 內容 | 成本 | 代價 |
|---|---|---|---|
| **A（建議）** | **自架/企業推播**：中繼站在 `#p` 命中時打 APNs/FCM，酬載只有「有新訊息」，內容在裝置上解密 | 中——**但卡在真 RN 移植**（NSE 是原生元件，`react-native-web` 拿不到） | 需要組織自己配 APNs/FCM 憑證（自架者本來就在配 env） |
| B | 公共節點推播（opt-in、預設關） | 同上＋同意流程 | 多一個觀察者，須在 UI 明講 |
| C | 不做，改用「常駐前景服務」（Android）／定期喚醒 | 低 | iOS 上根本做不到；耗電；治標 |

**先決條件要誠實說**：目前 `apps/mobile` 跑的是 `react-native-web`（ADR-0116 檔頭已註明日後換
expo-notifications）。**推播的真正阻擋不是隱私爭議，是還沒移植到真 RN。** 這件事應先排。

## 2. 1:1 前向保密：**已經寫完了，卡在錢不是卡在程式**

ADR-0245 狀態：**Phase 0–2 已實作＋全測綠**（core 密碼學、端到端 opt-in FS DM、capability＋TOFU＋
降級偵測、grace 刪除、多裝置 EK 同步、desktop UI），**僅剩 Phase 3 外部密碼學審計——
通過前不得產線啟用、文案不得宣稱 FS**。

這是個死結，值得點名：**ADR-0257 的結論是目前沒有營收面**，而外部密碼學審計要付錢。
於是一個已完工的競爭關鍵功能，因為一道非工程的閘門而無法上線，
同時對手（White Noise 的 MLS、Keychat 的 Signal 棘輪）在文案上都可以宣稱 FS。

追趕路徑（皆非工程）：

- **A（建議）縮小審計範圍**：只審 `core` 那幾百行密碼學原語與 EK 輪替狀態機，
  不審整個 App。範圍越小報價越低，且風險本來就集中在那裡。
- **B 申請開源資助**：~~**待查證本專案的資格與時程**~~
  → **✅ 已查證（2026-07-31）**，見 §2B。**結論：有三條路，其中一條是免費的、且有直接前例。**
- **C 分階段宣稱**：審計前先以「實驗性、預設關、UI 明示未經審計」開放給願意承擔的使用者。
  ⚠ 這與 ADR-0245「通過前不得產線啟用」直接衝突，**採用等於推翻既有決策**，需另立 ADR，
  且必須確保文案一個字都不宣稱 FS。

## 3. 群組沒有 FS／PCS —— 真正的阻擋是**語言**，不是決心

現況：成對扇出（ADR-0027），每則 O(N)；群組**無 FS 無 PCS**。ADR-0091 評估 MLS 後暫緩
（多設備、可靠性護欄、複雜度），ADR-0236 明載「完整 PCS／群組走 MLS、延後」。

盤點時看清楚的一件事：**White Noise 把密碼學放在 Rust（`whitenoise-rs`，前端無關），
本專案的引擎是 TypeScript。** 這才是成本差距的來源——成熟的 MLS 實作在 Rust 生態
（openmls），TypeScript 沒有同級品。

| 選項 | 內容 | 成本 | 代價 |
|---|---|---|---|
| A | 走 Marmot/MLS，密碼學核心以 Rust 編 WASM，engine 透過 binding 呼叫 | **高**（新語言、新建置管線、WASM 在三個平台的載入與體積） | 桌面已有 Tauri（Rust）可先落地；網頁/行動要 WASM |
| **B（建議先做）** | 把 ADR-0245 的**輪替加密子鑰**從 1:1 擴到群組 | 中（機制已存在、已測） | 只得到**粗粒度 FS，沒有 PCS**——不能宣稱與 MLS 對等 |
| C | 不追，明講「群組請用他牌」 | 零 | 在安全性比較上直接讓分 |

**⚠ 不要用功能表回應這一格。** ADR-0289 §2.5 那些（通話、行事曆、無障礙）證明的是
IM 完整度，拿來回答「群組有沒有 PCS」是偷換題目。

## 4. 元資料：**不追**，但要把適用範圍講清楚

Keychat 近乎每則訊息輪替收發地址；本專案的 `#p` 是穩定的 ⇒ 中繼能把收件匣分桶（ADR-0237）。

要追平必須讓 `#p` 變成成對共享的輪替假名——**動到收件匣模型本身**，
連帶衝擊離線投遞、多裝置、補送、NIP-62 清除（都以 `#p` 定位）。**投入與回收不成比例。**

且**自架幾乎讓這個威脅消失**（中繼是你自己的），而自架正是本專案的主戰場（ADR-0257）。
ADR-0240（真隱身）已提供客戶端側最強手段。

⇒ 建議維持不追，但在對外說明中**主動標明適用範圍**：
「公共節點下，中繼可觀察到你的收件時間樣態；要消除這一項請自架。」
主動講比被人指出好——而且這正是導向自架/企業版的自然理由。

## 5. ⚠ 網路效應：ADR-0061 的二分框架遮住了一條中間路

ADR-0061 決策 #5／0065 把互通當成**全有全無**：互通就要公開形狀，公開形狀就違反 ADR-0002。
查證後發現這個推論**對「出站可被發現」成立，對「入站可被聯絡」不成立**：

- 本專案的 1:1 訊息**就是標準 NIP-17**：rumor `kind 14` 包進 `kind 1059` Gift Wrap（`KIND.CHAT: 14`）；
- 與 NIP-17 的差異**只有一個 tag**：我們用 `["to", pk]`，規格用 `["p", pk]`
  （`packages/core/src/giftwrap.ts:22`）；
- 陌生人來訊已有歸屬：進**訊息請求**區，不自動成為聯絡人（ADR-0121）。

⇒ **「讓任何 Nostr 客戶端能寄 NIP-17 私訊給 Cinderous 使用者」的協定成本，
大約是收端多接受 `p` 作為 `to` 的別名。** 而且它**不違反 ADR-0002**——
DM 本來就是 Gift Wrap 加密的，接受入站不會產生任何公開形狀。

真正的不對稱在**另一個方向**：我們的 profile 是**加密廣播給聯絡人**（kind 0 作為 rumor，ADR-0061），
所以通用客戶端搜不到我們、也顯示不出名字——**我們對生態是隱形的**。那才是刻意的選擇，
而且應該維持。

| 選項 | 內容 | 成本 | 代價 |
|---|---|---|---|
| **A（值得評估）** | **單向入站互通**：接受來自任何客戶端的標準 NIP-17；出站可被發現性維持零 | **低**（tag 別名＋訊息請求路徑已存在） | 需重新檢視反濫用（陌生人來訊的 PoW／速率／請求區上限已有，ADR-0127） |
| B | 雙向完全互通（含公開 profile） | 中 | **推翻 ADR-0002 的前提**，不建議 |
| C | 維持現狀 | 零 | 換 App 從零開始的問題持續 |

⚠ **A 不是免費的午餐**：入站互通會讓公共節點成為任何 Nostr 使用者可寄達的目標，
反濫用與訊息請求區的配額需重新算；企業自架節點則因 allowlist 不受影響（ADR-0044）。

## 決策（研究記錄，未決策）

- 本文**不改變任何產品行為**。
- 建議優先序：**(1) 真 RN 移植 → 自架推播** → (2) 縮小 FS 審計範圍／找資助 →
  (3) 評估單向入站互通 → (4) 群組粗粒度 FS → (5) 元資料不追、改講清楚。
- 排序理由：前兩項是**已知可行、且解掉「產品不能用／功能不能開」**；
  後三項是安全性與成長，回收較慢。

## 後果

- 正面：把 ADR-0289 的落差清單變成帶成本的路徑；查出兩個原本被當成「原則問題」的其實是
  **工程排序問題**（推播卡在 RN 移植、互通卡在一個 tag 別名）。
- 已知限制：
  - **所有成本估計皆為量級判斷，未做任何實作評估或估工**。
  - §1 的「增量洩漏≈0」只對**自架同信任域**成立；公共節點情境未細算。
  - §5 的「只差一個 tag」是**協定形狀**層面的結論，未驗證與任一真實客戶端的互通性；
    真要做必須先跟 0xchat/Amethyst 實測，且要處理它們可能用 NIP-04 而非 NIP-17。
  - §2-B 的資助來源只是線索，**未查證本專案資格**。
- 後續行動（**皆待決策，本 ADR 不執行**）：
  1. 修訂 ADR-0116：把「不做推播」改為分情境（自架可做／公共需明示同意）。
  2. 排真 RN 移植的優先序——它同時是推播與原生日期選擇器（ADR-0265）的前置。
  3. 向密碼學審計單位詢價（範圍限縮版），並查證開源資助資格。
