## 背景與問題

使用者的目標：**讓使用第三方 Nostr 客戶端（Amethyst、0xchat 等）的人，只知道我的 npub 就能私訊我、看到我的名稱，而且雙方能來回對話**；
是否公開由每個人自己選擇。遠方的 Cinderous 使用者（不在同一組錨點，例如自架中繼）也要做得到。

### 現況：Cinderous 之間大致已經可以
- 「我的 ID」（QR、複製）是 `selfShareUri`＝`npub…@<home>`；錨點上 home 就是自己的分片，例如 `npub1…@wss://cinder-relay.cinderous1.workers.dev/s/1`。
- 只輸入裸 npub 時，分片模式由公鑰算出對方的分片（`foreignUrlOf`，ADR-0241），都在預設錨點就送得到。
- 收到訊息後，以加密路由提示學會對方的中繼（ADR-0035／0036／0066）。
- 缺口：對方不在同一組錨點又只給裸 npub 時找不到；加好友前看不到對方的名稱（個人檔只加密給聯絡人，ADR-0061）。

第三方客戶端完全不懂上面這些。它們的做法是查公開的中繼清單（NIP-17 kind 10050、NIP-65 kind 10002）與公開個人檔（kind 0）。
ADR-0035 以「把『這把公鑰用哪座中繼』公開」為由否決了 NIP-65——那個理由仍然成立，所以只能由使用者自己選擇打開。

### 2026-10-14 實測（nostr-tools 2.23.8 的 `nip17.wrapEvent`／`unwrapEvent`，與主流客戶端同一套格式）
| 測試 | 結果 |
|---|---|
| 外部格式寄給 Cinderous 後端（記憶體中繼；陌生人／聯絡人） | ✅ 收到；陌生人進訊息請求 |
| 反向：Cinderous 寄出的，`nip17.unwrapEvent` 解 | ✅ 解得開（rumor kind 14）；但收件人寫在自訂的 `to`，**沒有 NIP-17 規定的 `p`** |
| 開了前向保密的收件端 | ✅ `fsDecryptCandidates` 最後一把仍是身分金鑰；不要求後量子封裝 |
| 真實錨點：未認證就寄 | ❌ `auth-required`（主流客戶端收到挑戰會自動做 NIP-42） |
| 真實錨點：寄到根路徑、在根路徑讀 | ✅ 兩座 |
| **寄到根路徑、在收件人分片 `/s/x` 讀** | ❌ **讀不到**（根路徑是 `global` 那顆 DO） |
| 寄到收件人分片、在分片讀 | ✅ 兩座 |
| 錨點上發布 kind 0、別人以 `authors` 查 | ✅ 根路徑與分片都可以 |
| **錨點上發布 kind 10050** | ⚠ 回 `OK true`，但**查不到**——見下 |

### 錨點把標準 10050 當成刪除
`putAddressableResult`（`relay/` 與 SDK 的 `src/relay/` 兩份）對**所有**可取代／可尋址事件都套用 ADR-0071 的約定：`content === ""` ＝清除舊顆、不存新顆。
這條約定原本只為了雲端快照（kind 30078）「關閉備份要立即為真」。但 NIP-17 的 10050、NIP-65 的 10002、NIP-02 的 kind 3 依規格 content 都是空字串，
錨點對它們回 `OK true`，實際上卻刪了。Cinderous 自己的程式碼裡，用到這個 purge 約定的只有快照（`snapshot.ts`、`purgeCloudSnapshot`）。

### 第三方客戶端去哪裡找 kind 0 與 10050
Nostr 沒有全網目錄，客戶端通常靠兩條路：
1. **索引中繼（indexer）**：專門收 kind 0／10002／10050 的站（例如 purplepag.es、user.kindpag.es、indexer.coracle.social），拿到陌生 npub 時先問它們；
2. **outbox 模型（NIP-65）**：先查這個人的 10002，再到他列為 write 的中繼抓 kind 0（Amethyst、Coracle、Gossip 都這樣做）。
兩條路都要鋪，覆蓋率才夠。哪些索引中繼實際收、實際被查，要在實作時實測，不能寫死。

## 考量的選項

1. **維持現況**：Cinderous 之間已經可以；第三方找不到人。零成本、零公開。
2. **發布 kind 10050，內容是完整的分片網址**：第三方照著寄就落在正確的分片；錨點與收件端都不必改路由。公開的只有「這把公鑰在哪座中繼收信」。
3. **另外發布 kind 10002（NIP-65）**：私訊該看 10050；但 outbox 模型的客戶端靠 10002 找 kind 0。單獨用來找私訊中繼不夠。
4. **錨點把根路徑收到的 1059 轉送到收件人分片**：第三方只要知道錨點網址；但錨點要跨 DO 轉送，偏離「中繼只轉發」。
5. **Cinderous 也訂閱根路徑的收件匣**：每位使用者多一條連線、多一顆 DO 的讀取。
6. **公開名稱（kind 0，只含 `name`）**：輸入 npub 的人在加好友前看得到名稱。
7. **連頭像一起公開**：Cinderous 的頭像在本機（data URL），要先上傳到某處取得網址。**使用者 2026-10-14 決定不公開頭像。**
8. **用名稱搜尋（NIP-05 `name@domain`）**：需要有人營運名稱登記；登入畫面的「顯示名稱」只是本機標籤、不唯一，不能直接拿來用。

## 決策

採 **選項 2＋3（有條件）＋6**，做成**每個身分各自設定、預設關閉**的兩個獨立開關；同時補上 Cinderous 自己的查詢端與 rumor 的標準 `p` 標籤，才能來回對話。
選項 7（頭像）不做；選項 8（NIP-05）暫不做。

### 1. 兩個開關
- 設定頁身分區塊：
  - **「讓知道我 npub 的人能聯絡我」**→ 10050（§3）＋ 10002（§4）；
  - **「公開我的名稱」**→ kind 0（§5）。
- 兩個開關互相獨立；只開名稱時**不發布任何中繼清單**（不洩漏在哪收信）。
- 開關說明要寫清楚：**打開後即使再關掉也收不回**——公用中繼或第三方可能已經留了副本，關掉只能讓之後的人查不到。
- 企業身分不顯示這兩個開關（ADR-0044／0048 鎖定漫遊）。

### 2. 發布到哪裡
- 自己 home 所在錨點的根路徑（錨點上用 `authors` 查得到）；
- 一份**可設定的索引中繼清單**（預設值在實作時以實測決定，候選如 purplepag.es、user.kindpag.es、indexer.coracle.social），
  發布前先查 NIP-11 與實際 `OK`，不收的略過。
- 重新發布：開機時若上次發布超過 7 天就補發（錨點對可取代事件的保存上限 30 天，`cinder_addressable_ttl_sec`）；home 搬家（ADR-0066）、改名後立即重發。
- 關閉：發布一份內容清空的同 kind 事件取代舊的（10050／10002 不含 `relay`／`r` 標籤，kind 0 為 `{}`），再送 NIP-09 kind 5 刪除請求。

### 3. 10050（私訊收件中繼）
- `relay` 標籤列出**完整的分片網址**：home（`shardUrlOf(自己)`）以及錨點池裡其他錨點的同一分片。非分片模式（自架單座中繼）列 home 本身。
- content 依 NIP-17 為空字串——**前置條件是 §7 的 purge 修正**，否則錨點會把它刪掉。

### 4. 10002（outbox 模型用）
- 只在「能聯絡我」開著時發布：`r` 標籤列錨點根路徑，標 `write`（那裡放著我的 kind 0）。不列 `read`——私訊收件看 10050。
- 公開的資訊與 10050 相同（在哪座中繼），沒有多公開任何東西；目的只是讓 outbox 模型的客戶端找得到 kind 0。

### 5. kind 0 名稱
- 只放 `name`；**不放頭像**（使用者決定）、不放 `about`、狀態訊息、頭銜——那些仍只走加密個人檔（ADR-0061）。
- 名稱不唯一、可被冒用，UI 顯示時標成「對方自稱」，身分仍以完整 npub／QR 為準。

### 6. Cinderous 的查詢端（加好友與寄信）
- 加好友只輸入裸 npub（沒有 `@中繼`）時，向錨點根路徑與索引中繼查這個 npub 的 kind 0、10050、10002（具名查詢 `authors:[對方]`，ADR-0123）。
  - 查到 kind 0：加好友前顯示「對方自稱：<name>」。
  - 查到 10050：存為該聯絡人的路由提示（沿用 ADR-0034 的 `relayUrl`；多座取第一座、其餘做備援），之後的私訊寄到那裡。
  - 都查不到：照現況（分片模式由公鑰算分片，或寄到 home）。
- 帶內加密 hint（ADR-0035）仍優先：對方的 Cinderous 寄來的 `relay` 會覆蓋查到的 10050。
- 第三方寄來的訊息沒有帶內 hint：收到陌生人訊息時，若該聯絡人沒有提示，背景查一次 10050，讓回信寄得到。
- 寄到外部中繼沿用多中繼路由（ADR-0034 的 pool、惰性連線、NIP-42 自動認證）；自封副本照舊寄到自己的 home。

### 7. 前置修正：purge 只限快照
`putAddressableResult` 的「content 空＝清除」改成只對 `isAuthorOnlyKind`（kind 30078）生效；其他 kind 的空 content 就是普通內容，照常取代、保存。
`relay/` 與 SDK `src/relay/` 兩份一起改（TDD：10050／10002／kind 3 空 content 存得進、查得到；快照的 purge 不變）。

### 8. 來回對話：rumor 補標準 `p` 標籤（必做）
NIP-17 以 rumor 的 `p` 標籤（加上寄件人）決定一則訊息屬於哪個對話；Cinderous 把收件人寫在自訂的 `to`（ADR-0107），第三方客戶端解得開卻不知道該歸到哪裡。
- **送**：1:1 的 kind 14 rumor 加上 `["p", 收件人]`（保留 `to`，舊版 Cinderous 靠它歸檔自封副本）。
- **衝突**：`mention.ts` 把 rumor 內所有 `p` 當成 @提及（ADR-0050）。新規則：**等於 `to`（或 1:1 對話對象）的 `p` 不算提及**；
  第三方寄來的 rumor 裡 `p` 指向我自己的也不算提及。
- **上線順序**（避免舊版把每則訊息都當成「提及了你」）：
  1. 先發「收端」：新的提及判斷規則；
  2. 等所有裝置都更新（比照 v0.0.18 的「每台都要更新」流程）後，才發「送端」：rumor 帶 `p`。
- 群訊不在這次範圍：第三方客戶端的群組（NIP-17 多 `p`）與 Cinderous 群組（ADR-0027，無共用金鑰、逐成員扇出）語意不同，另案。

### 9. 來信把關
陌生人照現有規則進訊息請求（ADR-0121），防洪照 ADR-0127；錨點寫入仍需 NIP-42 認證。這個功能不放寬任何收信規則。

## 理由

- **只公開必要的最小資訊**：中繼位置與名稱各自一個開關；頭像不公開。
- **零路由改動**：10050 直接寫分片網址，選項 4、5 要改錨點或多開連線。
- **相容生態的兩種找法**：索引中繼與 outbox 模型都覆蓋到，第三方才找得到 kind 0。
- **來回對話要兩端都對**：寄得到（10050＋查詢端）、對方歸得了檔（`p` 標籤），少一個就只是「單向收信」。
- **ADR-0035 的隱私預設不變**：沒打開的人和今天完全一樣。
- **purge 修正本身就該做**：它讓錨點對三個標準 kind 回了 `OK true` 卻沒存；限縮到快照不影響現有行為。

## 後果

- 正面：第三方 Nostr 使用者只知道 npub 也能私訊開了開關的使用者、看到名稱、和他來回對話；遠方的 Cinderous 使用者也查得到。
  錨點不再默默丟掉標準的 10050／10002／kind 3。
- 負面 / 已知殘餘風險：
  - 打開後，npub 與收信中繼（以及名稱）的對應永久公開，可能招來垃圾訊息——靠訊息請求與防洪把關。
  - 索引中繼不受我們控制：可能不收、可能停站、可能保留副本。
  - kind 0 的名稱不唯一、可被冒用，只能用來「確認」，不能用來「信任」。
  - 查詢 kind 0／10050 時，被查的索引中繼看得到「有人在查這把公鑰」。
  - `p` 標籤分兩階段上線，期間第三方客戶端仍歸不了檔；舊版 Cinderous 若漏更新，會把每則訊息都當成提及。
  - 只涵蓋 1:1 文字訊息；Cinderous 特有的訊息類型（回應、收回、檔案、通話）第三方客戶端看不懂或忽略。
- 後續行動 / 待辦（依序）：
  1. §7 purge 修正（relay＋SDK，TDD）；部署錨點另需同意。
  2. §8 第一階段：收端的提及判斷規則（TDD）。
  3. §1–§5 發布端：兩個開關、10050／10002／kind 0 的發布、重發與關閉（TDD；i18n 兩語系）。
  4. §6 查詢端：加好友與陌生來信時查 kind 0／10050（TDD）。
  5. 實測決定索引中繼的預設清單。
  6. §8 第二階段：送端 rumor 帶 `p`（所有裝置更新後）。
  7. 實機互通驗收：用 Amethyst 或 0xchat 只輸入 npub → 看到名稱 → 寄信 → Cinderous 收到（訊息請求）→ 回信 → 對方在**同一個對話**看到。
  8. **暫不做**：用名稱搜尋（NIP-05）；群組互通。
