# 0383. 跨錨點路由：對方被分到另一座錨點時，寄到那座的分片

- 狀態：已接受
- 日期：2026-10-14
- 相關文件：ADR-0039（錨點與引導座）、ADR-0035（帶內 relay 提示）、ADR-0241（中繼分片）、ADR-0378（OK 計票）、ADR-0382 §6（分片模式下錨點池外的提示優先）；ARCHITECTURE.md〈Nostr 事件契約〉

## 背景與問題

登入時會從錨點清單自動挑一座（ADR-0039/0069），所以兩個 Cinderous 使用者確實會落在不同座（目前兩座：cinderous1、jt0856）。

分片模式（ADR-0241）的路由 `foreignUrlOf` 一律用**自己的**分片基底加上對方的分片路徑：落在錨點 1 的 Alice 寄給錨點 2 的 Bob，信落在錨點 1 上「Bob 的分片」，而 Bob 只讀錨點 2 上自己的分片——**永遠收不到**。對方分享字串（`npub…@wss://錨點2/s/x`）與帶內提示（ADR-0035）都寫著他在哪座，卻因為「提示在錨點池內就改由公鑰推算」被丟掉。

2026-10-14 驗收 PR #14／#18 時以兩個網頁版實測重現（v0.0.18 與 main 都一樣），在線狀態也同理看不到（心跳只發到自己那座的 presence 層）。

## 考量的選項

- 選項 A：提示在另一座錨點時，用那座的基底加對方的分片路徑；沒有提示時，每座錨點上對方的分片各寄一份。
- 選項 B：一律每座都寄（不看提示）。簡單，但每則私訊都多佔一份額度（錨點 1 的 DO 已到 95% 警告過）。
- 選項 C：讓錨點彼此轉送。要改中繼、跨 Cloudflare 帳號互信，範圍大，且錨點會變成知道彼此流量的中介。

## 決策

採選項 A：

1. **知道對方在哪座**：聯絡人／請求者的提示在錨點池內 → 取那座的基底（`wss://host`；自己這座仍用 `shardingBase`）加上 `shardPath(對方)`。提示在錨點池外照 ADR-0382 §6 直接寄提示網址。
2. **不知道對方在哪座**（只有裸 npub、還沒收到帶內提示）：主路由仍是自己這座的分片，**另外**寄到其他每座錨點上對方的分片（`unknownAnchorShards`）。對方回信帶上提示（ADR-0035）後就只寄那一座。
3. **OK 計票**：多寄的各座與主路由地位相同，任一座收下就算成功、全部拒收才判失敗（沿用 ADR-0378 × ADR-0382 §6 的 `voters`）。
4. **在線狀態**：心跳仍只發到自己這座的 presence 層；聯絡人的提示在別座時，**另外訂閱那座的 presence 層**（`foreignPresenceUrls`）。沒有提示的聯絡人等學到提示再連。

## 理由

- 提示本來就在（分享字串、帶內 rumor），只是被丟掉；用它路由不增加任何外洩，也不必改中繼。
- 只有「不知道在哪」時才多寄，成本只落在第一則訊息到對方回信之間；同座的聯絡人完全不多寄（有測試釘住）。
- 在線狀態選「多訂閱」而不是「心跳多發」：心跳每分鐘一次，多發會讓每座都多一份寫入；多訂閱只在真的有別座聯絡人時才多一條連線。

## 後果

- 正面：分到不同錨點的使用者可以互相傳訊、看到在線狀態；新增第三座錨點時自動適用（以錨點清單為準）。
- 負面 / 已知殘餘風險：
  - 裸 npub 的第一則訊息會寫到每座錨點（目前 2 份）；群組成員若沒有提示也一樣。
  - 別座錨點會看到我的 presence 訂閱（`authors:[聯絡人]`）——兩座是同一個維護者，元資料面與 ADR-0237 的評估相同。
  - home 遞補（ADR-0039）到另一座錨點時的提示更新沿用既有機制，未另外處理。
- 後續行動 / 待辦：無。測試：`packages/engine/src/backend/relay-cross-anchor.test.ts`（5 項）；`relay-sharded-ok.test.ts` 的冗餘座測試改用帶提示的分享字串，維持它原本只驗冗餘座的意圖。
