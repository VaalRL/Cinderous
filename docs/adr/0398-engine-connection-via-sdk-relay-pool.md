# 0398. 引擎的真實網路連線改由 SDK 的 RelayPool 負責

- 狀態：已接受（使用者 2026-10-29：「處理 連線層改接 SDK 的 RelayPool（第 2 項）：消除重複程式，以後 SDK 的修正會自動帶進來」；SDK 的去重表先修：「先修 SDK 再遷移」）
- 日期：2026-10-29
- 相關文件：ADR-0395（1013 與上線判定）、ADR-0385（認證前送出）、ADR-0041（外送匣）、ADR-0034／0039／0241（多中繼路由）、ADR-0370（中繼與協定改由 SDK 提供）；SDK ADR 0001（RelayPool）、0035（補訂閱游標）、0108（1013 冷卻）、0124（去重表上限）

## 背景與問題

聊天 App 的真實網路連線是引擎自己寫的 `webSocketConnector`，搭配 core `RelayClient`。SDK 的 `RelayPool` 是四款遊戲和外掛共用的連線池。下面這些事兩邊各寫了一份：
- 重連退避；
- 1013 的冷卻；
- NIP-42 認證，以及認證前被拒的重送；
- 拒收分類。

ADR-0395 就是這樣來的：SDK 早就處理好 1013（SDK ADR 0108），聊天 App 沒有，額度用完時每秒重連一次。只要兩份程式並存，修正就要做兩次，漏掉的那份會再出同樣的事。

## 考量的選項

- **A. 引擎整個改用一個多中繼的 `RelayPool`**：引擎自己的路由要全部改寫，包括 home、分片、錨點冗餘、presence 層、OK 的主路由投票（ADR-0378），以及單次的查詢與發布連線。這些都是 Cinderous 特有的設計，SDK 沒有。風險大，而且 `relay-backend.test.ts` 的 4,900 行要跟著改。
- **B. 每座中繼一個只有這一座的 `RelayPool`，轉成引擎原本的連線介面**：引擎的路由不動，只換掉「一條連線」怎麼實作。
- **C. 維持兩份，SDK 修了什麼就手動抄過來**：就是現況，不做。

## 決策

採 B。

1. **`RelayConnection` 介面**（`packages/engine`）：引擎只用到四個方法，`publish(event)`、`subscribe(subId, filters)`、`unsubscribe(subId)` 和 `close?()`。
   - 記憶體測試網路的 `RelayClient` 原樣就符合這個介面。
   - `CloseableRelayClient` 保留成它的別名。
2. **`webSocketConnector(url)` 改成轉接層**：每條連線一個 `new RelayPool({ urls: [url] })`，`RelayPool` 由 core 轉出。以下全部交給 SDK：
   - 重連退避：0.5、1、2、5、10 秒，連線撐過 30 秒才歸零；
   - 1013 的冷卻：健康標記，預設 5 分鐘，回了 EOSE 就清掉；
   - NIP-42 認證，以及認證前被拒的重送；
   - 補訂閱：從游標接續，禮物包往前退讓兩天；
   - 驗簽與以 id 去重。
3. **轉接層自己做的事**：
   - **什麼時候算上線**（ADR-0395）：中繼要求認證時立刻算（SDK 要簽 AUTH 時通知），或者連上 1 秒沒被關。
   - **1013 的原因**：從 SDK 的 `onRelayReject` 取得，恢復時間用健康標記的 `until`。SDK 會先改狀態、再回報拒收，所以離線晚一個微任務才報。
   - **NIP-42 簽章**：SDK 組好 kind 22242 的範本，轉接層取出 challenge，交給引擎原本的 `authSigner`。各連線用的金鑰不同，可能是身分、配對房間或一次性查詢的金鑰；ADR-0275 的「這座要求認證」觀測也保留在原處。
   - **發布**：
     - 還沒連上就先排著，連上再送，與舊版相同。
     - 等 OK 最多 30 秒，與外送匣的在途時間相同（SDK 預設 5 秒）。
     - **只有中繼真的回答了才轉給 `onOk`**：收下、`duplicate`，或帶原文的拒收。逾時、沒連上、斷線都不回，交給外送匣的重連補送與在途逾時（ADR-0041），與舊版收不到 OK 時一樣。
   - **訂閱**：一個 `subId` 對應一個 SDK 訂閱。filter 相同就不重送：引擎每次上線都會重訂，而 SDK 已經自己補送過了。filter 變了就關掉舊的、開新的；空的 filter 等於只關掉。
4. **SDK 升到 v0.83.1**（`packages/core`）：這一版的去重表有上限（SDK ADR 0124）。原本每個訂閱收過的 id 只進不出，聊天 App 一開好幾天，會被心跳慢慢吃掉記憶體。`relay/` 仍釘 v0.77.8，錨點的部署行為不變。

## 理由

- 引擎的路由是 Cinderous 的產品設計，連線怎麼維持則是共用的基礎設施。把切點放在「一條連線」，風險最小，SDK 的修正也全部帶得進來。
- 外送匣的「絕不誤判失敗」原則（ADR-0041）靠的是：沒消息就當沒消息。所以轉接層不把本機的逾時或斷線轉成拒收。

## 後果

- 正面：
  - 引擎少了自己寫的 WebSocket 迴圈、退避和 1013 處理；
  - SDK 以後對重連、拒收分類、健康狀態的修正，升版就帶進來；
  - 補訂閱改成從游標接續，重連時不再整段重播歷史，流量比較省。
- 與舊版不同的地方（刻意的）：
  - **退避**：改成撐過 30 秒才歸零。舊版只要上線就歸零。連上幾秒就被關的連線，下次會等比較久，這正是 SDK 防止重連迴圈的設計（Cinderous ADR-0368）。
  - **上線判定**：「中繼先開口」只認 AUTH 挑戰。不要求認證、又先送別的訊息的第三方中繼，改成等 1 秒才算上線。
  - **來自中繼的事件**：在 SDK 先驗簽一次。引擎原本的驗證照舊，所以會多花一次驗簽。
- 負面 / 已知殘餘風險：
  - **測試走的路和正式環境不同**：記憶體測試網路仍用 core `RelayClient`，所以 `relay-backend.test.ts` 測不到 SDK 的行為，例如去重、`onEose` 只叫一次、補訂閱。轉接層本身由 `ws-connector.test.ts` 用假 WebSocket 測。把記憶體網路也改成走 SDK 是後續項目。**已由 ADR-0400 完成**：轉接層搬到 core `connectRelay`，記憶體網路注入記憶體 socket 共用它。
  - core `RelayClient` 的認證前重送（ADR-0385）只剩記憶體網路在用（ADR-0400 之後只剩展示模式的 `connectDirect`）。與 SDK 的同一套行為是兩份程式，但不在正式環境的路徑上。
  - 手機 App 的 JS 打包大了約 32 KB（未壓縮，971 KB 增加到 1,003 KB，+3.3%），多出來的是連線池、健康狀態與拒收分類。
  - 每座中繼各一個連線池，健康狀態不跨座共享。引擎本來就自己管各座的狀態（`trackRelayState`），不受影響。
- 驗證：
  - `ws-connector.test.ts` 19 個測試，涵蓋：
    - 1013 的原因與 5 分鐘冷卻；
    - 上線判定；
    - SDK 的退避；
    - 發布排隊；
    - OK 的轉交規則；
    - 認證前被拒的重送；
    - 訂閱的換掉、不重送、`unsubscribe`；
    - `close`；
    - 引擎把原因交給 UI。
  - 破壞測試 7 項，每項都至少讓一個測試失敗：
    - 拿掉相同 filter 不重送；
    - 本機結果也轉成拒收；
    - AUTH 不算上線；
    - 不等拒收原因；
    - 用 SDK 預設的 5 秒等 OK；
    - 沒連上不排隊；
    - 一開就算上線。
  - 全套測試與 `pnpm -r typecheck` 都通過。
