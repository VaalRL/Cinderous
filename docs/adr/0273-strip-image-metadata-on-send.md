# 0273. 送出圖片一律去除 EXIF 等中繼資料（canvas 重編碼）

- 狀態：已接受
- 日期：2026-07-29
- 相關文件：ADR-0102（縮圖政策常數 SSOT）、ADR-0100（行動端檔案平台縫）、ADR-0103/0104（桌面選檔／拖放）、
  ADR-0088（元資料最小化）、ADR-0222（動畫 GIF 自訂 emoji）、`docs/research/mobile-camera-capture.md`

## 背景與問題

全 repo 搜尋 `exif`／`stripMetadata`：**零命中**。送檔路徑是原檔位元組直送——

```ts
// 行動端 native/files.ts 與桌面 App.tsx 的 sendFile 皆然
const bytes = new Uint8Array(await f.arrayBuffer());
```

因此傳一張照片會**連同 GPS 座標、拍攝時間、裝置型號一併送出**。這與本專案花大力氣藏元資料
（Gift Wrap 藏寄件者、presence jitter〔ADR-0088〕、威脅情報純本地比對〔ADR-0231〕）**明顯不一致**：
訊息內容加密了，照片卻把實際座標交出去。

**注意**：`makeThumbnail()` 的 canvas 重編碼確實清掉了**縮圖**的 EXIF，但那只是預覽圖，
**原檔照送**——現況並非「已有保護」。

此洞已存在於已發布的 v0.0.13。規劃中的「拍照直接傳」（研究記錄同名文件）會讓它從
「使用者得自己去相簿挑檔」的潛在洞，變成**每張都是剛拍、GPS 最準**的主要洩漏管道。

## 考量的選項

- **A：送出前 canvas 重編碼（採納）**——只保留像素，所有中繼資料自然消失。
- **B：解析並剔除 EXIF 區塊**——保留原始編碼品質，但需自寫／引入 EXIF 解析器，
  且各家相機的私有欄位（MakerNote 等）容易漏；攻擊面與維護成本都比 A 高。
- **C：維持現狀＋UI 警告**——把責任推給使用者，與隱私預設鐵則相違。
- 預設值：一律清除 vs 提供「傳送原檔」開關。

## 決策

1. **新增 `sanitizeImage(bytes, mime)`** 於 `@cinderous/engine`（與 ADR-0102 的縮圖政策同一處，
   常數不漂移）：canvas 重編碼 → 去除所有中繼資料，並限制最長邊。
2. **政策常數**（比照 THUMB_* 命名，放 `storage/types.ts` 當 SSOT）：
   - `SEND_MAX_EDGE = 2048`（足以閱讀文件與照片細節，同時把 12MP 原圖大幅縮小）；
   - `SEND_QUALITY = 0.85`（JPEG）。
3. **適用範圍**：`isSanitizable(mime)` ——**點陣圖才處理**，且**明確排除**：
   - `image/gif`：canvas 重編碼會**摧毀動畫**（ADR-0222 支援動畫 GIF），故不動；
   - `image/svg+xml`：可執行標記，不餵 canvas（沿用 ADR-0102 的既有理由）；
   - 非圖片檔（PDF／文件等）：無法安全重寫，不動。
4. **一律清除，不做「傳送原檔」開關**（v1）：隱私預設鐵則；多一個開關就是多一個誤觸的腳槍。
   若日後有明確需求（如攝影用途）再另立 ADR，且必須以明示警告呈現。
5. **失敗即原樣送出**：解碼失敗（格式異常、canvas 不可用、無 DOM）時回傳原位元組——
   **不因為清不掉中繼資料就讓使用者送不出檔案**。此殘餘須在 ADR 記明（見後果）。
6. **桌面與行動端共用**：兩邊的送檔入口（桌面 `sendFile`／`attachFile`、行動端 `pickFile`）
   都在轉成 `OutgoingFile` 前呼叫，不各寫一份。

## 理由

canvas 重編碼是「一石三鳥」：EXIF/GPS 隨編碼消失（不必信任某個 EXIF 解析器有沒有漏掉私有欄位）、
順帶壓縮解決大圖的記憶體與頻寬問題（Capacitor 相機路徑的已知障礙）、且與既有 `makeThumbnail`
同一套機制與心智模型。排除 GIF 是刻意的正確性取捨——保住 ADR-0222 的動畫功能比清掉 GIF 那點
（本就沒有 EXIF 標準的）中繼資料重要。

## 後果

- **正面**：照片不再洩漏 GPS／時間／機型；上傳體積大幅下降（頻寬、P2P 傳輸時間、離線信箱配額
  一併受益）；「拍照直接傳」可以安心開發。
- **負面 / 已知殘餘風險**：
  - **重編碼有畫質損失且不是原檔**——使用者若想傳無損原圖，v1 無此選項（刻意）。
  - **GIF 不處理**：動畫優先；GIF 無 EXIF 標準，但可含註解區塊——列為已知殘餘。
  - **失敗時原樣送出**：極端格式下可能仍送出含中繼資料的原檔（可用性優先於此處的完備性）。
  - 已發布的 v0.0.13 仍有此洞，需於下一版修復後提示使用者更新。

## 後續行動 / 待辦

- 行動端相機功能（`takePhoto()`）實作時另立 ADR，並確認其走同一條 `sanitizeImage` 路徑。
- 若日後要提供「傳送原檔」，須以明示警告呈現並另立 ADR。
