# 0262. 行程提醒：本機計時器、零中繼成本

## 背景

ADR-0259 §1.4 對提醒只給了一條紅線：**不得產生任何中繼流量**。ADR-0260／0261 把行事曆做完
之後，提醒是唯一剩下的功能缺口。本 ADR 記錄「零中繼成本」這個約束實際上決定了哪些事。

## 決策

### 1. 提醒不是「排程一則未來事件」，是**到期判定**

沒有伺服器、沒有推播服務、沒有排程佇列——那些都會產生流量或需要第三方。提醒因此是：
**一個週期 tick 問一次「現在有哪些該提醒了」**，`dueReminders()` 為純函式，答案完全由本機
資料決定。

### 2. ⚠ 用週期 tick，**不是每筆行程一個 `setTimeout`**

直覺寫法是「算出還有多久，`setTimeout` 那麼久」。**這對本專案的主要使用情境是壞的**：
`setTimeout` 的延遲是 32 位元毫秒（上限約 24.8 天），超過就溢位成**立刻觸發**——
於是「三個月後的婚禮」在你設定提醒的那一秒就叫你。

而行事曆的價值正好在遠期行程（ADR-0260 §8 的補送整段都在處理「資料有效期比傳輸 TTL 長」）。
故一律走 tick：**30 秒一次**——提醒的粒度是分鐘，每秒掃只是白費電；30 秒最壞遲到半分鐘，
感受不到。開機時另外掃一次（App 關著錯過的，開起來若還在寬限窗內仍該說一聲）。

### 3. ⚠ 提醒設定**不進 rumor**

行程 id ＝ 建立那則 rumor 的雜湊。把個人偏好塞進 rumor 會改變雜湊——**這正是 ADR-0260 §8
補送踩過的同一顆地雷**（形狀不同就是不同的行程）。

但就算沒有這個技術理由，它也不該進去：**「我要提前多久被叫」是每個人自己的事**，沒有任何
理由讓群組其他人知道。故 `remindLead` 只存在本機那份，`calendarRemind()` **刻意一個網路動作
都不做**（測試以「攔在 `client.publish` 上、確認一顆事件都沒多」釘住這一條——那是真正上線的
位元組，中繼看到什麼那裡就是什麼）。

**連帶要處理的**：`upsertCalendarEvent` 必須保留既有的 `remindLead`。收到的 rumor 裡不會有
它，不保留就等於「主揪一改時間，全體的提醒設定都被清掉」。

### 4. ⚠ 「已提醒過」記的是 `start`，不是布林旗標

`remindedFor` 存的是**已經提醒過的那個 `start`**。理由：主揪改時間時，提醒必須重新武裝——
改到明天的會議不該因為「昨天那場已經提醒過」就靜默。以 `start` 為鍵，改時間**自動**重新
武裝，不需要任何額外的清除邏輯。

同理，`setCalendarReminder` 會清掉 `remindedFor`：使用者本來關著、現在打開，若這個 `start`
曾經提醒過就再也不會響。

**這個欄位必須落盤**（`LocalStorage`／`TauriStorage` 都寫回）：只留在記憶體的話，
**每次重開 App 都會被同一個提醒轟一次**。

### 5. 寬限窗 `CALENDAR_REMINDER_GRACE_SECONDS = 5 分鐘`

**沒有它，「準時提醒」（`lead = 0`）永遠不會觸發**：提醒時刻恰好等於 `start`，而 tick 是
離散的，不可能剛好落在那一秒。

同一個窗也涵蓋「App 關著錯過了、開起來時已經稍微遲了」——遲 5 分鐘內仍值得說一聲；
更晚就只是噪音（行程都開始了，通知你「即將開始」是錯的）。

### 6. 已回覆「不參加」的不提醒

明說不去的行程還叫你，是純粹的騷擾。**只看自己那一格**——別人回覆不參加不影響你的提醒。

### 7. ⚠ 提醒**不走 `shouldNotify` 的 `windowHidden` 閘**

ADR-0217 的訊息通知有一條「視窗看得到就別跳」——**那條規則在這裡是錯的**：
你正盯著這個 App，不代表你知道十分鐘後有會。提醒只受**總開關**管，不受每對話靜音、
也不受下班靜音影響（那些是「別人打擾你」的閘門；提醒是你自己設的鬧鐘）。

引擎只發 `onCalendarReminder`，**不預設呈現方式**——要不要跳通知、跳什麼，是 App 的事。

### 8. UI：**沒選過就是不提醒**

預設值（`CALENDAR_REMINDER_DEFAULT_LEAD = 10 分鐘`）只在使用者主動打開提醒時當起始選擇，
**不會替他決定要被吵**。桌面用下拉（低調，它不是給別人看的）、行動端用 chip 列（拇指點得到，
看一眼就知道現在選的是哪個）。

- **已過去的行程不顯示提醒選項**——提醒一個過去的時間沒有意義。
- **非主揪也能設自己的提醒**：提醒與 ADR-0259 §1.7 的主揪權威**無關**——那是你自己的鬧鐘，
  不是對行程的修改。測試明確涵蓋這一點（非主揪看不到編輯鈕、但看得到提醒列）。
- 後端無 `calendarRemind` → 整列不出現。

## 後果

- 正面：ADR-0259 §1.4 的紅線完整兌現——**提醒功能的中繼流量是零**，中繼端零改動。
  行事曆自此無已知功能缺口。
- 負面 / 已知缺口：
  - **App 沒開就不會提醒**。這是「零中繼成本」的直接代價：要在 App 關著時提醒，就得有
    推播服務，那既是流量也是第三方（且會洩漏「你有一個行程」給推播供應商）。
    開機補掃只涵蓋寬限窗內的。**這個取捨是刻意的，不是還沒做完。**
  - **提醒設定不跨裝置同步**：它不進 rumor，也就不在多裝置同步的範圍內（ADR-0242 同步的是
    偏好，這裡刻意不接）。換裝置要重設。
  - **30 秒的 tick 粒度**：最壞遲到半分鐘。
- 測試：core 10（提前量到/未到、沒設不響、**`lead=0` 也要能響**＝寬限窗存在的理由、
  錯過但在窗內仍響、遲太久不響、自己拒絕不響、**別人拒絕不影響自己**、已響過不重複、
  **改時間自動重新武裝**）＋engine 6（開機補掃、**重開 App 不重複轟**、沒設不響、未到不響、
  **`calendarRemind` 零中繼流量**、改時間後本機設定不被 rumor 清掉且重新武裝）
  ＋desktop 5／mobile 5（選單/chip 顯示條件、預設是關、反映目前值、過去的不顯示、
  **非主揪也能設**）。
  全工作區綠：core 523／engine 386／desktop 578／relay 197／mobile 216；`pnpm -r typecheck` 綠。
- 過程中修掉一個**自己寫的弱斷言**：行動端「預設選中『關』」原本只斷言 chip 存在，沒斷言
  哪個被選中（RN-web 把樣式編成雜湊 class 名，斷言不到）。改為讓選中的 chip 帶 `-on` 尾綴
  testID——與 ADR-0261 的 `cal-item-past` 同一招。
