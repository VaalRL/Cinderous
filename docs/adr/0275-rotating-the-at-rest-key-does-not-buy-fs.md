# 0275. 評估：把輪替範圍擴到本機儲存金鑰＋預設開，能不能補齊 FS 缺口

- 狀態：**研究記錄（評估提案，未決策；本文不改變任何產品行為）**
- 日期：2026-07-28
- 相關文件：**0245**（手動 opt-in FS——本提案要改它的**範圍**與**預設值**；其〈後果〉自述
  「**本機明文封存仍是最大長期暴露面（FS 管不到）**」，正是本提案瞄準的那句）、
  **0238**（自動每週輪替——**預設開等於回到它**）、**0270**（方便性考量的重新審查）、
  0236（為何 EK 與 at-rest 金鑰分離）、**0112**（靜態加密：`deriveStorageKey`）、
  0053（OS 金鑰庫）、0111/0126（封存與保留上限）、0013（限時訊息）、0234（無痕收回）、
  0269 §2（FS 的現行阻擋＝外部審計）、**0274 §3.2**（我們目前唯一在 FS 這格贏對手的地方）
- 資料來源：本倉庫程式碼查證（`packages/core/src/at-rest.ts`、`storage/opfs-archive.ts` 等）

> **結論：不能，而且方向會反噬。**
> 「本機儲存的 FS」與「歷史保得住」是**互斥**的——輪替金鑰不會繞過這個互斥，只是把它改個名字。
> 而預設開會把 ADR-0245 特地移除的成本原封裝回來，還會**放大目前唯一真正卡住 FS 的那道閘門**。

## 1. 先確認兩個事實（提案的前提）

| 查證項 | 結果 |
|---|---|
| 本機儲存金鑰怎麼來 | `deriveStorageKey(sk) = HKDF(sha256, sk, undefined, INFO, 32)`（`at-rest.ts:36`）——**純由 nsec 決定，無 salt、無輪替計數** |
| 本機封存有沒有加密 | **有**（`opfs-archive.ts:70` 以 `dek` `sealValue`）。ADR-0245 那句「明文封存」指的是**應用層明文**（相對於中繼上的密文），不是磁碟上沒加密 |

⇒ **提案指出的缺口是真的**：nsec 一旦外洩，**過去所有本機歷史都可解**，而 EK 輪替完全管不到這一塊。
ADR-0245 自己就把這件事寫進〈已知殘餘風險〉。**問題不在有沒有看到缺口，在於輪替能不能補它。**

## 2. ⚠ 核心：傳輸與本機的不對稱，決定了輪替只對前者有效

| | 傳輸密文（中繼囤積／側錄） | 本機密文（你的磁碟） |
|---|---|---|
| 密文在誰手上 | **對手手上，你刪不掉** | **你手上** |
| 你之後還需要讀它嗎 | **不需要**——本機已有明文副本 | **需要，那就是你的歷史** |
| 「刪掉金鑰」的效果 | 對手**永遠**解不開 ✅ | **你自己也讀不到** ❌ |

FS 之所以在傳輸這側成立，正是因為**你可以扔掉金鑰而不損失任何東西**。
本機那側沒有這個性質——**你必須留著某把打得開現有資料的金鑰**。

## 3. 於是輪替 at-rest 金鑰會落進一個二選一

**威脅模型**：對手在 T 時刻取得你的磁碟映像，在 T+n 取得你的 nsec／裝置。

### 路徑 A：輪替時**重新加密**全部歷史（歷史保得住）

新金鑰 `K_new` 必須被某個東西包住，App 開機才載得回來。那個東西只能是：

1. **由 nsec 導出** → 與今天完全相同。對手在 T+n 拿到 nsec，就打得開 T 那份映像裡的包裝。**收益為零。**
2. **OS 金鑰庫**（ADR-0053 已在用）→ 收益來自**金鑰庫**，不是來自輪替。
3. **使用者密碼** → 收益來自**密碼**，不是來自輪替。

⇒ **路徑 A 的 FS 收益 ≈ 0。** 真正提供保護的是「根秘密住在哪」，輪替只是在同一個根之下換衣服。

### 路徑 B：輪替時**不重新加密**，舊金鑰銷毀（真的有 FS）

那舊資料就此讀不出來——**這不是「加密輪替」，這是「刪除資料」**，只是繞了一圈。
而刪除資料的機制專案早就有，而且更直接、更好調：
保留上限（ADR-0126 訊息、0264 §10 行程）、限時訊息（0013）、無痕收回（0234）。

⇒ **要 local FS 就得接受失去歷史；要歷史就沒有 local FS。輪替不能同時給你兩個。**

## 4. ⚠ 而且路徑 B 會**毀掉我們目前唯一在 FS 這格贏對手的地方**

ADR-0274 §3.2 剛查證出來：0xchat 的 Secret Chat 明文寫著
「若 App 被解除安裝或更換裝置，**secure chat 歷史即無法取回**」；
Marmot 的多裝置規格也寫「**新裝置解不開加入前的 epoch**」。

**而我們刻意把 at-rest 金鑰與傳輸金鑰分開，換得的正是「開了 FS 也不失去歷史」**
——這是設計上贏兩家的那一格。

⇒ **走路徑 B ＝ 主動放棄這個優勢，把自己變成 0xchat。**
⇒ 走路徑 A ＝ 保住優勢，但沒有拿到任何 FS。

## 5. 「預設開」的部分：三個新成本 ＋ 一個會反噬的

1. **把 ADR-0245 特地移除的成本裝回去**（ADR-0270 §1 逐項記過）：
   grace（7 天）後仍送舊鑰的在途訊息接不到、背景金鑰 churn ——
   從「你按了換鑰才付」變回「所有人常態付」。
2. **⚠ 新成本：每次輪替要重新加密整個本機庫**（路徑 A 必然如此）。
   手動時這是罕見的、使用者發起的事件；預設開就是**每台裝置的週期性背景重寫**。
   歷史大時是重量級操作，**中途失敗有把儲存寫成新舊混雜的風險**。
3. **⚠ 相容性懸崖**：ADR-0245 §6 的降級保護是 capability＋TOFU——已釘選者找不到可用 EK
   **不得靜默退回靜態**，要警告/暫緩。預設開＝**所有人上線即釘選** ⇒
   任何還在舊版客戶端的聯絡人都會觸發警告。這在發布當天就會發生。
4. **⚠ 會反噬的那個：它讓現行阻擋更難解。**
   ADR-0269 §2 已查證，FS 現在卡的**不是工程、是外部密碼學審計**（要錢，而 ADR-0257 說沒有營收面）。
   把範圍從「EK 輪替」擴大到「at-rest 金鑰輪替＋全庫重新加密＋預設開」，
   **等於把待審的東西變大、變複雜、風險面變寬** ⇒ 報價更高、時程更長。
   ADR-0269 §2 的建議正好相反：**縮小審計範圍**。

## 6. 對「補齊 FS 缺口」這個目標，實際上有沒有幫助？

| 缺口（ADR-0274 §5） | 本提案的效果 |
|---|---|
| **群組沒有 FS／PCS**（vs White Noise） | **完全沒碰**——ADR-0245 §6 的範圍是**僅 1:1**，本提案不改這一點 |
| **1:1 強度與元資料**（vs Keychat） | 仍是 epoch 粗粒度、仍不輪替地址 ⇒ **縮小差距但不補齊** |
| **1:1 FS 不可產線啟用** | **變更糟**（§5-4） |
| 本機歷史的長期暴露 | 路徑 A：無效；路徑 B：有效但＝刪資料，且失去 §4 的優勢 |

⇒ **對「補齊 FS 缺口」這個目標，本提案沒有一格是補齊的。**

## 7. 那本機那側該怎麼辦？三個方向，都比輪替直接

1. **把根秘密釘進硬體**（最有效）：OS 金鑰庫／Secure Enclave／TPM 的**不可匯出**金鑰。
   ADR-0053 已把 nsec 放進 OS 憑證管理員——**再往前一步是讓 at-rest 金鑰由裝置綁定的金鑰包住，
   使「複製磁碟」不等於「拿到金鑰」**。這直接打中 §3 的威脅模型，而輪替打不中。
2. **真的刪資料**：把保留上限/限時/無痕收回當成 local FS 的正解，並讓使用者看得懂
   （「保留 90 天」比「金鑰每週換」更誠實地描述它實際提供的保障）。
3. **維持 EK 與 at-rest 分離**（現況）：這是 §4 那個優勢的來源，不要動它。

## 決策（研究記錄，未決策）

- **不建議採納本提案的任一半**：
  - **擴大範圍到 at-rest 金鑰**——落進 §3 的二選一，且路徑 B 會毀掉 §4 的優勢；
  - **預設開**——回退 ADR-0245 的決定，且讓現行阻擋（審計）更難解。
- 若目標是「本機歷史的長期暴露」，建議改走 §7-1（裝置綁定金鑰）——那是**另一個 ADR 的題目**，
  與 FS 是不同的機制，不該混在 ADR-0245 的範圍裡。
- 若目標是「補齊對手的 FS 差距」，ADR-0269 的優先序不變：**先把審計弄過去讓現有的 FS 上線**，
  群組 FS 另案（粗粒度 → MLS）。

## 後果

- 正面：把一個直覺上合理的提案拆到它的根本矛盾（本機 FS ⟷ 歷史保得住，二選一），
  並指出它會與 ADR-0274 §3.2 剛查出的優勢相衝突；同時把「本機暴露面」導向真正有效的方向。
- 已知限制：
  - **§3 的分析是密碼學論證，不是實作評估**——沒有估過「全庫重新加密」在真實資料量下的耗時，
    §5-2 的「重量級操作」是量級判斷。
  - ~~**§7-1 未做可行性評估**~~ → **已由 ADR-0276 補做**。結論：B 級（不可匯出金鑰）
    在 Android／iOS／Apple Silicon Mac／有 TPM 的 Windows 可達，**Linux 與瀏覽器補不上**
    ⇒ 永遠是分級保障。且該文更正了一個對現況的誤讀：**我們今天用的 OS 金鑰庫是「祕密儲存」
    等級，不是裝置綁定**。
  - 未考慮「使用者密碼」路徑（§3-A-3）的可用性代價（每次開 App 輸密碼）。
- 後續行動（**待決策**）：
  1. ~~若要處理本機暴露面，另立 ADR 評估裝置綁定金鑰~~ → **已完成：ADR-0276**。
  2. ADR-0245 的範圍與預設值**維持不變**，優先把 Phase 3 審計弄過去（ADR-0269 §2）。
