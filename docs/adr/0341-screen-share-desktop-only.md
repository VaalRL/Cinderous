# ADR-0341：畫面分享只做桌面

- 狀態：提議中（**開工前必須先驗證 §2 的前提**）
- 日期：2026-08-05
- 關聯：ADR-0338（預先協商的視訊軌）、ADR-0337（畫質三檔）、ADR-0323（原生外掛的工作量參照）

## 1. 傳輸層幾乎是免費的

`getDisplayMedia()` 拿到的就是**一條視訊軌**。ADR-0338 已經讓視訊 transceiver 預先協商好，換軌走 `replaceTrack` ⇒ **不需要重新協商、沒有 glare、不必新增信令類型**（沿用 `call-media`，多一個型態值）。

⇒ 這份 ADR 的內容幾乎都不在傳輸，在**平台可行性**與**隱私**。

## 2. 🔴 桌面的前提尚未驗證

Tauri 桌面版跑在 WebView2（Chromium 核心），理論上有 `getDisplayMedia`。但 `getDisplayMedia` 需要一個**「要分享哪個視窗」的系統挑選器**，而嵌入式 WebView 不保證會自己叫出來——可能要從 Rust 端接。

**我沒有驗證過。** ⇒ 這是開工前的第一步，不是實作中途才發現的事：

- [ ] 在 Tauri 桌面版實測 `navigator.mediaDevices.getDisplayMedia({ video: true })`
- [ ] 挑選器出得來嗎？出不來的話 Rust 端要接什麼？
- [ ] 若接不出來 ⇒ **本 ADR 作廢**，不要為它硬做一個自製挑選器（那要列舉視窗、抓縮圖，是另一個量級的工程）

## 3. 行動端不做

Android WebView **不支援** `getDisplayMedia`。螢幕擷取要走原生 `MediaProjection`＋前景服務＋系統授權對話框——工作量等同 ADR-0323 的裝置金鑰外掛。

⇒ **不划算**。同樣的工時拿去做 ADR-0339 的切換鏡頭，對手機使用者有用得多。

行動端**不顯示入口**，而不是顯示一個按了說「不支援」的按鈕（同 ADR-0338 §4 的立場）。

## 4. 一次只有一條視訊軌

分享螢幕**取代**你的鏡頭畫面，不是並存。

要並存就得第二個視訊 transceiver ⇒ 重新協商 ⇒ glare ⇒ 把 ADR-0338 §3 迴避掉的整套複雜度請回來。**不值得**，尤其對一個 1:1 通訊軟體。

⇒ `localMedia` 的型態值從 `"audio" | "video"` 擴為含 `"screen"`，三者互斥。

## 5. 畫質要另一組參數

ADR-0337 的三檔是**為人臉調的**：`maintain-framerate`、640×480。螢幕分享要的正好相反——**文字要看得清楚**：

| | 人臉（ADR-0337） | 螢幕（本 ADR） |
| --- | --- | --- |
| `degradationPreference` | `maintain-framerate` | **`maintain-resolution`** |
| 解析度 | 640×480 | 螢幕原生（上限 1920×1080） |
| fps | 24 | **5–10** |

⚠ 直接沿用人臉那組，分享出去的程式碼與文件會糊到讀不了——那等於功能沒做。

## 6. 隱私比開鏡頭更需要小心

分享螢幕誤傷的面積遠大於鏡頭：通知橫幅、密碼管理器、另一個對話視窗、瀏覽器分頁標題，**全部都可能入鏡**。

1. **預設分享單一視窗，不是整個螢幕。** 挑選器的預設選項要是視窗。
2. **進行中必須有明顯且持續的指示**，不是只有一顆按鈕變色。
3. 🔴 **不得分享 Cinderous 自己的視窗**——那會把其他對話的內容送給現在這個人。挑選器如果擋不掉，至少要偵測到並警告。

第 3 點是這個功能最現實的風險，而且**它在其他 App 上真的發生過**。

## 7. 買不到什麼

1. **不含音訊分享**（`getDisplayMedia({audio:true})` 分享分頁音訊）。那是另一條路徑，且平台支援更不一致。
2. **不含遠端控制。** 只有單向觀看。
3. **對端不知道你分享的是哪個視窗**——只看得到內容。這是刻意的：告訴他視窗標題等於多洩漏一份資訊。
4. **暫停畫面分享**沿用 ADR-0340 的結論，不另做一套。
5. **不處理多螢幕的解析度差異**——分享 4K 螢幕時降到 1080p 會糊，本版接受。
