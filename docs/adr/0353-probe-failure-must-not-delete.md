# 0353. 探測失敗不得刪除 relay：一次逾時吃掉了一座錨點

- 狀態：已接受
- 日期：2026-09-16
- 相關文件：ADR-0039（混合式引導路由／最低 2 座錨點）、ADR-0189（第二座錨點 `jt0856`）、ADR-0092（分級收錄）、ADR-0069（營運欄位 `accepting`/`weight`/`status`）、ADR-0275（探測本體上移至 core、AUTH 挑戰迴歸）、ADR-0350（健檢排程與狀態外移）

## 背景與問題

ADR-0350 的收尾工作留下一筆看似無害的殘留：`health-history.json` 裡有一筆 `jt0856` 的計數（`probes: 158, live: 157`），而 `relays.json` 裡沒有這座 relay。當時記下的是「已下線節點的舊條目，要不要清掉」。

查下去發現順序是反的——**不是節點下線導致條目殘留，是清單把節點刪掉了，而條目是唯一剩下的證據。**

`jt0856` 不是普通候選節點。它是 ADR-0189 為了滿足 ADR-0039「最低 2 座錨點」而特地在**獨立 Cloudflare 帳號**部署的第二座錨點，至今仍硬編在 `packages/engine/src/bootstrap-config.ts` 的 `ANCHOR_RELAYS` 裡。

`relays.json` 的歷史：

| 日期 | 內容 |
|---|---|
| 2026-07-18 | 兩座都在，都是 `weight: 2`（正式收錄，uptime ≥ 99%） |
| 2026-07-29 | `jt0856` **整筆消失**——不是 `status: retired`，是不見了 |
| 之後 7 週 | 完全沒再變動 |

**而它一直是活的。** 2026-09-16 實測：接受 WebSocket 連線，並正確送出 NIP-42 `AUTH` 挑戰——一座運作正常、要求認證的 relay 該有的第一句話。

## 根因

```ts
const liveOnes = results.filter((r) => r.conf.live);
const nextEntries = [...liveOnes 的判定結果, ...entries.filter((e) => e.status === "retired")];
```

liveness 探測失敗、又不是 `retired` 的座，**從清單上整筆刪除**。刪掉之後它不在 `entries` 裡 ⇒ 下一輪的 `active = entries.filter(e => e.status !== "retired")` 不含它 ⇒ **再也不會被探測，永遠回不來**。

一次失敗＝永久除名，而且沒有任何告警。

這個設計只有在「探測可靠」時才成立，但探測並不可靠：

```ts
const TIMEOUT_MS = 8000;
export function probeLive(url: string): Promise<boolean> {
  return withWs(url, false, (ws, done) => { /* REQ → 等 EOSE */ });
}
```

**單次嘗試、8 秒逾時、沒有任何重試**（`grep -rn "retry\|重試\|attempt"` 在 `relay-probe.ts` 與 `health-check.ts` 皆為空）。逾時、連線錯誤、Cloudflare 冷啟動、worker 正在重新部署——全部壓成同一個 `false`，與「這座 relay 真的死了」在型別上與語意上都無法區分。

## 關鍵觀察：never-empty 守門保護不到這一格

清單更新有一道 never-empty 守門：全部探測失敗就整份不覆寫。它的存在本身就承認了「探測結果可能整批是假的」。

而 `relay-probe.ts` 自己的註解裡記著這正好發生過一次（ADR-0275 時期的 AUTH 迴歸）：

> **每一次 cron，我們自己的中繼站都被自己的健檢判定為「不存活」**，而那個結果會餵進 `health-check` 的滾動 uptime。這個 bug 一直都在。

那次之所以沒有刪掉任何東西，正是因為**每一座都失敗**，守門啟動了。

🔴 **但守門只防得住全滅。「N 座裡死一座」這種部分誤判，它零防護——而部分誤判才是常態。** 兩座錨點死一座，剛好落在守門看不到的那一格，於是 `jt0856` 被刪了。

代價嚴重不對稱：留著一座暫時連不上的 relay，客戶端最多浪費一次連線嘗試（而客戶端本來就有自己的健檢，ADR-0275）；誤刪一座錨點是**不可逆**的，而且把 ADR-0039 要求的 2 座韌性靜默減成 1 座。

## 決定

**一、探測失敗改為保留＋降級，不刪除。**

失敗的座留在 `entries` 裡、標成 `accepting: false`、**`status` 保持 `ok`** ⇒ 下一輪仍在 `active` 裡被探測 ⇒ **自己好起來就自己回來**。`weight` 原樣保留：在 `accepting: false` 之下 `pickRelay` 用不到它，留著是保住「它原本是一座 weight 2 的正式座」這個紀錄，復活時 `evaluateAdmission` 會重算。

`relays`（舊欄位，客戶端真正拿去連的那個陣列）維持**只收本輪存活的** ⇒ **客戶端行為完全不變**。

**二、不加重試。** 修好「不可逆」之後，單次探測的誤判下一輪就自己修正。重試只降低誤判機率、不改變誤判的後果；先把後果從「永久」變成「一輪」，才是對的順序。8 秒逾時與無重試因此降級為可接受的取捨，不再是缺陷。

**三、判斷邏輯搬到 `relay/bootstrap/relay-list.ts`（`decideList`），並補測試。**

這段是整條流程裡後果最重的判斷，而它原本住在 `health-check.ts` 的 `main()` 裡——一支讀檔、開 WebSocket、寫檔、簽章發佈的腳本，**測不到**。那正是這個 bug 能存在 7 週的結構性原因。同 ADR-0348 的原則：可測的邏輯不該只存在於測不到的地方。

**四、把 `jt0856` 加回 `relays.json`。** 只給 `url`，`accepting`/`weight` 由下一輪探測決定（人管加入/退役，機器管品質）。它的歷史是 157/158 ⇒ 探測通過即回到 `weight: 2`。

## 考量的選項

- **標成 `retired`**——否決：`retired` 的語意是「人決定退役」，而且 `active` 會跳過它 ⇒ 一樣回不來，只是換個說法。
- **要求連續 N 次失敗才降級**——否決：需要新增「連續失敗次數」狀態（又一份要存的執行期狀態，見 ADR-0350），而在「降級可逆」之後它買到的東西很有限。
- **錨點永不自動移除（特例保護）**——否決：把 `ANCHOR_RELAYS` 的知識帶進 relay 工具鏈，耦合更緊，而且它只保護錨點——第三方節點被誤刪同樣回不來，問題性質一樣。
- **加重試**——見「決定二」，順序不對。

## 後果

- 正面：誤判不再不可逆；一座 relay 暫時連不上不會從此消失。清單現在誠實記錄「這座我們探不到」而不是假裝它不存在。
- 正面：`health-history.json` 裡的計數不再會凍結——被刪的座原本連歷史都停止更新。
- 負面／已知殘餘風險：
  - **`relays.json` 會開始留下探測失敗的座**，清單變長，且一座真的永久死掉的節點需要**人手動標 `retired`** 才會被清掉。這是刻意的：自動刪除正是本 ADR 要修的東西。
  - 🔴 **探測失敗的座在 `entries` 裡與「一致性未過的試用座」長得一模一樣**（都是 `accepting: false`）。兩者的差別只能從 `health-history.json` 的 uptime 看出來。要區分需要新增 `RelayStatus` 值，那會動到客戶端的 schema，本 ADR 不做。
  - **`jt0856` 消失的那 7 週沒有留下任何可追溯的紀錄**——bot 的提交訊息是固定字串，沒有寫出「移除了誰」。本 ADR 沒有補這件事：現在不再自動移除，但降級同樣不會告警。
  - **無法確認 2026-07-29 那次探測失敗是誤判還是真的短暫離線。** 7 週前的 Actions log 已不可考。兩種情況下本 ADR 的結論相同——**即使是正確的移除，也該是可逆的**。
  - 🟡 **折半的捨入誤差會把復活的 relay 推過分級門檻。**（2026-09-16 實測）`jt0856` 重新收錄那一輪拿到 `weight: 2`，因為 `evaluateAdmission` 用的是**折半前**的 157/158 ＝ 99.37%（`health-check.ts` 先探測、後 `recordProbe`）。但 `round(159/2)=80`、`round(158/2)=79` ⇒ 折半後是 79/80 ＝ **98.75%**，跌破 99% 門檻 ⇒ **下一輪就被降成 `weight: 1`**（仍是正式收錄，只是低權重），實際發生在 04:46Z 那次排程。真實比例應是 158/159 ＝ 99.37%，捨入引入了 0.6pp 的向下偏差，剛好跨過門檻。
    自癒：需約 20 次成功探測（≈5 天）才爬回 99% 以上。影響僅限加權隨機分配的機率，不影響可用性，故不在本 ADR 處理。若要修，方向是讓折半保持比例不下降（例如 live 用 ceil、probes 用 floor），但那會讓 uptime 在折半時略微樂觀——是另一個取捨，需要單獨評估。
- 後續行動／待辦：
  1. ~~下一輪排程後確認 `jt0856` 被重新收錄（`accepting: true`、`weight: 2`），且 `relays.json` 收到一筆提交。~~ **已確認**（2026-09-16 01:52Z，`relays.json` 提交 `96771f7`，兩座錨點皆 `weight: 2`）。⚠ 但 04:46Z 那輪它就因折半的捨入誤差降為 `weight: 1`，見上。
  2. 重建客戶端以恢復 2 座錨點的實際韌性——`ANCHOR_RELAYS` 是編譯期常數，但它本來就一直包含 `jt0856`，所以這一項影響的是**簽章清單**那條路徑，不是錨點恆連。
  3. 考慮讓降級/復原產生可見訊號（`::warning::` 或提交訊息寫出哪幾座）——目前「安靜地降級」仍然安靜。
