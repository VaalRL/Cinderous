# 0366. 第三方應用走獨立車道——政策二分、路由多分、未知路徑一律拒絕

- 狀態：**提議中**（相依於「是否承接第三方流量」的產品裁示，見〈待決〉）
- 日期：2026-09-22
- 相關文件：`docs/research/shared-relay-for-game-clients.md`（本 ADR 的調查底稿）、
  ADR-0057（NIP-42 AUTH）、ADR-0123（訂閱必須具名）、ADR-0044／0048（企業 allowlist／kind 政策）、
  ADR-0071（可尋址快照）、ADR-0065／0160（TTL 有界）、ADR-0235（濫用防護）、ADR-0241（分片路由）、
  ADR-0243／0342（`/turn` 的 IP 限流先例）、ADR-0260（NIP-11）、PRD §6（威脅模型）、§8（濫用防護與容量）、
  `docs/research/public-relay-fallback.md`

## 背景與問題

四個獨立專案——《辭職信》《菜鳥教頭》《元素使》《沒當好爸爸》——都把
`wss://cinder-relay.cinderous1.workers.dev` 寫成主力中繼。逐一對照它們的需求與本中繼的實作後，
問題不是效能，是**設計前提相反**：

| | Cinderous | 四款遊戲 |
| --- | --- | --- |
| 訂閱 | 你得先知道要問誰（ADR-0123） | 開放大廳：**不知道對手是誰**才要找 |
| 元資料 | 盡量什麼都看不到 | 牌組／戰績／房間**刻意公開** |
| 房間 | 無伺服器端房間（ADR-0027／0241） | 房間是核心 |
| 保存 | 一切壽命有界（ADR-0065） | 牌組、勳章、禮物要永久 |

**而這不是紙上推論。** 四款之中唯一有真實程式碼的《沒當好爸爸》已經實測撞牆並繞過去了，
其 `docs/adr/0007` 2026-09-04 補記原話：

> 該中繼的訂閱只准 `#p`（自己）或 `authors`（Cinderous ADR-0123，防止全站流量分析）：
> 大廳的 `#g` 廣播訂閱會被它以 `restricted` 關掉，**由公共備援回應**

也就是說：`public-relay-fallback.md` §2 列為 🔴「收件匣變成公開可讀」的那條路，
**已經是某個下游專案的預設路徑**了。

## 考量的選項

- **A：直接放寬 `scoped()`。** 否決。ADR-0123 擋的是「一鍵拿到整個使用者名冊連同即時線上狀態」，
  那個風險與遊戲無關、也不因為遊戲而降低。放寬＝把一個為了隱私而付出的限制，為了不相干的用途拆掉。
- **B：認證應用身分，依 app 給不同權限。** 否決，**因為做不到**。四款遊戲都是開源、跑在使用者
  機器上、而且**都沒有後端**（《辭職信》ADR-0009 明文以 $0 OpEx 否決自建伺服器與 Firebase），
  沒有任何一方能簽發 token，嵌進客戶端的密鑰在出貨那天等於公開。`Origin`／subprotocol／事件的
  `t` tag 全都是客戶端自填；NIP-42 的 pubkey 只證明持有某把私鑰，而 `worker.ts:110-119` 已經為了
  `/turn` 記過同一件事：「pubkey 由請求方自選、換一把是微秒級的事，以它計數等於完全沒有限制」。
- **C：共用同一顆 DO，只依宣告換一組 `RelayCoreOptions`。** **強烈否決**。那個旗標會直接變成
  ADR-0057＋0123 的**繞過開關**：連線時宣告「我是第三方」拿到寬鬆規則，然後
  `{"kinds":[1059],"#p":["<受害者>"]}`——密文還是密文，但每則訊息的到達時間、訊息量、作息模式
  全部免費奉送。自己蓋一座比借用別人的更糟。
- **D：不承接，改推「每個應用自己部署一座」。** **仍然在檯面上**，見〈待決〉。ADR-0356 的一鍵
  部署器與 97KB 的 `node-relay` 讓這件事很便宜，且零隱私代價、零額度爭用。
- **E（本 ADR 採用）：獨立車道。** 政策二分、路由多分、未知路徑拒絕。

## 決策

### 1. 車道是**路由鍵**，不是權限憑證

判準一句話：**任何一條限制，如果攻擊者謊報之後會佔到便宜，那條就設計錯了。**

既然宣告不可信，寬鬆車道在任何設計下都是自由可達的。所以車道買到的不是門禁，
是**爆炸半徑的圍牆**——與 ADR-0241「一崩只影響 1/16」同一個思路。謊報只有兩種結局：
吃掉寬鬆車道自己的額度（等價於直接去打那些應用，無放大），或是想碰訊息平面而碰不到。

### 2. 判定發生在**選 DO 之前**，且**只看 URL 路徑**

這是本 ADR 最吃重的一條。寬鬆車道必須是**物理上不同的 Durable Object**——它的 SQLite 裡
從頭到尾沒有任何一顆 Cinderous 事件，規則放寬也就無從洩漏。

不看事件的 `t` tag：那樣同一條連線會混著兩種 profile，而 `scoped()` 是 per-REQ 的決定，
選項 C 的繞過風險立刻回來。

### 3. 政策二分、路由多分

兩件事拆開，**都不需要註冊表**：

- **政策**：兩份 profile（Cinderous 嚴格／第三方寬鬆）。不維護 app 名單。
- **路由**：`idFromName("app-" + hash(宣告字串) % 8)`。任何字串都能用、不用報備；
  取模是為了**上界**——否則惡意客戶端可以用亂數字串生出幾百萬顆冷 DO。血條 1/8。

### 4. 兩邊都正面列舉，未知路徑**拒絕連線**

```
嚴格車道 = "/"、"/s/<nibble>"、"/presence"     ← 這份清單已經存在、已被 shard.test.ts 釘住
寬鬆車道 = "/app/" 前綴，後面任何字串都行       ← 加新應用零改動、零部署、免報備
其他     = 拒絕（NOTICE ＋ close），不落入任何一邊
```

🔴 **刻意不設預設值。** 考慮過「未列入者一律走寬鬆」——它有真正的好處（permissionless），
但它會把**現存的三條 fallback 靜默地重新指向寬鬆車道**（`shard.test.ts:48-52` 釘著）：

| 路徑 | 現在 | 若「未知→寬鬆」 |
| --- | --- | --- |
| `/` | 舊客戶端回退（ADR-0241 遷移期，最低版本閘前仍在用） | 舊版 Cinderous 客戶端拿到公共 relay 規則 |
| `/s/zz`、`/s/ab` | 畸形前綴退回 global | 客戶端算錯分片就把訊息發進公開車道 |
| 未來新增的路徑 | — | 忘記分類就是寬鬆 |

共同點是**失誤的代價不對稱**：預設嚴格時，分類失誤＝功能壞掉（吵、看得見、當場修）；
預設寬鬆時，分類失誤＝隱私默默降級（不報錯、沒人發現）。這與 `vanish.ts` 對缺主機資訊時
fail-closed 是同一個判斷。而 permissionless 這個好處**用 `/app/<任何字串>` 就拿到了**，
不必靠翻轉預設值去換。

附帶：清單放**路徑**而不是 app 名稱。放名稱的話，Cinderous 自己的安全性會開始取決於它有沒有
正確宣告自己是 Cinderous——新增一個失敗模式，零收益。路徑本來就在那裡。

### 5. 寬鬆車道只開三道閘

不是「等同公共 relay」。需要動的只有三處，其餘（事件大小、tag 數、`MAX_P_TAGS`、時鐘窗、
`MAX_QUERY_ROWS`）**原樣保留**：

| 閘 | 位置 | 改成 |
| --- | --- | --- |
| `scoped()` 具名訂閱 | `relay-core.ts:426-447` | 放行 tag-scoped 訂閱（唯一真正解鎖大廳的那條） |
| 可尋址事件只回作者 | `:473`、`:584` | `isAddressableKind(kind)` 收窄為只對 `SNAPSHOT_KIND` 生效——現行寫法語意過寬 |
| `requireAuth` | `worker.ts:239` 寫死 | 改為 per-lane（《辭職信》的客戶端不處理 AUTH 挑戰） |

### 6. 保存仍然有界

公共 relay 多半沒 TTL 沒配額；照抄等於在免費層上跑無界儲存服務，直接推翻 ADR-0065
「每一列壽命必有界」。應用要的「永久」做成**長 TTL ＋ 每次更新刷新**（ADR-0071 既有機制，
只是把 30 天調長），不是無限。

### 7. 防濫用綁「比較貴的東西」，不綁身分

🔴 **關掉 AUTH 會讓速率限制幾乎沒牙**：`connect()` 在 `!requireAuth` 時直接 `return []`
（`relay-core.ts:248`）不建 authState，於是 `:538` 的 `rateKey` 恆為 `event.pubkey`——攻擊者自選。
誠實地說，**開著 AUTH 也沒好多少**（AUTH 只證明持有某把私鑰，輪替成本是一次簽章）；
AUTH 的價值是收件匣 ACL，不是防濫用。真正會咬人的是兩樣既有的東西：

- **IP 為鍵的 Cloudflare rate limit**：`/turn` 已有完整先例與理由（ADR-0342 §3.1）。
- **NIP-13 PoW**：`minPowDifficulty` 程式碼早就寫好（`:563-566`）但產線沒開，因為
  「客戶端無挖礦實作，啟用會讓現有安裝無法發訊息」（ARCHITECTURE §5）。
  **第三方客戶端現在才在寫**，寬鬆車道第一天就要求即無相容性包袱。這是唯一
  「不需要身分就能讓灌垃圾變貴」的手段。

### 8. `node-relay` 維持單一 profile，且**預設嚴格**

它只認 `/healthz`、沒有路徑路由。自架站不該因為升上新版就默默把自己變成公共站。
兩座宿主的設定仍由 `host-config.ts` 供應——ADR-0235 H1 的教訓（「組裝層沒人測」）原樣適用。

## 後果

**正面**

- ADR-0123／0057 對訊息平面**一字不動**；隱私保證不因第三方而打折。
- 第三方零報備接入；加新應用不需要改 relay、不需要重新部署。
- 遷移期的 catch-all（未知路徑→`global`）順手收掉——ADR-0241 當初就寫明那是暫時的。

**負面／殘餘風險**

- **新的可觀測項**：`/app/...` 這條路徑告訴營運者「這個 IP 在用某個第三方應用」。
  ⚠ 別高估其嚴重性也別低估：事件本身帶著 `t:nagd`／`t:lwd`／`t:openetg-deck` 明文 tag，
  有發事件就看得出來；這條路徑只對**純讀取**的連線多洩漏一點。仍應寫進 NIP-11 與自架文件。
- **寬鬆車道內部沒有應用之間的隔離**（只有 1/8 的雜湊分片）。同一片裡一款應用的爆量會影響另一款。
- **容量問題本 ADR 沒有解**。ADR-0006 的天花板是「並行上線 ≈ 100,000 ÷ 每人每日進站訊息數」；
  而三份下游文件都寫著「ephemeral 零 DB 寫入所以永不超標」——PRD §8 早就否定過這個誤解
  （「原 PRD 曾稱 Ephemeral『零消耗』，但實際仍消耗請求數」）。承接＝承諾一個算術上撐不住的量級。
- **NIP-11 會變得語意不清**：`nip11.ts` 目前寫死 `authRequired: true`，而該檔註解自己就預言過
  「拿一個獨立的旗標去描述它遲早會說謊」。一份文件無法同時描述兩種 profile ⇒ 需 per-path NIP-11。

**後續行動**

1. `shardNameForPath`：未知路徑→拒絕（含測試）。**此項獨立於本 ADR 其餘部分**，即使最後不承接
   第三方流量也該做。
2. `relay-core.ts`：`scoped()` 的寬鬆模式、可尋址讀取閘收窄、`requireAuth` 移出寫死。
3. `worker.ts`／`shard.ts`：`/app/` 路由與雜湊分片；per-path NIP-11。
4. `host-config.ts`：兩份 profile 的 SSOT；`node-relay` 明示單一 profile。
5. 下游各自修正位址（《菜鳥教頭》與《元素使》寫的 `cinderous.cinderous1.workers.dev` 是**網頁版 App**，
   不是中繼）與《辭職信》的 AUTH 缺口——**這兩項在下游，relay 改什麼都救不了**。

## 待決

🔴 **本 ADR 尚未接受，因為它相依於一個還沒裁示的產品問題：要不要承接第三方流量。**

承接＝這座中繼從「只轉發密文」變成「同時託管公開的第三方資料」，ADR-0090 的硬隔離精神、
ADR-0257 的營運模型、以及 NIP-11 對外的定位都要重新表述。替代方案（選項 D）是讓每個應用
各自部署一座——正在另行評估其可行性（一鍵部署＋自動遷移的使用者流程）。

那份評估的結論會決定本 ADR 是 `已接受` 還是 `已棄用`。
