# 0307. 密碼學實作維持 TypeScript 一套——不走 Rust/WASM，也不各平台自己寫

- 狀態：**已接受**（決策；**不改變任何現有程式**——本文是把現況正式化，並記錄「為何不換」）
- 日期：2026-07-31
- 相關文件：
  - **0004／0007**（不自行實作加密原語——**本決策的地基**）
  - **0067**（本地密碼／`passlock.rs`——**專案已回答過一次類似問題，見 §1**）
  - **0112**（靜態加密與瀏覽器 Argon2id 包裹＝同一功能的 JS 那條）
  - **0290 §2**（現行阻擋＝外部密碼學審計，其 §2-A 建議**縮小**範圍）
  - **0297**（裝置綁定金鑰的 L2／L1／L0 分級——**§4 顯示它比 WASM 更徹底解決同一威脅**）
  - **0302 §6**（審計面量測：FS 相關 420 行）、0303（棘輪的入場費）
- 資料來源：本倉庫程式碼查證（`apps/desktop/src-tauri/src/passlock.rs`、`Cargo.toml`、

> **起點**：使用者決策清單的 **D2「是否可以不同平台都自己寫」**，長期未決。
> 問題的實質是：棘輪 FS 要**用什麼語言、幾套實作**。

## 1. 🔵 專案已經回答過一次類似的問題——答案是「選擇性下放」

`apps/desktop/src-tauri/src/passlock.rs` 檔頭：

> 本地密碼（H4，ADR-0067）：以密碼衍生金鑰（Argon2id）包裹身分祕密。
> **KDF 在原生層執行（避免 JS 端計時/記憶體弱點）**；AEAD 與亂數重用 `encstore`。

而 `packages/core/src/passlock-web.ts:41` 用的是 `@noble/hashes/argon2`。

⇒ **同一個功能，桌面走 Rust、瀏覽器與行動端走 JS，而這個不對稱是被接受的。**

⇒ **既有答案不是「整套重寫」，是「只把 JS 真的弱的那一個原語挪到原生」**
（Argon2：長時間、記憶體硬、與祕密相關——JS 的弱點在此最明顯）。

## 2. 三個選項

| | 審計成本 | 行動端可行？ | 分歧風險 |
| --- | --- | --- | --- |
| **各平台自己寫** | **× N** | ✅ | 🔴 最高 |
| **Rust/WASM 一套** | ×1（但要重寫＋WASM 綁定＋建置管線） | ✅ | 低 |
| **TypeScript 一套（現況）** | **×1** | ✅ | 無 |

**「各平台自己寫」可直接排除**：它把 ADR-0290 §2 那個**唯一的阻擋**（審計要錢，
而 ADR-0257 說沒有營收面）**乘以平台數**，方向正好與 §2-A「縮小審計範圍」相反。

## 3. 🔴 Rust/WASM 買不到它最想被拿來買的那個東西

WASM 的兩個賣點：

**（a）常數時間** —— 真的，JS 引擎給不了保證。
⚠ 但 `@noble` 是照常數時間寫的且**已審計**（ADR-0004／0007：原語我們一行都沒自己寫），
而我們自己的那 420 行（ADR-0302 §6.2）是**組合層**。
⚠ **它在熱路徑上是否有依祕密分支——未驗證**，見〈後續行動 1〉。

**（b）記憶體清除** —— **這裡有個決定性的問題。**

WASM 線性記憶體確實可以歸零。但在我們的架構裡，
**金鑰是從 JS 側的儲存讀出來的**（`at-rest.ts` 的 DEK 在 TS、`passlock-web.ts` 在 TS）
⇒ **金鑰已經在 JS 記憶體裡待過。**

⇒ **只把棘輪搬到 WASM，清不掉那些副本。** 要真的解決，得把**整個金鑰生命週期**搬過去
——那是遠大於「換個語言寫棘輪」的改動，且會把 §1 那個已被接受的不對稱整個推翻。

## 4. 而記憶體衛生有更好的解法，且已在路上

ADR-0297 的 **L2 裝置綁定金鑰**（TPM／Secure Enclave／StrongBox）：**金鑰永不離開晶片**。

⇒ 那比 WASM **更徹底**地解決同一個威脅（§3-b），
而 ADR-0297 §7 已指出 **Android 那格性價比最高**（原生支援對稱金鑰、可直接包 DEK）。

⇒ **同一筆力氣花在 0297 的 Android 格，回報高於 Rust 重寫。**
⇒ 附帶：ADR-0303 §6.2b-1b 已確立 L2 還**順便**給了裝置授權的恢復性——一筆投入兩個回報。

## 決策

**密碼學實作維持 TypeScript 一套（`packages/core`），不走 Rust/WASM，也不各平台自己寫。**

四個理由：

1. **審計** —— 多一套實作就多一次審計，正對著 ADR-0290 §2-A 的反方向。
2. **行動端是 WebView** —— JS 不可避免；寫了 Rust 也還是得有 JS 那條，等於兩套。
3. **分歧** —— 兩套實作不一致是密碼學的經典失敗模式。
4. **先例** —— 專案既有的答案是選擇性下放（§1），不是整套重寫。

**例外規則**：若日後發現**特定原語**在 JS 真的不行，**照 `passlock.rs` 的形狀處理**
——只搬那一個，桌面走原生、其餘走 JS，並依 **ADR-0297 的分級誠實揭露**
哪個平台在哪一級（不得以最強平台的說法涵蓋最弱平台的現實）。

## 後果

**正面**

- 審計面維持單一，與 ADR-0290 §2-A 一致；FS 的 420 行仍是唯一標的。
- 不引入 WASM 建置管線、不動行動端打包（Capacitor）。
- 與 §1 的既有不對稱一致，不需要推翻任何既有決策。

**負面／代價（真實且不消失）**

- **常數時間在 JS 無法保證。** 我們依賴 `@noble` 的實作品質與其審計，
  但**自己那層未驗證**（見〈後續行動 1〉）。
- **可靠的記憶體清除在 JS 做不到。** 本決策**不解決**這一點，只主張
  WASM 也解決不了（§3-b），而 ADR-0297 的 L2 才是對的解法。
- ⇒ 這兩項應在**安全說明頁**誠實揭露，不得因為「選了 TS」就不提。

**已知限制**

- **未量測 WASM 重寫的實際成本**（綁定、建置管線、行動端打包）。
  本文是以「買不到最想要的東西」否決它，**不是**以成本否決。
- **未驗證那 420 行在熱路徑上是否有依祕密分支**——這是本決策唯一未被驗證的支點。
- 未評估 `@noble` 在各家 JS 引擎（V8／JSC／WebView）上的實際時序行為差異。
- 未評估若日後 `@noble` 停止維護或審計過期的替代方案。
