# 0259. 行事曆與 Podcast 擴充的可行性（研究記錄）

- 狀態：**研究記錄（未決策，本文不改變任何產品行為）**
- 日期：2026-07-27

  0002（隱私基線）、0027（群組成對扇出）、0034/0035/0039（relay pool 與錨點）、
  0038/0231（URL 風險與威脅情報）、0061/0065（自足生態、刻意不與通用客戶端互通）、

> 且理由比原本記的更具體。

## 背景與問題

問題：**能不能在客戶端加上行事曆與 Podcast？**

兩者要分開回答，因為它們卡住的地方完全不同：行事曆卡在**規格的公開語意**（可以繞過），
Podcast 卡在**內容來源在生態外**（繞不過）。

沿用 ADR-0255 導出的五條判準（自足生態／無公開內容／瓶頸是 requests／非金融 App／
relay 視為對手），另加一條本文特別關切的：**這個功能會不會把使用者的連線帶到我們控制不到的地方。**

## 一、行事曆（NIP-52）

### 1.1 NIP-52 原樣搬進來：三個硬阻礙

| 阻礙 | 細節 |
|---|---|
| **① 全公開，且公開的正好是我們在藏的東西** | NIP-52 沒有任何加密機制。`p` tag＝參與者、`location`／`g`（geohash）＝地點、`start`＝時間；而 **RSVP（kind 31925）帶 `a`＋`p`＝「某人出席某人的活動」——那是一條公開的社交圖譜邊**。整個專案用 Gift Wrap 承擔的全部複雜度，就是為了不讓 relay 拿到這種東西。 |
| **② 可尋址配額只有 5** | 行事曆事件（31922/31923）落在可尋址區間，而 `ADDRESSABLE_MAX_PER_AUTHOR = 5`（`relay/src/message-store.ts:106`）——**一個人最多 5 個行程**就被拒。那個 5 是為 ADR-0071 的「每人 5 台裝置快照」設的，不是為行事曆。 |
| **③ 30 天就過期** | `ADDRESSABLE_TTL_SECONDS = 30 * 86_400`。**三個月後的行程會先從 relay 上消失**，然後在對方還沒同步到時就不見了。 |

②③ 可以改常數，①改不了——它是規格的語意本身。

### 1.2 可行的形態：借形狀、不借傳輸

把 NIP-52 的**資料形狀**（`title`／`start`／`end`／`location`／`status`／參與者）當成一個
**app 內部 rumor kind**，包進既有的 Gift Wrap 管線——與 `GROUP_CONTROL=40`、`RECEIPT=41`、
`ORG_JOIN=42`、`ASSET_REQUEST=44` 完全同一個作法（`packages/core/src/constants.ts`）。

這樣三個阻礙一次消失：

- **①**：行程**內容、參與者名單、地點**全在 Gift Wrap 內層，relay 讀不到，也讀不到內層 kind
  ——**外層與一般聊天訊息完全一樣（1059 ＋ `#p`），relay 看不出這是行事曆。**
  ⚠ **但別把這句話讀太寬**：依 **ADR-0237**（連線歸屬打穿事件層隱藏），relay 看到的**不是**
  「某人寄了密文給 B」而是「**你**寄了密文給 B」——每條連線都以真實金鑰做 NIP-42 AUTH，
  發布走同一條連線，中繼靠 `authState` 就能把寄件人接回來，**即使外層作者是一次性臨時金鑰**。
  所以 Gift Wrap 在這裡買到的是「**藏內容與藏事件類型**」，**不是**「藏送出邊」。
  **社交圖譜的送出邊本來就對中繼可見（M1＋連線歸屬），加不加行事曆都一樣**——
  行事曆走的是與群訊完全相同的路徑，**不新增洩漏類別**（見下方 1.3）。
- **②③**：走一般離線留言路徑（kind 1059），不碰可尋址配額與 30 天 TTL。
- **本機是真實來源**（同訊息與便條），relay 只是傳輸——所以 7 天 TTL 不影響行程本身。

其餘設計自然落位：

- **邀請／RSVP**＝另一個 rumor，回給發起人與其他參與者（同群訊路徑）。
- **群組行程**＝成對扇出 O(N)，與 ADR-0027 的群訊同成本、同機制，**不新增擴充天花板**。
- **UI 的家已經有了**：每對話的右欄／輔助面板（ADR-0182/0183 的「便條」就住在那裡）——
  行程是它的天然兄弟，不必新造導覽層。
- **企業模式是加分項**：公司設定已有上下班時間與下班自動靜音（ADR-0157/0175），
  組織共用行事曆是直接延伸，且對 ADR-0253 的 B2B 路線是可賣的功能。

### 1.3 中繼看得到什麼：與群訊等價，但少一道槓桿

因為 §1.2 的設計走的是既有群訊路徑，中繼對行事曆的可觀測性**與一則群組訊息完全相同**：

| 中繼可觀測 | 行事曆 | 是否為新洩漏 |
|---|---|---|
| 這是不是行事曆（內層 kind） | ❌ 讀不到（密文內層；**前提是沿用外層 1059**） | — |
| 行程內容／參與者名單／地點／時間 | ❌ 讀不到 | — |
| 送出邊「你 → B」 | ✅ 看得到（M1 `#p` ＋ ADR-0237 連線歸屬） | **否**——聊天訊息本來就這樣 |
| 群組成員關聯（同時對 N 人扇出） | ✅ 看得到 | **否**——ADR-0027 的群訊本來就是成對扇出 |
| 流量形狀（大小/時間/頻率，M4） | ⚠ 邀請＝一次扇出 N、回覆＝N 顆流回同一人，**形狀有特徵、可被統計猜測** | 弱化的新訊號 |

**⚠ 唯一實質的新代價：行事曆的流量結構上無法卸載到 P2P。** ADR-0237 把 P2P 卸載列為
「目前最有效的槓桿」（presence 與 typing 在資料通道開著時可完全繞過中繼，ADR-0088e/0109），
但**邀請本質上是非同步的**——你約的人可能離線，所以**必須經過 relay**。量很小（行程變更頻率
遠低於聊天），但方向上是往壞的走，實作 ADR 應記錄。

**若要真正藏住送出邊，答案不在行事曆的設計裡**——ADR-0237 的排序是
**自架 ＞ 真隱身（ADR-0240）＞ P2P 卸載**，且指出沒有傳輸層匿名（Tor）之前，
crypto 層的混淆會被 IP 關聯抹平。

### 1.4 產品定位：不在 PRD §12 的排除範圍內

PRD §12 排除的是「Open Chat 公開大群／VOOM 社群動態牆」，理由寫得很清楚：
**「會將產品從私密即時通拉成社群平台」**。

「跟三個朋友約週六幾點」不是那件事——它是**私密群組內的協調**，LINE／Slack／Discord 都有，
而且與「Life is short, connect buddies」直接相關（約得成才見得到面）。判準上：

| 判準 | 私密共享行程 |
|---|---|
| 自足生態 | ✅ 借形狀不借互通（同 ADR-0061 對 kind 0 的取捨） |
| 無公開內容 | ✅ 全在 Gift Wrap 內 |
| requests 成本 | ✅ 走既有訊息路徑；行程變更頻率遠低於聊天 |
| 非金融 | ✅ 無關 |
| relay 視為對手 | ✅ relay 看不到任何行程欄位 |
| 不把連線帶出去 | ✅ 只連既有的 cinder relay |

**結論：技術可行、成本低、定位相符。值得做——但要當成「群組協調功能」，不是「NIP-52 相容功能」。**
若實作，必須誠實標示**不與其他 Nostr 客戶端的行事曆互通**（與 ADR-0061/0065 同一個取捨，
是刻意的代價而非缺陷）。

## 二、Podcast（NIP-F4）

### 2.1 規格與本專案的距離

NIP-F4 的形狀：kind 10154（節目後設）、kind 54（單集，`audio` tag 是**媒體 URL**）、
kind 10064（作者宣稱）、kind 10054（我的最愛，接 NIP-51）。每個節目自己一把 Nostr 金鑰。
**沒有付款／zap 機制**（所以不撞 PRD §12 的金流排除——它撞的是別的）。

### 2.2 三個代價，前兩個是結構性的

1. **內容不在我們的網裡。** 客戶端目前只連 cinder relay——兩座硬編碼錨點（`ANCHOR_RELAYS`）
   加維護者簽章清單（ADR-0039）、加聯絡人 hint 學到的座（ADR-0035）。**這些 relay 上不會有
   podcast。** 要聽就得連**通用公共 relay**，而那意味著：
   - 那些 relay 看得到你的 **IP** 與**訂閱 filter**——`authors: [節目 pubkey]` 就是
     **「這個 IP 在追這些節目」**的完整紀錄；
   - 這是一個**全新的元資料洩漏面**，完全在現行威脅模型之外（ADR-0002/0237 談的都是
     「我們自己的 relay 看得到什麼」，前提是只連自己的網）。
2. **音檔在第三方 HTTP 伺服器。** `audio` tag 是 URL，播放＝自動向第三方發請求＝把 IP 交出去，
   而且是**自動的**（不是使用者點連結）。本專案對 URL 謹慎到做了威脅情報遮罩（ADR-0231）與
   風險提示（ADR-0038）——**自動抓第三方媒體與那個立場正面衝突**。
3. **產品：把私密通訊工具變成內容消費 App。** 這正是 PRD §12 排除公開社群功能時所擔心的
   位移，只是換了個型態。

### 2.3 唯一與 IM 相關的切片，現在就能做

「把某一集分享給朋友」——**貼一個連結**即可，走既有訊息路徑，零 NIP-F4、零新相依、
且照樣有 URL 風險提示。想要更好一點的體驗（顯示標題/封面）也不需要 NIP-F4，那是連結預覽
的題目（另一個獨立問題，且本身也有「抓第三方預覽＝洩漏 IP」的取捨要處理）。

**結論：否決。** 不是「做不出來」，是**要付的代價（把使用者連線帶到控制不到的地方）遠大於
拿到的價值（一個現有貼連結就能達成的分享）**。

## 決策（研究記錄，未決策）

- **本文不改變任何產品行為**、不新增協定面。
- **行事曆**：修正 ADR-0255 的歸類——從「與 IM 定位無關」改為**值得做的候選**，
  但形態是「Gift Wrap 私密共享行程」而非 NIP-52 相容實作。真要做需另立 ADR，並先定：
  rumor kind 編號、行程的更新/取消語意（比照收回 ADR-0012 或另立）、
  多裝置一致性（走既有快照 ADR-0071 還是純訊息重放）、以及群組扇出的節流。
- **Podcast**：維持否決，理由改記為上述三點（比 ADR-0255 的「與 IM 定位無關」具體）。
- 兩者都**不進 ROADMAP**，直到有人明確要求。

## 後果

- 正面：把「能不能加 X」從直覺判斷變成有依據的取捨；並抓到 ADR-0255 裡一個過度一概而論的
  歸類（行事曆與 podcast 被放在同一格，實際上兩者卡住的地方完全不同）。
- 已知限制：行事曆的成本估算未做（群組扇出的實際訊息量、UI 工作量皆未估）；若日後要做，
  需先補一份實作 ADR。NIP 狀態擷取於 2026-07-27。
- 後續行動：無（研究記錄）。若決定做行事曆，另立實作 ADR 並回頭把本文標為已承接。
