## 背景與問題

問題：**能不能在客戶端加上行事曆與 Podcast？**

兩者要分開回答，因為它們卡住的地方完全不同：行事曆卡在**規格的公開語意**（可以繞過），
Podcast 卡在**內容來源在生態外**（繞不過）。

沿用 ADR-0255 導出的五條判準（自足生態／無公開內容／瓶頸是 requests／非金融 App／
relay 視為對手），另加一條本文特別關切的：**這個功能會不會把使用者的連線帶到我們控制不到的地方。**

## 一、行事曆（NIP-52）

### 1.1 NIP-52 原樣搬進來：三個硬阻礙

| 阻礙 | 細節 |
|---|---|
| **① 全公開，且公開的正好是我們在藏的東西** | NIP-52 沒有任何加密機制。`p` tag＝參與者、`location`／`g`（geohash）＝地點、`start`＝時間；而 **RSVP（kind 31925）帶 `a`＋`p`＝「某人出席某人的活動」——那是一條公開的社交圖譜邊**。整個專案用 Gift Wrap 承擔的全部複雜度，就是為了不讓 relay 拿到這種東西。 |
| **② 可尋址配額只有 5** | 行事曆事件（31922/31923）落在可尋址區間，而 `ADDRESSABLE_MAX_PER_AUTHOR = 5`（`relay/src/message-store.ts:106`）——**一個人最多 5 個行程**就被拒。那個 5 是為 ADR-0071 的「每人 5 台裝置快照」設的，不是為行事曆。 |
| **③ 30 天就過期** | `ADDRESSABLE_TTL_SECONDS = 30 * 86_400`。**三個月後的行程會先從 relay 上消失**，然後在對方還沒同步到時就不見了。 |

②③ 可以改常數，①改不了——它是規格的語意本身。

### 1.2 可行的形態：借形狀、不借傳輸

把 NIP-52 的**資料形狀**（`title`／`start`／`end`／`location`／`status`／參與者）當成一個
**app 內部 rumor kind**，包進既有的 Gift Wrap 管線——與 `GROUP_CONTROL=40`、`RECEIPT=41`、
`ORG_JOIN=42`、`ASSET_REQUEST=44` 完全同一個作法（`packages/core/src/constants.ts`）。

這樣三個阻礙一次消失：

- **①**：行程**內容、參與者名單、地點**全在 Gift Wrap 內層，relay 讀不到，也讀不到內層 kind
  ——**外層與一般聊天訊息完全一樣（1059 ＋ `#p`），relay 看不出這是行事曆。**
  ⚠ **但別把這句話讀太寬**：依 **ADR-0237**（連線歸屬打穿事件層隱藏），relay 看到的**不是**
  「某人寄了密文給 B」而是「**你**寄了密文給 B」——每條連線都以真實金鑰做 NIP-42 AUTH，
  發布走同一條連線，中繼靠 `authState` 就能把寄件人接回來，**即使外層作者是一次性臨時金鑰**。
  所以 Gift Wrap 在這裡買到的是「**藏內容與藏事件類型**」，**不是**「藏送出邊」。
  **社交圖譜的送出邊本來就對中繼可見（M1＋連線歸屬），加不加行事曆都一樣**——
  行事曆走的是與群訊完全相同的路徑，**不新增洩漏類別**（見下方 1.3）。
- **②③**：走一般離線留言路徑（kind 1059），不碰可尋址配額與 30 天 TTL。
- **本機是真實來源**（同訊息與便條），relay 只是傳輸——所以 7 天 TTL 不影響行程本身。

其餘設計自然落位：

- **邀請／RSVP**＝另一個 rumor，走同群訊路徑（成本見 §1.4——**RSVP 不是免費的，且不是 O(N)**）。
- **群組行程**的**邀請扇出**＝成對扇出 O(N)，與 ADR-0027 的群訊同機制。
- **UI 的家已經有了**：每對話的右欄／輔助面板（ADR-0182/0183 的「便條」就住在那裡）——
  行程是它的天然兄弟，不必新造導覽層。
- **企業模式是加分項**：公司設定已有上下班時間與下班自動靜音（ADR-0157/0175），
  組織共用行事曆是直接延伸，且對 ADR-0253 的 B2B 路線是可賣的功能。

### 1.3 中繼看得到什麼：與群訊等價，但少一道槓桿

因為 §1.2 的設計走的是既有群訊路徑，中繼對行事曆的可觀測性**與一則群組訊息完全相同**：

| 中繼可觀測 | 行事曆 | 是否為新洩漏 |
|---|---|---|
| 這是不是行事曆（內層 kind） | ❌ 讀不到（密文內層；**前提是沿用外層 1059**） | — |
| 行程內容／參與者名單／地點／時間 | ❌ 讀不到 | — |
| 送出邊「你 → B」 | ✅ 看得到（M1 `#p` ＋ ADR-0237 連線歸屬） | **否**——聊天訊息本來就這樣 |
| 群組成員關聯（同時對 N 人扇出） | ✅ 看得到 | **否**——ADR-0027 的群訊本來就是成對扇出 |
| 流量形狀（大小/時間/頻率，M4） | ⚠ 邀請＝一次扇出 N、回覆＝N 顆流回同一人，**形狀有特徵、可被統計猜測** | 弱化的新訊號 |

**⚠ 唯一實質的新代價：行事曆的流量結構上無法卸載到 P2P。** ADR-0237 把 P2P 卸載列為
「目前最有效的槓桿」（presence 與 typing 在資料通道開著時可完全繞過中繼，ADR-0088e/0109），
但**邀請本質上是非同步的**——你約的人可能離線，所以**必須經過 relay**。量很小（行程變更頻率
遠低於聊天），但方向上是往壞的走，實作 ADR 應記錄。

**若要真正藏住送出邊，答案不在行事曆的設計裡**——ADR-0237 的排序是
**自架 ＞ 真隱身（ADR-0240）＞ P2P 卸載**，且指出沒有傳輸層匿名（Tor）之前，
crypto 層的混淆會被 IP 關聯抹平。

### 1.4 中繼成本：1:1 等於兩則訊息；群組**不是** O(N)，是 O(N²)

計費模型（ADR-0109）：**進來的每則 WS 訊息＝1 個 DO request**，扇出不計。一則 1:1 訊息＝
**3 顆事件**（給對方＋自封副本 ADR-0107＋對方回的送達回條 ADR-0058）。

| 情境 | 事件數 | ≈ 幾則訊息 |
|---|---:|---:|
| **1:1 邀請＋回覆一輪** | ~6（邀請 3 ＋ RSVP 3） | **2** |
| 10 人群組，RSVP 只回主揪 | ~20 | ~7 |
| 10 人群組，**RSVP 全體可見** | **~100** | ~33 |
| 50 人組織公告，RSVP 全體可見 | **~2,500** | ~830 |

**⚠ 前一版本文誤記「群組行程＝O(N)、不新增擴充天花板」——錯的。** 它只算了邀請扇出，
漏掉 RSVP。而 **RSVP 的形狀不是群訊，是「群組回條」**：每位成員都要回應同一則事件。
ADR-0095 恰好量測過這個形狀並得出：

> 一則群訊每位成員各回一則儲存型回條給發訊者……全網回條 **≈ r·N²**、每裝置收件 ≈ r·N

ADR-0095 因此把群組回條**依成員數分級**（≤5 名單制／6–10 計數制／**>10 完全不送**），理由正是
「N² 成本與收件箱膨脹在大群失控」。**RSVP 與群組回條結構完全相同**，只是語意從「已讀」換成
「參加/不參加」——若要讓全體成員看到「誰要來」（行事曆的正常期待），每位成員各扇出 N 份＝
**每輪邀請 N²**。

**兩件本文前一版沒算進去的：**

1. **行事曆有生命週期，訊息沒有。** 訊息送出即結束；行程會改時間、改地點、取消——
   **每次變更都是一次完整扇出**。ADR-0109 的「每則 3 顆」不含這個。
2. **提醒必須是本機計時器（零中繼成本）**。若實作成由任何遠端觸發，就是另一條成本曲線
   ——實作 ADR 應寫死這一條。

**解法不需新發明**：直接沿用 ADR-0095 的分級到 RSVP（≤5 名單／6–10 計數／>10 只回主揪或關閉），
或一律「RSVP 只給主揪＋主揪節流後重播名單」。但**必須在實作 ADR 明確指定**，不能假設它與群訊同成本。

### 1.5 已評估並否決：讓中繼依「行程日期」決定保存範圍

**提案**：中繼只保存「過去 1 個月＋未來 2 個月」的行事曆事件，超出不存；已同步到本地的
就在本地保存（條件同訊息）。

**否決，因為中繼做不到——而要讓它做得到就得放棄 §1.3 的隱私性質。** 行事曆是 1059 內層的
rumor，中繼**看不出那是行事曆**（內層 kind 在密文裡），也**讀不到 `start`**。要依行程日期
決定保存，只有兩條路：

- **(a) 給行事曆獨立外層 kind**（如 `FILE_WRAP=1060`）→ 中繼知道你在傳行事曆；
- **(b) 把行程日期放進明文外層 tag**（NIP-40 `expiration` 本來就是明文）→
  **中繼得到一份你未來兩個月的行程時間表**。(b) 比 (a) 具體得多，是嚴重退步。

**而且提案想要的效果，現況已經達成且更嚴格**：1059 吃站方 TTL 上限（**預設 7 天**，ADR-0065），
且是硬夾的——`effectiveExpiration = min(客戶端標的, now + 站方上限)`，客戶端標 90 天也會被夾回
7 天。中繼是**傳輸**不是儲存；收件端抓走後那份就無意義。提案的「本地保存、條件同訊息」則
**本來就是設計本身**（§1.2）。

**但這個提案指向一個真問題：投遞窗，不是保存期。**

> 我約你三個月後的事，你離線 8 天 → gift wrap 過期 → **你永遠收不到這個邀請。**

訊息漏掉可以接受；行程邀請不同——**事件還在未來、還有效，但傳輸窗已經關了**。這是行事曆與
聊天訊息的真正差異：**資料的有效期比傳輸的 TTL 長**。而 **Outbox（ADR-0041）不覆蓋這個**
——它保證的是「中繼收下了」（`OK`），不是「對方拿到了」；ACK 後 Outbox 即完成。

**解法是重送，不是延長保存**：主揪的客戶端在**看到對方上線**時補送尚未確認送達的邀請。
訊號現成（presence 的 IDLE→ACTIVE 轉換偵測 ADR-0109、送達回條 ADR-0058），只重送未送達的，
**零中繼改動、零隱私代價、零新協定面**。列入實作 ADR 必須先定的事項。

（調站方 `MAX_TTL_DAYS` 是另一條路，但那會延長**所有**訊息的保存、改變整座中繼的儲存數學
（撞 ADR-0244 的天花板），對公共站是往壞的走；企業自架站本來就可自行調整。
自己的行程跨裝置同步走既有的加密雲端快照 ADR-0071，不需新機制。）

### 1.6 已評估：對話提到日期時「自動切換」右欄到行事曆分頁

**提案**：使用者或對方在對話中提到日期時，右側輔助欄自動切到行事曆分頁。

**技術可行性高，但「自動切換」這個動作否決；改為「偵測→提示」（下方設計已定）。**

技術面沒有難處：分頁狀態是 `DeckRight.tsx` 的一個 `useState<AuxTab>`（目前**沒有任何自動切換
行為**，`setTab` 只由分頁按鈕呼叫），日期偵測是純函式問題，專案已有兩個同型前例
（`calc.ts` 算式偵測、`sticker-triggers.ts` 尾端比對）。全本機、零中繼成本。

**但它違反專案立過兩次的原則：**

- **ADR-0037**（文字觸發貼圖）：偵測到觸發字→**建議列**，需 Tab／點擊才接受，並明寫
  **「不劫持 Enter——避免誤送貼圖的破壞性誤觸」**。
- **ADR-0097**（算式預覽）背景第一句：**「不要偷改正在打的訊息」**；解法是右欄有自己的輸入框、
  使用者**自行決定是否插回**。

兩者是同一形態：**偵測→提供選項，不代替使用者行動**。自動切換分頁屬同一類違反。

**三個具體問題：**

1. **搶走脈絡**：右欄現在顯示什麼是使用者剛主動選的；看相簿／對話串時被跳走＝focus stealing。
2. **偽陽性是常態**：中文日期樣式大量出現在非約時間語境（「我昨天看到」「三月的時候」
   「等一下」），數字更糟（「3/15」可能是分數／比數／版本號）。ADR-0037 已為此立過規則
   （長度 ≥2 才建議、「中文無空白分隔不能以詞切」、「≥2 防止任意字元都彈窗」）——這裡**更需要**
   同等謹慎，因為誤觸代價更高（整個面板跳走 vs 出現一列建議）。
3. **⚠ 對方的訊息是攻擊者可控輸入。** 依 ADR-0121/0127，陌生人可進「訊息請求區」且該區
   **可被灌爆**。若面板因**收到的訊息內容**自動切換，等於**任何能傳訊給你的人都能操控你的
   UI 狀態**——UI redressing 的輕量版。專案對這一類（ADR-0038／0231／0127）一向謹慎。

**設計（已定，2026-07-27）——偵測→提示，不導覽：**

1. **訊息氣泡內的日期加低調可點標記**，點了才開行事曆分頁並預填
   （＝ADR-0037 建議列的同構：呈現選項，由使用者觸發）。
2. **composer 端偵測到日期→建議列**（同 sticker trigger 的位置與鍵盤語意），Tab 接受＝開分頁
   並預填，**不劫持 Enter**。
3. **全本機、零外送**（同 ADR-0037「觸發字為純本地設定，不隨訊息外流」）——偵測結果不進任何
   事件、不寫入 rumor、不同步到其他裝置。

**不做：行事曆分頁上的未處理日期 badge。**（維護者決定，2026-07-27。）

> **已知取捨**：badge 原本是三者中**唯一持久且聚合**的提示。拿掉之後，未處理的日期只剩兩個
> 觸發點——氣泡內標記（隨訊息留在捲動區，但不聚合、不提醒）與 composer 建議列（暫時性，
> 打完就消失）。實務後果：**使用者若在讀訊息當下沒注意到標記，就不會再被提醒**。
> 這是刻意的低噪音取捨（badge 是另一個會累積未讀感的計數器），記錄在此以免日後當成疏漏重議。

**真正的工作量不在 UI，在日期解析**：中文相對日期（「下週三」「大後天」「月底」）需要基準時間、
週起始日、時區，且 zh-Hant／en 兩套。應為 core 的純函式＋測試（比照 `calc.ts` 的位置與風格）、
兩端共用。**這筆成本在「提示形態」就要付，所以自動切換省不了任何工。**

**若日後重議自動切換**（現已否決，此段僅留為當時的條件）：至少三個閘——**opt-in 預設關**、
**只對自己輸入的文字生效**（不對收到的訊息，避開問題 3 的攻擊者可控輸入）、
**只在右欄仍停在預設分頁時才切**（使用者主動選過就不動）。且應先有「提示形態實際不足」的
證據再重啟——比照 ADR-0165「先做簡單穩健的，有數據再上自動／學習機制」的作風。

### 1.7 群組行程的身分與權威：建立一次，不是每人各建一份

**問題**：群組裡每個人都要自己建立事件嗎？

**不用——一個人建立、扇出給全體，且全網是同一個事件。** 機制與群訊完全相同：主揪建一個 rumor →
`wrapGroupMessage` 產生 N 份 Gift Wrap（每位成員一份）→ 各成員的客戶端收到後在本機具現化。

而「這是同一個事件」有機制保證，不是靠約定。ADR-0095：

> rumor（kind/時間/tags/內容/作者）對每位收件人**完全相同** → 其雜湊也相同……
> 故 `rumor.id` 是**跨成員一致且可驗證**的群訊識別

ADR-0095 修的正是「群訊在每台裝置上 id 不同 → 回條/回應/引用對不回發訊者」。**RSVP 有完全相同的
需求**（必須指向一個所有人都同意的事件 id），所以前置條件已經具備，行事曆直接繼承。

**但三種情況會讓成員手上沒有這個事件**：

1. 離線超過 7 天（§1.5 的投遞窗）；
2. **事後才加入群組**——ADR-0027 無伺服器端房間、無歷史重播，新成員拿不到既有事件；
3. 被移除後再加回（同 2）。

聊天訊息漏掉可接受（晚進來就沒看到）；**行事曆比較糟——群組以為事情講定了，但某成員的行事曆
就是沒有這筆，且沒有任何訊號顯示他少了東西＝靜默分歧。** 實作 ADR 須連同 §1.5 的重送一起處理
（例如：加入群組時由主揪補送未過期的行程）。

**權威（v1 建議：主揪權威）：**

- **(a) 主揪權威（建議）**：只有建立者能改時間／地點／取消；他人手上的是複本；編輯＝指向原
  `rumor.id` 的新 rumor。符合「邀請」語意、不需衝突解決、可沿用收回／編輯的既有模式（ADR-0012）。
- **(b) 任何人可編輯**：N 份複本、無伺服器 → 需衝突解決。ADR-0242 有現成機具（per-field LWW
  ＋墓碑），**但它是為「同一身分的多裝置」設計的，不是多使用者共同編輯**。差別會帶出一個
  ADR-0242 從不必解的問題：**多使用者的 LWW ＝時鐘最快的人贏，而 `created_at` 是自報的**
  ——有人可靠謊報時間搶走權威。對多裝置良性（都是你自己），對多使用者是真的攻擊面。→ v1 不採。

**RSVP 不受此影響**：它是每位成員對事件的**自己的**狀態，本就由本人簽署，無衝突。

### 1.8 產品定位：不在 PRD §12 的排除範圍內

PRD §12 排除的是「Open Chat 公開大群／VOOM 社群動態牆」，理由寫得很清楚：
**「會將產品從私密即時通拉成社群平台」**。

「跟三個朋友約週六幾點」不是那件事——它是**私密群組內的協調**，LINE／Slack／Discord 都有，
而且與「Life is short, connect buddies」直接相關（約得成才見得到面）。判準上：

| 判準 | 私密共享行程 |
|---|---|
| 自足生態 | ✅ 借形狀不借互通（同 ADR-0061 對 kind 0 的取捨） |
| 無公開內容 | ✅ 全在 Gift Wrap 內 |
| requests 成本 | ⚠ 1:1 ≈ 2 則訊息；**群組 RSVP 若全體可見則為 O(N²)**，須沿用 ADR-0095 的分級（見 §1.4） |
| 非金融 | ✅ 無關 |
| relay 視為對手 | ✅ relay 看不到任何行程欄位 |
| 不把連線帶出去 | ✅ 只連既有的 cinder relay |

**結論：技術可行、定位相符，值得做——但要當成「群組協調功能」，不是「NIP-52 相容功能」。**
**成本要分開講**：1:1 便宜（≈2 則訊息）；群組**取決於 RSVP 的可見範圍**——照 §1.4 沿用
ADR-0095 的分級才便宜，不分級就是 O(N²)。
若實作，必須誠實標示**不與其他 Nostr 客戶端的行事曆互通**（與 ADR-0061/0065 同一個取捨，
是刻意的代價而非缺陷）。

## 二、Podcast（NIP-F4）

### 2.1 規格與本專案的距離

NIP-F4 的形狀：kind 10154（節目後設）、kind 54（單集，`audio` tag 是**媒體 URL**）、
kind 10064（作者宣稱）、kind 10054（我的最愛，接 NIP-51）。每個節目自己一把 Nostr 金鑰。
**沒有付款／zap 機制**（所以不撞 PRD §12 的金流排除——它撞的是別的）。

### 2.2 三個代價，前兩個是結構性的

1. **內容不在我們的網裡。** 客戶端目前只連 cinder relay——兩座硬編碼錨點（`ANCHOR_RELAYS`）
   加維護者簽章清單（ADR-0039）、加聯絡人 hint 學到的座（ADR-0035）。**這些 relay 上不會有
   podcast。** 要聽就得連**通用公共 relay**，而那意味著：
   - 那些 relay 看得到你的 **IP** 與**訂閱 filter**——`authors: [節目 pubkey]` 就是
     **「這個 IP 在追這些節目」**的完整紀錄；
   - 這是一個**全新的元資料洩漏面**，完全在現行威脅模型之外（ADR-0002/0237 談的都是
     「我們自己的 relay 看得到什麼」，前提是只連自己的網）。
2. **音檔在第三方 HTTP 伺服器。** `audio` tag 是 URL，播放＝自動向第三方發請求＝把 IP 交出去，
   而且是**自動的**（不是使用者點連結）。本專案對 URL 謹慎到做了威脅情報遮罩（ADR-0231）與
   風險提示（ADR-0038）——**自動抓第三方媒體與那個立場正面衝突**。
3. **產品：把私密通訊工具變成內容消費 App。** 這正是 PRD §12 排除公開社群功能時所擔心的
   位移，只是換了個型態。

### 2.3 唯一與 IM 相關的切片，現在就能做

「把某一集分享給朋友」——**貼一個連結**即可，走既有訊息路徑，零 NIP-F4、零新相依、
且照樣有 URL 風險提示。想要更好一點的體驗（顯示標題/封面）也不需要 NIP-F4，那是連結預覽
的題目（另一個獨立問題，且本身也有「抓第三方預覽＝洩漏 IP」的取捨要處理）。

**結論：否決。** 不是「做不出來」，是**要付的代價（把使用者連線帶到控制不到的地方）遠大於
拿到的價值（一個現有貼連結就能達成的分享）**。
