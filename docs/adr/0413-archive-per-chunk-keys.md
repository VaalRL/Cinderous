# 0413. 封存每塊一把隨機金鑰：刪除對話＝銷毀金鑰（ADR-0298 的第一階段）

- 狀態：**已接受（Accepted，2026-11-11）**——使用者 2026-11-11 決定推 ADR-0298，並採「先修刪除、保留救援路徑」的範圍
- 日期：2026-11-11
- 相關文件：**0298**（分層靜態保護與分段金鑰刪除，本文實作其 §2 與待辦 4）、0111（訊息封存）、0112（網頁／行動端靜態加密）、0054（桌面加密儲存）、
  0073（忘記密碼救援）、0202（移除身分＝刪本機資料）、0297（裝置綁定金鑰）、0278／0287（UI 不得說謊）

## 背景與問題

ADR-0298 §3 證實：封存（冷資料）的每一塊都直接用同一把根金鑰加密（網頁／行動端由 nsec 導出，桌面是金鑰庫裡的資料庫金鑰），而刪除只是刪檔。在 flash 與日誌式檔案系統上刪檔不保證位元組被抹掉，所以**殘留的塊拿到根金鑰就照樣解得開**。

ADR-0298 提了兩件可以分開採納的事：

1. 分段金鑰，讓刪除真的等於刪除（**不需要**放棄救援路徑）。
2. 冷層改用密碼當根、拿掉救援，擋「磁碟映像＋nsec」（代價：忘記密碼＝永久失去舊歷史）。

使用者選了第 1 件，加上 ADR-0298 待辦 4（設定頁如實說明本地密碼的保護範圍）。

動工前查證到兩件 ADR-0298 沒寫到的事：

- **封存目前只有一種刪除：移除整個對話**（刪好友、封鎖、退群）。保留上限的溢出是「搬進封存」不是刪除（ADR-0126）；限時訊息進封存前已拿掉原文（ADR-0408）。所以這次的保障落在「移除對話」與「移除身分」，不是按時間丟棄。
- **網頁與行動端「移除此身分」沒有刪 OPFS 封存**：只清 localStorage，封存整批留著，同一把 nsec 再輸入就解得開。這與 ADR-0202 不符。

## 考量的選項

- **分段粒度**
  - 按月一把：要另外維護「哪一塊屬於哪個月」的索引，而且一塊可能跨月。
  - **每塊一把（採用）**：塊（1,000 則）本來就是封存的讀寫單位，一塊一個包裹檔，不需要索引、沒有讀改寫的競態。
- **包裹存哪裡**
  - 單一索引檔：每次追加都要整份重寫，舊版本的索引本身就是殘留。
  - **每塊一個小檔（採用）**：寫一次、刪除時覆寫一次。
- **既有封存要不要整批重新加密**
  - 要：需要可中斷續跑的遷移狀態機，中途失敗有新舊混雜的風險。
  - **不要（採用）**：重寫只是多一份新檔，**舊密文的殘留還是在介質上、還是用根金鑰解得開**——遷移買不到任何刪除保障。舊塊照常可讀，保障只及於升級後寫下的塊。

## 決策

1. **封存每一塊用一把隨機的 32-byte 金鑰加密**；那把金鑰用根金鑰包起來，存成塊旁邊的小檔：
   - 網頁／行動端（OPFS）：`<convo>.<seq>.json`＝`s1:<kid>:` 接 `sealValue(K_seg, json)`、`<convo>.<seq>.<kid>.key`＝`wrapSegmentKey(dek, K_seg)`（`k1:` 前綴）。
   - 桌面（Tauri）：`<convo>.<seq>.enc`＝`CSK1`＋`kid`（8 bytes）＋`encrypt(K_seg, json)`、`<convo>.<seq>.<kid>.key`＝`encrypt(db_key, K_seg)`；邏輯搬進 lib 的 `archive` 模組（`cargo test` 才測得到）。
   - 🔴 **塊自己記下用的是哪一份包裹**（`kid`，隨機）；包裹的檔名帶同一個 `kid`。包裹不得只靠「同一個序號」對上塊（見下方「合併前審查」）。
   - 🔴 塊金鑰必須是**隨機**的，不得由根金鑰導出——導出的金鑰有根金鑰就能重建，銷毀就沒有意義（ADR-0298 §2 的更正）。
2. **寫入順序：先包裹、後塊**。中途當機留下「有包裹、沒有塊」；塊數只數塊檔，下一次追加會用同一個序號重來、另寫一份包裹（孤兒包裹留到移除對話時一起刪）。反過來會留下沒有金鑰的塊＝訊息遺失。桌面寫這兩個檔時先落盤（fsync）再換上：寫完之後熱區立刻被裁切，不能讓斷電把兩邊都弄丟。
3. **移除對話：先刪所有包裹、再刪塊**；一個檔刪不掉不影響其餘的。
   - 桌面刪包裹前先就地以等長的零覆寫並落盤。盡力而為：寫入時複製的檔案系統與 flash 上舊位元組仍可能留著。
   - OPFS 不覆寫：`createWritable` 依規格寫到另一份暫存檔、關閉時才換上，碰不到原本的位元組，覆寫只會多留一份痕跡。
   - 移除排在同一個儲存層的封存寫入佇列裡（`ArchiveWriter.remove`），不與正在寫的那一塊交錯。
4. **讀取**：塊有 `kid` 開頭就讀那一份包裹；包裹不在或解不開就是讀不到，不退回用根金鑰直接解。沒有開頭＝升級前（或降版時）寫下的舊塊，直接用根金鑰（更舊的明文塊也照常讀）。
5. **救援路徑不變**：根金鑰還是原來那一把，忘記密碼用 nsec 救援（ADR-0073）照舊，**沒有新增任何資料遺失方式**。
6. **網頁／行動端「移除此身分」連封存一起清**（新的 `wipeOpfsArchive`）：先刪每份包裹、再刪整個目錄。空的 namespace 不做事（同 `clearStorageNamespace`）。桌面的 `wipe_identity` 本來就刪整個目錄與金鑰庫裡的資料庫金鑰，不變。
7. **設定頁的本地密碼說明改成實話**：拿到這台裝置的人沒有密碼解不開；但**同時有這台裝置的資料與 nsec 的人不需要密碼**。原文案「不輸入密碼無法解開」不實。
8. **命名紅線**（沿用 ADR-0298 §4）：這不是前向保密，對外不得這樣稱呼。

## 理由

- 要銷毀的東西從「整段歷史」縮成「每塊幾十個位元組的包裹」，而且只寫一次。
- 不動根金鑰＝使用者感覺不到任何改變，也不必決定熱層天數（那是第 2 件事才需要的參數）。
- 不做遷移，拿掉了 ADR-0298 列為最大工程風險的那一項，而且沒有因此少掉任何實際保障。

## 後果

- 正面：
  - 升級後寫下的封存，在移除對話或移除身分之後，殘留的塊用根金鑰（nsec）解不開。
  - 補上「移除身分卻留下封存」的缺口。
  - 本地密碼的說明不再說過頭。
- 負面／已知殘餘風險：
  - **量的改善，不是質的保證**（ADR-0298 §6）：包裹自己也寫在同一個介質上，連包裹的殘留都撿得回來、又有根金鑰的人還是解得開。`archive-residue.test.ts` 有一則測試把這條界線釘住。要補上只能靠硬體銷毀根秘密（ADR-0297）。
  - **升級前寫下的封存沒有這個保障**（對照組測試釘住）。
  - **熱層不在範圍內**：近期訊息（localStorage／桌面的部位檔）被改寫或刪除後的殘留，仍用根金鑰解得開。
  - **「磁碟映像＋nsec」仍然擋不住**還沒被刪除的資料——那是 ADR-0298 的第 2 件事，這次沒做。
  - **降版會讀不到新塊**：舊版程式不認得新格式，會用根金鑰直接解而失敗。桌面舊版還會把解不開的塊改名成 `.corrupt`（資料沒丟，包裹也還在，但要手動改回）。降版期間寫下的舊格式塊升級後照常讀得到。熱區不受影響。
  - **沒有 Web Locks 的瀏覽器**：同一身分開兩個分頁、同時封存同一個對話的同一塊時，只留下後寫的那一塊（另一塊的一千則遺失；加金鑰之前就是這樣）。有 Web Locks 的環境已修，見文末「跨分頁互斥」。
  - 封存的檔案數變成兩倍（每塊多一個幾十位元組的小檔）；重用序號時會多出孤兒包裹，移除對話時一起刪。
  - 已被複製走的舊映像無法回收（任何刪除機制都一樣）。
- 後續行動：
  1. ADR-0298 第 2 件事（冷層以密碼為根、不提供救援）仍待決策；若要做，本文的包裹格式不必改，只換包裹用的根金鑰。
  2. 按時間丟棄封存（「只留最近一年」）目前沒有這個功能；要做的話每塊一把金鑰已經夠用。

## 合併前審查（2026-11-12）

合併前的獨立審查以測試重現了下列問題，本文與實作已一併修正：

- **包裹只靠「同一個序號」對上塊，會把一塊配到別人的金鑰**：
  - 兩個分頁同時封存同一個序號：包裹被後寫者覆蓋、塊卻留下先寫者的，兩塊都讀不到（加金鑰之前至少留得下一塊）。
  - 降回舊版又升級：舊版在同一個序號寫下的塊，被留下來的包裹拿去解，讀不到；桌面還會把它隔離，覆蓋掉先前隔離的那一塊。
  - 解不開而被隔離的塊，包裹在下一次追加時被覆蓋，隔離等於白做。
  - 修法：決策 1 的 `kid`。
- **移除與正在寫的那一塊交錯**：刪掉的對話留下一塊讀得到的封存。修法：決策 3 的佇列。
- **OPFS 移除時一個檔刪不掉就整個中斷**，後面的包裹全留著。修法：逐檔嘗試。
- **覆寫沒有蓋到原本的位元組**（OPFS 寫暫存檔；桌面先截斷）。修法：OPFS 不再覆寫，桌面改成就地覆寫並落盤；文字不再說它在一般情況下有效。
- **桌面寫包裹與塊沒有落盤就裁切熱區**。修法：決策 2 的 fsync。

## 跨分頁互斥（2026-11-12）

合併時留下的兩項殘餘風險，用 Web Locks 一起處理：

- **網頁版兩個分頁同時封存同一個對話**：每個分頁有自己的 `ArchiveWriter`，佇列只排得了自己分頁的寫入，兩個分頁會算出同一個序號，後寫的塊蓋掉先寫的。
- **行動端移除身分時沒有先停掉封存寫入**：正好碰上一次搬移，可能留下那一塊與它的包裹。

決策：OPFS 封存的追加、移除對話、移除身分，都在同一把鎖 `cinder-archive:<namespace>` 裡做（每個身分一把，同一個 origin 的所有分頁共用）。

- 追加時「算序號 → 寫包裹 → 寫塊」整段在鎖裡，第二個分頁拿到下一個序號。兩個分頁搬的可能是同一批訊息，那只是重複，讀取端本來就以 id 去重（ADR-0111「寧可重複，絕不遺失」）。
- 移除身分等正在寫的那一塊寫完才刪；之後的追加因為目錄已經不在而失敗，熱區不裁切。
- 沒有 Web Locks 的環境照舊直接做（同一分頁內仍由 `ArchiveWriter` 排隊）。目前主流瀏覽器與 Android WebView 都有。
- 桌面（Tauri）不受影響：單一執行個體，寫入本來就在同一個佇列裡。

考量過、沒採用：

- 用 `BroadcastChannel` 選出一個分頁負責封存：要處理那個分頁關掉時的交接，比鎖複雜得多。
- 用檔名搶占（`createWritable` 的獨占模式）：還不是每個瀏覽器都有，失敗時也要自己重試。
