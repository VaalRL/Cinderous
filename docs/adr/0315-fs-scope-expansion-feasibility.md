# 0315. FS 範圍能不能擴大到 1:1 文字以外（研究記錄）

- 狀態：已接受（**研究記錄，不改變任何產品行為**；結論含一項**阻擋性前置條件**）
- 日期：2026-08-03
- 相關文件：ADR-0245 §200（「其他事件型別暫維持靜態」的那條 ⏳）、ADR-0238（設計）、
  ADR-0313（自動輪替）、ADR-0314（停用）、ADR-0027（群組成對扇出）、
  `packages/core/src/giftwrap.ts`、`group.ts`、`reaction.ts`、`deletion.ts`

## 背景與問題

目前 `fsSendOpt()` 全庫只有一處呼叫（1:1 文字送出）。使用者開了 FS，很容易以為整個對話受保護，
實際上群訊、回應、收回、檔案、通話、typing／nudge 全部維持靜態金鑰。

問題：**擴大得動嗎？值得嗎？**

## 調查結果：技術上比預期便宜很多

`subkey.ts` 檔頭那句關鍵發現（「`nip59.sealAndWrap`/`openWrap` 已完全參數化在
`recipientPk`/`recipientSk` 上 ⇒ retarget 不需改 nip59」）比它自己宣稱的還要更成立——
**`wrapForBoth` 這個泛用包封器早就收 `encryptToFor`，而且早就支援 `recipients` 陣列**
（群組扇出用的就是它）。也就是說多數型別缺的只是「呼叫端沒把選項傳下去」。

更關鍵的是**收件側**：`openFs()`（多鑰解封）已經掛在

- kind 1059 收件箱的主處理路徑，以及
- relay 檔案分塊的處理路徑

⇒ **凡是走 1059 外層的事件，收件端今天就已經解得開 EK 密文了。** 擴大只是送件側的事。

### 分層

**Tier A — 走 1059、收件側已就緒，只差送件側傳選項**

| 型別 | 送件落點 | 現況 |
| --- | --- | --- |
| 群組訊息 | `group.ts:141`（每成員 `sealAndWrap`） | 未傳 |
| 群組控制 | `group.ts:188`（扇出） | 未傳 |
| 訊息回應 | `reaction.ts:28`（`wrapForBoth`） | 未傳 |
| 收回訊息 | `deletion.ts:24`（`wrapForBoth`） | 未傳 |
| 檔案 metadata | `giftwrap.ts:179`（`wrapFileMessage`） | 未傳 |
| 共享行程 | `calendar.ts:147` | 未傳 |
| 組織檔案分塊 | `file-relay.ts:67` | 未傳（收件側已就緒） |
| 資產 backfill | `asset-relay.ts:56/84` | 未傳 |

約 8–10 個呼叫點，改動形狀完全一致（把 `encryptToFor` 往下傳）。

**Tier B — 各自的 ephemeral kind，收送兩側都要改**

typing（20001）、nudge（20100）、在線狀態內容（21004）、SDP（21000–21999）、通話控制（21002）。
這些以身分金鑰各自解封（`readTyping`／`readNudge`／`readPresenceState`／…），
要擴大得為每一條加多鑰解封。

## 值不值得：看的是「密文會不會被留下來」

FS 防的是「**未來** nsec 失竊 → 解開**過去被記錄下來**的密文」。價值正比於「這段密文有多可能
被留著」乘上「留著多久還有意義」。

- **Tier A 是持久化的**：kind 1059 寫進中繼 DO SQLite，NIP-40 七天。取得那份儲存＝拿到密文。
- **Tier B 是 Ephemeral（20000–29999）**：中繼**純記憶體轉發、不寫持久層**。要有密文可解，
  攻擊者得**當時就在側錄流量**。而且「三個月前某人正在打字」這件事，解開了也沒有價值。

⇒ **Tier B 的 FS 價值接近零，成本卻是每條路徑各改一次。不建議做。**

Tier A 之中，價值差距也很大：

- **檔案 metadata**：檔名＋大小＋MIME。這是**真正敏感**的（`2026年裁員名單.xlsx`）。價值最高。
- **群組訊息**：內容本體。價值高。
- **共享行程**：標題／時間／地點。價值中高。
- **回應**：一個 emoji ＋ 指向哪則。內容價值低，但關聯性有價值。
- **收回**：見下——這條不是價值問題，是安全方向問題。

## 🔴 阻擋性發現一：解不開的訊息會靜默消失

`relay-backend.ts` 的兩處解封都是：

```js
try { opened = this.openFs(event); } catch { return; }
```

一則加密到「我已回收的舊 EK」的訊息，就這樣**無聲無息地不存在**。沒有錯誤、沒有佔位、
沒有計數器。這個 catch 本身是對的（畸形事件本來就該丟），但它讓「密文解不開」與
「這顆事件是垃圾」變成同一件事。

今天這條只影響 1:1 文字，而且輪替是手動的（多數人不換鑰＝不會發生）。
**ADR-0313 開啟自動輪替後，發生率會上升；再擴大到 Tier A，會乘以事件型別數。**

⇒ **前置條件：擴大範圍之前，必須先讓「解不開」成為可觀測的事件**（至少計數，最好能區分
「我沒有那把 EK」與「這顆事件本來就壞」）。在還看不見失敗的情況下擴大加密面，
等於擴大一個你不會知道它發生了的資料遺失面。

## 🔴 阻擋性發現二：收回訊息 retarget 的失敗方向是**不安全**的那一邊

其餘型別解不開的後果是 **fail-safe**：訊息沒出現＝你沒看到不該看到的東西。

**收回（kind 5）相反。** 使用者按了「收回」，收件端若解不開那顆刪除事件 ⇒ 刪除從未被套用 ⇒
**那則訊息繼續留在對方畫面上**。使用者以為收回了，實際上沒有，而且雙方都不會知道。

`deletion.ts` 的檔頭自己就寫著「使用者在手機按了收回，訊息卻還留在自己的電腦上——
那是隱私破損，不是不便」。retarget 收回事件會**製造同一類破損**，只是換一個成因。

⇒ **建議：收回不 retarget**（維持靜態身分金鑰），或若要 retarget，必須同時送一份加密到
身分金鑰的備援。前者簡單且損失極小——收回事件的內容只有一個 event id，其 FS 價值遠低於
它送不到的代價。

## 🟠 其他要先想清楚的

- **群組扇出需要每位成員的 EK**。`contactEks` 只從 10040 訂閱（`authors:[聯絡人]`）與 rumor hint
  學到 ⇒ **不是聯絡人的群成員拿不到 EK**，那幾份自動退回身分金鑰。結果是同一則群訊
  「部分成員有 FS、部分沒有」。這本身可接受（退回＝現況），但**降級警告在群組語意不明**：
  要對誰警告？沿用 1:1 的 `fsWouldDowngrade` 會變成洗版。需要先定義群組的降級語意。
- **檔案 metadata 與分塊必須同進退**：`tid` 要對得上，兩條路徑一個 retarget 一個沒有會出現
  「metadata 到了、位元組解不開」。
- **邀請（`invite.ts:120`）不可能有 FS**：對象是還不是聯絡人的人，定義上不知道他的 EK。

## 結論與建議順序

**可以擴大，而且技術成本比想像低（Tier A 約 8–10 個同形狀的呼叫點）。但不能現在做。**

建議順序：

1. **先做可觀測性**（前置條件，阻擋）：讓 EK 解封失敗可被計數／回報，區分「缺 EK」與「壞事件」。
2. 再做 **Tier A 的高價值三項**：檔案 metadata、群組訊息、共享行程。
3. 回應（reaction）可順手做，價值低但零額外風險。
4. **收回不做**（或做但帶身分金鑰備援）——理由見上，這是本研究最重要的單一結論。
5. **Tier B 不做**：ephemeral 不持久化，FS 價值接近零。
6. 群組的降級警告語意要先定義，否則第 2 步會產出洗版的警告。

⚠ 以上全部在「FS 仍未經外部密碼學審計」的前提下——擴大加密面**同時也擴大了尚未被驗證的
程式碼的作用範圍**。ADR-0306 的實驗性定位不因範圍擴大而改變；若擴大，設定頁的揭露文案
應同步說明涵蓋哪些型別（現在的文案只說「發給聯絡人的訊息」，在只涵蓋 1:1 文字的今天
其實已經偏寬鬆）。
