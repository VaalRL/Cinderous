# 0359. 補上 ADR-0273 的兩個破口：拖放不清 EXIF，大圖不清也不說

- 狀態：已接受
- 日期：2026-09-18
- 相關文件：ADR-0273（送出圖片清除中繼資料）、ADR-0102（縮圖政策常數 SSOT）、
  ADR-0103／0104（桌面原生選檔／拖放）、ADR-0346（大檔惰性讀取）、
  ADR-0355（合集的隱私提示）、ADR-0274（拍照直接傳）

## 背景與問題

ADR-0273 對使用者的承諾是一句話：**送出的相片不含位置與拍攝資訊**。

2026-09-18 的稽核發現這句話在兩個地方不成立，而且兩處都**沒有任何提示**。

### 破口一：原生拖放從頭到尾沒清過

ADR-0273 §6 寫「桌面與行動端共用：兩邊的送檔入口（桌面 `sendFile`／`attachFile`、
行動端 `pickFile`）都在轉成 `OutgoingFile` 前呼叫，不各寫一份」。

桌面**有第三個入口**：原生拖放（ADR-0104）。它走 `dropSendRef` → `readFileAtPath` →
`sendFileBytes`，中間沒有 `sanitizeImage`。ADR 沒列到它，程式碼也就沒有它。

結果是同一張照片有兩種命運：

| 動作 | EXIF／GPS |
| --- | --- |
| 按迴紋針選檔 | 清掉 |
| **把檔案拖進對話窗** | **原封不動送出** |

而**拖放是比按迴紋針更自然的動作**——使用者更可能用的那一條路，正是沒有保護的那一條。
畫面上兩者沒有任何差別可言。

### 破口二：超過 32 MiB 的圖片不清，也不說

ADR-0346 為了不讓「保護隱私」那一步先把 app 打掛，讓超過 `IMAGE_BYTES_LIMIT`
（32 MiB）的圖片走串流路徑、不進 canvas。那個取捨本身是對的：解一張 100 MP 的 PNG
需要數百 MB 的點陣，行動端 WebView 尤其吃不消。

**錯的是它沒有聲音。** 同一台相機、同一次出遊，檔案大一點的那張把座標帶出去了，
小的沒有，而使用者兩次都只是按了同一顆按鈕。

ADR-0355 遇到結構相同的問題（合集內的檔案原封不動，EXIF 清除在合集裡不生效）時，
的做法是**先問過**。這裡沒有跟上。

## 考量的選項

- **A：大圖也硬清。** 否決：這正是 ADR-0346 已經否決過的——OOM 之後使用者連檔都送不出去，
  「保護隱私」變成「不能用」。
- **B：只修拖放，大圖維持現狀。** 否決：破口二是 ADR-0273 承諾的實際例外，
  讓它繼續無聲等於讓那句承諾在使用者心裡比實際更強，而**過度的安全感比沒有安全感更危險**。
- **C（採用）：拖放改成真的清；大圖維持不清，但送出前問一次。**

## 決策

### 1. 三個原生入口收成一條路

新增 `sendPickedSource()`，迴紋針與原生拖放都走它。**不是為了少寫幾行**——
兩條路徑各寫一份正是破口一的成因。下次再加第四個入口，它會自動拿到正確行為。

### 2. 「本來該清卻沒清」的判斷放進引擎

```ts
export function sendsUnstrippedImage(mime: string, sizeBytes: number, limit = IMAGE_BYTES_LIMIT): boolean {
  return isSanitizable(mime) && sizeBytes > limit;
}
```

放在 `packages/engine/src/image-sanitize.ts` 與 `needsBytesToSend` 並排，因為它們是
同一條線的兩側：走串流＝不清，不清＝該問。桌面與行動端共用同一條規則，不各自寫一份。

排除 GIF／SVG 是刻意的：`isSanitizable` 本來就不處理它們（ADR-0273 §3），
它們沒有「本來該清卻沒清」這回事，提示了只會變成狼來了。

### 3. 提示文案說清楚原因，不只說結果

`image_unstrippedWarn`：「這張圖片有 {size}，大到無法在不影響 app 運作的情況下重新編碼，
所以它的**位置與拍攝資訊不會被清除**——會照原檔送出去。」

說出「為什麼」是必要的：只講結果的話，使用者無從判斷這是 bug 還是取捨，
也不知道「想要清掉的話，先縮圖再傳」是有效的自救。

### 4. 提示失敗時放行（fail-open）

拿不到 `confirm` 時照送。沿用 ADR-0273 §5 的同一個取捨：不因為清不掉中繼資料就讓
使用者送不出檔案。殘餘風險記在下面。

## 理由

- **破口一是純粹的疏漏**，沒有任何取捨可言：小圖在迴紋針那條路清得掉，在拖放這條路
  也清得掉，只是沒人呼叫。修它沒有代價。
- **破口二有真實的取捨**，所以不能靠「修掉」解決，只能靠**讓它看得見**。ADR-0355 已經
  在這個專案裡建立了「隱私行為改變時先問過」的模式，這裡沿用它，使用者的心智模型才一致。
- **判斷式放引擎而非各 app**，是因為破口一的成因就是同一規則寫了兩份。把新規則放進
  共用層，是不讓同一件事再發生一次的唯一辦法。

## 後果

- **正面**：拖放與迴紋針的隱私行為終於一致；ADR-0273 的承諾與實際行為之間不再有無聲的落差。
- **正面**：新增送檔入口時，正確行為是預設拿到的，不是要記得加的。
- **負面 / 已知殘餘風險**：
  - **大圖仍然不清 EXIF**。這份 ADR 讓它可見，沒有讓它消失。想要清掉的使用者必須自己先縮圖。
  - **多一次詢問**。專業影像使用者每次傳大圖都會看到它。可接受：這類使用者正是最該知道的人。
  - **fail-open**：取不到 `confirm` 時會靜默送出未清除的原檔。與 ADR-0273 §5 一致，
    但它確實是「揭露被跳過」的一種。
  - **已發布的版本（含 v0.0.16）兩個破口都在**。拖放送出過的照片已經帶著 GPS 出去了，
    而且**無法回收**——收件者手上那份就是原檔。發版說明必須明講這件事，不能只寫「已修正」。
  - 桌面的**企業儲存槽背景外送**（ADR-0161）走另一條路徑，本 ADR 未涵蓋；
    它送的是使用者主動指定要歸檔的檔案，語意與「傳給對方」不同，留待後續評估。

## 後續行動 / 待辦

1. 發版說明要明講：**先前用拖放送出的照片可能含 GPS**，且無法回收。
2. 實機驗收：拖一張含 GPS 的 JPG 進桌面對話窗，確認收到的檔案已被清除。
3. 實機驗收：選一張 >32 MiB 的 JPG，確認跳出提示、取消真的不送。
4. 評估企業儲存槽外送路徑是否也該納入（見上）。
