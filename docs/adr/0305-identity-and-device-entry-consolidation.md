# 0305. 身分與裝置入口整併為三條路——並讓「搬資料」成為「加裝置」之後的階段而非另一個功能

- 狀態：**提議中**（本文不改變任何產品行為；為資訊架構提議，實作待決策）
- 日期：2026-07-31
- 相關文件：
  - **0200**（術語正名：備份碼→救援登入碼、雲端備份→多裝置狀態同步——**本文是它沒做完的那一半**）
  - **0081**（行動端登入的兩條路：nsec 匯入／配對匯入）
  - **0072／0118**（配對搬家 D4a：一次性 P2P 全量搬家）、0070（救援登入碼）、0071（多裝置狀態同步）
  - **0303 §6**（裝置授權的加／刪不對稱——**本文的三入口正好對上它**）
  - **0304 §5**（新裝置對「加入前」的訊息永遠沒有金鑰——**本文據此更正「可選」的措辭**）
  - 0112（nsec 不得明文落盤）、0117（行動端記住我）、0278／0287（UI 不得說謊）

  `apps/mobile/src/screens/NsecSignInScreen.tsx`、`PairImportScreen.tsx`、`PairExportScreen.tsx`、

> **起點**：使用者回報「現在可執行的選項對一般使用者來說太多、太過雜亂」，
> 並提議把「新增裝置」與「搬家」整合，讓「是否同步舊裝置資料」成為前者之後的可選步驟。
> **查證結論：合理，且應擴大範圍**——問題不只在那兩個流程的關係，
> 在於**同一件事被切成好幾個入口**。而且**程式其實已經合併了，只有介面沒有**。

| --- | --- | --- |

## 2. 證據一：同一樣東西出現在兩個入口，用兩套文案

`nsec` 同時是：

- `signIn_useNsec`（`:872`）：「已經有身分？**用 nsec 登入**」
- `rescue_hint`（`:1330`）：「輸入你的**私鑰（nsec）或救援登入碼**…」

⇒ 這不是使用者搞不清楚，是**我們自己把同一件事切成兩塊**再讓使用者去分辨。

## 3. 證據二：🔵 程式碼**已經**把它們當成一件事了

`apps/mobile/src/auth.ts:86`：

```ts
if (isBackupCode(s)) {
  // 備份碼（NIP-49 信封）以 `isBackupCode` 偵測；偵測到就需要**備份密碼**才解得開。（:81 註解）
```

`apps/desktop/src/ui/UnlockScreen.tsx:105` 同樣：`const isCode = isBackupCode(secret.trim());`

⇒ **輸入欄早就自動辨識「這是裸 nsec 還是救援碼」並決定要不要問備份密碼。**
⇒ **合併在實作層已經完成，缺的只是介面沒有反映它。**
⇒ 這大幅降低本提議的實作成本——**不是重寫流程，是重排入口**。

## 4. 實際上只有三種處境

| 使用者的真實處境 | 需要 | 對應 0303 §6 |
| --- | --- | --- |
| **我是新來的** | 名稱（＋本地密碼） | 不適用 |
| **我還有另一台裝置** | 那台活著 ＋ SAS 比對 | **加＝B′ live 配對授權**（§6.2b） |
| **我的裝置都沒了** | 救援登入碼 ＋ 備份密碼 | **重建＝C 救援憑證**（§6.2） |

⇒ **三個入口就夠**，而且這個切分**不是為了好看而發明的**——
它正好是 ADR-0303 §6 的加／刪（重建）不對稱在使用者面的投影。
資訊架構與安全模型同構，是這個切分正確的證據。

## 5. 🔴 最強的論據：UX 簡化與安全收斂指向同一個方向

ADR-0303 §6 要求「加裝置＝既有裝置 live 授權」。
而**「用 nsec 登入」這條路繞過整個 §6**——貼上 nsec 即成為一台裝置，
不需要任何既有裝置參與、不需要 SAS、不留下 live 授權的痕跡。

⇒ 收成三個入口，**順手就把那條不安全的捷徑移除了**。

⇒ **這不是「為了安全犧牲便利」，兩者剛好同向。** 這種情況少見，應優先執行。

⚠ 誠實揭露：移除「用 nsec 登入」對**今天**的使用者是功能移除
（今天它是合法且方便的一條路）。本文不主張在 0303 §6 上線前移除它——
見〈後續行動〉的階段劃分。

## 6. ⚠ 更正提議中的一個措辭：不是「可選」，是「可延後但有期限」

原提議把「是否同步舊裝置資料」設為加裝置後的**可選**步驟。方向正確，但措辭要改。

**ADR-0304 §5 的查證結果**：per-device session 之後，訊息只加密給**送出當下已在清單裡的裝置**。
新裝置對更早的訊息**永遠沒有金鑰**——不是暫時看不到，是**不存在解法**。

⇒ 中繼那邊補不回來。**但 0072 的 P2P 搬家隨時可以補做——只要舊裝置還活著。**

⇒ 因此正確的文案是：

| | |
| --- | --- |
| ❌ | 「之後可以再同步」——暗示隨時能補 |
| ✅ | 「**現在不同步也可以，但要趁舊裝置還在的時候補做。舊裝置沒了就真的沒了。**」 |

這落在 ADR-0278／0287 的「UI 不得說謊」紅線上。

### 6.1 一句已經排隊等著出錯的文案

`signIn_useNsecHint`（`:873`）：

> 貼上你備份的 nsec…**原本的聯絡人與訊息會一起回來。**

**今天成立**（nsec 導得出儲存金鑰與雲端快照金鑰，見 ADR-0304 §3）。
**在 0303／0304 的設計下會變成謊話。**
⇒ 無論本提議是否被接受，這句都必須隨那條路一起改。

## 7. 實作關鍵：一個入口、兩個階段——授權不得被資料傳輸卡住

若把搬資料併進加裝置，必須避免讓它繼承 ADR-0072「兩台同時在線」的硬限制：

```
階段 1  授權      舊裝置掃碼 ＋ SAS 比對    → 完成即可用（秒級）
階段 2  搬資料    可跳過／可中斷／可事後續傳（依歷史量，分鐘級）
```

⇒ **「我只是想在平板上登入」的人不該等全量歷史傳完。**
⇒ 兩階段同時滿足「一個入口」與「不強迫傳資料」，
   而階段 1 正是 0303 §6.2b 要的那個 live 授權時刻。

## 8. 先例：ADR-0200 已經做過同一類整併

ADR-0200 把「加密備份碼」正名為「救援登入碼」、「雲端備份/快照」正名為「多裝置狀態同步」，
理由是原名描述的是**實作**而非**使用者處境**。

⇒ 本文是同一條線往前推：**0200 修的是名稱，本文修的是入口數量與其關係。**

## 提議（**皆待決策，本文不改變產品行為**）

1. **身分入口收斂為三條**：〈建立新身分〉／〈我還有另一台裝置〉／〈我的裝置都沒了〉。
2. **「搬資料」從獨立功能改為〈我還有另一台裝置〉的第二階段**，可跳過、可中斷、可事後續傳。
3. **授權與傳資料分階段**（§7），授權完成即可用。
4. **文案改為「可延後但有期限」**（§6），不得寫成「之後隨時可以再同步」。
5. **修正 `signIn_useNsecHint`**（§6.1）——此項**獨立於本提議**，隨 0303／0304 那條路必改。
6. **「用 nsec 登入」的移除排在 0303 §6 上線之後**，不提前——
   在 live 授權可用之前移除它，等於讓沒有第二台裝置的使用者無路可走。

## 後果

**正面**

- 入口由六降至三，且新切分**與 0303 §6 的安全模型同構**。
- 移除繞過 §6 的捷徑，**UX 與安全同向**（§5）。
- 實作成本低於預期——**辨識邏輯已經存在**（§3），主要工作在介面與文案。
- 承接 ADR-0200 未完的整併線（§8）。

**負面／代價**

- 「用 nsec 登入」對今天的使用者是功能移除（已排入階段，見提議 6）。
- 兩階段流程比單一動作**更難實作**：需要可中斷、可續傳的傳輸狀態機，
  而 0072 目前是「一次性全量」，未設計中斷續傳。
- 本文**不解決** 0304 §5 的退步本身——只讓它被誠實呈現。

**已知限制**

- **未實作、未測試**；三個入口的實際文案**尚未撰寫**。
- **未做任何使用者研究**。「六個入口太雜亂」來自使用者回報，
  「三個入口比較好」是**設計判斷，非實證**。
- **未評估 0071 多裝置狀態同步**在新架構下該放哪——本文把它留在設定頁，
  但它與「搬資料」在使用者眼中可能是同一件事，**這一格沒想清楚**。
- **未評估 0117 行動端記住我**與新入口的互動。
- §7 的兩階段需要傳輸可中斷續傳，**ADR-0072 未設計此性質**，其成本未評估。
- 未評估多身分（ADR-0138／0045）情境：三入口是否要在每個身分上各自成立。
