# 0402. 公開清單不指向主平面：改列公共收件中繼

- 狀態：已接受（使用者 2026-10-29：「好 那選A」）
- 日期：2026-10-29
- 相關文件：ADR-0382（公開聯絡方式；本 ADR 修改其 §3、§4 的「只列 home」）、ADR-0394（外流清單招來的爬蟲先接受）、ADR-0392／0393（爬蟲診斷）、ADR-0391（反覆重連限速）、ADR-0401（每日請求數用完時的連線列）

## 背景與問題

ADR-0382 的「讓知道我 npub 的人能聯絡我」會把 home 寫進公開的 10050／10002。home 在錨點上，就是主平面的分片網址（桌面），或錨點的根路徑（手機，沒有分片模式）。

ADR-0392／0393 查到這樣做的後果：

- 一把測試身分的清單在 2026-10-14 公開過一段時間，之後一個 outbox 型爬蟲就照那份清單，一直輪詢錨點 2 的 `/s/b`；
- 它會換 IP，以 IP 計的限速擋不到（ADR-0391）；給它空結果它也照樣來（ADR-0393）；
- 一天約 1.1 萬條連線、4.5 萬次 DO 請求，而這只是**一把公鑰**造成的。

這個爬蟲找的是「那個人的」10002，所以很可能是每把公鑰各輪詢一份。這點只有一個樣本，還沒證實。

如果真是這樣，開關已經在出貨的版本裡，只要再有兩三個人打開，就會把一座錨點的免費額度吃光。那時整座錨點所有人都停擺，連線列會顯示 ADR-0401 的「最可能是今天的額度用完了」。

清單一旦外流就收不回。已經外流的 `/s/b` 照 ADR-0394 繼續接受；能做的是讓**以後公開的清單不再指向主平面**。

## 考量的選項

- **A（採用）**：公開清單改列大型公共中繼。「能聯絡我」開著時，Cinderous 多訂閱那幾座收第三方的信。主平面網址不再出現在任何公開清單上。
- B：另開一個 Cloudflare 帳號，架一座專接第三方的公開中繼，額度和主平面分開。爬蟲只會吃光那一座，但多一座要維運的錨點；開了開關的人同樣要多訂閱一座。
- C：照舊指向分片，改成在 Worker 層就回答爬蟲、不碰 DO。可以降低成本，但 Worker 請求的額度一樣是每個帳號 10 萬次，治標不治本。

## 決策

### 1. 公共收件中繼：nos.lol、relay.primal.net

2026-10-29 以一次性金鑰實測：寄一顆 1059，再不認證讀回 `{kinds:[1059], "#p":[收件人]}` 與 `{ids:[…]}`。

| 中繼 | 收 1059 | 不認證讀回 | 備註 |
|---|---|---|---|
| nos.lol | ✅ | ✅ | 外層時戳往前推 43 小時也收 |
| relay.primal.net | ✅ | ✅ | 每條連線最多 20 個訂閱 |
| nostr.mom、offchain.pub、relay.snort.social | ✅ | ✅ | 候補 |
| relay.damus.io | — | ❌ | 讀寄給某人的 1059 要認證；同一個 IP 連發會被暫時封鎖（ADR-0382） |
| auth.nostr1.com | ❌ | ❌ | 認證後仍拒收 |
| inbox.nostr.wine | ❌ | ❌ | 要付費 |

五座都沒有在 NIP-11 宣告保存期限，要再複查（見後果）。

預設採前兩座（`PUBLIC_INBOX_RELAYS`），跟錨點放在同一個單一來源（`bootstrap-config.ts`）。每多一座，每台開了開關的裝置就多一條連線，所以只列兩座分散風險。

### 2. 只有 home 在官方錨點上才用

- `publicInboxRelaysFor(home)`：home 的主機是 `ANCHOR_RELAYS` 其中一座時，才回傳公共收件中繼。分片與根路徑都算，手機版用的是根路徑。
- 自架的 home 照舊只列自己。要不要讓爬蟲輪詢，是架站的人自己的事。
- 判斷交給 App（桌面 `App.tsx`、手機 `backend.ts`）；引擎只看 `publicInboxRelays` 有沒有設。

### 3. 發布

- 10050 的 `relay` 與 10002 的 `r`（write）列公共收件中繼，**不列 home**。
- 清單與 kind 0 除了發到 home 與索引中繼，也發一份到公共收件中繼：
  - outbox 型客戶端照 10002 去那裡找名稱；
  - 關掉時那裡的舊清單也要被空清單取代。
  - 走單次連線、只發布，跟索引中繼一樣。
- 開關狀態照舊以 home 上自己最新的 10050 為準（ADR-0382 §2）。
- **升版前就開著的人**：開機讀到自己的 10050 列的不是現在該列的，就重發一份。索引中繼上的舊清單因此被取代，但已經記住舊網址的爬蟲照樣會來，收不回。

### 4. 收信

- 「能聯絡我」開著時，在每座公共收件中繼開一條連線，**只訂** `{kinds:[1059], "#p":[自己]}`，帶跟 home 一樣的增量水位。
  - 不訂心跳、快照、裝置目錄等，不把聯絡人與其他資料交給它；
  - **不認證**：讀信用不到，認證只會把 IP 與身分金鑰綁在一起。
- 收到的照一般收件匣處理：陌生人進訊息請求、照 ADR-0127 防洪、依 id 去重。這個功能不放寬任何收信規則。
- 關掉、或讀到別台裝置把它關了，就斷線。別台裝置打開的，這台讀到也會開始收。

### 5. 路由不改

- 回信給第三方：照舊寄到對方 10050 上的每一座（ADR-0382 §6）。
- 用裸 npub 加一個開了開關的 Cinderous 使用者時，查到的 10050 指向公共收件中繼（錨點池外），照現有的路由優先序，最初幾則會寄到那裡。對方兩邊都在收，所以收得到；學到對方的帶內提示以後，就回到錨點。為了這個情況去分辨「對方是不是 Cinderous」不值得。

### 6. 文案

設定頁「讓知道我 npub 的人能聯絡我」的說明加上：

- 用官方錨點的話，公開的是兩座公用中繼站，不是錨點；
- 打開時這台裝置會連過去收信，那兩座看得到你在收信。

## 後果

- 正面：
  - 公開清單不再指向主平面。以後再外流，被爬蟲輪詢的是為公開流量設計的設施，錨點的額度不受影響。
  - 要換位置只要改預設清單、重新發布，不必讓所有用戶端更新。
  - 主平面要認證，很多 outbox 型客戶端讀不到 home 上的 kind 0；名稱發到公共收件中繼以後，**反而比較找得到**。
- 負面／殘餘：
  - 多依賴兩座第三方中繼，它們可能停站、限流、清掉信。要是兩座都停了，第三方寄不到，Cinderous 之間不受影響。
  - **保存期限未知**：使用者離線太久，第三方寄來的信可能已經被清掉。錨點保存 7 天，這兩座沒宣告。複查方式：用 scratchpad 裡記下的事件 id，隔幾天以 `{ids:[…]}` 讀讀看。
  - 那兩座的營運者看得到「這把公鑰從這個 IP 收信」：`#p` 訂閱本身就帶公鑰，不認證也一樣。
  - 每台開了開關的裝置多 2 條連線（手機會多一點耗電與流量）。
  - 已經外流的 `/s/b` 照舊被輪詢（ADR-0394）。
  - 「每把公鑰各輪詢一份」只是推測。這次的改動不靠它：不管是不是，主平面都不再出現在公開清單上。
- 驗證：
  - `public-reach.test.ts` 新增 9 個：
    - 清單只列公共收件中繼，home、公共中繼、索引中繼上都查得到，任何一份都不含 home；
    - 名稱也發到公共收件中繼；
    - 開著時在公共收件中繼只訂寄給自己的 1059、收信連線不認證，第三方寄到那裡的信進請求區；
    - 關掉後那裡換成空清單、不再收信；
    - 只開名稱時不去收信；
    - 另一台裝置讀到開著也去收信；
    - 升版前的舊清單開機就換掉；
    - 單座中繼模式（手機）一樣不列 home；
    - 沒設公共收件中繼時（自架）照舊。
  - `bootstrap-config.test.ts` 新增 3 個：預設清單、不含錨點主機、只有官方錨點才用（分片與根路徑都算，自架不算）。
  - 破壞測試 9 項全部抓到。`pnpm typecheck`、`pnpm test` 全過。
