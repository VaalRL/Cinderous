# 0321. 裝置清單（E-lite）：讓「我有幾台裝置」看得見，並在多出一台時說一聲

- 狀態：已接受
- 日期：2026-08-03
- 相關文件：**ADR-0303 §6.6（E-lite：本文實作的那一項，該文列為「可獨立先行」）**、
  ADR-0303 §4.3（裝置清單變動通知是真緩解）、ADR-0303 §7（清單住在哪＝**未決策**，本文不碰）、
  ADR-0071（加密雲端快照，`d` tag ＝ deviceId）、ADR-0072／0118（配對搬家）、
  ADR-0297（平台金鑰分級）、`packages/engine/src/storage/device-id.ts`

## 背景與問題

ADR-0303 §6.6 的原話：

> **顯著呈現「我有哪些裝置」＋任何清單變動即警示**⋯⋯不依賴 A/C/棘輪任何一項
> ——在今天的模型下就有價值（**今天使用者根本看不到自己有幾台裝置**）。

而 §4.3 引論文（Wichelmann 等, DIMVA 2021）指出 Signal 那個攻擊裡，
「**There is no notification to the user that a device requested their conversations**」，
受害者與對話對象**都**看不到有新裝置加入。§6.7 因此把 E-lite 定性為
「**承重結構，不是加分項**」——入侵當下的窗關不掉，只能靠偵測與移除。

今天本專案連「有幾台裝置」都沒有任何呈現。

## 🔴 先講清楚：在我們的模型裡，E-lite 比在 Signal 弱

ADR-0303 §4.3 說「隱藏與收訊互斥」——攻擊者的裝置若想收訊，就得註冊、就會出現在清單裡。
**那個論證建立在 Signal 有伺服器負責路由到裝置**。

**我們沒有那個角色。** 中繼只按 `#p` 轉發，任何持有 nsec 的人都能**純被動地訂閱並解密**，
不需要向任何人宣告自己存在。

⇒ **本功能偵測得到的是「會寫入的裝置」，偵測不到「只讀取的裝置」。**
一個拿到你 nsec 但只是安靜地讀取的攻擊者，**這份清單完全看不到他**。

這句話必須進 UI，否則就是安全劇場——使用者會把「清單只有一台」讀成「沒有人在偷看」，
而那正是 ADR-0278／0287「UI 不得說謊」的反面。

## 考量的選項

- **選項 A：實作簽章裝置目錄（ADR-0303 選項 A）。** 那是完整方案，但 §7 明記
  「清單住在哪」是**未決策的分歧**（兩個先例互相衝突），且 §6 已論證它必須與裝置授權綁定。
  超出 E-lite 範圍。否決。
- **選項 B：新增一種「裝置心跳」事件（自封、定期發）。** 能看到所有裝置（含只讀的？不能——
  只讀的攻擊者不會發）。**它其實解不掉上面那個根本限制**，卻要新增一個協定面。否決。
- **選項 C（採用）：只從既有訊號建清單**，並誠實揭露看不到什麼。

## 決策

1. **裝置來源＝既有訊號，不新增協定面：**
   | 來源 | 訊號 | 何時 |
   | --- | --- | --- |
   | 本機 | `getDeviceId()`（已存在，隨機 8 bytes，per-device KV） | 恆有 |
   | 雲端快照 | 自己簽章的 kind 30078，**`d` tag ＝ deviceId**（ADR-0071 已有） | 對方裝置有開雲端備份時 |
   | 配對搬家 | 匯出／匯入完成（ADR-0072／0118） | 使用者自己做的動作 |
2. **記錄落在該身分的加密儲存**（`AppStorage.loadDevices/saveDevices`），
   欄位 `{ id, firstSeen, lastSeen, source }`。**不進雲端快照、不進配對捆包**——
   這是**這台裝置的觀測**（同 ADR-0316 的 `failures`）。
3. **新裝置＝發 `onNewDevice`**：出現一個從未見過的 id 就通知一次（以 `firstSeen` 判定，
   不是每次收到快照都喊）。UI 呈現為顯著提示，不是預設關的小徽章。
4. **UI**：設定 → 身分分頁「我的裝置」，列出 id 縮寫、首見／最近可見時間、來源；
   本機那台標明「這台」。**清單下方常駐一句限制揭露**（見 §🔴）。
5. **本文不做**：撤銷／移除裝置、簽章目錄、授權新裝置。那些屬 ADR-0303 §6 的 A／C，
   且 §7 尚未決策。E-lite 只做**呈現與警示**。

## 理由

- **不新增協定面**是 E-lite 的定義（§6.6「不依賴 A/C/棘輪任何一項」）。
  選項 B 要付協定成本卻買不到那個根本限制的解，不划算。
- **誠實揭露優先於功能感**。一份看起來完整、實際上有大盲點的清單，比沒有清單更危險。
- **只做呈現與警示**讓這一項可以獨立出貨，不必等 ADR-0303 §7 的分歧收斂。

## 後果

- 正面：使用者第一次看得到自己有幾台裝置；多出一台會被告知；
  零協定變更、零額外事件、零中繼成本。
- 負面 / 已知殘餘風險：
  - 🔴 **看不到純被動讀取的裝置**（見上）。這是模型層的限制，不是實作缺口。
  - **雲端備份關閉時，其他裝置對這份清單是隱形的**——最常見的漏看情境。
    UI 必須說出來（「只看得到有開雲端備份的裝置」）。
  - 中繼可扣住快照事件 ⇒ 清單可被延遲（ADR-0303 §6.7 第 3 點的同一面）。
  - 沒有移除／撤銷：看到可疑裝置時，使用者能做的只有換 nsec（ADR-0052 的範圍）。
- 後續行動 / 待辦：
  - ADR-0303 §6.6 另提「**F：新裝置延遲 N 小時生效**，把偵測變否決權」——
    那需要裝置授權（§6.2），不在 E-lite。
  - 若日後實作簽章目錄（選項 A），本文的觀測清單應由目錄取代而非並存。
