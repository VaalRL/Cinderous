# 0393. 主平面：沒認證、只要公開清單的 REQ 直接回 EOSE

- 狀態：被取代 by [0394](./0394-revert-public-list-eose.md)（2026-10-20 部署錨點 2 後量測無效，已還原）
- 日期：2026-10-20
- 相關文件：ADR-0392（診斷結果）、ADR-0391（反覆重連限速，擋不到輪替 IP）、ADR-0382（公開聯絡方式：kind 0／10002／10050 發佈到索引中繼）、ADR-0057／0123（NIP-42 與「拒絕要說得出原因」）

## 背景與問題

ADR-0392 的診斷在錨點 2 抓到 `shard-b` 那個來源送的內容：

`unauth-diag in=REQ kinds=10002 out=CLOSED:auth-required,AUTH code=1006`（活了 0.5 秒）

- 它只送一個 REQ，要 **kind 10002**（NIP-65 中繼清單）；
- 被回 `auth-required` 就斷線，幾秒後換 IP 重試；
- 從 2026-10-14 起，一天約 1.1 萬條連線、4.5 萬次 DO 請求。

這是典型的 outbox 型爬蟲：照 10-14 短暫公開的那份清單，到清單上的每座中繼找那個人的 10002。它把 `auth-required` 當成錯誤，所以一直馬上重試。

## 考量的選項

- 選項 A：沒認證、而且只要公開清單類 kind 的 REQ，直接回 EOSE（空結果）。
- 選項 B：送一則 NOTICE 說明「這裡不放公開清單」，再以 1008 關閉。人看得懂，但爬蟲多半照樣當錯誤重試。
- 選項 C：不處理，等公開聯絡方式正式開放前再說。

## 決策

採選項 A（使用者 2026-10-20 選定）。只在要求認證的平面（嚴格政策）生效：
- 沒認證的 REQ，如果**每個 filter 都指定了 kinds，而且全部是 0、10002 或 10050**，就直接回 `["EOSE", subId]`；
- 不查儲存、不建立訂閱、不重發 AUTH 挑戰；
- 只要混到別的 kind、有 filter 沒指定 kinds、或 kinds 是空陣列，就照舊回 `auth-required`。

這和 ADR-0123「拒絕要說得出原因、不用沉默的空回應」不衝突。對沒認證的第三方來說，這裡本來就沒有要給他的公開清單：那些資料發佈在索引中繼。認證過的用戶端照舊能讀到自己 home 上的 kind 0／10050。

## 理由

- 爬蟲要的就是「查到或查不到」。給它一個正常的空結果，它就照自己正常的排程再來，不會遇錯馬上重試。
- 回 EOSE 是最便宜的一條路：不碰儲存，跟回 auth-required 的成本一樣。
- 不會洩漏任何東西（空結果），也不能拿來繞過認證：只要摻了其他 kind 就照舊拒絕。

## 後果

- 正面：預期 `shard-b` 的連線大幅減少。以後真的使用者開「公開聯絡方式」時，也不會因為爬蟲而吃掉額度。
- 負面：沒認證的讀者看不到嚴格平面上的 kind 0／10002／10050（之前也看不到，只是現在改成空結果，不再是 auth-required）。
- 後續：部署錨點 2 後，用 GraphQL 比較 `shard-b` 的連線數。沒降的話，代表爬蟲不吃這一套，再回來討論。
