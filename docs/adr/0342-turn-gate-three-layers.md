# ADR-0342：`/turn` 的三層防護——並更正 ADR-0336 §3.1 的一句事實錯誤

- 狀態：已採用
- 日期：2026-08-06
- 關聯：**ADR-0336（§3.1 更正、§3.2 取代）**、ADR-0243（TURN 保底）、ADR-0235 C1（事件結構驗證）、`cbcbcf1`（以認證身分計數的速率限制）

## 1. 🔴 先更正：ADR-0336 §3.1 寫錯了

該節寫著：

> 客戶端本來就在半 TTL 前刷新（`turn-fetch.ts` 檔頭寫明），所以縮短只是讓它多刷幾次，功能不變。

**檔頭是那樣寫的，程式碼不是。** `relay-backend.ts` 的實際排程是：

```ts
this.turnTimer = setInterval(() => void this.refreshPublicTurn(), 6 * 3600_000);
```

**寫死 6 小時**，與 TTL 無關。而且 `/turn` 的回應**沒有 `ttl` 欄位**（只有 `urls`／`username`／`credential`），所以客戶端**無從得知**憑證多久過期。

⇒ 依 §3.1 把 TTL 改成 300 秒之後，客戶端拿到的憑證 5 分鐘就死、然後 6 小時不刷新。**開機後前 5 分鐘之外的通話，TURN 形同不存在。**

這是把 ADR 當成事實來源、卻沒有回去對程式碼造成的。**同一個形狀已經發生第二次**——ADR-0335 那次也是「註解比程式碼樂觀」。

⚠ 尚未造成實害：預設 relay（`cinderous1`）當時還沒配 secret，另一座用量極小。

## 2. 決策⓪：TTL 由回應攜帶，客戶端依它排程

- Worker 在 `/turn` 回應加上 `ttl`（就是它送給 Cloudflare 的那個值，**唯一真實來源**）。
- 客戶端排程改為 `ttl / 2`，夾在 `[60s, 6h]`。
- **`ttl` 缺席時退回 1 小時**——舊 Worker（TTL 86400）走這條仍然安全；不用更短的值是因為那會在正常情況下浪費請求並吃掉速率限制配額。

⚠ 這件事**必須在放 secret 之前完成**，否則預設 relay 一開就是壞的 TURN。

## 3. 決策：三層防護，取代 ADR-0336 §3.2 的單一機制

§3.2 原本要求「由 relay 在 WebSocket 連線期間發出的短期 token」。實作時發現架構代價比預期高：**`/turn` 在 Worker 上、WebSocket 在 Durable Object 裡，而 DO 還是分片的（ADR-0241）**——Worker 要驗證得多算一次分片、多一次往返，並在 DO 新增查詢路徑。

改為三層。**先講清楚每層各自買到什麼，因為它們不是同一件事：**

| 層 | 限制的是 | 客戶端要改嗎 |
| --- | --- | --- |
| ① 短 TTL（ADR-0336 §3.1 ＋ 本 ADR §2） | 一張憑證**能活多久** | 否 |
| ② 取得速率（Workers `ratelimit` binding） | 每單位時間**能拿幾張** | **否** |
| ③ NIP-98 簽章 | **誰**能拿 | 是 |

### 3.1 為什麼速率限制排在簽章前面

**它是三者中 CP 值最高的**：只改 `wrangler.toml` 加幾行 Worker 程式碼，**客戶端零改動**，而且與短 TTL 相乘後直接轉成頻寬上限——濫用者要維持流量就得持續取新憑證。

正常使用者每半個 TTL 才取一次（TTL 300 ⇒ 2.5 分鐘一張），`20/60s` 的額度綽綽有餘。

⚠ 兩個限制必須寫下來：Cloudflare 明說這個 API 是 **per-location 計數**（分散式攻擊者拿到 limit × colo 數）且**最終一致、刻意寬鬆**（「not to be used as an accurate accounting system」）。**它是成本乘數，不是閘門。**

### 3.2 NIP-98 簽章（kind 27235）

客戶端以身分金鑰簽一個綁 **URL ＋ method ＋ 時間** 的事件，放進 `Authorization: Nostr <base64>`。Worker 驗完才換發，未帶或不合法 → **401**（不是 204——204 的語意是「未配置」，兩者不可混）。

🔴 **驗章前必須先驗結構**：直接重用 ADR-0235 C1 的 `isValidEventShape`（改為匯出，**不另寫一份**）。該 ADR 的教訓是 `verifyEvent` 只保證雜湊與簽章相符，**完全不檢查欄位型別**——攻擊者可以對 `{tags:{}}` 這種形狀自簽並通過驗章，後續 `tags.find(...)` 拋 `TypeError`。

簽章讓速率限制的 key 可以從 IP 換成 **pubkey**，避開行動網路共用 IP 的誤傷。

### 3.3 不做 DO 活性檢查（§3.2 原案）

**留著不做，但寫下重啟條件。**

它真正買到的是**執法把手**：濫用者必須是一條通過 NIP-42 認證的連線，於是自動落進 `cbcbcf1` 那套「以認證身分計數」的既有速率限制，可以被斷線、被封。

⚠ **在沒有濫用跡象時，那是一份空的保險。** 而且 **NIP-98 是它的前綴不是分岔**——它同樣需要簽章，所以 §3.2 的工不會白做。

⇒ 觸發條件：**實際觀察到濫用**（帳單警示觸發、或用量與通話量明顯脫節）。

## 4. 買不到什麼

1. 🔴 **三層加起來仍然擋不住有心人。** 產一把金鑰是微秒級的事；NIP-98 擋掉的是 `curl` 一行，不是自動化腳本。買到的是**成本**與**可歸責性**，與 ADR-0336 §5-1 的結論一致。
2. **「可歸責性」在實務上偏弱**——Worker 的 log 預設不持久，拿到 pubkey 也沒有現成的地方對它執法。那正是 §3.3 留著的東西。
3. **速率限制的 per-location 特性**（§3.1）：分散式來源會放大額度。
4. **客戶端時鐘偏移會被擋**。時間窗設 ±60 秒；偏移超過的裝置拿不到 TURN（退回純 STUN，不影響其他功能）。
5. **不涵蓋企業自架 TURN**（ADR-0048 的 `turnServers`）——那條路不經過 `/turn`。
6. **⓪的 `ttl` 缺席退回 1 小時是猜的**：若有人跑舊 Worker 又手動把 TTL 設得比 1 小時短，客戶端仍會拿到過期憑證。新舊 Worker 一起更新即無此問題。
