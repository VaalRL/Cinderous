# 0425. 通話取麥克風／鏡頭晚回來時的漏關，以及連按換鏡頭

- 狀態：已接受
- 日期：2026-11-18
- 相關文件：ADR-0338（通話中升降級）、ADR-0339（切換鏡頭）、ADR-0340（指示燈要誠實）、ADR-0424（實機驗收）；SDK ADR 0141「程式碼審查修正」（SDK 的 `CallManager` 有同一類問題，同時修）

## 背景與問題

PR #96（ADR-0424）之後做程式碼審查，發現 `WebRtcCall` 有四個非同步操作「回來的時候世界已經變了」的問題。
FakePc 的 `getUserMedia` 一律立刻回來，所以測不到；真機上權限提示、開鏡頭都可能要好幾秒：

1. **接聽時還在等權限，對方就掛斷了**：`teardown` 先跑完，權限回來後 `acquireMedia` 把麥克風（和鏡頭）放進已關閉的連線、
   記成 `localStream`——沒有人會再關它們，**麥克風與相機一直開著**，直到 App 關掉。
2. **開視訊時還在等鏡頭，又按了關（或對方掛斷）**：鏡頭開好後照樣放上去、通知對方「我開視訊了」，相機一直亮著。
3. **連按兩次換鏡頭**：兩個 `swapCamera` 同時跑、都把同一顆當成「舊的」，第一顆新鏡頭被第二顆換掉但沒人關。
4. **答方把鏡頭放上協商過的 transceiver 失敗**（`replaceTrack` 丟例外）：例外往上冒，鏡頭沒關、`onLocalStream` 也沒送。

## 考量的選項

- 選項 A：每個 `await` 之後檢查「這一通還在不在、使用者還要不要」，不要了就關掉剛拿到的裝置；換鏡頭排隊。
- 選項 B：取消機制（AbortController 傳進 `getUserMedia`）。瀏覽器的 `getUserMedia` 不吃 signal，權限提示也取消不了，
  最後還是要在回來時檢查——等於 A 再多一層。

## 決策

採 A：

- `acquireMedia`：記下開始時的 `pc`，`getUserMedia` 回來時 `this.pc` 已不同（`teardown` 跑過）⇒ 全部 `stop()`、不放、不送。
  每放一條軌之後再檢查一次。放上協商過的 transceiver 失敗 ⇒ 關掉鏡頭、回報錯誤、這通先用語音（本地預覽不留那條已停的軌）。
- `attachVideo` 回 `boolean`：鏡頭開好時連線已換、或 `session.localMedia` 已不是 `video`（使用者又按了關）⇒ 關鏡頭、回 `false`，
  `changeMedia` 就不送 `call-media`。`replaceTrack` 之後再檢查一次。
- `setCamera` 排進 `cameraChain`：一次只換一個，第二次以第一次換好的那顆為「舊的」。`swapCamera` 每個 `await` 後檢查連線與型態，
  不要了就關掉新開的那顆；鏡頭全開不了時的「降級成語音」也只在這一通還在時做。
- `detachVideo` 的 `replaceTrack(null)` 加上 `.catch`：連線已關時它會 reject，不留未處理的 rejection。

## 理由

這幾個都是「指示燈不誠實」（ADR-0340）：使用者以為掛斷了，相機或麥克風其實還開著。
檢查「連線物件是不是同一個」就能涵蓋掛斷、拒接、對方取消、失敗收尾——它們最後都走 `teardown`、把 `pc` 設成 `null`。

## 後果

- 正面：掛斷、拒接、關視訊之後不會再有晚回來的裝置留著；連按換鏡頭最後只有一顆開著，送出去的就是預覽的那一顆。
- 負面 / 已知殘餘風險：換鏡頭排隊後，連按很多次會依序全部做完（不是只做最後一次）；每次都會短暫開關一顆鏡頭。實際上使用者不會連按很多次，先不做「只留最後一次」。
- 測試：`webrtc-call.test.ts`「程式碼審查（2026-11-18）」的 5 個案例用可以「卡在權限提示」的 `getUserMedia`，修正前都紅（裝置留著）。
- 後續：仍待真機驗收（OPERATOR-TODO §B-Call）——權限提示期間掛斷、手機連按翻轉鏡頭。
