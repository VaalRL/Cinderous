# 0299. 發布側 AUTH 的元資料洩漏，與「匿名發布 plane」的評估（P5）

- 狀態：**研究記錄（評估結論：不建議現在動；本文不改變任何產品行為）**
- 日期：2026-07-30
- 相關文件：**0293 §3**（White Noise 拆解指出的發布側問題）、**0294 §3**（記錄但本輪未動）、
  **0237**（元資料洩漏面盤點——本文補上其發布側的一格）、**0057**（NIP-42 AUTH 契約）、
  **0162**（企業檔案暫存與 allowlist）、0129／0240（隱身：訂閱側已補，發布側未補）、
  0275（客戶端 relay 健檢：A 層觀察「這座要不要 AUTH」）
- 資料來源：本倉庫程式碼查證（`relay/src/relay-core.ts`、`packages/engine/src/backend/relay-backend.ts`）

> **結論：問題是真的，但「拆一條匿名發布連線」只修掉一半，而且很可能撞掉企業 allowlist
> 唯一的執行點。不建議現在動；先做的是把它記進 ADR-0237 的洩漏面，以及讓使用者知道。**

## 背景與問題

### 1. 查證：`requireAuth` 的站台，連發布都要 AUTH

`relay-core.ts:327–330`：

```ts
case "EVENT":
  if (this.requireAuth && !this.isAuthed(connId)) {
    return this.authRequired(connId, ["OK", msg.event.id, false, "auth-required: 請先認證（NIP-42）"]);
  }
```

而客戶端**一條連線兼發布與訂閱**（`relay-backend.ts` 的 `this.client`）。

⇒ 那條連線已用真名 AUTH 過（NIP-42 簽章帶 pubkey），所以中繼知道
**「這顆一次性金鑰簽名的 Gift Wrap，是這個真名送出的」**。

Gift Wrap 的外層作者刻意是一次性金鑰（NIP-59），為的正是讓中繼看不出誰在發。
**AUTH 把它還回去了**——在發布側。

### 2. 這一格 ADR-0237 沒有記到

ADR-0237 盤點元資料洩漏面時，處理的是**訂閱側**（`authors:[聯絡人]` 把聯絡人集合交給中繼），
ADR-0240 的真隱身也是補訂閱側。**發布側的 AUTH 關聯從未被記錄**。

### 3. ⚠ 拆連線只修掉一半

假設另開一條**不 AUTH** 的連線專門發布：

- ✅ 中繼不再知道「這顆 wrap 的真名發送者是誰」。
- ❌ **但它仍然知道那條連線的 IP、時間、以及與你 AUTH 連線的同時性。** 同一個裝置在同一時刻
  一條匿名連線發、一條真名連線收，關聯起來不需要密碼學。要真的斷開需要獨立的網路路徑
  （Tor／不同出口），那是完全另一個量級的工程與可用性代價。

⇒ **「拆連線」買到的是「中繼不必主動記錄關聯」，不是「中繼無法關聯」。** 這個差別必須說清楚，
否則會做出一個聽起來解決了、實際上沒解決的功能。

### 4. ⚠ 而且 AUTH 身分很可能是企業 allowlist 唯一的執行點

`requireAuth` 的站台上，allowlist 要判斷「這個發布者是不是本組織成員」。
Gift Wrap 的外層作者是一次性金鑰——**對 allowlist 完全沒用**。
唯一能拿來比對名冊的身分就是 **AUTH 的 pubkey**。

⇒ 允許不 AUTH 發布，等於在那些站台上**把 allowlist 的執行點拿掉**。
企業自架站（ADR-0162 的檔案暫存正是靠它擋外人）會直接失去門禁。

⇒ 若要做，只能**分部署**：公開節點允許匿名發布、企業節點不允許。
那又要先算公開節點的濫用面（無身分＝無從限流、無從封鎖），而目前沒有這份評估。

## 考量的選項

- **A：現況**（單一 AUTH 連線兼發布與訂閱）。洩漏存在，但 allowlist 有執行點。
- **B：拆一條匿名發布連線**。修掉「中繼主動記錄關聯」，但 §3 的同時性關聯仍在，
  且 §4 會撞掉 allowlist ⇒ 必須分部署。
- **C：不動實作，補上揭露**：把這一格寫進 ADR-0237 的洩漏面，並讓使用者
  知道「連到要求認證的中繼時，該站知道你在發訊息（但不知道內容與對象）」。

## 決策（研究記錄，未決策）

**採 C 的方向，不建議現在做 B。** 理由：

1. B 的收益被 §3 打了折——沒有獨立網路路徑，關聯只是變得「需要中繼主動做」而非「不可能」。
2. B 的代價是 §4 的門禁，且需要先做公開節點的濫用面評估（**目前不存在**）。
3. 依 ADR-0275 的分級精神，**要求 AUTH 的站台其實是比較好的站**（不要求 AUTH＝任何人都能
   訂閱你的收件匣，那是研究列出的最大風險）。所以「AUTH 帶來發布側關聯」是**一個取捨，
   不是純粹的缺陷**——把它講成缺陷會推向錯的方向（鼓勵連不要求 AUTH 的站）。

## 後果

**正面**

- 把 ADR-0237 缺的一格補上，且指出「拆連線」這個直覺解只修一半。
- 記錄了 allowlist 與匿名發布的衝突——那是日後任何人想動這裡都會撞到的牆。

**負面／代價**

- 洩漏**繼續存在**。要求 AUTH 的中繼知道「這個 pubkey 在這個時間發了一顆事件」
  （不知內容、不知對象、不知是給誰的 wrap）。
- 本文只做評估，沒有任何實作或 UI 改動。

**待辦（皆待決策）**

1. 把發布側 AUTH 關聯**寫進 ADR-0237** 的洩漏面清單（純文件，成本低）。
2. 官網／設定的隱私說明補一句實話：連到要求認證的中繼時，該站知道你在發訊息的時間點。
   與 ADR-0297 §6「如實顯示保護等級」同源。
3. 若日後真要做 B，前置是**公開節點的濫用面評估**（無身分下如何限流／封鎖），
   以及分部署的設定與文案。
4. 不要把「發布側 AUTH 洩漏」當成「別連要求 AUTH 的站」的理由——那會讓使用者
   落到更差的位置（ADR-0275 §5 的 `warn` 分級）。
