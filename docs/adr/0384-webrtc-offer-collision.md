# 0384. 直連信令碰撞：雙方同時發起時由公鑰較大的一方讓步

- 狀態：已接受
- 日期：2026-10-14
- 相關文件：ADR-0088（P2P 資料通道）、ADR-0210（直連失敗降級走中繼）、ADR-0213（直連狀態晶片）；ARCHITECTURE.md〈WebRTC 流程〉

## 背景與問題

打開對話時會呼叫 `WebRtcTransfer.connect()` 主動建立直連。兩個人同時打開彼此的對話（最常見：一則訊息進來、兩邊都點開），兩邊都送出 offer，在中繼上交錯：

- 各自把對方的 offer 套進「自己已送出 offer」（`have-local-offer`）的連線，瀏覽器丟 `InvalidAccessError: Failed to set SSL role for the transport` 或 `InvalidStateError`；
- 錯誤一路回報到對話裡，出現一行「⚠️ 信令處理失敗：…」；
- 直連沒建立。訊息照常經中繼送達，所以只是多了一行嚇人的錯誤、少了直連的好處（傳檔、輸入中、在線狀態卸載）。

2026-10-14 驗收時在 v0.0.18 之間與新版之間都看到，是一開始就存在的問題。

## 考量的選項

- 選項 A：WebRTC 標準的「perfect negotiation」：兩端事先約定誰讓步。讓步的一方收回自己的 offer、接受對方的；不讓步的一方略過對方的 offer、等自己那顆的 answer。
- 選項 B：只讓一方發起（例如公鑰較小的一方）。另一方要直連就得請對方發起，多一輪信令，而且舊版不知道這個規則。
- 選項 C：碰撞時兩邊都放棄、隨機延遲後重試。慢，而且仍可能再撞。

## 決策

採選項 A：

1. **誰讓步**：公鑰（hex）較大的一方讓步。兩端算出的結果必然相反，不需要額外協商。
2. **判斷碰撞**：收到 offer 時，自己正在產生 offer（`makingOffer`）或連線不在 `stable` 就是碰撞。
3. **不讓步的一方**：略過對方的 offer；之後那顆 offer 帶來的 ICE 候選套不上是預期的，不報錯（`ignoredOffer`）。
4. **讓步的一方**：拆掉自己建的資料通道（先卸掉事件處理，不回報「直連中斷」）→ 明確 `rollback` 自己的 offer → 套用對方的 offer、回 answer；資料通道改用對方 offer 帶來的那條（`ondatachannel`）。若自己的 offer 還在產生中，產生完發現已經接受了對方的就不送出。
5. **過期的 answer**（已經不在 `have-local-offer`，例如收回了自己的 offer、或重開 App 後收到舊的）安靜略過。

明確呼叫 `rollback`，不依賴瀏覽器的隱式 rollback——較舊的 Android WebView 沒有隱式 rollback。

## 理由

- 這是 WebRTC 規範推薦的做法，不增加信令輪數。
- 舊版（v0.0.18、v0.0.19）不懂這個規則也不會更糟：舊版那一側照樣會在收到 offer 時報錯；新版讓步時，舊版仍收得到新版的 answer，直連照樣建立；新版不讓步時與修正前一樣建不起來。新版這一側都不再報錯，全部升級後就消失。

## 後果

- 正面：同時打開對話不再出現「信令處理失敗」，直連能建立。
- 負面 / 已知殘餘風險：
  - 與舊版之間，舊版那一側仍會看到錯誤，且約一半的機率建不起直連（見理由）。
  - 只處理資料通道（`webrtc.ts`）；通話（`webrtc-call.ts`）由撥號方單方面發起，配對（`pairing-transport.ts`）也是單方面，都不受影響。
- 後續行動 / 待辦：無。測試：`packages/engine/src/backend/webrtc-glare.test.ts` 以照瀏覽器規則丟錯的假連線重現原錯誤訊息，驗證雙方停在 `stable`、只採用一顆 offer、過期 answer 不報錯。

## 修訂（2026-10-14，實機驗收後）

合併後以兩個網頁版、各在一座錨點上實測：同時打開對話已不再報錯，但「一方先開、另一方晚一點才開」仍出現
`Failed to set remote answer sdp: … Failed to set SSL role for the transport`。加上記錄每次設定描述的掛勾後重現出順序：

1. A 送 offer，B 回 answer——**B 的連線 DTLS 角色從此定了**；
2. 這顆 answer 沒送到 A（跨錨點新連線在認證前送出被拒，見 ADR-0385），A 一直停在「等 answer」；
3. B 之後打開對話，通道沒開，就在**同一條舊連線**上重送 offer；A 讓步、rollback 後以全新的狀態回 answer，角色和 B 舊連線已定的角色衝突。

另外也看出原設計會卡死：offer 掉了、而等著的那方剛好是不讓步的一方，它會永遠略過對方之後的每一顆 offer。

因此決策改為（取代上面第 3、4 點的做法；誰讓步不變）：

- **offer 一律在新連線上接受**：之前談過的連線（有協商時間或通道）先拆掉（卸掉事件處理再關，原本開著才回報「直連中斷」；待送的檔案帶到新連線），在新連線上套用 offer、回 answer。不再用 rollback。
- **卡住的協商會過期**（`NEGOTIATION_STALE_MS` = 10 秒）：自己的 offer 等超過 10 秒，對方的 offer 照收，不讓步也一樣；打開對話時，通道沒開且協商超過 10 秒的連線換新的再談，10 秒內視為談判中不動。
- **信令或候選套用失敗不在對話裡報錯**（直連是盡力而為，ADR-0210）：記 debug、換一條乾淨的連線等下次再談；候選套不上一律略過（換掉的舊連線、被略過的 offer 帶來的候選本來就對不上）。
- **同一顆信令只處理一次**（記最近 256 個事件 id）：重播的 offer 會把剛談好的連線換掉。

修訂後實測（網頁版、跨錨點，記錄 `connectionState`）：同時打開、先後打開、冷啟動後先後打開三種順序，雙方都到 `connected/stable`，對話裡沒有任何錯誤。
測試補上 DTLS 角色模型：「answer 掉了」重現原錯誤、「offer 掉了且不讓步」重現卡死，兩者修正後都能談成。
