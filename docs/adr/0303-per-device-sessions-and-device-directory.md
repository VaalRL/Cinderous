## 背景與問題

ADR-0236 §43 寫道（本專案「FS 最尖銳的技術點」）：

> **多設備共用同一把 nsec。** 身分金鑰**就是** nsec，所有裝置共用它（ADR-0107）。
> Signal 靠 Sesame **給每台裝置獨立身分**與 per-device session；Cinderous 沒有這層。
> 若兩台裝置在同一條發送鏈上並行送訊，會**重用 counter → 金鑰重用**（對串流加密是災難）。

這句話被後續多份 ADR 引用，並據以推導出「**per-device 身分是棘輪的入場費**」
（0290 §4、0291 §78/§97、0292 §88、0301 §126、0302 §70），進而支撐了
「棘輪要動到配對、快照、備份、名冊，比密碼學本身更深」的成本估計。

**問題：這個前提沒有被一手查證過。** 六處引用全是對 0236 §43 的轉述，而 0236 §43
本身未列 Sesame 規格為資料來源。這與 ADR-0292 §5 對 Keychat 的處境完全同形
（該節原寫「沒讀過原始碼或規格…**不應據此下任何結論**」，後由 0300 補上並更正兩處）。

## 1. 查證：Signal 的多設備模型（✅ **證據等級已升級為原文**，2026-07-31）

> **原文核對完成（2026-07-31）。** 本文原記「證據等級＝檢索引述，非原文」，因撰寫環境的
> 出口政策擋下 `signal.org`。另一個工作環境取得得到，已逐條核對，**三段引述全部屬實且為逐字**：
>
> | § | 引述 | 來源 | 結果 |
> | --- | --- | --- | --- |
> | 1.1 | 「per-user identity keys, all devices under a user share the same key pair…」 | `signal.org/docs/specifications/sesame/` | ✅ 逐字相符 |
> | 1.1 | 「Linked devices … share an identity key pair, but have independent prekeys, resulting in independent session keys」 | **`signal.org/blog/a-synchronized-start-for-linked-devices/`**（Signal 官方部落格） | ✅ 語意相符；⚠ 原稿為**意譯非逐字**，原文見下方 §1.1 |
> | 1.3 | UserRecord／DeviceRecord 結構 | Sesame 規格 | ✅ 逐字相符 |
> | 1.4 | 伺服器糾正裝置清單 | Sesame 規格 | ✅ 相符（原文更精確：伺服器**拒收**該批訊息，並回報 old/new DeviceIDs 與新裝置的身分公鑰） |
>
> ⚠ **一個必須指出的區分**（本文原稿把兩件事併在 §1.1）：
> **Sesame 規格只說「支援兩種模型」，它沒有說 Signal 部署哪一種。**
> 「Signal 用共用身分金鑰」這件事的來源是**官方部落格**，不是規格。
> 兩個來源合起來才足以支撐 §1.1 的結論——單靠規格不行。
>
> ⇒ **〈提議〉1 的前提已滿足**：ADR-0236 §43「Signal 靠 Sesame 給每台裝置獨立身分」
> **確為事實錯誤**，可據以更正。



### 1.1 Sesame 規格支援兩種身分模型，Signal 部署的是「共用」那種

Sesame 規格原文（✅ 已核對，逐字）：

> Sesame supports two different models for key pairs: With **per-user identity keys, all
> devices under a user share the same key pair**. With per-device identity keys, each device
> may have a different key pair.

⚠ **規格到此為止只說「支援兩種」，沒說 Signal 選哪一種。** 決定這件事的是官方部落格
〈A Synchronized Start for Linked Devices〉（✅ 已核對，逐字）：

> …linked devices for an account **share an identity key pair, but independent prekeys**,
> so they end up with **independent session keys**.

（本文原稿此處作「Linked devices for a Signal account share an identity key pair, but have
independent prekeys, resulting in independent session keys」——**語意相同但非逐字**，
且未標明其來源是部落格而非規格。以上為更正後的原文與出處。）

⇒ **Signal 的多台裝置也共用同一把身分金鑰**，與 Cinderous 共用 nsec 是同一個形狀。
配對流程（掃 QR、`ProvisionMessage` 帶身分私鑰）與 ADR-0072 的桌面配對克隆亦同形。

⇒ **0236 §43 的「Signal 給每台裝置獨立身分」與此不符。**

### 1.2 讓棘輪可行的不是身分，是「每裝置各自的預金鑰 → 各自的 session」

身分金鑰共用，但**預金鑰每台裝置各自產生、各自發布**。X3DH 的輸入含預金鑰，
故即使身分金鑰相同，導出的 session 金鑰仍不同 ⇒ **棘輪鏈天生是分開的，counter 不會撞。**

0236 §43 擔心的「兩台裝置在同一條發送鏈上並行送訊」——**Signal 是靠分鏈解決，不是靠分身分。**

### 1.3 狀態結構：session 掛在裝置那一層

Sesame 規格（✅ 已核對，逐字）：

> Each device stores a set of **UserRecords** for its correspondents, indexed by UserID.
> Each UserRecord contains a set of **DeviceRecords**, indexed by DeviceID.
> Each DeviceRecord may contain an active session and/or an ordered list of inactive sessions.

送訊＝對每台目標裝置各加密一次 ⇒ **O(N×D) 扇出**（與我們群組扇出同性質，見 §3.3）。

### 1.4 裝置清單的權威是伺服器

Sesame 規格（✅ 已核對；⚠ 原文比原稿更精確——伺服器是**拒收整批訊息**，
且回傳的清單**含新裝置的身分公鑰**）：

> If some of the DeviceIDs are no longer up to date, the **server will reject the messages**,
> and notify the sender of the **old and new DeviceIDs**… the server will also return the
> **identity public keys** for any new devices.

即 Signal 服務的 `MismatchedDevices` / `StaleDevices`（HTTP 409）糾正迴圈：
送訊者持過期清單發訊 → 伺服器**主動糾正並附上正確清單** → 客戶端補建 session 重送。

## 2. 據此重新拆解「棘輪的入場費」

原本被綁成一件事的，其實是兩件：

| 目標 | 真正需要 | 需放棄共用 nsec？ | 動到 0015/0072？ |
| --- | --- | --- | --- |
| **棘輪可行（per-message FS）** | per-device 預金鑰＋per-device session 狀態＋可列舉對方裝置 | **不用** | **不用** |
| **裝置撤銷** | 身分金鑰不在每台裝置上＋一個權威 | 要 | 要 |

⇒ **修正六處引用的推論**：per-device **身分**不是棘輪的入場費，per-device **session** 才是。
前者是「裝置撤銷」的入場費，那是另一個目標。

⇒ 且據 **ADR-0301 §1**，1:1 有棘輪則群組 FS 免費附贈（成對扇出＝N 份獨立密文），
**群組不需要任何群組專屬密碼機制**。故本文全程只談 1:1 的前置。

## 3. 裝置目錄的形狀：不是 OR-Set 墓碑，是簽章單調版本清單

無論走哪個目標，都需要一份「這個身分現在有哪些裝置」的目錄。
討論中提出「墓碑直接做成黑名單」——**查證後：現有 OR-Set 墓碑不能複用。**

### 3.1 現有墓碑有三個性質正好與撤銷相反（`packages/core/src/or-set.ts`）

| 行 | 現況 | 對撤銷為何致命 |
| --- | --- | --- |
| `:104` | `if (t !== undefined) tombAt.delete(k); // 復活：丟棄過時墓碑` | 元素 `at` 比墓碑新即**復活且清掉墓碑**。攻擊者持被撤銷裝置，自填一個更新的 `at` 即復活自己 |
| `:24` | `OR_SET_TOMBSTONE_RETENTION_MS = 90 天`（`pruneTombstonesByTime`） | 被偷的金鑰**永不過期**，撤銷卻在 90 天後被 GC ⇒ 任何持舊清單的裝置合併回來即復活 |
| `:17`/`:130` | `OR_SET_TOMBSTONE_MAX = 256`，輸出 `.slice(0, tombstoneMax)` | 製造 256 筆更新的墓碑即可把關鍵撤銷擠出去（廉價攻擊） |

### 3.2 更根本：信任方向相反

現有墓碑活在**自己的加密雲端快照**內，而 `relay-backend.ts` 的 `receiveSnapshot()`
第一行即 `if (event.pubkey !== this.self.pubkey) return;`（只信自己的快照）。
它**從不需要被別人採信**，故 `{ key, at }` **沒有簽章**——安全性全由「只有我解得開」提供。

但撤銷是一份要給**別人**看、並改變**別人送出行為**的宣告。無簽章的 `{key, at}` 在此毫無意義。

同理，複用封鎖清單亦不成立：封鎖是**入站過濾**（純本地偏好，無人需採信），
撤銷是**出站定址指令**；且 `unblockContact()` 特地寫了解封墓碑＝設計成可逆，方向相反。

### 3.3 提議的形狀：整份清單、帶版本號、身分金鑰簽章

```
{ v: 6, devices: [ {id, prekeyBundle…}, … ], at }   ← 身分金鑰簽章
```

合併規則＝**版本號大的整份取代**（非逐元素 OR-Set）。四個問題一次消失：

- **復活**：v5 移除的裝置不可能從陳舊的 v4 回來
- **GC／256 上限**：**不需要墓碑**——移除＝不出現在新版清單裡，沒有東西要保留
- **偽造**：攻擊者產不出 v6（無身分金鑰）
- **信任方向**：簽章即為給他人採信而存在

**這個模式專案裡已在跑**：組織簽章名冊（0047/0049）的 `reconcileOrgGroups()` 正是
權威整份對帳（加入名冊內的、移除名冊外的）。ADR-0068 甚至因此把組織群排除於快照廣播：
「簽章名冊已是**更強的權威對帳**」。

⇒ **裝置清單與組織名冊同類**（單一權威簽發的完整清單），不是多方協作的可變集合。
用 OR-Set 表達它，是把一個**有**權威的問題塞進為「**沒有**權威」設計的資料結構。

### 3.4 傳播：版本號搭便車進訊息 tag

殘留問題是「清單傳播不出去」：離線三週的聯絡人持 v5，會繼續加密給已撤銷的裝置，
而無伺服器可推送。緩解＝把版本號塞進每則 rumor 的 tag（比照 `group.ts:96` 的 `relayHint`）：
任何人收到你任何一則訊息即發現落後並補抓 ⇒ 收斂速度從「下次開機廣播」變成「下次通訊」。
成本接近零。

## 4. 撤銷無權威：這是公開未解問題，不是我們的落後項

ADR-0301 §126 把「撤銷無權威」記為 per-device 身分的待議取捨。查證後應提高其定性：

**Signal 有伺服器、有權威，這題照樣沒解好。**

> **✅ 全文已核對（2026-07-31）。** 完整出處：
> Jan Wichelmann、Sebastian Berndt、Claudius Pott、Thomas Eisenbarth（University of Lübeck），
> **《Help, my Signal has bad Device! Breaking the Signal Messenger's Post-Compromise
> Security through a Malicious Device》**，**DIMVA 2021**；
> eprint `2021/626`，PoC 原始碼 `github.com/UzL-ITS/signal-attack`。
> 本倉庫留存：`docs/research/2021-626.pdf`。
> 原稿僅有摘要層級的結論，**沒有威脅模型**；以下為全文補上的前提。

### 4.1 攻擊前提（全文 §4.2）：兩個長期祕密，一次性外洩

攻擊者需要且**只需要**：

| 祕密 | 說明 |
| --- | --- |
| `sec(IK)` 私有身分金鑰 | 只存在裝置上 |
| `pwA` API 密碼 | 與 Signal 伺服器做 HTTP 認證用；隨機，須外洩 |

（`pn` 電話號碼與 `unA` 使用者名稱論文列為「可假設攻擊者已知／可輕易猜出」；
`pk` profile key **非必要**；**`pin` 非必要**，除非攻擊者想順便拿完整聯絡人清單。）

**不需要**：實體接觸、簡訊驗證碼、受害者掃 QR、受害者任何互動。
論文原文：攻擊者可以「fully emulate the protocol and set up the new device,
**without any interaction from the victim or their app**」。

⇒ **我原先懷疑這是「實體接觸」等級的威脅模型——錯了。** 它就是標準的 PCS 情境：
**一次性憑證外洩 ⇒ 所有未來通訊全開**（論文 §6：「eavesdrop on all communication
after a **one-time credential breach**」）。§4 的定性成立，且比原稿寫的更強。

### 4.2 ⚠ Signal 的正式回應：這不在他們的威脅模型內

論文 §1.2 責任揭露：2020-10-20 通報，2020-10-28 收到回覆——

> they state that they **do not treat a compromise of long-term secrets as part of their
> adversarial model**. Therefore, they **do not currently plan to mitigate** the described
> attack or implement one of the proposed countermeasures.

⇒ 正確的敘述**不是**「Signal 有這個漏洞沒補」，而是
**「Signal 明確把這個情境劃出範圍外」**。這對我們是更有用的一課：
**PCS 在多裝置下要成立，得先有人把它放進威脅模型**——而 ADR-0292 正是在做這件事。

### 4.3 可偵測性：裝置清單的變動通知是**真緩解**，不只是化妝

論文 §4.3／§5.1 的兩段合起來很關鍵：

- 偽造裝置**會**出現在受害者的裝置清單裡；但攻擊者若能操控（不可信的）伺服器，
  可把自己從回傳清單中濾掉 ⇒ 幾乎不可偵測。
- **但** §5.1：若攻擊者為了躲清單而在伺服器端完全隱藏自己，
  「they **won't receive any messages, making the attack useless**」。

⇒ **隱藏與收訊互斥。** 所以「裝置清單變動即警示」不是安全劇場，
它把攻擊者逼進一個二選一。**這是本文 §6.6「E-lite」最強的一項外部佐證**，
而 E-lite 正是本文列為**可獨立先行**的那一項。

⇒ 另一項數據點：論文 §4.2 指出偽造裝置完成註冊後會拉取對話清單，
而「**There is no notification to the user that a device requested their conversations**」。
配上 Fig. 3 的截圖：Alice 與 Bob **都**看不到有新裝置加入，也看不出哪台裝置發的訊息。
⇒ 與我們 ADR-0278／0287 的「UI 不得說謊」是同一條紅線的反面教材。

### 4.4 🔴 論文推薦的修法，**否定了本文 §6 的提案 C（冷救援碼授權）**

這是全文對我們**最重要**的一段，而摘要層級完全看不到。論文 §5.2 推薦的根治方案是
Campion、Devigne、Duguey、Fouque《Multi-Device for Signal》（ACNS 2020）——
其裝置註冊**強制使用一台已註冊的裝置**，且各裝置以**去中心方式**互相追蹤（不靠伺服器），
透過 Ratcheted Dynamic Multicast（RDM）通知彼此。關鍵的那一句：

> Note that the RDM can only be used if the **current ephemeral keys** are known, which means
> that **an attacker who has only extracted long-term secrets is not able to register a new device**.

⇒ **修法的承重點是「授權憑證必須是當期的短期狀態，不能是長期祕密」。**

⚠ **而本文 §6 的提案 C 是「冷救援碼授權裝置註冊」——救援碼是長期祕密。**
一次外洩 ⇒ 攻擊者永久可加裝置。這正是論文證明會失敗的那一類設計：
把授權掛在長期祕密上，等於把 PCS 換成了「再撐一層長期祕密」，**沒有恢復性**。

⇒ **本文〈已知限制〉原本記的那項張力（C 與 ADR-0245 §2：救援碼從只讀憑證升級為
簽發憑證後外洩後果變重）——現在不只是張力，是設計缺陷。** 論文直接指出了正確方向。

⇒ **修正方向**：裝置授權應綁定**當期短期狀態**（僅現役裝置能授權新裝置），
冷救援碼移到**刪除與重建**那一側。

> 🔵 **已於 §6.2／§6.2b 完成重新設計（2026-07-31）**，結論比此處初步方向更好：
> **我們不必發明新機制**——ADR-0072 的配對流程（一次性金鑰＋雙方 nonce＋SAS 人工比對＋
> 來源端活體參與）**已具備論文要求的性質**，缺的只是「配對成功時順帶簽出 v+1 清單」那一步。
> 且 C 並非「被推翻」而是**用錯位置**：它在**刪除**那一側完全成立（見 §6.2 C 列）。
> ⚠ 本節下方原記「§6 的張力實為設計缺陷」——該定性**過重**，正確的說法是
> **「C 的前提沒有被當成閘門，且被放在錯誤的那一側」**。

### 4.5 ⚠ 對我們而言攻擊成本**更低**：兩個祕密塌縮成一個

論文的兩個祕密裡，`pwA` 是**伺服器 HTTP 認證**用的。**我們沒有那個角色**
（中繼不認證身分、不管理裝置）。⇒ 在我們的模型裡，攻擊者只需要 **nsec 一個**。

而本文 §2 已記：**今天每台裝置都有身分金鑰**（0015／0072 的佈建就是在複製 nsec）。

⇒ **在身分金鑰改成冷保存之前，我們連論文攻擊的那道門檻都沒有。**
這強化本文 §6 對「根 nsec 冷保存」的主張，但**弱化提案 C 的具體形式**（見 §4.4）。

### 4.6 對 §7「清單住在哪」的證據

論文 §4.3：攻擊者若能操控伺服器，可**竄改回傳的裝置清單**把自己藏起來。
⇒ 佐證本文〈提議〉2 的方向（**簽章**單調版本清單，權威在使用者的簽章而非傳輸方），
也佐證 ADR-0068「否決 relay 端群組狀態」的既有立場。
⇒ 但論文**沒有**回答 §7 的分歧（清單放公開可取代事件 vs 加密扇出），
它的方案有伺服器可依賴，我們沒有。**§7 仍是未決分歧。**

### 4.7 在野利用（⚠ 證據等級：仍為檢索引述）

已有在野利用（2025）：惡意 QR code 誘使受害者把帳號連結到攻擊者控制的實例，
之後所有訊息即時同步送達雙方。

⚠ **這一項與上述論文無關、且未核對原文。** 注意它與論文攻擊是**不同**的威脅模型：
論文攻擊**不需要**受害者互動，這一項則是**社交工程誘使受害者主動掃碼**。
兩者不應混為一談——原稿把它接在論文結論後面，容易讀成同一件事。

⇒ 弱點在**裝置註冊流程**，不在密碼學。
⇒ 「靠伺服器當權威」**不是值得羨慕的參考答案**——它把攻擊面從密碼學搬到註冊流程，而那裡更軟。
⇒ 與 ADR-0092 的既有立場一致：「本就假設 relay 為對手、不依賴其誠信。
   號稱能驗誠信的介面＝安全劇場。」

## 5. ⚠ 預金鑰的生命週期：無狀態中繼上「一次性預金鑰」不可行

§2 把「per-device 預金鑰」寫得像是免費的。**它不是**——這一節補上漏掉的成本。

### 5.1 一次性預金鑰需要一個會「消耗」它的伺服器

Signal 的 one-time prekey 是**被消耗的資源**：伺服器每次發出一把即劃掉，用盡時通知客戶端補傳。

我們沒有這個角色：

- 中繼**無狀態**（零伺服器狀態鐵則），不會記「這把發過了」。
- 可取代事件（ADR-0099）**沒有消耗語意**——它是廣播，人人取到**同一把**。
- 就算硬要做，也等於要求中繼維護每個使用者的預金鑰配額狀態 ⇒ 同 ADR-0068 選項 D 的否決理由。

⇒ **推論：只能用簽章預金鑰（signed prekey），放棄一次性預金鑰。**

### 5.2 代價：首則訊息的 FS 要等棘輪推進一步

> **✅ 原文核對（2026-07-31）＋⚠ 本節原稿說得比實際嚴重。** X3DH 規格逐字：
>
> - 沒有一次性預金鑰時協定照跑，只是少一個 DH：
>   「If the bundle does not contain a one-time prekey, she calculates:
>   `DH1 = DH(IK_A, SPK_B)`, `DH2 = DH(EK_A, IK_B)`, `DH3 = DH(EK_A, SPK_B)`, `SK = KDF(DH1 || DH2 || DH3)`」
> - **`DH3` 本身就提供前向保密**（規格：「DH3 and DH4 provide forward secrecy」），
>   而 `DH3` **不含**一次性預金鑰。
> - 一次性預金鑰買到的是這一句：「If one-time prekeys are used for a protocol run then a
>   compromise of Bob's identity key **and prekey private keys** at some future time will not
>   compromise the older SK, assuming the private key for OPK_B was deleted.」
>
> ⇒ **修正**：無一次性預金鑰**不是「首則訊息沒有 FS」**，而是
> **「首則訊息的 FS 改為取決於簽章預金鑰（SPK）的輪替與刪除，而非一次性預金鑰的刪除」**。
> 只要 SPK 有確實輪替並刪除舊私鑰，FS 的缺口就**被輪替週期界住**，不是永久的。
>
> ⇒ 這**改善**了這條路的評估：§5.3 的「簽章預金鑰輪替搭開機廣播便車」從
> 「衛生習慣」升級為**FS 的承重結構**——它決定缺口有多寬。
> 同時 §5.2 末「必須先量化只有一則訊息的對話佔比」的急迫性下降（但仍值得量）。
>
> ⚠ 另一併核到 §5.1 的直接佐證：「**The server should provide one of Bob's one-time prekeys
> if one exists, and then delete it.**」——一次性預金鑰的消耗語意**明文寫在規格裡由伺服器承擔**，
> 我們沒有那個角色，§5.1 的推論成立。

X3DH 允許在一次性預金鑰不可得時照跑（規格明定的降級模式），代價是
~~**該次會話的第一則訊息不具前向保密，須待棘輪推進一步後才建立**~~
→ **更正**（見上框）：**該次會話首則訊息的前向保密改由簽章預金鑰的輪替與刪除界住**，
不是消失。缺口寬度＝SPK 的輪替週期。

這不是死路（是有文獻記載的取捨），但它**削弱一部分我們一開始想買的性質**，
且對我們的使用形態特別不利：離線留言是主要路徑（ADR-0065 七天倉），
「第一則訊息」在許多對話裡就是**唯一**的訊息。

⇒ 真要往下走，必須先量化「有多少對話只有一則訊息」——若比例高，這個降級會吃掉大半收益。

### 5.3 簽章預金鑰的輪替沒有伺服器提醒

signed prekey 需要定期輪替才有意義，而沒有伺服器會提醒你。
可搭現成便車：比照 ADR-0061 個人檔／ADR-0068 群組快照的**開機廣播＋每日節流**模式
（`groupSnapshotDue()` 那套），輪替與發布都掛在 `start()` 上。

### 5.4 發布本身洩漏裝置數（接 ADR-0237）

每台裝置各發一份預金鑰 ⇒ 中繼看得到「這個身分有幾把預金鑰在線」＝**裝置數**。
與〈後果〉記的扇出爆發洩漏是**兩條獨立的洩漏路徑**，且這一條連時序關聯都不必做——
直接讀可取代事件即可。

### 5.5 附帶：Signal 的「誰能加裝置」那一關，我們等於沒有

Signal 的裝置註冊由**帳號憑證**把關（而 §4 顯示那已是它最軟的地方）。
我們的模型裡「誰有身分金鑰誰就能加裝置」，而**今天每台裝置都有身分金鑰**
（ADR-0015／0072 的佈建就是在複製 nsec）。

⇒ 在身分金鑰改成冷保存之前，**裝置註冊這一關不存在**——
這也再次說明 §2 那張表的第二列（撤銷需要 per-device 身分）為何不能省。

## 6. 裝置清單的管理方式：選項空間與冷金鑰的真實成本

§3.3 提議了清單的**資料結構**，但沒說**誰有權簽它**。這一節補上，並記錄該選擇的代價。

### 6.1 ⚠ 先說一件會改變評估的事：冷身分金鑰我們已經有了

「身分金鑰改冷保存」聽起來像要引進新概念，但查證後——**它已經在產品裡**：

- **ADR-0070**：加密備份碼＝`{ v, ncryptsec(nsec), relayUrl }`，NIP-49 密碼加密，
  **使用者自持、不上雲、不發佈到 relay**（§4）。
- **ADR-0200**：正名為「**救援登入碼**」。
- **ADR-0245 §2**：定案**身分-only、不含 EK** ⇒「**一次存終身、不隨換鑰改變**」。

一把寫下來的、終身不變的、只含身分金鑰、且刻意不上網路的東西——**這就是冷身分金鑰**。
⇒ 本選項不是「新增一個冷金鑰」，是**把既有救援碼從「救援憑證」提升為「簽發憑證」**。
這讓原本估最貴的那條路便宜很多。

### 6.2 選項空間（🔴 **2026-07-31 重排**：前提閘門釐清後，B′ 與 C 的評價對調）

> §4.4 讀完論文後一度把 C 記為「被推翻」，但那個定性也不夠精確——
> **論文的論證不是「長期祕密一律不能當授權憑證」**，而是
> **「授權若掛在長期祕密上，一次入侵即可永久註冊裝置，因此沒有恢復性」**。
>
> 對我們而言真正的問題在別處：§5.5／§4.5 已確立**今天每台裝置都有 nsec**，
> ⇒ **在 nsec 熱的前提下，C（救援碼授權）與 B（裝置自簽）是同一件事**——
> 攻陷任一台即取得 nsec，也就取得救援碼所代表的一切。
>
> ⇒ **C 的缺陷不是「長期祕密」四個字，是它的前提沒有被當成閘門。**
> 原表把「需把身分金鑰移出熱路徑」放在〈代價〉欄——**它不是代價，是 C 能否成立的門檻**。

### 6.2b 🔵 論文要的「當期短期狀態」性質，我們已經寫好了——在 ADR-0072 裡

查證 `packages/core/src/pairing.ts`，既有的配對搬家流程具備這些性質：

| 性質 | 位置 |
| --- | --- |
| **一次性金鑰**（不重用） | `createPairing()` |
| **雙方 nonce**，每次連線新產生 | `runPairingSource`／`runPairingTarget` 的 `nonceA`／`nonceB` |
| **SAS 四位短碼，兩端各自算、人工比對** | `deriveSas(key, nonceA, nonceB)` |
| 來源端**必須活著參與** | `runPairingSource` 須實際執行 |

原始碼註解已寫明其抗重放性質：
「SAS 綁定（金鑰＋本次連線的雙方 nonce）：剪貼簿竊取者即使拿到載荷，
其連線的 nonce 不同 ⇒ SAS 不同」。

> 🔴 **2026-07-31 更正：本節原本的結論太強，且理由是錯的。**
>
> 原文寫：「抽走長期祕密後離線操作的攻擊者，完成不了這個流程——他需要既有裝置活著參與，
> 還需要一個人比對 SAS。**這正是 §4.4 論文要求的『當期短期狀態』性質。**」
>
> **⚠ SAS 擋不住這個攻擊。** 攻擊者**同時控制兩端**：他以被攻陷裝置的權限當**來源**、
> 自己的裝置當**目標**——**SAS 是他自己跟自己比對的**。
> SAS 防的是**第三方攔截一次合法配對**（原始碼註解講的正是這個：剪貼簿竊取者），
> 它**不防**「持有來源裝置授權的人配對給自己」。
>
> ⇒ 真正決定成敗的只有一件事：**攻擊者能不能行使來源裝置的簽章權？**
>
> | 攻擊者拿到 | 能否加裝置 |
> | --- | --- |
> | 磁碟映像，裝置簽章金鑰在 **L2 晶片內**（TPM／SE／StrongBox） | ❌ 取不到金鑰 |
> | 磁碟映像，裝置簽章金鑰在 **L1／L0**（密碼包裹／祕密儲存） | ✅ **可以，離線即可簽** |
>
> ⇒ **本節的安全性質是平台相依的**（分級見 **ADR-0297 §6**）。
> **在 Linux 與瀏覽器上，§4 論文那個攻擊仍然成立。**

### 6.2b-1 修正後的正確說法：我們有活體性與抗攔截，**沒有恢復性**

ADR-0072 的配對流程實際提供的是：

| 性質 | 有沒有 | 說明 |
| --- | --- | --- |
| **活體性** | ✅ | 來源端必須實際執行 `runPairingSource` |
| **抗第三方攔截** | ✅ | SAS 綁定本次連線的雙方 nonce |
| **恢復性（healing）** | ❌ | **沒有**——簽章權來自**長期的**裝置金鑰，不隨時間失效 |

Campion／RDM 的恢復性來自「授權憑證**本身**隨棘輪推進而失效」。
我們的配對每次產生新的一次性金鑰與 nonce，**但「有資格當來源」這件事不會過期**。

⇒ 要取得恢復性只有兩條路：

1. **讓裝置簽章金鑰本身輪替**（真的做 RDM 那件事）——新的密碼學設計，撞 ADR-0290 §2 的審計面；
2. **讓它不可匯出**（ADR-0297 的 **L2**）——只在部分平台成立。

⇒ **要嘛接受分級，要嘛做路 1。本文不決定**（路 1 的評估見〈後續行動〉）。

### 6.2b-2 仍然成立的部分

即使更正上述，以下不變：

- **要做的是把配對流程接上授權**：配對成功時，來源裝置額外簽出一筆 `v+1` 的清單條目
  （含新裝置公鑰）。機制已在，缺的是那一步輸出。
- **在 L2 平台上，這確實達成論文要求的性質**——只是不能宣稱全平台。
- 相對於「貼 nsec 即成為一台裝置」的現況，**任何一級都是進步**。

⇒ **同時消掉 §6.4 表格最痛的一格**：原表記「加裝置（只有 1 台）→ 需要救援碼」。
**不需要**——單裝置一樣跑得了配對流程；n=1 但它是 live 的，
論文要的性質不依賴 n≥2，依賴的是**當期**與**活體參與**。

⚠ **但有一項要重新評估：SAS 只有四位數（10⁴）。**
它今天保護的是「確認搬家」；升級為「授權裝置」後，它保護的東西變重了。
對線上主動攻擊者而言 10⁴ 偏薄。**這條列為本方案的具體待辦，見〈後續行動〉。**

### 6.3 澄清：救援碼**不需要**隨裝置變動重產

討論中出現的自然疑問。答案是不需要——救援碼是**簽章金鑰**，裝置清單是**被簽的文件**；
簽名不消耗也不改變金鑰（同一把根 CA 金鑰簽發無數張憑證）。

`救援碼 = ncryptsec(nsec) + relayUrl`（**終身不變**）；`裝置清單 = {v, devices, at} + 簽章`（每次 v+1）。

這正是 ADR-0245 §2 已為另一理由定案的性質（EK 輪替不碰身分 ⇒ 備份碼不用重存）。
**唯一需要更換救援碼的情況是身分本身報廢**（救援碼外洩 ⇒ 換 npub），與今日無異。

### 6.4 ⚠ 真正的成本是頻率，不是重產

冷保存的天敵是**使用頻率**。若每次增刪裝置都要貼上救援碼＋輸入備份密碼，
使用者會把它放到方便的地方（密碼管理器、截圖、記事本）——
ADR-0070 §4 的「使用者自持、不上網路」擋得住系統性洩漏，**擋不住使用者為了方便而把它放熱**。

三個方向：

1. **接受**：增刪裝置一年幾次，這個量級對冷金鑰是合理的（同硬體錢包助記詞）。
2. **委任憑證**：身分金鑰簽一把帶有效期的「裝置管理金鑰」，日常由它簽清單。
   減少觸碰次數，代價是**委任金鑰自己也需要撤銷機制**——問題往下推一層，未必划算。
3. **增／刪不對稱**（推薦探討）：把冷金鑰留給**對抗性**操作。

🔵 **2026-07-31 修訂：結論（增／刪不對稱）成立，但理由與內容都要換。**

| 操作 | 需要 | 理由 |
| --- | --- | --- |
| **加**裝置（任何台數，含只有 1 台） | **既有裝置的 live 配對授權**（§6.2b） | ~~具恢復性：攻擊者離線後其竊得的狀態隨棘輪推進失效~~ 🔴 **更正**：**沒有恢復性**，強度取決於裝置簽章金鑰可否匯出（§6.2b-1）。仍採此路的理由是**活體性＋抗攔截，且相對「貼 nsec 即成為一台裝置」的現況是明確進步**。~~原表按台數分兩列、單裝置需救援碼~~ → **不必分**，見 §6.2b |
| **刪**裝置 | **救援碼** ＋ 必須在**全新裝置**上，且該裝置**不入列、用畢即焚**（§6.5a–d） | 被攻陷的裝置**必須無法**阻止或反轉。刪除用長期祕密**不違反** §4.4——論文管的是註冊那一側；且持有救援碼者本就擁有你的身分，**不新增暴露面**。⇒ **不需要先走新增裝置流程**：簽章權來自身分金鑰而非成員身分 |

⇒ 不對稱的正確理由**不是**「刪比較對抗性」（雖然也對），而是：
**加的授權需要恢復性（故用當期狀態），刪的授權需要不可被攻陷者反轉（故用攻陷者沒有的東西）。**
兩側要的性質不同，所以本來就不該用同一把。

⚠ 誠實揭露（原文保留，仍然成立）：**§4 的攻擊本身就是一次「加」**。
live 配對擋掉了「抽走祕密後離線操作」那一類，**但擋不掉在裝置上有執行權的攻擊者**
——他可以直接驅動配對 UI。⇒ 見 §6.7。

### 6.5 ⚠ 操作陷阱：救援碼會把 nsec 解回**那台**裝置

輸入救援碼＝把 nsec 解密到當下這台裝置的記憶體。

⇒ 若你懷疑某台被攻陷、卻**在被攻陷的那台**上輸入救援碼去移除它——
**你剛把身分金鑰整個交出去**，而移除操作同時失去意義。
而現實是「剛出事的當下」正是你對哪台可信的判斷**最不可靠**的時候。

⇒ 這與 §4 的結論同源：**弱點在人與流程，不在密碼學。**

⇒ 產品層的緩解方向：把「移除裝置」設計成可在**全新裝置**上完成
（以救援碼登入一台乾淨裝置 → 從那裡簽發新清單），而**不是**在既有裝置上操作。
這條規則必須寫進 UI 流程，不能只寫在文件裡。

### 6.5a 🔵 簽章終端 ≠ 成員：不需要先走「新增裝置」流程

原 §6.5 只說「在一台乾淨裝置上簽發新清單」，**沒說那台之後算不算你的裝置**。補上：

**不需要先把它加進清單。** 簽章權來自**救援碼（身分金鑰）**，不是來自「是清單成員」——
簽的是身分金鑰、被簽的是清單，簽署者不必在被簽的名單裡
（同一把根 CA 金鑰簽發憑證時，CA 自己也不在憑證清單內；§6.3 已用過這個類比）。

⇒ 那台裝置的角色是**臨時簽章終端**，**不是**「先加入、辦完再退出」。**沒有加入這一步。**

> ⚠ **更正一條在討論中提出、但會導致矛盾的原則。**
> 討論時曾提出「任何把身分金鑰帶進一台裝置的動作，都是『重建』而非『加入』」，
> 該說法會推導出「救援登入＝自動入列」，與本節衝突。
> **正確的表述：救援碼授權的是「簽章」，不是「入列」。**
> 那台要不要成為成員，是**另一個獨立且必須明示**的選擇。
>
> 至於原本要擋的「攻擊者拿到救援碼就安靜多一台」——**那件事擋不住**
> （持有救援碼者已有你的 nsec，本就全拿）。能做的只有讓它**吵**，
> 而讓它吵的是 §6.6 E-lite 的清單變動警示，不是入列規則。
> ⇒ 與 §6.7-1「E-lite 是承重結構」同源。

### 6.5b 🔵 閱後即焚模式：與「救援登入」必須分成兩條路

若那台乾淨裝置是**借來的**（他人筆電、公用電腦），流程結束後它上面有你解密過的 nsec。

⇒ 需要一個明確的一次性模式：

```
救援碼 ＋ 備份密碼 → 解出身分 → 簽新清單 → 發布 → 抹除本機一切
                                              ↑ 不寫入本地儲存、不入清單
```

⚠ 這與「一般用救援碼登入」（那條是真的要在這台常駐）**是兩條不同的路**，
UI 必須在入口就分開，不能靠使用者事後選擇。**目前 ADR-0070／0200 未區分，此為缺口。**

### 6.5c 決策：**選擇性移除**，且規則為 fail-closed

新清單該長什麼樣，有兩種做法：

| | 全面重建 | **選擇性移除（採用）** |
| --- | --- | --- |
| 新清單內容 | 只剩簽章當下確認的（等於全部重來） | 保留其他好裝置，只踢掉目標那台 |
| 好處 | **不依賴取回舊清單**——中繼扣留或餵舊版都影響不到 | 其餘裝置不必全部重新配對 |
| 代價 | 好裝置也被踢掉，**全部要重新配對**——而重新配對要求那些裝置**活著且在手邊** | 需先取回目前清單 ⇒ 中繼可餵舊版 ⇒ 有**復活**風險 |

**採用選擇性移除**，理由是全面重建**會反噬安全性**：

> 你人在外面、身上只有手機，發現筆電被入侵。若移除操作會把家裡的桌機一起踢掉，
> 而桌機要重新配對得等你回家——**你很可能選擇不執行移除**。
> **安全操作因為代價太痛而不被執行，是最糟的失敗模式。**

**⇒ 但規則必須 fail-closed 以消掉復活風險：**

> 乾淨裝置取回目前清單後，要求使用者**逐台當場確認**要保留哪些。
> **未確認的一律移除。**

⇒ 中繼餵舊清單的最壞後果變成：你「漏掉」一台 ⇒ 它被移除 ⇒ 事後重新配對（**可恢復**）；
而**不會**發生「已移除的裝置被復活」（**不可恢復**）。
**壞的方向倒向安全那側**——這正是 fail-closed 的定義。

⚠ 誠實揭露：這條規則把「中繼餵舊版」的成本轉嫁給使用者（多一次重新配對）。
它換到的是「絕不復活」，我們認為這個交換划算，但它**不是免費的**。

### 6.5d 完整流程（本節的產出，UI 須照此實作）

1. 取一台乾淨裝置，開啟**「移除裝置」模式**（⚠ **不是**「登入」）
2. 貼上救援登入碼 ＋ 輸入備份密碼
3. 畫面列出目前清單 → 使用者**逐台勾選要保留的**（未勾＝移除）
4. 簽出新版清單（`v+1`）、發布
5. **該裝置抹除一切、不入列**（§6.5b）
6. 沒勾到但仍需要的裝置，事後以配對流程加回（§6.2b）

⇒ 步驟 1 與步驟 5 是**驗收條件**，不是建議：入口若與「登入」共用、
或該裝置流程結束後仍持有身分，本節的安全性質即不成立。

### 6.6 E-lite：可以最先做、且不依賴前面任何工作

**顯著呈現「我有哪些裝置」＋任何清單變動即警示**。

- 這正是 §4 論文建議的「提高可偵測性」方向，成本是所有選項裡最低的。
- **不依賴 A/C/棘輪任何一項**——在今天的模型下就有價值（今天使用者根本看不到自己有幾台裝置）。
- 偵測 ≠ 防禦，但 §4 顯示連 Signal 都只做到這一層。

### 6.7 ⚠ 這條路關不掉的三件事（誠實邊界）

**1. 🔴 論文那個攻擊只在部分平台被擋掉（2026-07-31 更正）。**

~~live 配對擋的是「抽走長期祕密後離線操作」——正是 §4 論文那個攻擊，這是實質進展。~~

**更正**：擋不擋得住，取決於**裝置簽章金鑰能不能被抽走**（§6.2b-1）：

| 平台（ADR-0297 §6 分級） | §4 論文攻擊 |
| --- | --- |
| **L2**：Android StrongBox/TEE、iOS、Apple Silicon Mac、有 TPM 的 Windows | **擋得住**（金鑰不可匯出） |
| **L1／L0**：瀏覽器、無 TPM 的 Windows、Intel Mac、**Linux** | 🔴 **仍然成立**——抽走裝置金鑰即可離線簽出 `v+1` |

⇒ **不得宣稱「我們解決了論文的攻擊」。** 誠實的說法是
「**在具備不可匯出金鑰的平台上擋得住；其餘平台是分級保障**」——
與 ADR-0297 §6 的紅線一致（降級必須可見、設定頁要如實顯示本機在哪一級）。

**1b. 而在任何平台上，入侵當下的窗都關不掉。** 攻擊者若有裝置上的**執行權**
（惡意程式、而非只是抽走祕密），他可以直接請 TPM/SE 簽（ADR-0297 §5：
裝置綁定金鑰擋離線攻擊，**不擋以你的身分正在執行的惡意程式**），
也可以直接操作配對 UI——**而 SAS 是他自己跟自己比對的**（§6.2b 更正框）。

⇒ **因此 E-lite 是承重結構，不是加分項。** 這一層防不住的，只能靠偵測與移除。
⇒ 也因此 **F（新裝置延遲 N 小時生效）值得一併採用**：它把偵測變成否決權。
⇒ 定性上與 §4.2 的 Signal 立場相同——差別在**我們把它放進威脅模型並誠實揭露**，
   而不是劃出範圍外（同 ADR-0278／0287 的立場）。

**2. SAS 四位數（10⁴）在新用途下偏薄。** 見 §6.2b 末。

**3. 中繼可扣住清單更新。** §3.4 的版本搭便車緩解（要扣撤銷就得連訊息一起扣，
而訊息不到是看得見的），但仍是 best-effort ⇒ 這正是選項 E（社交見證）針對的面。

## 7. 清單住在哪：⚠ 未決策的分歧（兩個先例互相衝突）

§3.3 定了清單的資料結構、§6 定了誰有權簽，但**清單放在哪、給誰看**仍未定。
查證後這不是一個可以順手決定的細節——**專案既有兩個先例指向相反方向**，
且其中一邊會撞上 ADR-0302 剛立下的非目標。**本節刻意不做選擇。**

### 7.1 先例一致的部分（可直接沿用，非分歧）

- **§3.4 的版本搭便車已有實作先例**：`subkey.ts:92` `withEkHint()` ——
  EK 就是「公告事件當**發現**管道、rumor tag 當**帶內同步**管道」。裝置清單版本號照此形狀即可，非新機制。
- **可取代事件的決勝規則**已由 ADR-0099 §2 統一（`created_at` 較新者勝、相同時 id 字典序較小者勝），
  跨中繼收斂一致——單調版本清單可直接搭這條。

### 7.2 ⚠ 硬約束：預金鑰與清單**必須分層**，否則冷金鑰變熱

**預金鑰輪替頻率 ≫ 裝置清單變動頻率**（前者週期性，後者一年幾次，§6.4）。
若把預金鑰塞進「身分金鑰簽的清單」內，**每次輪替預金鑰都要動用救援碼** ⇒ §6 的 C 當場崩潰。

```
裝置清單事件   身分金鑰簽   罕見      → 只列 device pubkeys
      ↓ 信任鏈
預金鑰事件     各裝置自簽   常態輪替   → author = device pubkey
```

附帶性質：**裝置可保存簽好的清單 blob、開機原樣重播**（簽章涵蓋內容，重播同一顆事件即可）
⇒ 解決 7 天 TTL（ADR-0065）需定期重發的問題，而**不必把冷金鑰拿出來**。

**這一條不是分歧，是任何方案都得遵守的約束。**

### 7.3 分歧的根源：兩個先例，相反方向

| | 做法 | 理由 |
| --- | --- | --- |
| **ADR-0061** 顯示名稱 | ❌ 拒絕公開 kind 0，改 **Gift-Wrap 扇出給聯絡人** | 「名字 ↔ npub 的對映公開給中繼站與任何人，違反隱私鐵則」 |
| **ADR-0245** EK 公鑰 | ✅ **公開明文**可取代事件 kind 10040（IK 簽章、`content` 不加密，`subkey.ts:62`） | ADR-0099 §4：「**可取代事件維持公開扇出**」 |

可歸納的區分原則：**公開的是密碼學材料**（隨機公鑰，本身不洩漏關於你的事實），
**不公開的是可識別資訊**（名字）。

⇒ **裝置清單正好落在中間**：裝置公鑰本身是隨機值（像 EK），
但**基數與拓樸不是**——「這個人有 3 台裝置」「這 3 把金鑰屬於同一人」是**關於你的事實**，
性質上更接近名字那一類。**這就是分歧無法自動化解的原因。**

### 7.4 三個選項

| | 方案 | 陌生人可發起？ | 裝置數對外 | 主要代價 |
| --- | --- | --- | --- | --- |
| **1** | 公開可取代事件（比照 10040） | ✅ | **公開給任何人** | 隱私退步 |
| **2** | 加密扇出給聯絡人（比照 0061） | ❌ | 只給聯絡人 | O(N)/次變動；離線 >7 天漏掉需開機廣播（0068 形狀）；**打破 ADR-0121 訊息請求**——對方不知 device pubkeys 即抓不到預金鑰，無法建立 X3DH |
| **3** | 分層降級：陌生人走現行靜態 ECDH，接受為聯絡人後才升級棘輪 | ✅ | 只給聯絡人 | **兩套並存＝降級面** |

### 7.5 ⚠ 為什麼這是分歧而非選擇題

**選項 3 在隱私上最好，但它與 ADR-0302 剛立下的〈非目標〉直接衝突。**
0302 明確排除「使用者可設的 FS 模式」，理由是：降級面隨模式數成長、
審計面加倍（與 0290 §2 相反）、**群組混模無法誠實呈現（強度＝最弱成員）**。
那些理由在這裡**一字不差地適用**——差別只在觸發模式切換的是「對方是否為聯絡人」而非使用者設定。

⇒ 採選項 3 等於部分推翻 0302 的非目標。**這不該由本 ADR 單方面決定。**

兩個立場各自成立：

- **以 ADR-0302 立場優先 → 選 1**：「EK 公告已經公開了密碼材料，裝置清單是同一類。」
- **以 ADR-0061 立場優先 → 選 3**：「裝置拓樸是可識別資訊，不是隨機公鑰。」

### 7.6 ⚠ 基準線修正：今天已經洩漏了什麼（程式碼查證）

評估「選項 1 是不是新洩漏」之前得先知道基準線。**協定層今天沒有裝置清單**
（§6.2 選項 D）：定址按身分不按裝置——所有裝置共用 nsec，一顆定址給你 npub 的
Gift Wrap **每台都解得開**（自封副本 ADR-0107 即靠此運作）。本機只有
`storage/device-id.ts` 的 16 hex `nb.deviceId`，全專案僅一個使用點，不構成清單。

**但雲端快照在中繼上已構成事實上的裝置清單**（`packages/core/src/snapshot.ts:25-36`）：

```ts
kind: SNAPSHOT_KIND,
tags: [["d", deviceId], ["expiration", …]],    // ← d tag 明文
content: encryptDM(plaintext, sk, getPublicKey(sk)),
}, sk);                                         // ← 用真實 sk 簽，非一次性金鑰
```

作者＝真實 pubkey、`d` 明文、可尋址事件按 `(pubkey, kind, d)` **一台一顆**
⇒ 中繼手上就有「此 npub 有 N 台裝置、各自 deviceId 與最後備份時間」。
閘門 `relay/src/relay-core.ts:473` 擋的是**別人讀**、且**僅在 `requireAuth` 時**生效——
不擋中繼自己知道；開放中繼上連陌生人都數得出來。

| 對象 | 今天已洩漏裝置數？ |
| --- | --- |
| 中繼（已開雲端同步） | **是**——`d` tag 就在那裡 |
| 中繼（未開雲端同步） | 否 |
| 公眾／陌生人（AUTH 中繼） | 否 |
| 公眾／陌生人（開放中繼） | 是（若已開雲端同步） |

⇒ **選項 1 對「中繼」不是新洩漏，對「公眾」是**；且會把洩漏從
**opt-in 的雲端同步使用者**擴大到**全體使用者且無法關閉**（預金鑰是棘輪的必要條件）。
**這比原先的評估更不利於選項 1。**

### 7.7 撰寫者傾向（非決策）＋其理由的更換

原傾向選項 1 的理由是「預金鑰發布已洩漏裝置數 ⇒ 清單再藏也藏不住」。
經 §7.6 修正，**該理由只對中繼成立、對公眾不成立**，強度顯著下降。

**但 §8.5 提供了一個更有力的新論據**：選項 2／3 對「未知裝置的第一則訊息」存在
**結構性死鎖**——你需要清單才認得出他，卻要先認得出他才收得到清單。
這不是隱私取捨，是功能上解不開的環。

⇒ 傾向**維持選項 1，但理由已更換**：不再是「隱私沒損失」（那是錯的），
而是「選項 2／3 有結構性死鎖」。**隱私代價（對公眾公開裝置數）是真實的，必須誠實承擔**，
不得以「反正已經洩漏了」搪塞。

⚠ 仍未驗證的前提：「預金鑰是否真的必須公開」。若預金鑰能只給聯絡人，
選項 3 就真能藏住基數，代價是陌生人只剩靜態 ECDH 一途（且 §8.5 的死鎖仍在）。

## 8. 裝置歸屬：定義是簡單的，工作量在正規化收口

### 8.1 歸屬的定義＝簽章清單的包含關係

```
身分公鑰 (npub)          ← 使用者可見、群組成員、封鎖名單、安全碼
   └─ 簽 ─→ 裝置清單 { v: 6, devices: [dpk₁, dpk₂, …] }
                └─ 各裝置自簽 ─→ 預金鑰事件（author = dpkₙ）
```

給定裝置公鑰 `dpk`：**`dpk` 屬於 `IK` ⟺ `IK` 當前簽章清單包含 `dpk`**（驗簽後）。
沒有別的判準。§7.2 的兩層結構已經把這條信任鏈定好。

### 8.2 ⚠ 真正的工作量：`openWrap()` 的 sender 語意會改變

`openWrap()` 回傳 `sender = seal.pubkey`。**今天那是身分公鑰；per-device 之後是裝置公鑰。**
而 `relay-backend.ts` 有二十餘處拿 `sender`／`from` 去比對**身分層**集合。查證出的斷點：

| 位置 | 檢查 | per-device 之後 |
| --- | --- | --- |
| `relay-backend.ts:1630` | `isBlocked(sender)` | **封鎖失效**——被封鎖者換一台裝置即繞過 |
| `relay-backend.ts:1942` | `canPostToGroup(g, sender)` | **合法成員被當非成員拒收**（`members` 是身分） |
| `group.ts:259/264/270` | `from !== group.admin` | **管理員從第二台裝置管不了成員／快照被拒** |
| `relay-backend.ts:2887` | `group.members.includes(from)` | 群組回條被丟棄 |
| `relay-backend.ts:1730` | `contacts.find(c => c.pubkey === sender)` | 個人檔更新對不上人 |
| `relay-backend.ts:1259` | `contacts.some(c => c.pubkey === from)` | 陌生人判定錯誤 |

⚠ **這些全是靜默失敗**——不拋錯，只表現為「訊息莫名不見」或「封鎖沒用」。
這正是 ADR-0027 §129 警告過的同一種形狀（「這個 bug 已經以同一個形狀出現過三次」）。

### 8.3 架構解法：單一正規化收口

**不要讓裝置公鑰流進下游。** 在 `openWrap()` 之後、**任何授權檢查之前**插一道解析：

```
openWrap → sender = dpk → resolveIdentity(dpk) → sender = IK → 既有全部邏輯不變
```

⇒ 封鎖／群組成員／admin／回條／聯絡人**一行都不必改**，繼續活在身分層。

解析失敗（未知裝置）時**複用 ADR-0131 的形狀**：不丟棄，緩存起來，
抓到該身分的裝置清單後 `drain` 重放。與「群訊比 group-create 先到」同一個問題形狀，
連有界／去重的紀律都可沿用。

### 8.4 三條紅線

1. **使用者看到的永遠是身分，不是裝置。** 安全碼／npub 維持身分層；
   若 UI 開始顯示裝置公鑰，使用者就得驗證 D 把金鑰而非 1 個身分
   ——那是把密碼學細節洩漏給使用者，並撞上 ADR-0055（分身不可連結）／0138（多身分）的語意。
2. **群組成員資格維持身分層。** `Group.members: PubkeyHex[]` 不改；
   只在**扇出那一刻**展開 identity → devices。ADR-0027 的「移除即下次扇出略過」原封不動。
3. **回條要收斂回「人」。** ADR-0095 的「已讀 M/N」若按裝置計，N 會變成裝置總數，語意即錯
   （一人兩台不等於讀了兩次）。須在套用回條前 collapse 回身分。

### 8.5 ⚠ 未知裝置的第一則訊息：選項 2／3 的結構性死鎖

陌生人、或聯絡人剛加的新裝置發訊來時，你手上沒有他的清單 ⇒ **無法歸屬**。

Signal 的答案是 **sealed sender certificate**（伺服器簽發、綁定帳號/裝置/身分金鑰，
放進密封信封，收端以伺服器公鑰驗）。我們沒有伺服器 ⇒ 只能靠**身分簽的清單**，
**前提是拿得到**。

可行補救：rumor 帶一個 IK hint（自稱身分，比照 `EK_HINT_TAG` 的形狀），
收端拿它當「去哪裡查」的線索、抓清單後驗證。**自稱不可信，但當索引可用。**

⇒ **但這會繞回 §7 的分歧**：清單若走選項 2／3（加密扇出給聯絡人），
未知裝置的歸屬就**解不開**——需要清單才認得出他，卻要先認得出他才收得到清單。

⇒ **這是支持選項 1 的新論據，且強度高於「裝置數反正藏不住」**：
後者只是主張隱私沒損失（且 §7.6 已證明那對公眾不成立），
這一條主張的是**選項 2／3 有功能上解不開的環**。

## 後果

- 正面：
  - 若 §1 引述屬實，**棘輪的前置成本比六份 ADR 假設的小一個數量級**，
    且 0015/0072 的救援通道不必為 FS 而犧牲。這會實質改變 ADR-0290 的補課路徑排序。
  - 把「撤銷無權威」從**我方缺陷**重新定性為**公開未解問題**（Signal 亦然），
    避免用一個沒人解得掉的標準來否決自己的方案。
  - 釐清裝置目錄與組織名冊同類，可直接複用既有的權威對帳模式，不必新設計 CRDT。
  - **§3.4 的版本搭便車比 Signal 的 409 迴圈更耐扣留**：Signal 的裝置清單是**獨立**向
    伺服器取的，伺服器扣住更新可以悄無聲息；我們的版本號跟著訊息本體走 ⇒
    中繼要扣住撤銷就得連訊息一起扣，而**訊息不到是看得見的**。
    這一格我方設計優於 Signal，是「沒有權威」意外換來的性質。
- 負面／代價：
  - **O(N×D) 扇出**（§1.3）：三人群組每人兩台＝一則訊息 `(N-1)×D + (D-1)` 顆事件。
    回條在 0263 已是 O(N²)，再乘 D² ⇒ 會壓縮 `GROUP_RECEIPT_LIST_MAX = 5` 的門檻。
  - **新洩漏（接 ADR-0237）**：扇出爆發原本只洩漏群組成員；per-device 之後，
    同一次爆發**同時洩漏每位成員的裝置數與拓樸**（哪幾把金鑰屬於同一人）。
    per-device 在 crypto 層讓裝置不可連結，扇出形狀又把它們接回去 ⇒
    印證 0237「無傳輸層匿名前，crypto 層混淆對託管中繼幾乎不付出實質效益」。
  - **審計面擴大**，與 ADR-0290 §2「縮小審計範圍」的方向相反。
  - 本文**不解決任何現存的使用者問題**；買的是未來路徑的正確性。

- 未估算 §3.4 版本號搭便車對事件體積與 0109 流量預算的影響（應該很小，但沒算）。
- **§6.4 的「頻率」未量化**：一般使用者一年增刪幾次裝置沒有數據，而
  「接受現狀」這條路的成立與否完全取決於它。
- **「清單住在哪」為未決策分歧**（§7）：兩個既有先例（0061 加密扇出／0245 公開可取代）
  指向相反方向，且選項 3 會部分推翻 ADR-0302 的〈非目標〉。**本文刻意不選。**
- **§7.7 傾向所依賴的前提「預金鑰是否必須公開」未驗證**——這是決定 §7 分歧的關鍵事實，
  且**不需要等 signal.org 原文**即可由我方協定推導。應優先於其他待核項處理。
- **§8.2 的斷點表以 grep 掃出，未逐一追完呼叫鏈**——實際受影響處**可能更多**
  （尤其 UI 層與行動端）。真要實作前應以型別手段強制（例如把身分公鑰與裝置公鑰
  做成**不同的 branded type**，讓編譯器找出全部斷點），而非靠人工掃描。
- **§6.2 的 C 與 ADR-0245 §2 存在張力**：救援碼從「只讀救援憑證」升級為「簽發憑證」後，
  其外洩後果變重——今日外洩＝歷史被解；之後外洩＝攻擊者可把自己加進裝置清單，
  取得**所有未來通訊**。0245 把 EK 排除於備份碼外是為了 FS，本提議在某種程度上反向拉。
  未評估此張力是否需要 0245 的修訂。
- 我的訓練資料截至 2026 年 5 月。
