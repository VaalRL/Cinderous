# 0276. 錨點全失聯的自動備援：帶外簽章清單＋確定性收斂（不靠通知對方）

- 狀態：提議中（設計定案，尚未實作）
- 日期：2026-07-29
- 相關文件：ADR-0039（錨點＋帶內簽章清單）、ADR-0034（Relay Pool／`REDUNDANT_K`）、
  ADR-0036（hint 陳舊）、ADR-0188/0239（維護者信任根、信任根移出 CI）、ADR-0092（一致性稽核）、
  ADR-0275（客戶端健檢）、ADR-0189（第三座錨點宜換平台）、
  `docs/research/public-relay-fallback.md`

## 背景與問題

目前的容錯拓樸有一個**在最需要時失效**的環節：

- 錨點是**硬編碼**的（`ANCHOR_RELAYS`，2 座，且**都在 Cloudflare**——ADR-0189 已記平台單點）；
- 動態調整靠**帶內**簽章清單（kind 10037，經中繼發佈）——**中繼全掛時就拿不到**。

也就是說：**備援清單最需要被取得的時刻，正是它取不到的時刻。**

### 直覺解法的致命缺陷

自然的想法是「錨點掛了 → 上網找一座公有 relay → **通知對方換過去**」。
但**通知不可能送達**：訊息、離線信箱、WebRTC 信令**全部都要經過中繼**——那正是剛失去的通道。
（唯一例外是已建立的 WebRTC 資料通道，只涵蓋「當下正在通話／傳檔的對象」，救不了一般情況。）

## 考量的選項

- **A：出事後才向對方協調新 relay**——**否決**，見上：沒有通道可協調（雞生蛋）。
- **B：把公有 relay 直接寫進硬編碼錨點**——**否決**：等於預設就把元資料交出去，且無法更新。
- **C：帶外簽章清單＋確定性收斂（採納）**——雙方各自跑同一套演算法、吃同一份輸入，
  **自動落在同一組 relay，零協調訊息**。

## 決策

### 1. 收斂而非通知

雙方**各自**執行相同流程即自動相遇：

```
錨點全失聯 → 各自取得同一份備援清單 → 各自以同一規則排序 → 各自連前 K 座 → 相遇
```

**不要求精準收斂到同一座**：沿用既有 `REDUNDANT_K`（ADR-0034/0039），雙方各自**同時連前 K 座**，
只要**有交集**即通。這比要求「兩邊選一模一樣」穩健得多——兩人的網路狀況與健檢結果本就可能有差異。

### 2. 清單走**帶外**通道，且**必須驗簽**

- **通道**：官網靜態檔（新增 `docs/fallback-relays.json`，比照 `releases.json`／`threat-intel.json`
  已有的 `siteFile()` 取得模式——**現成、零新增基礎設施**）。
- **驗簽**：清單內容為維護者簽章的 kind 10037 事件，客戶端以硬編碼的 `MAINTAINER_PUBKEY`
  經既有的 `verifyRelayList()` 驗證後才採用。

**這一條是本 ADR 的安全核心**：「即時從網路上取得 relay 網址」若不驗簽，
**誰控制那份清單就能把所有使用者導向他控制的中繼**——那是**主動攻擊**，
遠比公有站的被動元資料洩漏嚴重。有了簽章，**來源（官網／任何鏡像）被入侵也無法改寫清單**，
與 ADR-0239 把信任根移出 CI 的立場一致。

### 3. 緊急選座**只驗 liveness**，行為健檢在背景補

完整一致性探測每項最長 8 秒且**會寫入事件**（ADR-0275）；錨點掛掉時使用者要的是**趕快通**。
故：緊急路徑只做 liveness 排序；ADR-0275 的行為健檢在背景補跑，結果只影響 UI 徽章與**下次**排序。

### 4. 觸發、退出與 UI

- **觸發**：Tier 1 全部失聯 ≥ 5 分鐘（沿用 `RELAY_STALE_MS` 語意，避免抖動誤觸）
  **且使用者事先於設定同意**——隱私降級**絕不靜默發生**。
- **企業身分不適用**：企業是 allowlist 封閉節點（ADR-0044/0048），公司政策可全域禁止。
- **UI 常駐標示**降級狀態（非一次性提示）：「目前走公共中繼，元資料保護降級」。
- **退回錨點是簡單方向**：錨點硬編碼、雙方一致 → 各自定期重試，一通就切回，**天然收斂**。

## 理由

把「協調」換成「確定性收斂」，繞開了無通道可用的死結；`REDUNDANT_K` 的交集策略讓收斂不必完美。
帶外通道解掉「帶內清單在中繼掛掉時拿不到」的根本矛盾，而簽章讓新增的通道**不新增信任**——
這是整個設計能成立的前提。緊急路徑捨棄深度健檢是刻意的取捨：**斷線期間，速度就是可用性**。

## 後果

- **正面**：錨點全掛時仍有恢復通訊的路徑，且不需要任何協調訊息；清單來源被入侵無法導流；
  換回錨點天然收斂；重用既有的 `verifyRelayList`／`REDUNDANT_K`／`siteFile()`／ADR-0275 健檢。
- **負面 / 已知殘餘風險**：
  - **審查情境仍可能失效**：若連官網也被封鎖，第 2 步取不到清單。故本機制與
    **「補第三座換平台的錨點」（ADR-0189）互補而非替代**——後者才是對「Cloudflare 全掛」
    這個最可能斷線原因的直接解。
  - 降級期間元資料保護僅剩 Gift Wrap 一層（研究文件 §2 已詳列）。
  - 備援清單的維護者需持續確認清單內的公有站仍存活（清單陳舊＝備援失效）。
  - 雙方若在不同時間進入／退出降級，仍可能短暫錯開（`REDUNDANT_K` 交集與定期重試緩解）。
