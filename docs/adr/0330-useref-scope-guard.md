# ADR-0330：`useRef` 也要被分類——階段 0 的最後一塊

- 狀態：已採用
- 日期：2026-08-04
- 關聯：ADR-0294 §2／Phase P4、ADR-0328（互動測試）、ADR-0329（世代守衛）

## 1. 兩支既有守衛都看不到 ref

| 守衛 | 掃什麼 |
| --- | --- |
| `MobileApp.perIdentityState.test.ts`（ADR-0294 §2） | `const [x, setX] = useState` |
| `MobileApp.asyncEpoch.test.ts`（ADR-0329） | `.then(` 回呼裡的 setter |

**`useRef` 兩支都不在射程內。** 而 ref 一樣存得下 per-identity 的東西，且它**不隨 render 重來**——切身分時沒人碰它，它就原封不動地跟著新身分走。

## 2. 這支測試的直接理由：我自己漏了

盤點 Phase P4 時，我用 `const .*Ref = useRef` 去數，得到 **12 個**，結論是「都安全」。

那個 regex **漏掉三個不以 `Ref` 結尾的**——`pairDecision`、`statusBcTimer`、`typingTimer`。實際是 **16 個**。

三個之中兩個剛好已經在 `signInWith` 裡被清（計時器類），一個沒有（`pairDecision`）。

🔴 **靠命名慣例做安全稽核，就是這樣漏的。** 而且它會漏得很安靜：所有測試都綠，稽核報告寫「都安全」，錯的只是取樣。

## 3. 決策

掃描器**不看名字**，只看每一個 `useRef` 有沒有落進三類之一：

1. **render 期鏡像**——在元件本體最外層由 state 指派（`activeIdRef.current = activeId;`）。它每次 render 跟著 state 走，而 state 已由 ADR-0294 §2 的守衛保證會重設 ⇒ 天然安全。
2. **切身分時被清**——`signInWith` 內出現 `<name>.current`。
3. **明列為裝置／外殼層**——例外清單，且**必須寫下理由**（少於 10 個字元就算沒寫）。

不在三類之內就紅。形狀與另外兩支一致，也與 `sub-plan.ts` 的「續取策略＝宣告必填項」同源：**把「想過了沒」變成型別系統以外的必填欄位。**

另外釘住兩條具體的：計時器類的 ref 必須在切身分時 `clearTimeout`（否則上個身分排的計時器會在新身分身上響），以及那三個漏網的回歸。

### 順手修的一處

`pairDecision`（配對 SAS 的確認回呼）過去不在任何一類裡。已在 `signInWith` 內清空——上個身分那場配對的回呼不該還接在新身分身上。影響很小（配對是外殼流程、promise 多半已結算），但它是**未分類**的，而未分類正是這支測試要消滅的狀態。

## 4. 掃描器自己驗自己

餵一段合成的、沒被分類的 ref 必須被標出來；三條出路（鏡像／`signInWith` 清除／例外清單）各自都要能讓它變乾淨。

**否則它綠著也不代表任何事**——掃描器寫壞了同樣會全綠，那時它只是個裝飾。同 ADR-0329 的做法。

## 5. 買不到什麼

1. **擋不住「分錯類」。** 例外清單是人寫的；把一個真正 per-identity 的 ref 塞進去並編個理由，測試照樣綠。擋得住的是**忘了想**。
2. **`useEffect` 內部的可變閉包變數不在範圍。** 目前 5 個 effect 都沒有這種寫法。
3. **不是行為測試。** 同 ADR-0329 §4-1：這裡驗的是「每個 ref 都被處理過」，不是「切身分時真的沒有殘留」。

## 6. Phase P4 階段 0 至此完成

| 盲點（ADR-0328 §2） | 狀態 |

| 1. 分錯類 | 🟡 ADR-0328 由 UI 行為雙向驗證（per-identity 不得殘留／裝置層必須保留） |
