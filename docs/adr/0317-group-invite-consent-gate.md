# 0317. 誰可以把我加進群組：入群邀請的同意閘門

- 狀態：已接受
- 日期：2026-08-03
- 相關文件：**ADR-0121（訊息請求——本 ADR 是它明列的待辦：「沒有『只接受聯絡人訊息』的
  全域開關——留給使用者選項的 ADR」）**、ADR-0027 §安全強化補述（入群同意 #1 與其殘餘）、
  ADR-0131（早到群訊的緩存與重放，本 ADR 沿用同一形狀）、ADR-0242 階段③（跨裝置同步設定）、
  `packages/engine/src/backend/relay-backend.ts`

## 背景與問題

今天把你加進群組的守門只有兩道（`applyControl`）：

```js
if (this.isBlocked(from)) return;                              // 沒封鎖就過
if (!control.members.includes(this.self.pubkey)) return;        // 你要在名單內
```

**沒有「必須是聯絡人」這道檢查。** 任何知道你 npub 的陌生人發一顆 `group-create`，
那個群組就直接出現在你的清單裡。

兩份既有 ADR 都記過這件事，都沒解：

- ADR-0027 §安全強化補述的殘餘：「陌生人仍可對你**發起**一個含你的群」。
- ADR-0121 已知限制：「群組邀請不走請求流程：把你拉進群組的人若不是你的聯絡人，
  群組仍會直接出現。」以及「沒有『只接受聯絡人訊息』（白名單）的全域開關——
  **留給使用者選項的 ADR**。」

而 ADR-0121 為 DM 立的門檻（陌生人的訊息進請求區、碰不到你的任何注意力管道）
在群組這扇門上完全不成立——**同一個陌生人，走 DM 進不來，走群組直接進來**。

## 考量的選項

- **選項 A：一律禁止非聯絡人邀請（無設定）。** 有真實情境會壞掉：同事把你拉進工作群，
  而你還沒把他加進聯絡人。硬擋＝拿走一個正常用法。否決。
- **選項 B：維持現況（任何人都能邀）。** 就是本 ADR 要解的問題。否決。
- **選項 C：群組邀請自成一個「邀請請求區」UI。** 最完整，但要一整套新的清單／接受／
  拒絕介面。與 ADR-0121 已有的請求區並列兩個「待處理的陌生人」清單，對使用者是重複概念。
  否決（可作為日後演進）。
- **選項 D（採用）：可設定的閘門 ＋ 擋下時走既有的訊息請求區**。

## 決策

1. **新增設定「誰可以把我加進群組」**，兩態：
   - `anyone`（**預設**）：任何人都可以，即今日行為。
   - `contacts`：只有聯絡人可以（**選用的嚴格模式**）。
2. **存在跨裝置同步設定**（ADR-0242 階段③ 的 `SyncedPrefs`，鍵 `groupInvite`）。
   理由：這是**身分層級的隱私決定**，不是某台裝置的偏好——在手機上設嚴格、桌面卻仍照收，
   等於沒設。沿用既有的逐鍵 LWW，不新增機制。
3. **預設維持 `anyone`（不收緊既有行為）。**

   ⚠ **本 ADR 初稿選的是相反的預設，實作後被測試推翻，這裡記錄過程。**

   初稿的理由是「被收緊的不是使用者的能力，是別人對你做的事」。實作完跑全庫測試，
   **17 個既有測試變紅**——全部是「A 建群、B 與 C 收到」這類最基本的群組流程。原因是
   **加聯絡人在本專案是單方面的動作**（ADR-0121：「加好友是純本地、單方面的動作」）：
   Alice 把 Bob 加進自己的聯絡人，**不代表 Bob 的聯絡人裡有 Alice**。而 Bob 收到 Alice
   的 DM 時，Alice 只會進 Bob 的**請求區**。

   ⇒ 在嚴格預設下，「同事把你拉進工作群」這個**最正常的用法**會被大量擋下，
   而使用者完全不知道要去請求區接受誰。那不是測試寫壞了，是預設值選錯了。

   ⇒ 改為：**保留既有行為為預設，嚴格模式作為使用者可選的加強**。這也更貼近
   使用者的原始要求——他要的是「**可設定**」，不是「預設要嚴」。
4. **擋下 ≠ 丟掉。** 被擋的邀請：
   - **緩存**（有界、FIFO，比照 ADR-0131 的 `pendingGroupMsgs` 形狀）；
   - 邀請者走 `ensureKnown()` 進**訊息請求區**——他就是「一個想聯繫你的陌生人」，
     那正是 ADR-0121 那塊 UI 的用途，不另立第二個待處理清單；
   - 發 `onGroupInviteHeld` 供 UI 提示。
5. **接受請求＝邀請生效**：`acceptRequest(pubkey)` 時把該人緩存的邀請重放（實例化群組）。
   語意與 ADR-0121 §4「你主動聯絡的人就是聯絡人」對稱——**你接受的人就能拉你進群**。
6. **封鎖仍然是最高優先**：`isBlocked` 的檢查不動，設定成 `anyone` 也擋得住封鎖者。

## 理由

- **同一個陌生人不該有兩種待遇**。DM 走請求區、群組長驅直入，是同一個威脅模型下的不一致。
- **重用請求區而非新造 UI**：使用者只需要理解一個概念（「有陌生人想聯繫我」），
  而接受的動作與後果（成為聯絡人）也完全相同。
- **緩存而非丟棄**：丟棄的話，使用者日後接受了那個人，群組也回不來，而邀請者以為你在群裡——
  那是 ADR-0121 §5「錯過就沒有第二次」的同一類問題。

## 後果

- 正面：ADR-0121 與 ADR-0027 各自記下的殘餘同時關閉；群組不再是繞過 DM 同意門檻的側門。
- 負面 / 已知殘餘風險：
  - **緩存只在記憶體、有界**（比照 ADR-0131）。App 重啟後未處理的邀請會消失，
    需邀請者重邀。持久化留待有實際需求再說。
  - **請求區仍可被灌爆**（ADR-0121 已知限制）：現在多一條灌爆路徑（群組邀請）。
    數量上限／速率限制仍未做，屬 ADR-0121 已記的同一項待辦。
  - **預設不變＝洞仍然開著**，除非使用者主動去開嚴格模式。這是本 ADR 最大的殘餘：
    保護只給找得到那個開關的人。若日後有實際的濫用回報，應重新評估預設值——
    屆時的正確做法**不是**直接翻預設，而是先解決「單方面加聯絡人」造成的誤擋
    （例如把「我已接受過他的請求」也算進白名單）。
  - 開啟嚴格模式後，「非聯絡人的同事拉你入群」會多一次接受動作。這是選了嚴格的人的取捨。
- 後續行動 / 待辦：
  - 若日後需要，可把緩存持久化，或升級為選項 C 的獨立邀請清單。
