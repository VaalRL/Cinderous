# 0345. 送檔管線串流化（第一階段）：兩端各砍掉一份整檔複製

- 狀態：已接受（第一階段；真正的「不落 RAM」見 §後續行動）
- 日期：2026-09-15
- 相關文件：ADR-0017（WebRTC P2P 檔案傳輸）、ADR-0029（二進位分塊框架）、ADR-0344（ICE 路徑判定與大檔把關）、ADR-0111（OPFS 封存）、`packages/core/src/datachannel.ts`、`packages/engine/src/backend/webrtc.ts`

## 背景與問題

`DEFAULT_MAX_FILE_SIZE` 是 100 MiB，而那個數字不是產品決策——**是記憶體逼出來的**。實際量一下一個 100 MiB 檔案在兩端佔多少：

**送出端（約 3 份）**
1. `App.tsx` `await f.arrayBuffer()` → 整檔第 1 份。
2. `encodeFile()` **一次把全部分塊框架都配置出來**再回傳 → 第 2 份（16 KiB 分塊 ⇒ 6,400 個框架物件），而它們唯一的用途是等著被逐一送出。
3. `new Blob([bytes])` 做本機 blob URL → 第 3 份。

**接收端（約 2 份）**
1. `DataChannelReceiver` 把每一塊留在 `Map<seq, Uint8Array>` 裡 → 第 1 份。
2. 收滿後 `new Uint8Array(size)` 再逐塊拼進去 → 第 2 份。

⇒ 天花板拆不掉，不是因為協定有上限，是因為**同一份資料被複製了好幾遍**。ADR-0344 已經把「大檔會不會不知情地經 TURN 送出」這個閘門補上，可以開始動這一層了。

本 ADR 做**可以在不改動 `OutgoingFile`／`ReceivedFile` 契約前提下拿掉的兩份複製**，並修掉背壓的輪詢。真正的「整檔不進 RAM」需要把收檔改成 sink 介面，那會擴散到儲存槽、縮圖、relay 暫存等路徑，留待下一階段（§後續行動）。

## 考量的選項

- **選項 A（採用）：分階段。** 先拿掉純屬多餘的兩份複製（不改對外契約），再另案改 sink。
- 選項 B：一次做到底（`onFile` 改成串流 sink）。收益最大，但 `ReceivedFile.bytes` 有三條消費路徑（P2P、ADR-0162 relay 分塊重組、ADR-0161 公司儲存槽）外加縮圖與桌面/行動各自的落盤，一次改完等於同時動五個地方，且其中兩條沒有端到端測試。
- 選項 C：只把天花板調高。最省事也最不負責——記憶體行為沒變，只是把 OOM 往後挪。

## 決策

**一、送出端：分塊惰性產生**

`encodeFile` 由回傳陣列改為 **generator**。同一時間只有一塊框架存在，送出後即可回收 ⇒ 上面的第 2 份消失。

呼叫端照舊 `for...of`；需要陣列的地方（測試）自行 `[...encodeFile(...)]`。`webrtc.ts` 的 pump 改為消費迭代器。

**二、送出端：背壓改事件驅動**

原本 `bufferedAmount` 超過高水位就 `setTimeout(pump, 50)`。改為掛 `bufferedamountlow` 事件，並把 `bufferedAmountLowThreshold` 設在高水位的一半——等它**全空**才續傳會讓管線一鬆一緊、吞吐掉一截；留一半在路上，續傳時網卡不會有空窗。

⚠ **保險計時器（250 ms）**：`bufferedamountlow` 只在 `bufferedAmount` **下降穿越**門檻時觸發。若它恰好在「我們檢查」與「掛上監聽」之間就降下去了，那一次觸發就錯過了——而錯過的後果是**傳輸永久卡住且不報錯**，是檔案傳輸最糟的失敗型態。保險計時器把「可能永久卡住」換成「最壞多等 250 ms」。**這不是輪詢**：事件一到就清掉，正常傳輸中它一次都不會觸發。

**三、接收端：單一緩衝區直寫**

不再逐塊留存後重拼。`file-begin` 新增 `chunkSize` 欄位，收端據此把每塊**直接寫進最終緩衝區的 `seq * chunkSize` 位移** ⇒ 上面的第 1 份消失，且**亂序送達的既有契約不變**（ADR-0017 起就有那條測試）。

- **舊版對端沒有 `chunkSize`** ⇒ 退回「依到達順序循序寫入」。資料通道是可靠且**有序**的，正常情況等價；真的跳號時**中止並報錯**，不靜默寫錯位置。ADR-0029 已載明分塊格式是 Buddy P2P 內部協定、無外部相容顧慮。
- `chunkSize` 是遠端可控欄位 ⇒ 只接受正整數，不合理即當作沒給。
- 新增「序號必須落在宣告範圍內」。這條讓「收滿 N 塊」**等價於**「每一塊都到齊」——舊版是收滿之後再逐一檢查有沒有洞，現在是不可能有洞。
- 去重改用 `Set<number>`（存的是數字，不是位元組）。

🔴 **緩衝區延後到第一塊才配置。** 在 `file-begin` 就配置很誘人（程式更短），但那等於讓對方**一個位元組都不用送**就吃掉 `size` 的記憶體——`maxConcurrentFiles` 16 × 100 MiB ＝ 1.6 GB，免費。延後配置把成本拉回「他得真的送資料」，與改動前一致。

**四、天花板不動**

`DEFAULT_MAX_FILE_SIZE` 維持 100 MiB。收檔峰值從約 2 份降到約 1 份是實質改善，但**整檔仍然進 RAM**——在收檔改成串流落盤之前調高上限，只是把 OOM 往後挪（選項 C 被否決的同一個理由）。

## 理由

- **行為不變，只是不再多複製一份。** 既有的往返一致、亂序重組、資源上限那些測試**一個字都沒改**就繼續綠——那正是這件事做對了的證據。
- **Fix First。** 不動 `OutgoingFile`／`ReceivedFile` 契約，所以儲存槽、縮圖、relay 暫存、桌面/行動落盤全部不受影響。
- **先把最糟的失敗型態擋掉。** 背壓從輪詢改事件是效能改善，但真正重要的是那個保險計時器：檔案傳輸「卡住且不報錯」比「慢一點」嚴重一個量級。

## 後果

- 正面：送出端少一份整檔複製、收檔端少一份；背壓不再每 50 ms 醒來，且滿載時的續傳延遲從「最多 50 ms」變成「事件即時」。收滿即無洞成為結構性保證。
- 負面／已知殘餘風險：
  - **整檔仍然進 RAM**，兩端皆然。這一階段買到的是「少複製」，不是「不落 RAM」；100 MiB 天花板因此維持不動。
  - **舊版對端 ＋ 亂序 ⇒ 中止**（新版之間不受影響，因為新版一定帶 `chunkSize`）。實務上資料通道有序，這條路徑只有在對端實作異常時才會走到。
  - **保險計時器是防禦性的，沒有辦法測到它真正想防的競態**——測試是手動製造「事件不來」的情境來驗證它會救場，而不是重現那個競態本身。
  - **送出端的第 3 份複製（blob URL）沒有處理**：那是 UI 為了讓自己也能重播/下載而留的，屬於 `App.tsx` 的範圍，不在本 ADR 的管線內。
  - 桌面 `App.tsx` 的 `await f.arrayBuffer()`（第 1 份）同樣沒動——那要等 `OutgoingFile` 能接受惰性來源。
- 後續行動／待辦：
  1. **送出端接受惰性來源**：`OutgoingFile` 由 `{ bytes }` 擴為可帶 `File`/`Blob`，`encodeFile` 改用 `file.slice(offset, end)` 逐塊讀 ⇒ 送出端整檔不進 RAM。⚠ 會動到縮圖（ADR-0102）、EXIF 清除（ADR-0273）、blob URL 重播三處消費點。
  2. **收檔端串流落盤**：`onFile` 改為 sink 介面（桌面走 Tauri fs、web/行動走 OPFS，`packages/engine/src/storage/opfs-archive.ts` 已有 `createWritable()` 的底子）⇒ 收檔端整檔不進 RAM。⚠ 會動到 `ReceivedFile.bytes` 的三條消費路徑（P2P、ADR-0162 relay 分塊、ADR-0161 儲存槽）。
  3. **1、2 都落地後才調高 `DEFAULT_MAX_FILE_SIZE`**，並依 ADR-0344 §後果重新檢視 50 MB 的中繼門檻——天花板一拆，那個門檻就成為唯一攔在使用者與「不知情地經中繼送出數 GB」之間的東西。
