# 0397. 裝置能力回報：自己有一台裝置跟不上加密方式時，每台裝置都看得到

- 狀態：已接受（使用者 2026-10-29：「1」——從設計缺口清單選了第 1 項「沒有最低版本的防護」）
- 日期：2026-10-29
- 相關文件：ADR-0365（後量子 EK 開播，§後續「發版前必須人工確認」）、ADR-0322（裝置目錄）、ADR-0321（裝置清單 E-lite）、ADR-0324（久未出現的裝置）、ADR-0302／0306（能力宣告）、ADR-0316／0325（解不開的密文）、ADR-0071（雲端快照）

## 背景與問題

ADR-0365 在 v0.0.18 開始公告後量子 EK（kind 10040 `v:2`）。對方看到之後，會用混合式加密寄給我。我自己還沒更新的那台裝置拿得到 EK 私鑰，卻沒有 pq 種子，也沒有混合式的程式碼，所以那台上的訊息會**永久解不開**。

ADR-0365 的結論是「程式擋不住，只能發版前人工確認」。這有三個問題：

1. **沒有人看得到。** 新的裝置不知道舊的那台跟不上；舊的那台只會把訊息算成「可能缺 EK」（ADR-0316），使用者不會知道該去更新。
2. **每次發版都會重演。** 往後只要再加一種「改變別人怎麼加密給我」的能力，就是同一個問題。
3. **人工確認也看不到版本。** 設定→裝置只列出裝置，沒有各台的版號。

能用的現有通道都不合適：
- **裝置目錄（kind 10041）是撤銷的承重結構。** 只有已在目錄內的裝置能授權別台（ADR-0322 S5），裝置不能改自己那一項。
- **雲端快照（kind 30078）只有開了備份才有**，而且舊版會把同 kind 的事件當成快照、記成一台新裝置。

## 考量的選項

- **A. 每台裝置發一份自己的報告（新的可尋址 kind，`d`＝裝置 id，內容加密給自己）**：只寫自己那一項，不會互相覆蓋，舊版也不會誤讀。
- **B. 把版本寫進裝置目錄**：會讓裝置改到撤銷的承重結構，不做。
- **C. 偵測到有裝置跟不上就自動停止公告 pq**：已升級的對方會看到 v2 退回 v1，被判成降級（ADR-0365 的 rollback 偵測），使用者會收到錯的警報。而且舊裝置不一定還在用，因此不自動決定，只提示。
- **D. 公告一個最低版號，低於它的客戶端拒絕運作**：舊版沒有這段程式碼，擋不住現在已經在外面的舊版；對以後的版本，能力比版號準確。

## 決策

採 A，並且只做提示、不自動決定。

1. **裝置報告**（`packages/core` 的 `device-report.ts`，kind **30079**，App 專用）：
   - 每台裝置在連上 home 之後發一份，內容是 `{ id, pk, ver, caps, at }`：`id` 是 `getDeviceId()`，`pk` 是裝置公鑰，`ver` 是 App 版號，`caps` 是這一版讀得懂的能力（現在是 `ek-v1`、`ek-pq-v1`）。
   - 身分金鑰簽章，NIP-44 加密給自己。中繼只看得到 `d` tag，而那個值雲端快照早就公開了；版號與能力不外洩。
   - 讀取時：不是自己發的、簽章壞、解不開、畸形的一律丟棄；`d` tag 必須等於內容裡的 `id`。
   - 訂閱併進裝置目錄那個 REQ 的 `kinds`，不多開訂閱。
2. **算出缺口**（`RelayChatBackend.capabilityGap()`，有變化時發 `onCapabilityGap`）：
   - **目前需要的能力**：這個身分正在公告的機制。現在只有一種：`announcedPq()` 成立時需要 `ek-pq-v1`。沒開前向保密就沒有要求，也就不會提示。
   - **要檢查的裝置**：裝置目錄內的裝置，加上觀測清單上的裝置；排除本機、已移除的（ADR-0322 S3）、久未出現的（ADR-0324）。
   - 每台的結果分三種：報告裡有需要的能力就沒事；報告裡沒有，列出缺哪些；**沒有報告**，標成「未回報（可能是舊版）」。舊版本來就不會發報告，而它們正是最危險的那群。
   - **本機跟不上**：別台的報告宣告了本機不認得的能力，就列出來，請使用者更新這台。這一條管的是以後的版本：舊版沒有這段程式碼。
3. **UI**：
   - 設定→裝置：每台顯示回報的版號（沒回報的不顯示），人工確認時可以對照。
   - 有缺口時，主畫面常駐一條提示，直到補上為止：「有裝置可能收不到訊息：『Windows 桌機』沒有回報支援目前的加密方式，請把它更新到最新版」；或「這台裝置的版本太舊，可能收不到訊息，請更新」。
   - 只說事實，不宣稱「量子安全」（ADR-0306 的文案紅線）。
4. **以後要再翻開一種會改變別人怎麼加密給我的能力，要先接上這裡**：把它加進「目前需要的能力」。發版前的人工確認改成看設定→裝置，不再靠記憶。

## 理由

- 受害的是**自己的**裝置，而每台裝置都持有 nsec，所以自己發、自己讀就夠了，不需要中繼或對方配合。
- 能力比版號準確：版號說不出這台讀不讀得懂某種機制，能力說得出。
- 沒有報告就當成可能是舊版：誤報的代價是使用者去更新一台其實已經沒問題的裝置；漏報的代價是永久丟訊。

## 後果

- 正面：
  - 跟不上的裝置在每台都看得到，而且指名是哪一台；
  - 以後的能力切換有一個固定的檢查點。
- 負面 / 已知殘餘風險：
  - **早於這一版的裝置不會發報告**，所以會一直顯示「未回報」，直到它更新為止。這是刻意的。
  - 舊裝置自己不會提示：它沒有這段程式碼。提示只出現在新的裝置上。
  - 中繼對每個（作者、kind）最多存 5 筆可尋址事件（SDK `ADDRESSABLE_MAX_PER_AUTHOR`），第 6 台以後的報告會被拒收，那幾台會顯示「未回報」。雲端快照本來就有同一個上限。
  - 企業自架站如果設了 `allowedKinds`，要加上 30079，否則報告會被拒收，同樣顯示「未回報」。
  - 任何持有 nsec 的人都偽造得出報告。這是提示，不是安全邊界；撤銷仍以裝置目錄為準。
- 後續行動 / 待辦：
  - 發版前的人工確認改成：設定→裝置裡沒有缺口。
- 驗證：
  - core `device-report.test.ts`：往返、別人發的、`d` 與 id 不符、畸形內容。
  - engine `device-capability.test.ts`：需要的能力、未回報、缺能力、本機跟不上、排除已移除與久未出現的裝置、沒開前向保密就沒有要求。
  - i18n 文案測試。
