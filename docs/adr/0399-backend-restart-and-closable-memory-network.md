# 0399. 後端 stop 之後可以再 start；記憶體網路的連線真的能關

- 狀態：已接受（使用者 2026-10-29：「好 開始」——研究「記憶體網路改走 SDK」的風險後，先修研究中發現的既有問題）
- 日期：2026-10-29
- 相關文件：ADR-0119（`stop()` 關閉所有中繼連線）、ADR-0398（真實網路連線改由 SDK 負責）、ADR-0156（入職自動核准）、ADR-0241（分片）

## 背景與問題

研究「把記憶體測試網路也改走 SDK 連線池」時，有兩個測試失敗，查下去是兩個本來就有的問題。

1. **同一個後端 `stop()` 之後再 `start()`，home 連線就死了。**
   - home 連線在建構子裡建一次。ADR-0119 讓 `stop()` 把它關掉、停止重連，`start()` 卻不會重建。
   - 桌面版開了 React StrictMode。開發模式下 effect 會跑「start → stop → start」，用的是同一個後端，所以**開發模式的桌面版 home 連線可能是死的**。正式版不會重跑 effect，不受影響。
   - 這一點是從程式碼推出來的，沒有實際開 App 驗證。
2. **記憶體網路的連線沒有 `close()`，`stop()` 過的後端變成殭屍。**
   - 停掉的後端照樣收訊息、照樣反應。測試靠它通過，卻沒有人知道。
   - 企業主重啟那個測試（ADR-0156「重啟不失憶」）就是這樣：替新人核准的其實是停掉的舊企業主。那個測試的記憶體中繼也沒有給儲存，名冊根本沒存下來，重啟後的企業主一直沒被真的測到。
   - 分片的往返測試也同時踩到上面兩點：它重用同一個實例 stop 再 start。

## 決策

1. **`RelayChatBackend`**：
   - 建 home 連線的工廠存起來，`openHome()` 在建構時用一次。
   - `stop()` 記下「home 已關」。
   - `start()` 看到 home 已關，就用同一個工廠重建。
   - 沒 stop 過就再 start，不會多開一條。
2. **記憶體網路的 `connect()` 回傳可以關的連線**：`close()` 之後：
   - 不再收到東西；
   - 送出的不再處理：中繼不收、也不轉給別人；
   - 中繼忘掉這條連線的訂閱（`core.disconnect`）；
   - 同一個 connId 已經被新連線接手時，舊的 `close()` 不影響新的。
3. **企業主重啟的測試給中繼加上儲存**（`MessageStore`）：重啟後的企業主要從中繼訂回自己的名冊，自己核准新人。

## 理由

- 修正 1 讓 StrictMode 與「重用實例」不再靜默失效。這個專案反覆出現的失敗模式，就是「安靜地做錯的事」。
- 修正 2 讓測試的連線行為跟真實 WebSocket 一致。這也是記憶體網路改走 SDK 的前置條件：SDK 的連線池在 `close()` 之後就真的斷了，殭屍實例會消失，而靠殭屍通過的測試要先修好。

## 後果

- 正面：
  - 引擎測試裡不再有殭屍實例。改成真的斷線之後，引擎 840 個測試只有上述兩個失敗，兩個都修好了，其他測試都沒有依賴殭屍。
  - 「重啟不失憶」現在是真的在中繼上讀回名冊。
- 負面 / 殘餘：
  - StrictMode 下的連線狀況沒有實際開 App 驗證。
  - `BrowserChatBackend`（不設中繼時的展示模式）也用記憶體網路，展示用的機器人連線現在也能真的關，對使用者沒有可見的差別。
- 後續：記憶體網路改走 SDK（ADR-0398 的殘餘）。研究結果是：
  - 28 個測試要改成 async，因為 OK 回覆會變成下一個微任務；
  - 3 個容量相容測試要改成在 socket 那層記錄訊框；
  - 心跳去重那 1 個要改寫。
- 驗證：
  - engine 新增 2 個測試：同一個實例 stop 再 start 照樣收得到、不多開一條。
  - relay 新增 `in-memory-network.test.ts` 3 個測試：關掉之後收不到、也送不出；中繼忘掉訂閱；新連線接手後，舊的 close 不影響新的。
  - 破壞測試 4 項，每項都至少讓一個測試失敗：
    - `stop()` 不記「home 已關」；
    - 不呼叫 `core.disconnect`；
    - 舊的 close 不檢查是不是自己；
    - 關了照樣送。
