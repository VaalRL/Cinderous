# ADR-0326：群組 FS 的發現機制——seal 層 EK hint

- 狀態：已採用
- 日期：2026-08-04
- 關聯：ADR-0320（Tier A 批二；把本工作列為「**若**覆蓋率長期偏低」的後續）、ADR-0318（批一：不在 rumor 帶 hint 的理由）、ADR-0319（群組 FS 狀態呈現）、ADR-0317（入群邀請閘門）、ADR-0245（1:1 FS 與 rumor hint）、ADR-0002/0027（NIP-59 與群組扇出）

## 1. 先量，再決定

ADR-0320 把「群組覆蓋率會偏低」列為已知殘餘，並寫下：

> 若群組覆蓋率長期偏低，該解的是**發現機制**（seal 層 hint），不是放寬聯絡人語意。

那個「若」從來沒有被量過。這次量了，**結果和 ADR-0320 的描述不完全一樣**——真正的問題是一個**不對稱**：

| 我的角色 | 其他成員是不是我的聯絡人 | 覆蓋率 |
| --- | --- | --- |
| **建群者** | **是**——`createGroup()` 對每位成員 `ensureContact()` | 天然是滿的（對方也開 FS 就有） |
| **被邀請者** | **否**——`applyControl()` 明講「不自動把其他成員塞進個人聯絡人」（避免被強行灌入聯絡人清單） | **結構性為 0** |

ADR-0320 只寫「同群但沒加過的人一律 `unknown`」，沒有指出**這件事只發生在被邀請的那一方**。而被邀請者是群組裡的多數——一個 N 人群裡有 N-1 個。

實測（`group-fs-coverage.test.ts`，被邀請者視角）：

- 同群成員**明明發了 kind 10040 公告**，我仍然把每一則群訊加密到他的**身分金鑰**。
- 原因很直接：10040 的訂閱是 `authors:[聯絡人]`，他不在裡面 ⇒ **他的公告我根本沒訂**。
- 而且**不會隨時間改善**。這不是「偏低」，是零，且是穩定的零。

⇒ ADR-0320 的條件成立，且比預期嚴重。

## 2. 為什麼不是「把群成員也加進 10040 訂閱」

那是最直覺的修法，且**被否決**：`authors:[…]` 的 REQ 走在我**已 NIP-42 認證**的連線上 ⇒ 中繼會學到我的**群成員集合**。ADR-0237 已經把「presence 訂閱洩漏聯絡人集合」列為 🔴 殘餘，這等於再開一個同型的洞。

用**確定且立即**的元資料洩漏，換**條件性**的前向保密（只在未來私鑰外洩時才兌現）——方向錯了。

## 3. 決策：hint 放 seal 層

NIP-59 有三層：rumor → seal（kind 13）→ wrap（kind 1059）。

- **rumor**：❌ ADR-0318 已否決。`rumor.id` 是跨成員一致的群訊識別碼（回條與引用的鍵，ADR-0095），而 EK 每 7 天輪替 ⇒ 放進去會讓同一則訊息在不同時間得到不同 id。
- **wrap tags**：❌ 那是明文的，中繼看得到 ⇒ 直接公開 EK↔身分的對應，比訂閱洩漏更糟。
- **seal tags**：✅ **逐收件人**、**加密在 wrap 內層**（只有解得開的人看得到）、**不參與 `rumor.id` 的雜湊**。

三個性質剛好對上三個限制。故 `sealAndWrap()` 增加可選的 `sealTags`，`Opened` 回傳 `sealTags`，群組扇出在其中夾一個 `["ek", <我的當前 EK>]`。

收件端 `openFs()` 兩處都學：`ekHintOf(rumor.tags) ?? ekHintOf(sealTags)`——1:1 維持原樣（ADR-0245 的 rumor hint 不動，Fix First）。

### 3.1 這讓發現變成「對話式」

不再需要「他是我的聯絡人」，只需要**他在群裡發過一次言**。測得的行為：

- 他發言前：我的群訊 → 他的身分金鑰。
- 他發言後：我的群訊 → **他的 EK**。

而我的群訊也帶著我的 EK，所以是雙向的——否則發現只有單向，對方永遠給不了我 FS。

## 4. 成本：比 rumor hint 便宜一個量級

掃描 1..400 字的訊息內容，逐長度比較「帶 hint」與「不帶」的單份 wrap 位元組：

| | 跳一階的比例 | 平均 |
| --- | --- | --- |
| **seal hint（本 ADR）** | **5.8%**（23/400） | **+9.9 位元組/份** |
| rumor hint（ADR-0318 量的 1:1 做法） | 38% | +139 位元組/份 |

原因是 NIP-44 的填充：seal 本來就是一塊大 JSON（內含整個加密後的 rumor），多 72 字元通常**落在同一個填充級距內＝免費**；rumor 本身小得多，同樣的 72 字元容易把它推過邊界。

⇒ seal 層不只是唯一正確的位置，也是最便宜的位置。未啟用 FS 時不帶，一個位元組都不多送。

## 5. 買不到什麼

1. **不說話的成員仍然沒有 FS。** 對話式發現的必然結果。潛水者的那份仍加密到身分金鑰——但那是**他的**選擇造成的，不是我們的機制漏掉他。
2. **第一則訊息一定沒有 FS。** 他發言之前我不可能知道他的 EK。
3. **`contactEks` 會長出非聯絡人的條目。** 上限是我見過的群成員數，且它進雲端快照（本來就是同步欄位）。同時 `learnContactEk` 會 TOFU 釘選「此人用 FS」——若我日後把他加為聯絡人，而他那時剛好停用了 FS，1:1 送訊會出現一次降級提示。條件對，但來源是群組——**已知且接受**。
4. **群組控制訊息（群名、成員清單）仍是靜態的**，沒有 FS（ADR-0320 已記，未變）。
5. **偏離 NIP-59 慣例**：標準的 seal `tags` 是空的。我們放了一個 tag。它加密在 wrap 內 ⇒ 對中繼與其他客戶端**不可見**，不構成指紋；但**能解開的收件人**若是別家客戶端，會看到一個它不認得的 tag——依 Nostr 慣例應忽略未知 tag。

## 6. 後果

- 正面：被邀請者的群組 FS 覆蓋率從**結構性 0** 變成「對方發過言就有」；成本 +9.9 位元組/份；**沒有多洩漏任何東西給中繼**。
- 負面：見 §5。
- 這是 **Nostr 事件契約的變更**（seal 層新增一個 tag）⇒ `ARCHITECTURE.md` 已同步。
