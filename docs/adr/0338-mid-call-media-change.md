# ADR-0338：通話中語音↔視訊升降級——不重新協商，也不替對方開鏡頭

- 狀態：已採用
- 日期：2026-08-05
- 關聯：ADR-0101（通話媒體平台縫）、ADR-0337（畫質三檔與關鏡頭）、M8（通話）、ADR-0099 §2（平手判準的既有慣例）

## 1. 問題

`CallMedia` 在 `call-invite` 時就定死，`CallSession` 沒有任何改變它的路徑。想從語音轉視訊只能掛斷重打——而掛斷重打會**丟掉通話時長、對端要重新接聽**，實務上沒人會這樣做。

## 2. 決策一：升級是單方的，不會替對方開鏡頭

這是本 ADR 最重要的一句：

🔴 **「我升級成視訊」的意思是「我開始傳送我的畫面」，不是「我們都開鏡頭」。**

考慮過的另一種語意——A 升級時 B 的客戶端自動取用相機——**直接否決**：那等於讓遠端的人打開你的鏡頭。對一個把「明文與私鑰不離開裝置」當賣點的 App，這條紅線比功能完整性重要得多。

⇒ 通話的媒體型態因此是**每方向各自獨立**的：

| | 意義 |
| --- | --- |
| `localMedia` | 我正在送什麼 |
| `remoteMedia` | 對方正在送什麼 |

四種組合都是合法狀態，包括「我送視訊、他只送語音」——他看得到我，我看不到他。UI 必須照實呈現這件事，不能假裝是對稱的。

`onState` 的 `media` 維持既有意義並改為**有效值**（任一方為視訊即視訊，決定要不要顯示視訊版面），另外新增 `onCallMedia(local, remote)` 給需要分辨方向的地方。**加一個回呼而不是改既有簽章**——後者要動雙端每一個消費點，而它們多數只關心「要不要開視訊版面」。

## 3. 決策二：預先協商視訊軌道，靠 `replaceTrack` 換人上場

WebRTC 改變媒體的教科書作法是**重新協商**（一方 `createOffer`、另一方 `answer`）。那條路要處理 **glare（雙方同時發 offer）**，需要 perfect-negotiation 的 polite/impolite 角色與 rollback。

**我們不走那條路。**

改成：**建立通話時一律 `addTransceiver("video", { direction: "sendrecv" })`，即使是語音通話。**

- 語音通話 ＝ 視訊 sender 的 track 是 `null`（不送任何 RTP，**也不取用相機**——沒有權限提示、沒有指示燈）。
- 升級 ＝ `getUserMedia({ video })` ＋ `sender.replaceTrack(track)`。
- 降級 ＝ `sender.replaceTrack(null)` ＋ `track.stop()`（真正關閉相機，與 ADR-0337 的「停止視訊」不同——那個只送黑畫面）。

🔴 **`replaceTrack` 在軌道與已協商的媒體相容時不需要重新協商**（規格明文，也是切換前後鏡頭的標準作法）。m-line 方向不變、視訊編碼早已協商好 ⇒ **沒有 SDP 交換，就沒有 glare，也沒有 rollback**。

對端只需要知道「型態變了」以更新畫面，所以新增的信令 `call-media` **只帶 `media`，不帶 SDP**：

```ts
{ type: "call-media", callId, media }
```

⇒ 整個功能不觸碰 SDP，狀態機新增的路徑是**一個賦值加一個送出**，不是一套協商協定。

### 代價

1. 每通語音通話的 SDP 多一個閒置的視訊 m-line（數百位元組）與一個協商好的 SSRC。相對於「不必實作 glare 處理」，這個交換划算得不能再划算。
2. 答方需要在 `setRemoteDescription` 之後、`createAnswer` 之前把視訊 transceiver 的 `direction` 設為 `sendrecv`——規格上答方自動建立的 transceiver 預設是 `recvonly`，不改它就**永遠送不出視訊**。這是這個設計唯一容易寫錯的地方，有測試釘住。

## 4. 舊版相容

| 情境 | 行為 |
| --- | --- |
| 新版 → 舊版 | 舊版 `parseCallSignal` 對未知類型丟例外，`onCallSignalEvent` 已 catch ⇒ **靜默忽略**。舊版仍會收到視訊軌（它的 offer 沒有視訊 m-line，所以其實收不到），UI 維持語音。不會壞。 |
| 舊版 → 新版 | 舊版的 offer **沒有視訊 m-line** ⇒ 新版找不到視訊 sender ⇒ 升級按鈕按了沒有效果。 |

第二列不可接受地不誠實 ⇒ **偵測不到視訊 transceiver 時，升級入口就不顯示**。寧可少一個按鈕，也不要一個按了沒反應的按鈕（同 ADR-0243「明確標示、非靜默失敗」的立場）。

## 5. 何時可以改

只在 `active`（已連通）時允許。`outgoing`／`incoming`／`connecting` 期間改型態會與初次協商賽跑，而它買不到什麼——那幾秒鐘使用者按不到也不會想按。狀態機在非 `active` 時回傳空動作，與其他非法轉移的處理一致。

## 6. 買不到什麼

1. **沒有徵詢對方同意。** A 開自己的鏡頭不需要 B 批准（B 隨時可以掛斷或不看）。反過來說 **A 也無法要求 B 開鏡頭**——連要求的協定都沒有。想做「對方開了鏡頭，要不要也開？」的提示是 UI 層的後續，不影響本協定。
2. **降級不保證對方立刻看到黑畫面。** `replaceTrack(null)` 後對端的最後一幀可能停留數百毫秒。UI 收到 `call-media` 就該把版面切掉，不要等視訊軌真的停。
3. **不處理「升級失敗」的回滾。** `getUserMedia` 被拒（使用者不給相機權限）時就停在語音，**不送 `call-media`**——不能先宣告再失敗，那會讓對端顯示一個永遠不會來的畫面。
4. **舊版對端無法升級**（§4），且**偵測方式是本端有沒有視訊 sender**，不是對端版本號——所以它同時也涵蓋「對端瀏覽器不給視訊 m-line」這類非版本因素。
5. **與 ADR-0337 的關鏡頭是兩件事**：關鏡頭＝仍在視訊通話、只是送黑畫面（軌道開著）；降級＝退回語音通話、真正 `stop()` 相機。兩個入口都留，因為「暫時遮一下」與「這通不用視訊了」是不同意圖。
6. **沒有處理通話中對端斷線後重連的型態同步**——重連走的是重撥，型態回到 invite 當時。
