## 背景與問題

問題：**經營 Cinderous relay 有沒有盈利的可能？**

ADR-0166 已從**授權**角度回答了「他人能不能營利」（AGPL 不禁止收費），但未回答**經濟**問題：
成本多少、收入從哪來、哪條路徑真的有毛利。本文補上數字與可執行的形態，並把「什麼**不能**賣、
賣之前必須先揭露什麼」一併寫清楚——後者比前者重要，因為那是退款與信任崩盤的來源。

## 一、成本模型：relay 實際要花多少錢

計費關鍵（ADR-0109 已量測）：

- **進來的每則 WS 訊息 ＝ 1 個 Durable Object request**（EVENT／REQ／CLOSE／AUTH 都算）
- **中繼扇出給客戶端的事件不計 request**（只計 duration）——省法建立在這一點上
- 只有**非 ephemeral** 事件寫 row；心跳（kind 20000）不寫庫
- **Cloudflare Workers／DO／R2 不收 egress 流量費**

ADR-0109 落地後每位「同時在線」使用者的 requests/日（自適應心跳：有人在線 60s、無人 5 分鐘；
P2P 通道通了直接不經中繼）：

| 來源 | requests/日（量級） |
|---|---:|
| 心跳（ACTIVE 60s／IDLE 300s） | 288–1,440 |
| 輸入中（1 秒節流；P2P 通時卸載） | ~200 |
| 訊息（每則 3 顆事件） | ~150 |
| 訂閱（合併後每次連線 1 個 REQ） | ~30 |

以 **~1,500 requests/日/在線使用者**估算（保守取偏高值），換算 Cloudflare 價目
（引自 ADR-0244：requests $0.15/百萬、DO 儲存 $0.20/GB-月、R2 $0.015/GB-月、免費層 10 萬 req/日）：

| 規模（同時在線） | requests/月 | 每月成本（含 Workers Paid $5 底費） |
|---|---:|---:|
| 30–60 人 | — | **$0**（免費層即可，見 ADR-0006） |
| 100 人 | ~4.5M | ~$5.7 |
| 1,000 人 | ~45M | ~$12 |
| 10,000 人 | ~450M | ~$73 |

**⇒ 每位使用者每月的邊際成本約 $0.007（不到 0.25 台幣）。**

唯二真正會花錢、且已被刻意上鎖的兩項：

- **TURN（ADR-0243）**：按 GB 計流量，故 `wrangler.toml` 註解明寫「於 Cloudflare 端設用量上限封頂」。
- **公共檔案後備（ADR-0244，提議中）**：天花板估算 1 萬人塞滿配額 ＝ 5TB → DO 上 ~$1,000/月、
  R2 上 ~$75/月；階段 A 的公共政策（50MB/收件人、TTL 2–3 天、單檔 ≤8MB）就是為了壓這個天花板。

> 數字皆為**估算**，且 Cloudflare 價目以 ADR-0244 記錄時點為準；正式報價前須重新核對官方價目，
> 並以 ADR-0006 待辦的「真實流量實測」回填校準。

## 二、收入面現況：**導流管道尚未實作**

ADR-0089 設計了營運者贊助入口（relay 以 NIP-11 自報 `cinder_donations` → 桌面角落卡純導流）。
**查核結果：尚未實作。**

- `relay/src/worker.ts` 對非 WebSocket 的 HTTP GET **一律回純文字** `"Cinderous relay"`，
  沒有 `Accept: application/nostr+json` 的 NIP-11 分支；`node-relay.ts` 同。
- 全 repo 搜 `cinder_donations` 只出現在 `packages/core/src/node-attestation.ts` 的註解
  與 `apps/website/src/copy.ts` 的對外文案；**客戶端無讀取端、桌面無角落卡**。

即使實作，ADR-0089 的設計本身就把收入壓到最低（皆為刻意）：純外部導流、無站內金流、卡片可關閉
且關閉後記住、**行動端刻意不放**、企業身分隱藏、且只對 home 與使用者主動加入的座顯示。

## 三、公共 relay 為何結構上不可盈利

1. **零轉換成本**：relay pool（0034）＋hint 自動學習（0035）＋home 自動遞補（0039）＝你的座掛了或
   要收費，客戶端自動搬走，使用者無感。沒有鎖定就沒有定價權。
2. **競爭者價格恆為 0**：進官方選座池免費（`docs/NODE-SUBMISSION.md`），標準是「穩不穩、行為對不對」
   而非付不付費。你在跟一群志願者的**免費且功能完全相同**的座競爭。
3. **看不到內容就沒有加值空間**：Gift Wrap 之後 relay 只是轉發密文的水管。
4. **市場尚不存在**：`relay/bootstrap/relays.json` 全網僅 2 座（皆官方），ADR-0241 自述
   「pre-release 幾乎無使用者」。

粗算：即使做到 1,000 位同時在線、開源專案捐款轉換率抓 0.1–1%、平均 $3–5，月收約 $3–50、
成本約 $12。**最佳情況是打平，不是盈利。**

**結論：公共 relay 應被視為貢獻或品牌投資，不是生意。**

## 四、可行路徑：企業導入與託管服務

### 4.1 賣的不是軟體，是營運責任

- 全套 AGPL-3.0，且 `docs/SELF-HOSTING.md`／`self-hosting-zeabur.md`／`self-hosting-raspberry-pi.md`
  已把自架寫成教學——客戶 IT 照做即可自架，**軟體本身賣不了錢**。
- **也不能靠閉源加值功能建護城河**：AGPL §13 要求你改過的 relay 一旦以網路服務提供，就須對其使用者
  公開修改後源碼；散佈改過的客戶端同受 GPL §5/6 拘束。**任何你加的功能，客戶拿到的同時就有權拿到源碼。**

⇒ 護城河只能是**服務、責任承擔與可問責的對象**，不能是程式碼。

### 4.2 四塊可賣項（皆對應 repo 內的真實工作量）

| 項目 | 形態 | repo 依據 |
|---|---|---|
| **導入佈建** | 一次性 | 管理者金鑰產生與保管流程、簽章名冊 kind 10038（0047）、`rosterAllowlist` 匯出佈建到 `allowedAuthors`（0044）、邀請碼含 `escrow` 旗標（0163）、政策開關 `disableFiles/Calls/forceTurn`＋`allowedKinds`（0048）、教育訓練 |
| **託管營運** | 月費（主要收入） | 自架 relay（CF Worker 或客戶機房跑 `node-relay.ts`）、TURN 憑證與用量封頂（0243）、`MAX_TTL_DAYS`／`MAX_FILE_MB` 政策、監控與 uptime、**版本升級**（ADR-0241 明列「運維：relay 需 deploy 最新 worker」＝持續性義務） |
| **客製開發** | 專案制 | **G5（SSO 綁 AD/LDAP/OIDC → npub、元資料稽核）是明確未實作的缺口**（ROADMAP G5，且註明「等企業試點」）＝第一個付費開發合約的天然標的 |
| **桌面版企業派送** | 一次性＋年費 | **Tauri 程式碼簽章憑證是缺口（ROADMAP B6，需憑證）**；憑證有年費與申請門檻，客戶不會為內部通訊自辦 → 代辦＋出鎖單座企業建置 MSI |

### 4.3 單位經濟

一家 50 人公司：50 × 1,500 req/日 ≈ 2.25M requests/月 ≈ **$0.34**；含 Workers Paid 底費，
整體 **< $6/月**。合理報價 $150–300/月 → **毛利率 95%+**。

**天花板不是基礎設施，是人力**：一個人能同時服務幾家客戶（導入工時、支援回應、升級窗口）。
這是標準開源商業模式，AGPL 完全允許。

## 五、成交前必須揭露的產品硬邊界

不先講清楚，後期必然退款與信任崩盤：

1. **法遵歸檔／eDiscovery／DLP 不支援**，且結構上不可能（ADR-0044「後果」、PRD §13.1 明確排除）。
   金融、醫療、上市公司的資安稽核第一關就問這題——這類客戶要嘛接受，要嘛不是你的客戶。
2. **員工工作身分的金鑰不託管**（ADR-0052 否決金鑰託管、無後門）。只有企業主在邀請碼勾選
   「公司帳號」的身分才有託管與離職接管（ADR-0163）。所以「公司可稽核全體員工訊息」——做不到。
3. **`allowedAuthors` 只擋發布，讀取層靠客戶自己的私網/VPN/防火牆**（ADR-0044 決策 #4）——
   這直接影響部署方案與報價（要不要幫客戶做網路邊界）。
4. **接管看到的「歷史」只是 relay 仍持有的離線信箱殘留**（ADR-0163 決策 #4）；員工裝置本機的
   聊天記錄無法遠端取得（那從不上雲）。不得對客戶隱含承諾「完整歷史可稽核」。

## 六、員工金鑰託管現況（實作查核）

企業銷售必然被問這題，故本節把**程式碼現況**釘死（而非只引 ADR）：

| 面向 | 現況 | 依據 |
|---|---|---|
| 員工**一般**工作身分 | **不託管、無後門**。遺失＝輪替新 npub、名冊標 `supersededBy`，公司全程不碰 nsec | ADR-0052 |
| **公司帳號**（邀請碼勾 `escrow`） | 入職時員工 nsec 隨入職請求 Gift Wrap **加密送給管理者**並持久化，供離職接管 | ADR-0163；`core/invite.ts`、`engine/relay-backend.ts:3240,3263` |
| 揭露與同意 | 邀請碼帶 `escrow` 時登入/新增身分面板**明示警語**（`signIn_joinEscrow`），員工建立即同意 | `apps/desktop/src/ui/SignIn.tsx:259` |
| 離職封鎖 | 名冊移除 → `rosterAllowlist` → relay `allowedAuthors` 不含其 pubkey ＝ 舊金鑰在公司座發不出任何事件 | ADR-0163 決策 #2、ADR-0044 |
| 託管落盤（**行動端**） | **加密**：以企業主 nsec 導出金鑰 `sealValue` 封裝，`c1:` 密文 | ADR-0179；`apps/mobile/src/org-escrow.ts:45,64` |
| 託管落盤（**桌面**） | ⚠ **明文** `localStorage.setItem` JSON（含 nsec），未經 ADR-0112 的 `sealValue` 封裝 | `apps/desktop/src/ui/org-escrow.ts:39-64` |

### 6.1 待決策：桌面託管清單為明文落盤

- **事實**：桌面 `org-escrow.ts` 直接以 `localStorage.setItem` 存 `{pubkey, name, nsec, relayUrl, at}[]`，
  **繞過**引擎的加密儲存基質（`packages/engine/src/storage/local.ts:55` 的 `sealValue` 路徑）。
- **ADR 文字與實作不一致**：ADR-0163 決策 #1 寫「App 存 `nb.orgEscrow.<admin>`（隨管理者身分的
  **加密儲存**落地，ADR-0112）」，但實作未加密；反倒是後續的 **ADR-0179 誠實記錄了這個差異**
  （「桌面把託管 nsec 明文存 localStorage……行動端一律加密落盤」），並在行動端修正。
- **影響面**：
  - **桌面 web 版**（`cinderous.cinderous1.workers.dev` 等自架 web app）：任一 XSS 可一次撈走
    **該公司全部公司帳號的私鑰**——這正是 ADR-0179 為行動端加密的理由，桌面 web 面對同一威脅。
  - **Tauri 版**：webview 的 localStorage 仍以明文落在磁碟，保護僅來自 OS 檔案權限／帳號邊界，
    非 ADR-0112 的靜態加密。
- **修法明確且低風險**：把 `apps/mobile/src/org-escrow.ts` 的 `deriveStorageKey`＋`sealValue`／
  `openValue` 作法搬到桌面（純函式不動，只改 `loadEscrow`／`saveEscrow` 簽章帶 `ownerSk`），
  並補一次舊明文條目的遷移與抹除。
- **對商業化的意義**：這是企業客戶資安稽核**會**問到的項目。**建議在承接任何企業客戶前先修**，
  否則等於在「賣營運責任」的同時交付一個已知的金鑰暴露面。
- **本 ADR 不實作**（研究記錄）；建議另立 ADR 或列入 ROADMAP 安全待辦。

## 七、合約與責任風險清單

1. **管理者金鑰是單點信任根**：ADR-0047 已知限制寫明「單一管理者金鑰為信任根；多管理者/輪替為後續」。
   金鑰遺失 ＝ 名冊簽不動 ＝ 成員管理癱瘓。這既是託管服務最值錢的一項（你保管、你備援），
   **也是你的責任上限——必須寫進合約，不要口頭承諾**。
2. **接管能力有邊界**（見 §5.4）：合約用語不得寫成「可稽核員工通訊」。
3. **AGPL 交付義務**：若為客戶改了 relay 或客戶端，須對客戶的使用者提供對應源碼——寫進合約，
   避免客戶事後主張「我以為是專屬功能」。
4. **商標**：ADR-0166 建議專案註冊「Cinder」商標與 Logo。**商業服務應以自己的品牌名銷售**，
   標示「基於 Cinderous（AGPL-3.0）」但**不得暗示官方背書**。
5. **SLA 與基礎設施風險**：兩座錨點皆在 Cloudflare（ADR-0189 已知殘留：全域故障仍同倒）。
   企業 SLA 承諾前須評估跨平台備援。

## 八、G5 開發範圍草案（第一個付費客製標的）

ROADMAP G5 = SSO 整合／元資料稽核，尚未實作、且註明「需你決策（等企業試點）」。作為付費合約標的：

- **SSO**：佈建階段綁 AD/LDAP/OIDC → npub 對應；SSO 通過才解鎖本機金鑰。
  **紅線**：IdP 不得成為解密路徑——它守的是「本機金鑰解鎖」，不是「金鑰託管」（否則退回 ADR-0052 已否決的後門）。
- **元資料稽核**：自架 relay 記錄**連線元資料**（時間、pubkey、IP），**不碰內容**，E2E 不破。
  須明確告知：這能回答「誰在什麼時候連線」，**不能**回答「誰對誰說了什麼」。
- **前置**：ROADMAP 已註明「實作前須立 ADR（並備外部 IdP）」——付費合約應把立 ADR 納入交付項。

## 決策（研究記錄，未決策）

- **不新增任何站內金流／營利面**：PRD §12 排除清單維持不動；本文不改變產品行為。
- **公共 relay**：定位為貢獻／品牌，**不以盈利為目標**。若要降低營運者負擔，優先實作 ADR-0089
  的 NIP-11 導流（目前未實作），而非引入任何付費機制。
- **企業服務**：若要商業化，**唯一建議路徑**是導入＋託管＋支援＋客製，以獨立品牌經營，
  並在承接前完成 §5 的揭露、§6.1 的修補、§7 的合約條款。
- **本 ADR 不啟動任何商業行為**，僅供決策時取用。

## 後果

- 正面：把「relay 能不能賺錢」從直覺變成有數字的判斷；把可行路徑收斂到一條；把賣之前必須揭露的
  硬邊界與合約風險一次列清；順帶查出 §6.1 的桌面託管明文落盤（ADR 文字與實作不一致）。
- 已知限制：成本數字為估算，Cloudflare 價目與真實流量皆須重新校準（ADR-0006 待辦未完成）；
  定價區間為市場判斷、無實測支撐；商標與合約條款涉及法律專業，本文不構成法律意見。
- 後續行動（**皆待決策，本 ADR 不執行**）：
  1. **（安全，建議優先）** 桌面託管清單改加密落盤，比照 `apps/mobile/src/org-escrow.ts`，
     含舊明文條目遷移與抹除——另立 ADR。
  2. 若要支撐社群營運者：實作 ADR-0089 的 relay NIP-11 `cinder_donations` 與桌面角落卡。
  3. 若要商業化：先做一家試點客戶驗證導入工時，再據以定價；同步推進 ADR-0166 的商標待辦。
  4. 回填 ADR-0006 的真實流量校準，讓成本模型從估算變量測。
