# ADR-0324：觀測老化——久未出現的裝置不再參與撤銷判定

- 狀態：已採用
- 日期：2026-08-04
- 關聯：ADR-0322（裝置撤銷，尤其 S2a）、ADR-0321（裝置觀測 E-lite）、ADR-0323（裝置金鑰保管）

## 1. 這不是「清單好看一點」的問題

我原本把「久未出現的裝置永遠留在清單裡」列為 UI 雜訊。查下去發現它是**安全性質沒有開啟**。

裝置觀測清單**只增不減**。ADR-0322 S2a 已經抓過一次這個形狀的錯——布林判定被一支丟掉的舊手機永遠卡住——並改用**證據**取代推論。但**證據本身也沒有到期日**，於是同一個病從另一扇門回來：

| 判定 | 卡住的方式 | 後果 |
| --- | --- | --- |
| `revocationState()` | 某台四個月前的快照帶著 EK ⇒ 永遠算「還有裝置走舊路徑」 | **永遠報 dual-track** |
| `shouldOmitFsKeys()` | 某台四個月前觀測到、不在目錄內 ⇒ 永遠不敢停 | **這台永遠把 EK 放進自己的快照** |

第二列才是重點：那不是顯示問題，是**撤銷從來沒有真正生效過**，而且完全靜默——UI 會說 dual-track，但沒有人會把「一支三年前的舊手機」和「我按了移除卻沒有用」連起來。

## 2. 決策

**90 天沒見到就推定已經不在**，排除於上述兩個判定之外，並在清單上標明。

門檻沿用 `OR_SET_TOMBSTONE_RETENTION_MS` 的 90 天——這個專案已經用它當作「久到可以放心當作不會再回來」的長度，不另立新標準。抽屜裡放一個夏天的手機仍在窗內。

時鐘倒退（`now < lastSeen`）時判為**未老化**：寧可多等，也不要因為時鐘怪怪的就把自己的裝置踢出判斷。

## 3. 買不到什麼

**「沒看到」不等於「不存在」。** 推定已離線的裝置若哪天回來，它拿不到新的 EK（因為我們已經停止在快照裡放 EK）⇒ **它會讀不到新訊息**。

這是刻意的取捨，成立的前提是**復原路徑看得見**：它一回來就會出現在裝置清單裡、標著「不在目錄內」，按一次授權即可（ADR-0322 S5）。

相對地，不老化的代價是**撤銷對所有曾經有過裝置的人都不生效，而且沒有任何人看得出來**。兩害相權，選看得見的那個。

## 4. 順手修掉一個假裝有作用的按鈕

查這件事時發現：清單上「觀測到但不在目錄內」的裝置也顯示撤銷按鈕，而 `removeDevice()` 需要目錄項裡的 pk——那些裝置沒有目錄項 ⇒ **按下去 `if (!pk) return;`，靜默什麼都不做**。

改為分流：

- **在目錄內** → 撤銷（`removeDevice`，真的換鑰、真的斷它）。
- **不在目錄內** → 「從清單移除」（`forgetDevice`），文案明說**不會撤銷任何東西、也不會動到任何金鑰**。

🔴 **`forgetDevice()` 對在目錄內的裝置一律拒絕。** 對那些裝置「從清單移除」只會把它從眼前藏起來，而它手上的授權原封不動——那是假的安全感，比看得見的髒清單糟得多。

兩端的二次確認**刻意用不同的失敗方向**：撤銷用 fail-closed（`confirmRequired`，文案講的是這個按鈕買不到什麼，跳過等於默許誤解，同 ADR-0323 §3.6）；忘掉觀測用 fail-open（`confirmAction`，文案只是說明它做得少，跳過不會讓人誤以為自己更安全）。

## 5. 後續

- 老化門檻沒有做成可設定：多一個旋鈕、少一個共識，而 90 天已經涵蓋合理情境。
- 老化只影響**判定**，不自動刪除觀測紀錄——刪除由使用者按「從清單移除」決定。
