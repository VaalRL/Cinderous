# 0319. 群組的 FS 狀態：靜態呈現，不發 per-member 降級警告

- 狀態：已接受（**先定語意，實作＝ADR-0315 第 2 步批二**）
- 日期：2026-08-03
- 相關文件：**ADR-0315（Tier A 擴大順序；本文是批二動工前的必要前置）**、ADR-0318（批一：
  只 retarget 不帶 hint）、ADR-0245（1:1 降級偵測與 TOFU 釘選）、ADR-0302 §4（把「可能」
  說成「是」＝說謊的紅線）、ADR-0316（解不開的可觀測性）、ADR-0027（群組成對扇出）

## 背景與問題

批二（群訊 retarget）在技術上與批一同形狀，但有一件事**不能照抄 1:1**：降級警告。

1:1 的語意（ADR-0245）很清楚：

```ts
private fsWouldDowngrade(to) {
  return (this.fsState.pinned?.[to] ?? false) && !this.fsState.contactEks[to];
}
```

「我曾經確認這個人用 FS（TOFU 釘選），現在卻沒有他的 EK」⇒ 在**那一個對話**留一句警告，
意思是「**對方可能正在被攻擊**」。單一對象、單一對話、去重後只講一次。

**群組把這三個前提全部打破：**

1. **對象不是一個，是 N 個。** 15 人群裡若 3 人符合降級條件，一則群訊要發 3 次警告嗎？
2. **沒有「那一個對話」可以放。** 警告放進群組對話 ⇒ 一則訊息換三行系統訊息，洗版；
   放進各自的 1:1 對話 ⇒ 使用者在完全無關的地方看到跟這則群訊有關的話。
3. **群成員未必是聯絡人。** EK 只從 `authors:[聯絡人]` 的 10040 訂閱與 rumor hint 學到
   （ADR-0317 也確認了「加聯絡人是單方面的」）⇒ **「沒有他的 EK」在群組裡是常態，不是異常**。
   而 1:1 的警告文案建立在「這是異常」之上。

第 3 點是關鍵：**把常態顯示成「對方可能正在被攻擊」就是 ADR-0302 §4 的紅線**——
把「可能」說成「是」，把「我不知道」說成「出事了」。

## 考量的選項

- **選項 A：沿用 1:1，對每位降級成員各發一次警告。** 上述三個問題全中。
  而且洗版的直接後果是**使用者學會無視它**——那會連帶廢掉 1:1 那條真正有意義的警告。否決。
- **選項 B：群組只發一次匯總警告（「本群有 3 位成員未受保護」）。** 比 A 好，但仍是
  **事件驅動**：每送一則訊息就要判斷要不要再講一次，而狀態其實沒變。噪音仍在，且
  「未受保護」對常態（對方根本沒開 FS）而言用詞過重。否決。
- **選項 C（採用）：不發警告，改為在群組資訊面板呈現靜態狀態。**

## 決策

1. **群訊送出路徑不呼叫 `onFsDowngrade`／不做任何 per-member 警告。**
   `fsWouldDowngrade` 與 `fsNoticed` 去重維持原樣，**只服務 1:1**。
2. **群組成員面板顯示每位成員的 FS 狀態**（既有的 `members-panel` / 行動端成員清單），
   三態，且**名稱必須誠實**：
   - **加密子鑰已知**（我有他的 EK ⇒ 這則群訊對他有 FS）
   - **未知**（沒有他的 EK ⇒ 對他退回身分金鑰；**這是常態，不是警告**）
   - **⚠ 曾知現無**（`pinned && !contactEks` ⇒ 與 1:1 的降級條件相同）——
     只有這一態用警示色，且文案沿用 1:1 那句「可能」而非斷言。
3. **面板頂端一行匯總**：「本群 N 位成員中，M 位的訊息有前向保密」。
   純狀態、不隨送訊觸發、不進對話訊息流。
4. **自己不算在內**（自封副本永遠加密到自己的 EK）。
5. **FS 未啟用時整段不顯示**——沒開的人不需要知道這個維度存在。

## 理由

- **狀態該用狀態呈現，事件才用事件呈現。** 「這位成員有沒有 EK」是一個**持續狀態**，
  不是一個發生過的事。用訊息流表達狀態，必然要在「重複講」與「講一次然後過期」之間二選一，
  兩個都錯。
- **保護 1:1 那條警告的價值。** 警告的效力來自稀有。讓群組每天洗出十幾條，
  使用者會連 1:1 那句「對方可能正在被攻擊」一起無視。**降低警告總量是安全設計，不是省事。**
- **誠實的三態勝過二元的「安全／不安全」。** 「未知」與「曾知現無」在密碼學上是不同的事實，
  合併成一個紅色驚嘆號會讓真正該注意的那一態失去意義——與 ADR-0316 為
  `notFs` / `maybeEkLoss` 分桶的理由完全相同。

## 後果

- 正面：批二可以動工，且不會製造洗版；1:1 警告的稀有性被保住；
  使用者第一次看得到「群組裡誰受保護」這個維度。
- 負面 / 已知殘餘風險：
  - **靜態狀態要使用者主動去看**（開成員面板）。不會有人被動得知某位成員降級了。
    這是刻意的取捨——群組場景下，主動性換來的是警告不被廢掉。
  - 群成員的 EK 只能靠「他也是我的聯絡人」或「他發過帶 hint 的 1:1 訊息」學到，
    所以**「未知」在群組裡會很常見**。這不是本 ADR 造成的，是 ADR-0027（群組對中繼隱形）
    與 ADR-0317（聯絡人是單方面的）的必然結果——面板只是把它顯示出來。
  - 面板不解決「為什麼未知」。使用者看到「未知」時沒有可執行的動作（除了把對方加為聯絡人）。
- 後續行動 / 待辦：
  - **實作＝ADR-0315 第 2 步批二**：`group.ts` 的兩個扇出點接 `encryptToFor`
    （形狀同 ADR-0318）＋ 本文的成員面板狀態。
  - 若日後群成員的 EK 發現率仍太低，該解的是**發現機制**（ADR-0315 曾評估過的
    seal 層 hint），不是把警告加回來。
