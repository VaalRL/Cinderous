# 0360. uptime 改用真正的滑動視窗——「折半」從來沒有讓任何東西衰減

- 狀態：已接受
- 日期：2026-09-18
- 相關文件：ADR-0350（滾動窗長度由探測頻率推導）、ADR-0092（節點自報與分級收錄）、
  ADR-0069（引導清單健康檢查）、ADR-0353（探測失敗不刪除）、
  `relay/bootstrap/uptime.ts`、`packages/core/src/node-attestation.ts`

## 背景與問題

分級收錄（ADR-0092）用滾動 uptime 決定一座 relay 的權重：

| uptime | 判定 |
| --- | --- |
| ≥ 99% | 正式收錄，**weight 2** |
| ≥ 95% | 收錄，weight 1 |
| < 95% 或未知 | 試用，不自動分配 |

2026-09-18 的稽核注意到第二座錨點 `jt0856` 一直停在 weight 1。查狀態分支：

```json
{
  "wss://cinder-relay.jt0856.workers.dev": { "probes": 89, "live": 88 },
  "wss://cinder-relay.cinderous1.workers.dev": { "probes": 66, "live": 66 }
}
```

88/89 = 98.876%，差 0.124 個百分點。**一次逾時**——幾乎可以確定是 GitHub runner 的網路，
不是 relay 真的掛了。這本身還算合理（再探幾次就爬回去了）。

真正的問題在 `recordProbe` 的「到頂折半」。它的註解寫著：

> 超過上限即**兩者同時折半**——保留可用率的比例，但讓遠古紀錄的權重衰減，
> 使一座修好的節點不必用同樣長的時間才洗得掉舊污點。

🔴 **折半根本沒有讓任何東西衰減。** 同時折半保留的正是**比例**：120/119 折半是 61/60，
那一次失敗原封不動地還在裡面，而且因為樣本數變小，它在比例裡的**份量反而變重**
（0.83% → 1.64%）。唯一真的發生的事是精度變粗，於是 99% 那道懸崖被反覆跨過。

實際模擬（以現況 89/88 起算，之後**每一次探測都成功**）：

```text
  第  11 次後  100/99   99.00%  → weight 2
  第  32 次後   61/60   98.36%  → weight 1   ← 折半，同一段歷史，相反的判決
  第  71 次後  100/99   99.00%  → weight 2
  第  92 次後   61/60   98.36%  → weight 1
  …永遠如此
```

一座**連續 300 次探測全部成功**的 relay，會每五天被降級一次，原因是三個月前的一次逾時。
而降級的後果是整個容錯拓樸長時間只剩一座正常權重的錨點——那正是第二座錨點存在的理由。

這個缺陷沒有被任何測試抓到，因為既有測試問的是「折半後比例有沒有保住」（有），
沒有人問「同一段歷史會不會給出兩種判決」。

## 考量的選項

- **A：把門檻從 99% 調低。** 否決：治標。震盪的成因是同一段歷史在折半週期的不同位置
  給出不同答案，換一個數字只是把懸崖挪到別處，下一次還是會有人踩到。
- **B：加遲滯（升上 weight 2 之後要跌破 97% 才降級）。** 否決：遲滯是用來吸收**真實訊號**
  的抖動的。這裡抖動是計算方式自己造出來的假象，用遲滯蓋住它等於承認算錯了還不修。
- **C（採用）：改用真正的滑動視窗**——把最近 `UPTIME_CAP` 次的結果逐格記下來。

## 決策

`UptimeRec` 從 `{ probes, live }` 改成 `{ window: string }`：一串 `"1"`／`"0"`，
**舊的在最前面**，長度上限 `UPTIME_CAP`（＝ `PROBES_PER_DAY × UPTIME_WINDOW_DAYS` = 120）。

```ts
export function recordProbe(rec: UptimeRec, live: boolean, cap = UPTIME_CAP): UptimeRec {
  const w = rec.window + (live ? "1" : "0");
  return { window: w.length > cap ? w.slice(w.length - cap) : w };
}
```

於是判決只取決於「最近 30 天發生過什麼」，與「現在處在折半週期的哪一段」無關，
而失敗**滿 30 天就真的消失**——那才是當初註解想要的意思。

### 規則因此變得講得出口

視窗 120 格、門檻 99% ⇒ **最近 30 天內至多一次失敗＝正式收錄**。
這句話任何人都驗證得了，而「61/60 為什麼不算 99%」沒有人講得清楚。

### 舊形遷移

舊形只留下「總共幾次、其中幾次存活」，失敗**發生在什麼時候是查不回來的**。
`toRec()` 把失敗**均勻散佈**在視窗裡：擠在最舊那端等於假裝「早就修好了」，擠在最新那端
等於假裝「剛剛才壞」，兩者都是在編造我們沒有的資訊。均勻是唯一不偏袒任何一邊的重建，
而且三十天內它們本來就會全部滑出去。

遷移在 `historyOrThrow()` 讀檔時發生，所以狀態分支不需要人工介入。

### `jt0856` 會怎麼樣

遷移後仍是 98.88%（那一次失敗是真的），但 **12 次探測（約 3 天）後回到 ≥99% 並從此穩定**，
不再每五天掉一次。這裡刻意**不去手動改狀態檔**把它直接升上去——它確實失敗過一次，
把紀錄改掉就等於讓這套機制對自己人失效。

## 理由

- **舊實作的註解描述的是一個沒有發生的行為。** 這比單純的 bug 更值得記一筆：
  註解讓所有讀過它的人（包括寫測試的人）相信衰減有在運作，於是沒有人去驗證它。
- **狀態檔變大的代價可以忽略**：每座 relay 從兩個數字變成 120 個字元。那是一個住在
  git 分支上、只有維護者工具會讀的檔案。用「省 120 bytes」換「權重永久震盪」是荒謬的交易。
- **不加遲滯**：視窗修好之後，剩下的抖動全是真實訊號。一座真的在 99% 邊緣遊走的 relay
  應該被看見，不該被平滑掉。

## 後果

- **正面**：一次網路抖動不再造成永久性的週期降級；第二座錨點會回到 weight 2 並留在那裡。
- **正面**：收錄規則變成一句人話（「30 天內至多一次失敗」），可稽核、可爭辯。
- **正面**：失敗真的會過期，修好的節點不必用更長的時間洗掉舊污點。
- **負面 / 已知殘餘風險**：
  - **狀態檔格式變了**。舊形在讀檔時遷移，但**遷移是有損的**——失敗的實際時間點永遠找不回來，
    均勻散佈只是最不偏頗的猜測。遷移完那一輪的判定可能與真實情況有出入。
  - **仍然是硬門檻**。119/120 過、118/120 不過。與舊版的差別是這次的邊界**穩定且可解釋**，
    不會因為內部狀態在哪一段而改變答案。
  - **探測失敗仍然一律算成 relay 的責任**。CI runner 自己的網路問題會被記成該座的失敗。
    重試機制（探測失敗先重試一次再記錄）是另一個題目，本 ADR 未處理。
  - 視窗長度依然綁在 `PROBES_PER_DAY` 上（ADR-0350），cron 改了要同步改——那條測試還在。

## 補記（2026-09-18，實測後）

狀態分支已轉成新格式（後續 1 完成）。但實測發現**遷移的散佈有 bug**：Bresenham 的累加器
從 0 起跳時，**單一**失敗會落在視窗的**最後一格**——也就是「假裝剛剛才壞」，正是上面
〈舊形遷移〉那段說要避免的那一端。`jt0856` 的 89/88 就是這樣遷過去的（`0` 在第 88 格）。

已修（累加器改從半個相位起跳），並補一條測試釘住「單一失敗要落在中間」。

⚠ **這個修正救不了已經遷移過的資料**：`toRec` 看到 `window` 就原樣放行，不會重跑遷移。
`jt0856` 手上那個尾端的 `0` 仍要滑滿一個窗口才會消失。**刻意不去手改狀態分支**——
理由與本 ADR「不手動把 `jt0856` 升上去」同一條。實際影響是它回到 weight 2 的時間比
原本預估的三天長一些。
