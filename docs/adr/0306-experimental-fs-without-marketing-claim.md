# 0306. 前向保密以實驗性選項先行——但**不進功能表、不宣稱**，並以版本協商為逃生口

- 狀態：**提議中**（方向已由使用者決定；實作與排序待執行。
  **本文推翻 ADR-0245 Phase 3 的一項既有決策**，故必須以 ADR 記錄，不得默默執行）
- 日期：2026-07-31
- 相關文件：
  - **0245**（手動 opt-in FS——**本文推翻其「通過前不得產線啟用」**，但**維持**「文案不得宣稱 FS」）
  - **0290 §2-C**（分階段宣稱——**本文是它的具體化**，並指出原提案外一個更貴的變體）
  - **0290 §2B**（開源資助查證：OTF Security Lab 免費且有 Briar 前例、OpenSats 有 NIP-44 審計前例）
  - **0302**（FS 機制的版本協商——**本文把它從「未來的可判斷性」升為上線前置**）
  - **0236／0238**（審計要求的來源）、**0257**（無營收面＝原死結的另一半）
  - 0278／0287（UI 不得說謊——本文的判準）、0303 §5.2／§7.4a、0304 §6（FS 先行）
- 資料來源：本倉庫既有 ADR 與程式碼查證（`packages/core` 密碼學面 420 行，量測見 ADR-0302 §6.2）

> **起點**：使用者問「**如果在官網介紹標明有這個功能但未經外部審計呢**」。
> 查證後：這條路 **ADR-0290 §2-C 已評估過**，但該提案**明確禁止文案宣稱**，
> 而本次提問的正是宣稱那一半 ⇒ 本文要回答的其實是**兩個可分開的問題**。

## 1. 先把兩件事拆開——它們的成本與收益完全不同

| | 做（讓使用者拿得到） | 宣稱（官網寫出來） |
| --- | --- | --- |
| 收益 | **想要 FS 的使用者拿得到** | 補競爭落差 |
| 成本 | 推翻 0245 的上線閘門 | **誠信** |

**原提案把兩者綁在一起，但它們沒有必然關係。** 拆開後結論很清楚。

## 2. 🔵 關鍵反轉：官網宣稱**買到的最少、付出的最多**

去官網寫它的動機是補競爭落差（對手 White Noise／Keychat 在文案上都能宣稱 FS，ADR-0290 §2）。

**但「未經外部審計的前向保密」補不了那個落差。**
對手寫「前向保密」、我們寫「前向保密（未經外部審計）」——
在比較表上這**看起來更差**，不是更好。

⇒ 而讓使用者真正拿到 FS 的價值，**不需要官網宣稱就能實現**。

⇒ **宣稱的成本最高（誠信）、收益最低（競爭）。兩者拆開後，這題就不難了。**

## 3. 誠實性判準：兩種寫法差很多

| | 判定 |
| --- | --- |
| ❌ 官網功能表「前向保密 ✅」＋小字註明未審計 | 使用者讀到打勾就停了——**小字是遮羞布，不是知情同意** |
| ✅ 不列入功能表；設定內標為實驗性；**每次啟用都明示** | 才是知情同意 |

本專案在 **ADR-0278**（隱身狀態點）與 **ADR-0287**（搜尋範圍揭露）反覆守的就是這條線。
**功能表打勾配小字，正是那條線的反面。**

⇒ 且 FS 的失效特別隱蔽（見 §4），使用者**無法自行察覺**免責聲明是否成真
⇒ 免責聲明在此處的資訊價值比一般情況更低，**不能拿它當風險轉嫁**。

## 4. 為什麼這件事的誠實性門檻比一般功能高

> **FS 的 bug 不會讓東西壞掉，它只是不保護。**

訊息照送、照收、UI 照樣顯示。金鑰沒真的刪掉、conversation key 被重用、grace 窗算錯
——**沒有任何症狀**。全測綠只證明「我們想到的情況都對」，不證明「沒有洩漏」。

⇒ 這正是外部審計不可替代的原因（ADR-0245:97「FS 的密碼學正確性照樣要外部審計才上線」），
也是**宣稱門檻該更高**的原因：使用者無從驗證，只能相信文案。

## 決策

### D1. **做**：以實驗性選項開放，推翻 ADR-0245「通過前不得產線啟用」

- 設定內為**實驗性選項、預設關**；
- 啟用時**明示「尚未經外部審計」**，不得只在說明文件寫；
- 現況已有此形狀的雛形——`0245:138` 的 `fsUiEnabled`／`localStorage nb.fs=1`
  即是「審計通過前不對使用者露出」的閘門，**本決策是把它改為可由使用者明示開啟**。

### D2. ~~**不宣稱**~~ → 🔵 **不得以「對等形式」宣稱**（2026-07-31 修訂）

> 🔴 **本節初版的論證有一個沒說出口的前提，該前提已不成立。**
>
> 初版寫：「未經外部審計的前向保密」補不了競爭落差——對手寫「前向保密」、
> 我們寫「前向保密（未經外部審計）」，在比較表上**看起來更差**
> ⇒ 宣稱的成本最高、收益最低。
>
> **那個論證預設「審計終究會發生」。** 在該前提下「現在不宣稱」只是延後，代價很小。
> 但使用者已決定**暫不投任何申請**（2026-07-31）⇒ 選擇不再是
> 「現在宣稱 vs 審計後宣稱」，而是「**限定式宣稱 vs 永遠不提**」——
> 那是不同的題目，而初版的論證沒有回答它。

#### D2.1 三種宣稱，風險差很多

| | 例子 | 判定 |
| --- | --- | --- |
| ❌ **對等式** | 比較表裡與 Signal 並列打勾 | 那句話的意思是「與 Signal 同級」——**那是假的**（他們有多輪審計） |
| 🟡 **無條件式** | 功能表只寫「前向保密」 | 沒說謊，但讀者會自行補上「所以是可靠的」 |
| ✅ **限定式** | 「前向保密（實驗性，尚未經外部審計）」 | **真實且完整** |

**判準只有一條：讀者看完之後，對自己拿到什麼的認知正不正確。**

#### D2.2 規則

**得宣稱，但不得以對等形式宣稱：**

- ✅ 功能列表**得**列入，**但必須同時帶「實驗性」與「未經外部審計」**——不得只有名稱。
- ❌ **比較表那格維持「開發中」、不得打勾**（`cp_r9a`，由 `Compare.test` 鎖住）。
  該表的語意**就是**對等比較，而我們不對等。
- ✅ 藍圖頁的事實陳述照舊（`roadmap-fs`）。

⇒ **讓使用者知道功能存在是有價值的；讓使用者以為它與 Signal 同級是說謊。
這兩件事可以分開，而初版規則把它們綁在一起了。**

⚠ **殘留風險（不因限定而消失）**：若那 420 行組合有 bug，宣稱就是假的——
限定措辭管理的是**期待**，不是**正確性**。這一點在任何未經審計的安全功能上都成立，
但本專案以隱私為賣點，踩錯的代價比一般產品高。**這是採 D2.2 明知並接受的風險。**

### D3. 🔴 **前置**：**退場語意**必須先實作——但**不是整份 ADR-0302**

> 🔵 **2026-07-31 修訂。** 本節初版寫「ADR-0302 的版本協商必須先實作」，
> 那**寫得太重**。討論中提出的問題——「退回到可以手動觸發更新金鑰就可以了嗎」
> ——迫使把「審計未過」拆開來看，結論是：**前置比原本寫的小很多，但不是零。**

#### D3.1 「審計未過」有三種，退回需求不同

| | 失敗類型 | 手動輪替夠嗎 |
| --- | --- | --- |
| **1** | **實作 bug**（grace 窗算錯、金鑰沒真刪、狀態機有洞） | 🟡 **部分夠** |
| **2** | **設計缺陷**（輪替模型本身不給 FS、EK 公告協定洩漏） | ❌ **完全不夠** |
| **3** | 原語誤用（conversation key 跨情境重用） | 🟡 同類型 1 |

**類型 1／3**：修 bug、發版、使用者輪替一次即取得乾淨的 EK。
⚠ 但兩個洞：輪替是**向前的**，已送出的訊息補不回來；
且 ADR-0245 把輪替設為**手動**，多數使用者不會按（見 D3.4）。

**類型 2**：修不了，要做的是**整個停用**。而手動輪替給的是「換一把新 EK」，
**不是「不再有 EK」**——**那是兩件不同的事**。

#### D3.2 類型 2 才是真正需要退場機制的那個，而它的難處在「停用看起來像被攻擊」

停用 `ek-v1` 要做四件事：停止發布公告／停止加密到對方 EK／
**告訴聯絡人「我不做這個了」**／讓對方停止期待。**後兩件是難的。**

現行程式：

```
relay-backend.ts:1174  fsWouldDowngrade(to) = 已釘選 且 無其 EK
types.ts:490           pinned?: Record<string, boolean>      ← 布林
relay-backend.ts:2568  成立 → onFsDowngrade(to) → UI 警告
```

⇒ 一旦停用，**每個曾釘選過你的人都會永遠看到「疑似降級」**，
而那句話的意思是「對方可能正在被攻擊」。

⇒ **停用與被攻擊在現行語意下無法區分。**
⇒ **手動輪替解決不了這個**——它讓你換鑰，不讓你退場。

#### D3.3 ⇒ 退回分**軟／硬兩條**，共用同一個原語

> 🔵 **2026-07-31 二次修訂。** 本節初版只設計了「停用」一條路。
> 討論中提出更好的形狀：**不停用，退回到「固定子鑰＋可手動更換」**。
> 該提案應為**預設退路**，「停用」降為極端情況。

| | 何時採用 | 動作 | 對方看到 |
| --- | --- | --- | --- |
| **軟退（預設）** | 機制**可用但比宣稱的弱** | **保留 EK 與輪替按鈕**，只改宣告的能力字串 | 「較弱的能力」——**不是**缺席 |
| **硬退（極端）** | 機制**有害**（公告本身洩漏／輪替製造新漏洞） | 真的停用 | 無 EK ⇒ 吃下 D3.2 的假警報代價 |

**軟退為什麼更好——三個具體理由：**

1. **降級偵測從頭到尾不會誤觸。** EK 仍在、公告照發、加密照走
   ⇒ `fsWouldDowngrade`（`:1174`＝已釘選且**無其 EK**）**不成立**
   ⇒ 沒有 D3.2 那個「停用長得像被攻擊」的問題。
2. **退路的 UI 已經存在。** `messages.ts` 的 `fs_rotate: "立即更換加密金鑰"`
   那顆按鈕**不必動**——**使用者不會失去任何東西**，只有說明文字要改成正確的。
   對比硬退會讓按鈕消失、感覺功能被拿走，落地軟得多。
3. **同一塊實作也是升級路徑。** 「宣告一個不同的能力」順便涵蓋
   `ek-v2`／`ratchet-v1` ⇒ 與 ADR-0302 §1 是同一件事，**一塊實作兩個用途**。

#### D3.3a 但**前置沒有消失**——它只是換了形狀（而且換好了）

問題在 `profile.fs` **不是 UI 文案，是講給別的客戶端聽的宣告**：

```
subkey.ts:25           FS_CAPABILITY = "ek-v1"
relay-backend.ts:1725  profile.fs === FS_CAPABILITY → pinFs(sender)
```

⇒ 明知它不給 FS 卻繼續宣告 `ek-v1`，**那個謊是說給對方的程式聽的**
（對方會繼續釘選、繼續期待），不只是說給使用者聽。

⇒ **所以仍然需要「能宣告 `ek-v1` 以外的值」這個原語——軟退與硬退共用它。**

| | 原設計 | 修訂後 |
| --- | --- | --- |
| 要宣告什麼 | 「我已停止」 | **「我有子鑰，但不是你以為的強度」**（軟）／「我已停止」（硬） |
| 對方的反應 | 停止期待 | **改期待較弱的**／停止期待 |
| 使用者感受 | 功能消失 | **功能還在，說明改了**／功能消失 |

**⇒ 前置的大小不變，形狀變好。**

#### D3.3b 🔴 軟退的**硬條件**：它覆蓋「比宣稱的弱」，不覆蓋「有害」

- 若審計指出的是**機制有害**（EK 公告本身洩漏、輪替過程製造新漏洞）
  ⇒ **保留機制就是錯的**，必須走硬退。
- 若審計指出**輪替根本不刪舊鑰**（＝按下去什麼都沒買到）
  ⇒ **留著按鈕、改個說法仍然是說謊**，一樣不得走軟退。

> **軟退的前提是「輪替仍有實質作用，只是達不到 FS 的標準」。**
> **該判斷必須等審計報告才能做，本文寫不死，也不得預先假定。**

⇒ 這是採軟退的**驗收條件**，不是建議：走軟退前必須先回答
「按下更換金鑰之後，使用者實際得到什麼？」並據實改寫文案。

#### D3.3c 最小前置的範圍

> **上線前置＝「能宣告 `ek-v1` 以外的值」這個原語，不是整份 ADR-0302。**

關鍵性質 **ADR-0245 §81 已經定好**：`fs:ek-v1` 寫在**簽章個人檔**內、**不可偽造**。

⇒ 攻擊者**無法偽造**一句「我停用了」來剝奪你的 FS；他只能**扣住**你的新個人檔，
而那樣對方仍看到舊的 `ek-v1`、**仍然警告** ⇒ **失敗方向落在安全那側。**

⇒ 實作面比整份 0302 小得多：**一個欄位值 ＋ `fsWouldDowngrade` 多一個判斷 ＋ 一句文案。**

| | 內容 | 阻擋上線？ |
| --- | --- | --- |
| **能力宣告原語** | 個人檔可宣告 `ek-v1` 以外的值＋客戶端認它（軟／硬退共用） | ✅ **是，必要** |
| ADR-0302 其餘 | 強度順序表、三態 UI、`pinned` 改記 `{scheme, at}` | ❌ 否，後續 |

⚠ **誠實揭露一個填不掉的洞**：**舊版客戶端不認得新的能力值**。

- **軟退**：舊版看到 `fs` 不等於 `ek-v1` ⇒ 不釘選（`:1725` 是精確字串比對）
  ⇒ 對已釘選過的人，EK 仍在故**不觸發**降級警告；對新接觸者則**當作沒有 FS**
  ⇒ **保守但不說謊**，可接受。
- **硬退**：舊版落回 `fsWouldDowngrade` **繼續假警報**。

⇒ 兩者都無法強制對方更新，但**都失敗在安全側**（保守／警告，而非靜默降級），可接受。

#### D3.4 補救時的輪替：**得自動、且先做後說**（2026-07-31 已決定）

類型 1／3 的退回依賴「使用者去按輪替」，而 ADR-0245 **刻意**把輪替設為手動
（其〈決策〉即為把 0238 的自動輪替降階為使用者控制）⇒ 今天沒有任何強制手段，
而「依賴自願按鈕」實際上意味著**多數使用者不會退回**。

**🔵 先說一個把成本歸零的發現：補救不需要現在建任何東西。**

原以為要加「金鑰世代」欄位才能讓修正版分辨哪批金鑰不可信。查 `StoredFsKey` 後——**不需要**：
修正版在首次啟動時，**它找到的所有金鑰都不是它自己產的** ⇒ 全部視為可疑、輪替一次即可。
不必比對版本、不必新欄位。⇒ **整個補救機制可完全在修正版裡實作，此刻一行都不用寫。**

**⇒ 因此本節的產出是政策決定，不是程式。** 而有一件事**不能事後補**：
「補救時可不可以自動輪替」這個決定本身。現在不決定，修正版就會在**出事的當下、
時間壓力下**重打同一場辯論——那是最糟的決策時機。

##### 決策

| 情況 | 規則 |
| --- | --- |
| **一般** | 輪替**維持手動**（ADR-0245 不變） |
| **補救**（審計或事後發現實作 bug） | 修正版**得**在首次啟動時**自動輪替一次** |

三個附帶條件（皆為**驗收條件**，非建議）：

1. **僅限修正已知缺陷**——不得用於任何其他目的（例如「順便讓大家換一下」）。
2. **必須告知並說明原因**，不得靜默（沿用 ADR-0245 的「非靜默」原則）。
3. **事後告知即可，不需事前確認。**

> **為什麼第 3 點與一般功能不同。** ADR-0245 的換鑰確認對話存在，是因為輪替有代價
> （在途訊息可能收不到）。但在補救情境，**不輪替的代價更高**，而先問會讓一部分人
> 選擇「不要」然後繼續暴露。
> ⇒ **保護性動作、延遲有害 ⇒ 先做後說。** 這是事件回應，不是一般功能。

##### 這不是推翻 ADR-0245

0245 的決策是「把 0238 的**自動輪替政策**降階為使用者控制」——它反對的是**背景常態輪替**。
一次性的缺陷補救**不是政策，是事件回應**，兩者不衝突。
⚠ 仍已於 ADR-0245 加註記，避免兩份文件被讀成打架。

##### 解不掉的殘留

**不更新的使用者，任何補救都到不了他們。** 這對所有軟體補救都成立，
不是本設計特有——但要寫進來，不得假裝沒有。

### D4. 執行順序

```
1. 實作「退場語意」（D3.3）——個人檔可宣告已停止＋客戶端認它   ← 前置，不可跳
2. 依本 ADR 開放實驗性選項（D1）＋ 藍圖頁聲明（D2）
3. 同時投 OTF Security Lab 與 OpenSats（ADR-0290 §2B）
4. 審計通過後：才把 FS 列入功能表與文案

（不阻擋上線、可平行進行：ADR-0302 其餘部分——強度順序表、三態 UI、

```

### D5. 🔵 附帶效益：這反而有利於補助申請

OTF 與 OpenSats 資助的正是這個階段的專案——**程式在跑、有真實使用者、缺的就是審計**。
一份公開的「已實作、等待外部審計」聲明，比純紙上申請更有說服力。
⇒ 且真實使用能在審計前產出回饋，甚至先撞出問題。

## 後果

**正面**

- 想要 FS 的使用者拿得到，**而誠信一分未花**。
- 解開 ADR-0290 §2 的死結中**不需要錢的那一半**：功能不再被閘門完全封死。
- 為補助申請提供實證材料（D5）。
- 迫使 ADR-0302 落地——那本來就是遲早要做的地基（0303 §7、0304 都依賴版本語意）。

**負面／代價**

- **明確推翻一項既有決策**（0245 Phase 3 的上線閘門）。這是本文存在的理由，
  但也意味著 0245 的〈狀態〉需同步標註。
- **競爭落差沒有被補上**——D2 是刻意的：本文主張那個落差**不值得用誠信換**。
- 多一條實驗性程式路徑要維護，且它會有真實使用者 ⇒ **不能隨意拔掉**。
- ADR-0302 從「純成本、買未來」變成**必須先做**，其實作成本提前發生。

**已知限制**

- **未實作、未測試**；D1 的 UI 文案**尚未撰寫**。
- **沒有做任何使用者研究**——「小字是遮羞布」是設計判斷，非實證。
- ~~**未評估法遵面**~~ → **✅ 已查（2026-07-31）**，見下。
  ⚠ **撰寫者不是法律專業；以下是查到的事實與出處，不是法律意見。真要上架前應找專業確認。**

  **（a）美國出口管制：依定義不適用通知義務，但結論綁在一個看不出來的條件上。**

  EAR `§742.15(b)` 的通知義務**只適用於「非標準密碼學」**，而該詞的定義要求
  **兩個條件同時成立**：既非國際標準組織（IEEE／IETF／ISO／ITU…）採納，
  **且未曾以其他方式公開**（"proprietary or **unpublished**"）。對照本專案：

  | | 狀態 |
  | --- | --- |
  | 原語（AES-GCM／XChaCha20-Poly1305／secp256k1／SHA-256／HKDF／Argon2id） | 全為公開標準（ADR-0004／0007：一行都沒自己寫） |
  | 協定（NIP-44／NIP-59／NIP-42） | **公開發布**的 Nostr 規格 |
  | 自有的 420 行組合＋EK 輪替設計 | **AGPL 開源＋設計公開於 ADR** |

  已查證：`VaalRL/Cinderous` 為 **`PUBLIC` ＋ `AGPL-3.0`**
  ⇒「未公開」條件不成立 ⇒ 依定義**不屬於非標準密碼學** ⇒ 通知義務不適用。

  🔴 **但這個結論完全綁定「倉庫維持公開」**——轉為私有即需重新評估。
  **這是一個看不出來的耦合**，故明寫於此。

  **（b）上架那一關是另一回事，且遲早會撞到。**
  Apple App Store Connect 會問加密問題（`ITSAppUsesNonExemptEncryption`），
  答 YES 會帶出**每年 2 月 1 日前向 BIS 提交自我分類報告**（ERN 框架）的義務；
  Google Play 有對應的美國出口法聲明。而 **ADR-0229 的官網下載按鈕已標「即將推出」**。

  **（c）🔴 AGPL × App Store 的張力，可能比加密這條更會擋住上架。**
  2011 年 VLC 因 GPL 與 App Store 條款不相容而**被下架**：Apple 對所有 App
  （含免費）加上 DRM 與使用限制，與 GPL／AGPL「不得附加額外限制」相衝突。
  ⚠ 觸發點是**共同著作權人提出異議**——`GNU Go` 亦有先例。

  ⇒ **但本專案的處境不同**，已查證兩件事：
  - **相依樹中沒有任何 GPL／AGPL 套件**（掃過 `node_modules/.pnpm` 全部 `package.json`）
    ⇒ 不受他人的 copyleft 條款拘束。
  - 提交者僅 `Ch.Lien`／`Vaal`（＋機器人與 AI co-author trailer）
    ⇒ 著作權高度集中。
  ⇒ **著作權人自己選擇散布管道，不構成對自己授權的違反**；
    若需要，亦可比照業界作法**加註 App Store 例外條款或雙授權**（VLC 後續即走此路）。
  ⚠ **AI co-author trailer 是否產生著作權主張，本文不判斷**——那超出撰寫者的能力範圍。

  **（d）完全未查**：中國／俄羅斯／印度等**各地對加密的限制**；
  Google Play 的具體要求細節。
- **未定義「實驗性」的退出條件**：審計通過是其一，但若審計長期無下文，
  這個「暫時」狀態會變成事實上的永久狀態——**沒有時限機制**。
- **未評估** D1 對 ADR-0245 既有的降級偵測與 TOFU 釘選在真實使用者間的行為
  （目前只有開發者手動啟用過）。
- 未評估：若實驗性使用者與未啟用者混用，`fsWouldDowngrade` 的警告頻率是否會擾民。
