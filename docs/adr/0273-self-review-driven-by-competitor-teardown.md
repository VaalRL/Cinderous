## 1. ⚠ 檔案塊的兩個缺陷——從「靜態閱讀的推測」升級為「測試證實」

ADR-0267 §2.2／§2.3 是靠讀程式碼得到的，該 ADR 自己寫著「未寫測試重現」。本輪補上。

### 1.1 過程本身值得記：**前兩次嘗試得到了錯誤的結論**

第一版測試「重開後沒有重收」，我一度判斷 ADR-0267 的結論是錯的。實際原因是**測試環境的兩個預設值**：

1. `createInMemoryRelayNetwork` **預設整類拒收檔案塊**（企業限定，ADR-0162）→ 未傳 `acceptFileEvents: true` 時，事件根本沒進中繼；
2. 它**預設沒有離線留言庫**（`store`）→ 沒有東西可重放，自然測不到重取。

⇒ **「測不出來」不等於「沒有問題」。** 兩個預設值都是對的設計（公共站零儲存風險），
但它們讓測試預設跑在一個**不存在於產線的組態**上。這兩點已寫進測試檔頭。

### 1.2 缺陷 A：重開 App 會把 TTL 內收過的檔案再交付一次（已證實）

```
第一次開機 → 收到檔案 → onFileBytes("tid-1")
stop() → 用同一份儲存與同一座中繼重開
第二次開機 → onFileBytes("tid-1")   ← 又來一次
```

對照組同時證實**訊息這條路徑不會**（有 `inboxSince` 水位）。
⇒ **不對稱是真的，而且只有檔案塊這一條**：13 組訂閱 filter 裡，
只有離線私訊帶水位；其餘要嘛是 ephemeral、要嘛是可取代/可尋址（天然只有一顆），
**唯一「會累積的儲存型 kind」除了私訊就是 FILE_WRAP，而它沒有水位。**

使用者可見的後果：桌面端 `onFileBytes` 內是**無條件** `saveIncomingFile(...)`
（`apps/desktop/src/App.tsx`），⇒ **每次重開 App，7 天內收過的每個 relay 檔案都會再跳一次
「另存新檔」。**

### 1.3 缺陷 B：缺一塊 → 永遠不重組，而且**一個錯誤訊號都沒有**（已證實）

測試以「seq 0 缺席」模擬中繼在 `MAX_QUERY_ROWS = 1024` 截斷後的結果：

- `onFileBytes` **從未觸發**（檔案永遠交付不出來）；
- `onFileError` **也從未觸發** ← 這才是問題所在；
- 殘骸由 `sweepChunkAsm()` 在 `CHUNK_ASM_TTL_SEC = 120` 秒後靜默刪除。

⇒ **寄件者看到「已送出」（ADR-0041 只保證中繼收下），收件者什麼都沒有，雙方都不知道。**
這正是 ADR-0264 §8 為行事曆邀請解掉的那類靜默分歧，在檔案這條路徑上仍然存在。

### 1.4 這些測試是**特徵化測試**，不是規格

新增的 3 個測試**斷言目前的錯誤行為**，並在檔頭明確標示。
**修好之後它們會紅**——屆時應把斷言改成正確行為（重開不重收、缺塊要報錯），**不是刪掉測試**。

## 2. ⚠ ADR-0272 §2.2 的類比也成立：行動端換身分有殘留狀態

ADR-0272 抄回 White Noise 的教訓：
「account scope 是慣例、不是型別保證；編譯器抓不到傳錯 pubkey 的 bug」，
並註明「本文只做類比、未查證」。本輪查了。

### 2.1 兩端的做法根本不同——而且只有一端是安全的

| | 換身分機制 | 保證強度 |
|---|---|---|
| **桌面** | **`location.reload()`**（`App.tsx:1866` 註解：「讓所有 per-身分狀態乾淨重建（ADR-0045）」） | **結構性**——不可能有殘留 |
| **行動端** | 就地 `signInWith()` ＋**手寫的 reset 清單** | **靠人維護**——漏一項就殘留 |

### 2.2 那份手寫清單目前漏了三項

`MobileApp.tsx` 的換身分路徑重設了 13 項（self*／contacts／groups／convos／reactions／
unsent／blocked／requests／unread／calendar／slotQueue／escrowList／orgTitle…）。**沒有重設**：

| 殘留狀態 | 實際後果 | 嚴重度 |
|---|---|---|
| **`archived`**（每對話封存塊數） | 它是「歷史」入口的閘門（`(archived[activeId] ?? 0) > 0`）。兩個身分若都與**同一個 pubkey** 對話（工作/私人身分很常見），身分 B 會看到**幽靈「歷史」入口**——點開是空的（封存本身有命名空間隔離，ADR-0045） | **低—中**（UI 假象，非資料外洩） |
| **`purged`**（無痕收回的訊息 id） | 跨身分沿用。訊息 id 是內容雜湊，碰撞實務上不可能 | **極低**（但同一類別） |
| **`calDraft`**（行程預填，本 session 新增） | 以 convo 為鍵，同上的 pubkey 共用情境下，另一身分的對話可能冒出預填表單 | **極低** |

⚠ **重點不是這三項的嚴重度，是「清單靠人維護」這件事**——
White Noise 已經因為同一個模式吃到一個真的 bug（跨帳號滲漏）。我們今天漏的三項恰好都不嚴重，
**但沒有任何機制保證下一個新增的 state 會被記得加進去**（`calDraft` 就是本 session 新增、當場就漏了）。

### 2.3 結構性的解法（優於補三行）

讓行動端也拿到桌面的那種保證，兩條路：

- **A（建議）把 per-identity 狀態關進一個以身分為 `key` 的子元件**：
  `<Session key={selfPubkey} … />`，React 在身分變更時整棵重掛 ⇒
  **reset 清單可以整個刪掉**，且日後新增 state 天然安全。
  代價：`MobileApp.tsx`（1,519 行）要拆，是一次真實的重構。
- **B 行動端也 reload**：react-native-web 今天做得到，**但真 RN 做不到** ⇒
  與 ADR-0269 的 RN 移植方向衝突，不建議。
- **C 先補三行**：立刻可做、但沒有解決「靠人維護」。

## 3. 已知但本輪未動的：發布側的 AUTH（ADR-0272 §3）

已在 ADR-0272 記錄並查證：`this.client` 一條連線兼發布與訂閱，
中繼在 `requireAuth` 時**連 EVENT 都要求 AUTH**（`relay/src/relay-core.ts:328`），
⇒ 中繼知道「這顆匿名 wrap 是誰送的」。**本輪未做任何變更**——
它動到 ADR-0057 的既有契約與企業 allowlist 的執行點，需要單獨評估濫用面。

## 4. 改善優先序（本文的建議，未決策）

| 優先 | 項目 | 理由 | 規模 |
|---|---|---|---|
| **1** | **檔案塊補水位**（`since`）＋**重組失敗要 `onFileError`** | 兩個已證實缺陷、使用者可見、零協定變更；測試已就位 | 小 |
| 2 | 把「重取策略」變成訂閱工作負載的屬性 | ADR-0272 §2.1：治本。避免下一個累積型 kind 又漏 | 中 |
| 3 | 行動端 per-identity 子元件（§2.3-A） | 把慣例變成保證 | 中（要拆 `MobileApp.tsx`） |
| 4 | 評估匿名發布 plane（§3） | 補 ADR-0237 的一半，但要先算濫用面 | 中—大 |

⚠ **1 與 2 應該一起做**：只補 `since` 是治標，下一個會累積的 kind 仍會重蹈覆轍。

## 後果

- 正面：ADR-0267 的兩個疑慮從推測升級為**可重現的事實**，且測試會在修好時提醒更新；
  ADR-0272 的類比查證為真並找到結構性差異（桌面 reload vs 行動端手寫清單）。
- 已知限制：
  - **§1.3 沒有真的產生 1024+ 顆事件**——測試以「缺一塊」模擬截斷後的狀態。
    截斷本身另有中繼端測試（`sql-message-store.test.ts` 已斷言 `MAX_QUERY_ROWS` 夾取），
    但**「3 個滿版檔會觸發」這個門檻沒有端到端驗證過**。
  - §2 只查了行動端與桌面端的**換身分路徑**，**沒有做全面的 pubkey 參數化寫入路徑審查**
    （ADR-0272 §2.2 建議的那項仍未執行）。
  - 本文未評估任何修法的實作成本，§4 的規模欄是量級判斷。
- 後續行動（**待決策**）：
  1. 修 §1 的兩個缺陷，並把特徵化測試的斷言翻正。
  2. 決定 §2.3 走 A 還是 C。
  3. 補做「pubkey 參數化寫入路徑」的全面審查（ADR-0272 §2.2 原始建議）。
